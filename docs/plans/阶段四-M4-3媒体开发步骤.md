**硬约束（继承 AGENTS.md + 阶段三 §10 + 阶段四方案）**：
- **媒体访问控制是工程硬约束（NFR-3/NFR-4）**：图片/语音/文件/表情访问均需鉴权；未授权返回 403/404，绝不静默放行；私密媒体不得进入共享缓存（`Cache-Control: private`）。
- **媒体安全（阶段三 §10.3）**：MIME allowlist 与文件头嗅探同时检查；分类型大小/像素上限；压缩炸弹防护；只允许已登记 `media_id` 下载，禁止 path traversal；事件/序列化只带 descriptor 不暴露绝对路径。
- **完整性（阶段三 §10.2）**：`content_hash`（sha256）上传时校验，媒体去重 + 完整性保证；命令成功至少证明"有权读取 + 内容已进受管对象存储 + hash/size/MIME 已验证 + 元数据已耐久记录 + 生成稳定 `media_id`"。
- **派生与 ready 分离（阶段三 §10.2）**：元数据已提交但派生（缩略图/波形）失败时，媒体保持 `ready`，派生单独 `failed`；禁止把派生失败伪装成媒体失败或空结果。
- **幂等**：同一 `upload_id` 重复 `:complete` 必须返回同一 `media_id`，不重复建对象/不重复派生。
- **主体性铁律（AGENTS.md §4.1 / 需求 FR-12）**：爱莉表情是"以普通图片消息发出"，应用只渲染/投影，绝不生成爱莉第一人称内容、不做 VLM 决策（那是 Elysium 表情包插件的事）。
- 每次改动要有与风险相称的契约测试（上传/下载/权限/MIME/派生/表情包/越权）。
- 只写 `apps/media/`、`apps/emoji/` 相关代码与必要配置接线；不动 accounts/chat/elysia_bridge 已有模型与接口（除非公共契约确有缺陷，先说明再动）。

## 1. 目标（M4-3 验收定义）

完成**媒体闭环**：对象存储上传 + 缩略图/波形派生 + 表情包 + 文件，并接入 M4-2 消息链。

- **对象存储（MinIO/S3 兼容）**：受控上传三步（创建会话 → 传二进制 → complete 校验生成 `media_id`），`content_hash` 完整性校验，下载鉴权 + Range 支持。
- **缩略图 / 波形**：图片消息生成缩略图派生资源；语音消息生成波形图派生资源（并记录 `duration`）；派生失败媒体仍 `ready`。
- **文件**：任意合法 MIME 文件消息上传/下载，大小上限，MIME allowlist + 文件头嗅探。
- **表情包**：系统预置包（管理员维护）+ 用户收藏表情（上传图片加入个人表情包）；`type=emoji` 消息引用表情媒体。
- **接入消息链（M4-2 复用）**：`CreateMessageSerializer` 已收 `media_id`；M4-3 补齐校验——`type=image/voice/file/emoji` 时 `media_id` 必须存在、`status=ready`、类型匹配、且调用方有权访问该媒体；消息序列化返回媒体 descriptor。
- **契约测试**：上传-完成-下载闭环、幂等、越权 403/404、MIME/大小校验、缩略图/波形派生、表情包 CRUD、系统包权限、爱莉表情投影（通道预留）。

**不包含（本里程碑边界）**：
- **爱莉媒体/表情的真实投影**（M4-4 已交付文本 `elysia.reply`）：爱莉发出图片/语音/表情时，媒体如何从 Elysium 侧（阶段三 `/media/*`）进入应用侧对象存储，属**待协调的未决点**（第 6.3/10 节）；本期只保证应用内消息链支持媒体渲染，爱莉媒体消息真实 E2E 不验收。
- **视频**：消息类型无 video（M4-2 模型即无），直播归 M4-6；不做视频转码/播放。
- **预签名 URL / CDN**：下载走应用内鉴权流式端点（Range），不签 URL、不上 CDN（后续按需）。
- **TTS 合成**（归属爱莉能力，非应用内用户媒体）；语音消息仅指用户上传的语音文件 + 波形。
- **VLM 表情决策 / 现场生成**（Elysium 表情包插件 `plugins/emoji/` 的能力）：应用侧只做收藏/系统包/发送引用，不做 AI 决策。

### 3.2 MediaUploadSession（受控上传会话）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | AutoField | |
| `upload_id` | CharField(64) | **uuid，唯一**，三步上传的握手指纹 |
| `owner` | FK → User | 只有上传者可 complete/看到该会话 |
| `kind` | CharField(16) | `image`/`voice`/`file`/`emoji`，创建会话时声明（用于 MIME/大小/派生策略） |
| `expected_size` | PositiveBigIntegerField | 声明大小上限（complete 时与实际 size 比对，防压缩炸弹） |
| `mime_type` | CharField(128) | 创建会话时声明期望 MIME（用于 complete 校验） |
| `status` | CharField(16, default="pending") | `pending`/`completed`/`expired`，choices |
| `created_at` | DateTimeField(auto_now_add) | |
| `expires_at` | DateTimeField | `pending` 会话 TTL（默认 10 分钟，超时置 `expired`，由 cleanup 或惰性清理） |

Meta：`db_table="media_upload_sessions"`；`unique(upload_id)`；`db_index`：`owner`、`status`、`expires_at`。

**为什么用"受控上传会话"而不是直接 PUT 就建 MediaObject**（阶段三 §10.1 三步语义）：
- 创建会话先声明 `kind`/`expected_size`/`mime_type`，服务端先做策略校验（类型是否允许、大小上限），**不信任客户端最终声明**；
- 传二进制只落到对象存储的临时前缀（`tmp/{upload_id}`），未 complete 前不产生正式 `media_id`；
- `:complete` 才是权威动作：读回临时对象做 sha256、比对 size/MIME、**文件头嗅探**、按需去重（同 hash 已存在则复用既有 `media_id`）、原子建 `MediaObject`、触发派生。complete 幂等：同一 upload 重复 complete 返回同一 `media_id`。
- 失败路径（hash 不符/MIME 不符/超限）：会话置失败，临时对象由 owner 清理，**不落 MediaObject**（不伪造成功）。

### 3.4 关于唯一约束的说明（别跳过）

- `EmojiPack.unique(owner, name)`：系统包 owner 为 NULL，SQLite/MySQL 的 NULL 唯一语义不同。**在 services 做幂等**：`get_or_create_system_pack(name)` 先按 `is_system=True, name=...` 查找，不存在则建；个人包用 `get_or_create(owner=user, name=...)`。DB 层不加会误导的约束，幂等放 services（与 M4-2 私聊幂等同思路）。
- `MediaObject.media_id` 唯一是硬约束（DB 层）——`media_id` 是对外稳定指纹，重复即冲突，绝不能由 services 兜底。
- `MediaUploadSession.upload_id` 唯一是硬约束（DB 层）。
- `EmojiItem.unique(pack, media)` 是硬约束（DB 层）——同一包内重复收藏必须被 DB 拒绝，services 捕获后幂等返回。

### 4.1 storage.py：S3/MinIO 同步封装（可注入 fake）

```python

class ObjectStorage:
    """MinIO/S3 兼容对象存储的同步薄封装（boto3）。"""

    def put(self, key: str, data: bytes, content_type: str) -> None: ...
    def get(self, key: str) -> bytes: ...
    def get_range(self, key: str, start: int, end: int) -> bytes: ...
    def head(self, key: str) -> int:          # 返回 size
    def exists(self, key: str) -> bool: ...
    def delete(self, key: str) -> None: ...

def get_storage() -> ObjectStorage:
```

- **配置（settings.py 新增，全部走 env，默认值仅本地开发）**：
  - `S3_ENDPOINT_URL`（默认 `http://127.0.0.1:9000`，MinIO）
  - `S3_ACCESS_KEY` / `S3_SECRET_KEY`（默认 elysia_minio/elysia_minio_pass，与 docker-compose 默认一致）
  - `S3_BUCKET`（默认 `elysia-media`；启动/首次上传时 `create_bucket` 幂等）
  - `S3_REGION`（默认 `us-east-1`，MinIO 兼容）
  - `S3_PUBLIC`（默认 False；私密媒体，**不得进入共享缓存**）
  - `MEDIA_TMP_TTL_SECONDS`（默认 600，上传会话 TTL）
  - `MEDIA_MAX_IMAGE_BYTES` / `MEDIA_MAX_VOICE_BYTES` / `MEDIA_MAX_FILE_BYTES` / `MEDIA_MAX_EMOJI_BYTES`（分类型上限，见 5.1）

- **boto3 同步客户端**：视图/服务在同步线程跑，直接同步调用即可（不占用事件循环）。`get_storage()` 用 module-level 单例 + `settings.S3_*`，测试里 `override_settings` 或 monkeypatch 注入 FakeStorage。

### 4.2 derivatives.py：缩略图 / 波形

- **缩略图（image / emoji）**：Pillow 打开原图 → 等比缩到 `MEDIA_THUMB_MAX`（默认 320px 长边）→ JPEG（白底，`quality=80`）→ 写 `thumbnail` key。记录 `width`/`height`（原图）。
- **波形（voice）**：解析 WAV（`wave` 模块，PCM 16bit）→ 分 N 段（默认 48）采样峰值/均方根 → Pillow 画灰色波形图（透明背景，深色柱）→ 写 `waveform` key。记录 `duration`（秒）。**本期只支持 WAV 波形**；MP3/M4A 等编码的波形生成属待确认（第 10 节：可降级为"无波形"并标注，不伪造）。
- **派生失败语义（阶段三 §10.2）**：元数据已提交（`status=ready`）、派生单独标记。派生生成放在 `:complete` 后的同一请求内做**尽力而为**：
  - 缩略图/波形生成或上传失败 → 记录 warning（失败路径留日志，AGENTS.md），`thumbnail_path`/`waveform_path` 留空，**不把 MediaObject 置 failed、不回滚完整上传**；
  - `status` 只表示"原始对象是否可用"：processing（刚 complete、派生中）→ ready（派生完成或派生失败但原始可用）。**禁止把派生失败伪装成媒体失败或空结果**。

## 5. REST API

### 5.1 媒体（挂 `/api/v1/media/`，对齐阶段三 §10.1 三步语义）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/v1/media/uploads` | 创建受控上传会话 `{kind, expected_size, mime_type}` → `{upload_id, kind, max_bytes, expires_at}` | 登录 |
| PUT | `/api/v1/media/uploads/{upload_id}` | 上传二进制（body 原始字节，`Content-Type` 忽略，以会话声明为准） | 会话 owner |
| POST | `/api/v1/media/uploads/{upload_id}:complete` | 校验 hash/size/MIME/文件头 → 生成 `media_id` → 触发派生 → `{media_id, descriptor}`；**幂等**：同 upload 重复 complete 返回同一 media_id | 会话 owner |

**媒体 descriptor（`MediaObjectSerializer`，对外统一形态，阶段三 §10 descriptor 对齐）**：

```json
{
  "media_id": "a5bdf36b...",
  "kind": "image",
  "mime_type": "image/png",
  "size": 102400,
  "status": "ready",
  "width": 800,
  "height": 600,
  "duration": null,
  "thumbnail": "/api/v1/media/{media_id}/thumbnail",
  "waveform": null,
  "created_at": "2026-08-11T00:00:00Z"
}
```

> descriptor 只含媒体标识、尺寸/时长等派生元数据与**应用内派生资源路径**；不暴露 `storage_path`、宿主机路径或任何签名 URL。

### 5.2 下载 / 派生 / descriptor

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/media/{media_id}` | 获取 descriptor + 处理状态 | 登录 + 有访问权 |
| GET | `/api/v1/media/{media_id}/content` | 流式下载原对象（支持 `Range`、`ETag`、`Cache-Control: private`） | 有访问权 |
| GET | `/api/v1/media/{media_id}/thumbnail` | 下载缩略图（无缩略图 → 404，`media_not_ready` 区分） | 有访问权 |
| GET | `/api/v1/media/{media_id}/waveform` | 下载波形图（无波形 → 404） | 有访问权 |
| POST | `/api/v1/media/{media_id}:save` | 将已授权媒体保存到本应用受管对象存储（**爱莉媒体投影通道预留**，本期返回 501，见 6.3） | 预留 |

**下载实现要点**：
- 从 `MediaObject` 读 `storage_path` → `storage.get_range()` → 组装 `StreamingHttpResponse`（`Content-Type`、`Content-Length`、`Accept-Ranges`）。
- **Range 支持**：解析 `Range: bytes=start-end`，返回 206 + `Content-Range`；非法 Range 返回 416。私密媒体 `Cache-Control: private, no-store`，**绝不进入共享缓存**（阶段三 §10.3）。
- 404 vs 403：媒体不存在 → 404；存在但无权 → **403**（不泄露是否存在，见 5.3 访问控制）。

### 5.3 媒体访问控制（工程硬约束）

媒体是"会话内共享"的私密资源，访问权按以下规则判定（`apps/media/services.py: can_access_media(user, media)`）：

1. **owner**：上传者本人永远可访问。
2. **消息引用**：`media` 被某条 `Message` 引用，且 `user` 是该消息所在会话（`conversation`)的成员 → 可访问。这是核心路径——"在聊天里收到图片/文件，就能打开它"。
3. **表情包**：`media` 属于某个 `EmojiItem`，且该表情包是**系统包**（全员可见）或**用户自己的个人包** → 可访问。他人个人包里的表情 → 403（不泄露）。
4. **其他情况**：403。

> **实现提示**：不要在下载视图里裸查 `Message.objects.filter(media_id=...)` 就放行——必须落到"该 user 在会话 members 里"（复用 `apps.chat.services.user_can_access`）。表情包路径同理。未授权一律 403/404，绝不静默放行（NFR-3）。

### 5.4 接入 M4-2 消息链（关键接线）

`apps/chat/serializers.py` + `services.py` + `views.py` 的改动（**最小改动，不重写既有逻辑**）：

- **CreateMessageSerializer 增加媒体校验**（`validate`）：
  - `type=image/voice/file/emoji` 时 `media_id` **必填**；`type=text/system` 时 media_id 忽略。
  - 媒体存在校验：`MediaObject.objects.filter(media_id=...).first()`；不存在 → 400（`media_not_found`）。
  - `status` 必须 `ready`（processing/failed → 400，`media_not_ready`）。
  - `kind` 与 `type` 匹配（image↔image、voice↔voice、file↔file、emoji↔emoji）→ 400（`media_type_mismatch`）。
  - **访问权**：调用方对该媒体有访问权（`can_access_media`）→ 403。防"拿别人的 media_id 发消息"。
- **MessageSerializer 增加 `media` descriptor 字段**：`media_id` 引用的 `MediaObjectSerializer`（无引用为 null）。消息帧 `message.new`/`elysia.reply` 里的 `media` 从字符串 `media_id` 升级为 descriptor 对象，**兼容性**：前端已按 M4-2 的 `media`（字符串或 null）处理，升级为对象属**公共契约变更**，需在 README 与 M5-2 前端同步注明（见第 10 节）。
- **广播**：`services._message_new_event` 的 `media` 字段带 descriptor（落库后查一次，或序列化时懒加载）。

> **不动**：`create_message` 的幂等/seq 逻辑、会话模型、撤回/已读。媒体校验只加在"发消息"入口与序列化输出，避免破坏 M4-2 的 77 个既有用例。

## 6. 爱莉媒体/表情（主体性边界 + 通道预留）

### 6.1 主体性铁律（继承 AGENTS.md §4.1）

- 爱莉在应用内是**一个真实 User**（M4-4 `elysia_profile` 绑定）；她发的图片/语音/表情在应用内就是 `sender=爱莉user`、`type=image/voice/emoji` 的普通消息。
- 应用侧**绝不生成、改写爱莉的第一人称媒体内容**；爱莉发的表情只做**渲染/投影**（如同 `elysia.reply` 只投影文本）。VLM 决策、现场生成是 Elysium 表情包插件（`plugins/emoji/`）的事，应用侧不做。

### 6.2 本期能力（应用内消息链）

- 应用内任意用户（含爱莉 user，通过 M4-4 通道）发的图片/语音/文件/表情消息，M4-3 的消息链媒体校验与渲染全部可用。**这部分契约测试必须覆盖**（发 emoji 消息、图片消息带 descriptor、越权媒体 403）。

### 6.3 未决点（爱莉媒体/表情的真实投影，必须显式标注，不阻塞本期）

- **爱莉从 Elysium 侧发出的图片/语音/表情如何进入应用侧对象存储**：Elysium 阶段三有 `/api/v1/media/*`（受控上传、`media_id` descriptor、`{media_id}:save`）。应用侧桥接在收到爱莉带媒体的 `chat.message.*` 事件时，需要：① 从事件 payload 的媒体 descriptor 拿到 Elysium 侧 `media_id`；② 经 `GET /media/{id}/content` 下载字节；③ 走本应用 `:save` 流程落到本应用对象存储生成应用侧 `media_id`；④ 投影为应用内带 `media` descriptor 的消息。
- **首期策略**：`POST /api/v1/media/{media_id}:save` 路由**预留但返回 501**（未实现）；爱莉媒体消息真实 E2E 不验收。等 M4-4 真实 E2E 跑通文本闭环后，再按此流程补媒体投影（与阶段三协调确认事件 payload 是否携带媒体 descriptor，若缺属公共契约缺陷，先说明再动）。
- 需求 FR-12「爱莉可用自己的表情包能力」：本期以"爱莉发的表情是普通 `type=emoji` 消息 + 应用内表情媒体"呈现；真实跨系统表情同步留待 6.3 未决点。

## 10. 已知取舍与待确认（遇到先记录，不阻塞）

- **爱
莉媒体/表情真实投影未做**（第 6.3 节）：爱莉从 Elysium 侧发图片/语音/表情，如何进入应用侧对象存储需 M4-4 真实 E2E + 阶段三协调验证（事件 payload 是否携带媒体 descriptor）。本期 `:save` 返回 501，爱莉媒体消息不验收。
- **消息 `media` 字段升级为 descriptor 是公共契约变更**：M4-2 时 `media` 是字符串 media_id（或 null），M4-3 升级为对象（含 thumbnail/waveform 路径）。README 必须注明；M5-2 前端（已按字符串/占位渲染）需同步升级渲染逻辑，否则图片/语音/文件消息无法展示真实内容。这是 M5-2→M5-2.1 的小改，不是新里程碑。
- **波形仅支持 WAV**：MP3/M4A/Opus 等编码的语音消息本期不生成波形（可降级为"无波形"并如实标注，不伪造）；若需要，后续加 ffmpeg 解析（属新增依赖，先说明再动）。
- **派生为同步尽力而为**：缩略图/波形在 `:complete` 请求内同步生成，大图/长语音可能拖慢 complete 响应；量小可接受，量大再异步任务化（保留派生失败不阻塞上传的语义）。
- **去重策略**：同 `content_hash` 已存在 MediaObject 时复用既有 `media_id`（减少存储）；但**不改变 owner 语义**（复用对象的 owner 仍是首传者）。若需"每人独立副本"再调整（记录 README）。
- **表情包检索只做基础 tag/名称匹配**：不做语义/向量检索（那是 Elysium 表情包插件的 VLM 能力）；检索排序只影响可达性，不自动改变事实状态（AGENTS.md §5.3）。
- **上传会话惰性清理**：`expires_at` 到期未 complete 的会话，由 `cleanup_media` 管理命令清理（含临时对象）；本期不引入后台调度，运维手动/计划任务执行即可（避免自动拉起，继承 Elysium 手动启动纪律）。
- **系统表情包 seed 幂等**：`seed_system_emoji` 可重复执行不重复建包；系统包图需管理员先上传 `kind=emoji` 媒体再关联（本期不内置图片资产，README 注明）。
- **视频不在本期**：消息类型无 video（M4-2 模型即无），直播/视频归 M4-6；不做视频转码/播放。

> 完成 M4-3 后，应用内图片/语音/文件/表情消息即可真实发送与渲染（M5-2 前端同步升级媒体渲染）。下一步按序 M4-5 语音（LiveKit，媒体/文件基础可复用）或先补 M4-4 真实 E2E 的爱莉媒体投影（6.3 未决点）。
