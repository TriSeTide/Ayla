# Ayla 直播性能与稳定性优化 —— 需求文档

> 版本：v1.0 · 2026-11-01
> 状态：**需求已固化，待开发**
> 适用端：**Web（Ayla/web）+ Flutter（Ayla/flutter）双端同步**
> 关联文档：[开发文档](./直播性能与稳定性优化-开发文档.md) · [设计事实源](../design.md)

---

## 1. 背景与问题陈述

### 1.1 用户实报（原文）

> 1. 「目前 Ayla 的问题是各种窗口状态变化或网络变化，都会使直播变黑屏，要过一会才恢复甚至不恢复，并且 Ayla 的直播延时长达 1 分多钟。」
> 2. 「我目前需要解决的就是一个刷新要跟上直播节奏、一个总是黑屏的问题（我希望任何窗口尺寸变化等都不会导致黑屏）、还有一个是延时 1 分钟的问题。」
> 3. 「延时目标 10 秒内就行，你看能不能做到 10 人左右看直播。」（**2026-11-01 修订：见下方 1.3**）
> 4. 「我说的经常黑屏甚至不恢复其实有 bug 的成分，不完全是网络原因，你要把他当代码逻辑修，因为窗口变化、网络抖动都不应该直接把直播给断了黑屏。」

### 1.2 问题定性（**核心结论**）

三个问题中，**两个是代码缺陷，一个是配置缺陷，全部与带宽无关**（10 人并发已按 §1.3 移出需求）：

| 问题 | 定性 | 依据 |
|---|---|---|
| 黑屏 / 不恢复 | **代码 bug**（6 条独立缺陷） | 见 §3.1，全部为状态机 / 生命周期 / 渲染层逻辑错误 |
| 延时 60s+ | **配置默认值叠加**（6 层） | 见 §3.2，无一为带宽导致 |
| 刷新键无效 | **代码逻辑错误** | `seek(duration)` 语义错误，见 §3.3 |
| ~~10 人同时观看~~ | **已移出需求**（见 §1.3 修订） | 服务器上行实测中位 ~5 Mbps，见 §4.2 |

> ⚠️ **本需求的核心立场**：窗口尺寸变化、网络抖动**在任何情况下都不应导致直播断流黑屏**。播放器必须具备自愈能力，且自愈必须是「快速、有界、可恢复」的，不能出现「封顶后永久放弃」。

---

### 1.3 需求修订（2026-11-01，**以本条为准**）

> 用户原话：「忽略我说的 10 人，我要 1080p3000 码率 4-5 秒延时」
> 补充：「就写 1 人看直播的就是了」

**修订后目标（取代 §1.1 第 3 条中的「10 人」）**：

| 项 | 值 |
|---|---|
| 观看人数 | **单观众（1 人）** |
| 分辨率 | **1080p** |
| 码率 | **3000 kbps** |
| 帧率 | 30fps |
| 编码器 | NVENC |
| **端到端延时** | **4~5 秒** |

「10 人同时观看」**已从需求中移除**，不再作为本期目标，也不再作为验收项。多人并发能力登记为「本期不做」（见 §2.2 N6），原因与实测数据见 §4.2 约束 C1。

## 2. 目标定义

### 2.1 功能目标（必须达成）

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | **任何窗口状态变化不黑屏** | 全屏↔窗口化、最大化↔还原、最小化↔恢复、拖动改变窗口尺寸、多显示器切换，**画面不中断**；允许 ≤300ms 的帧间隙，不允许黑屏超过 1s |
| G2 | **网络抖动后自动恢复** | 断网 ≤10s 后恢复网络，播放**自动恢复**，无需人工点重试；恢复时间 ≤3s |
| G3 | **切后台再回来自动恢复播放** | 移动端切后台→回前台、桌面端最小化→恢复，**自动续播** |
| G4 | **刷新键真正跳到直播最新** | 点击刷新后，播放位置与直播边缘的距离 ≤2 个分片（当前配置下 ≤4s）；有可见的「已贴边」反馈 |
| G5 | **端到端延时 4~5 秒** | 端到端延时（主播动作→观众看到）稳定在 **4~5 秒**，最差不超过 6 秒 |
| G6 | **1080p30 @3000kbps 单观众流畅播放** | 1 个观众观看 1080p30 @3000kbps，连续 30 分钟无卡顿、无黑屏 |
| G7 | **Web 与 Flutter 行为一致** | 两端在 G1~G6 上的表现必须一致；差异必须在开发文档中登记 |

### 2.2 非目标（本期明确不做）

| # | 不做 | 原因 |
|---|---|---|
| N1 | 追求 B 站级 1~2 秒延时 | 受链路抖动限制（RTT 18~105ms 抖动、带宽波动 9 倍），1~2s 缓冲无法吸收，会变成持续卡顿 |
| N2 | ~~1080p 高清 + 10 人同时观看~~ | **已被 §1.3 修订取代**：本期只做 1080p 单观众 |
| N3 | 更换播放内核 | 现有 media_kit（Windows）/ video_player（移动端）经调参可满足 G5，换内核风险大于收益 |
| N4 | 弹幕开关 / 清晰度切换 / 倍速 | 与 [design.md](../design.md) §12.7 既有规格冲突，非本期范围 |
| N5 | iOS 小窗脱离 | iOS 无跨应用窗口 API，且 Flutter 帧进不了系统 PiP（既有结论） |
| N6 | **多人并发观看** | 服务器上行实测 4.8~5.0 Mbps，1080p@3000kbps 下理论仅支持 1 人；多人需降码率，非本期目标 |

## 3. 缺陷清单（需求侧视角）

> 详细代码位置与修复方案见[开发文档](./直播性能与稳定性优化-开发文档.md) §3。

### 3.1 黑屏缺陷（6 条，全部为代码 bug）

| # | 缺陷 | 触发条件 | 用户可见现象 | 定性 |
|---|---|---|---|---|
| B1 | **全屏层是冻结的 Widget** | 全屏期间播放器自愈重建 | 全屏中黑屏，**点刷新/重试都无效**，必须退出全屏再进 | 渲染层 bug：全屏 overlay 持有捕获时刻的 widget 快照，播放器重建后没有通知它 |
| B2 | **自愈封顶后永久放弃** | 连续 2 次自动重建仍无画面 | 停在「播放失败」，必须人工点重试 | 状态机 bug：封顶后只报错，无时间窗重置，无后续重试 |
| B3 | **attach 幂等只比 URL** | 平台播放器实例已死但 URL 未变 | 永久黑屏，任何操作都不恢复 | 状态机 bug：幂等条件缺少「实例健康」判定 |
| B4 | **窗口缩放触发纹理注销重建** | 改变窗口尺寸 / 最大化 / 全屏切换 | 闪黑一帧，严重时永久黑 | 渲染层 bug：未固定纹理尺寸，窗口尺寸变化驱动了纹理重建 |
| B5 | **后台暂停后不自动恢复** | 切后台 / 最小化后返回 | 回到前台是黑屏，需手动刷新 | 生命周期 bug：`pauseUponEnteringBackgroundMode` 默认 true 但 `resumeUponEnteringForegroundMode` 默认 false，未显式传参 |
| B6 | **状态刷新无条件重挂播放器** | 小窗/脱离态期间收到 SRS 状态更新 | 页面与小窗双路抢流，主窗口黑屏 | 编排 bug：`refreshSrsStatus` 读到 live 就 attach，缺少「当前画面槽位」守卫 |

### 3.2 延时缺陷（6 层默认值叠加，共 60~90s）

| 层 | 现状 | 贡献延时 | 归属 |
|---|---|---|---|
| L1 | **推流 GOP = 8.33s**（实测，250 帧 @30fps）→ 目标 **1s** | 决定分片时长下限 | 推流端（OBS） |
| L2 | **SRS `hls_fragment` 未配置** → 默认 10s → 目标 **1s** | 分片实际 16.67s | 服务器配置 |
| L3 | **SRS `hls_window` 未配置** → 默认 60s → 目标 **10s** | playlist 4 片 ≈ 66s | 服务器配置 |
| L4 | **FFmpeg `live_start_index` 默认 -3** | 从边缘前 3 片起播 ≈ 落后 50s | 播放器参数 |
| L5 | **mpv `cache=yes` + `demuxer-max-bytes=32MB`**（media_kit 默认，Ayla 未覆盖） | 再囤数秒 | 播放器参数 |
| L6 | **ExoPlayer `MIN/MAX_BUFFER_MS = 50000`**（Media3 默认，插件锁死不可调） | Android 目标缓冲 50s | 播放器参数 |

### 3.3 刷新键缺陷

| # | 缺陷 | 定性 |
|---|---|---|
| R1 | `refreshToLiveEdge()` 最终执行 `seek(duration)`，而直播的 `duration` 是**整个 playlist 总长**（实测 ≈66s），不是直播边缘 | 语义错误 |
| R2 | 刷新后**无任何 UI 反馈**（无「已贴边」提示，也无失败提示） | 交互缺失 |
| R3 | 状态非 playing 时刷新键退化为「整条重建」，用户感知为「刷新一下等于重连」 | 策略错误 |

## 4. 性能目标与物理约束

### 4.1 目标指标

| 指标 | 目标值 | 当前值 | 测量方法 |
|---|---|---|---|
| **端到端延时** | **4~5s（最差 ≤6s）** | 60~90s | 秒表同屏对比 |
| **首帧时间** | ≤2s | 5~15s | 点击进房到出画 |
| **刷新键贴边误差** | ≤2 分片（≤4s） | ≈50s | 刷新前后 position 对比 |
| **窗口变化黑屏时长** | 0（允许 ≤300ms 帧间隙） | 1s~永久 | 人工 + 录屏 |
| **断网恢复时间** | ≤3s（断网 ≤10s 场景） | 不恢复 | 人工断网测试 |
| **1080p30@3000kbps 单观众** | 连续 30 分钟无卡顿 | 未验证 | 单端长时观看 |

### 4.2 物理约束（**不可突破，需求必须在此范围内定义**）

#### 约束 C1：服务器上行带宽（决定单观众上限）

实测（2026-11-01，真实链路经樱花隧道，多次采样）：

| 采样 | 单流速率 |
|---|---|
| 1 | 1,174,604 B/s ≈ 9.4 Mbps |
| 2 | 637,949 B/s ≈ 5.1 Mbps |
| 3 | 247,908 B/s ≈ 2.0 Mbps |
| 4 | 646,701 B/s ≈ 5.2 Mbps |
| 5 | 356,179 B/s ≈ 2.8 Mbps |

**中位数约 5 Mbps，波动区间 2.0~9.4 Mbps。**

**对 1080p@3000kbps 单观众的影响**：

| 场景 | 需要 | 实测能力 | 结论 |
|---|---|---|---|
| 1 人看 1080p30 @3000kbps | 3 Mbps 持续 | 中位 5 Mbps，低谷 2.0 Mbps | ⚠️ **大部分时间够用，低谷时会卡** |
| 1 人看 1080p30 @2500kbps | 2.5 Mbps | 低谷 2.0 Mbps | ⚠️ 仍可能卡 |
| 1 人看 720p30 @1500kbps | 1.5 Mbps | 低谷 2.0 Mbps | ✅ 有余量 |

> **这是本需求唯一的物理风险点**：目标「1080p @3000kbps + 4~5s 延时」在带宽低谷（2 Mbps）时会卡顿。
> 缓解手段（按优先级）：
> 1. **插网线**（千兆口当前 NO-CARRIER）——最彻底；
> 2. 保持 3000kbps 但**接受低谷时偶发卡顿**（自愈会在 3s 内恢复）；
> 3. 降到 2500kbps 留余量。
>
> **注意**：低延时（4~5s）要求缓冲小，缓冲小则无法吸收带宽低谷。**延时与抗抖动仍是矛盾关系**，本期选择「保延时，接受偶发卡顿 + 快速自愈」。

#### 约束 C2：链路抖动

实测：RTT 18~105ms（抖动 87ms），带宽 0.25~2.2 MB/s（波动 9 倍），丢包 0%。

**这意味着低延时与抗抖动天然矛盾。** 延时目标定为 4~6s（而非 1~2s），正是为了留出吸收抖动的缓冲余量。

#### 约束 C3：拉流入口受限

| 入口 | 状态 | 约束 |
|---|---|---|
| `live.trise.top:7882`（volx，流量无限） | **HTTPS 被阿里云备案拦截**（SNI 含 trise.top 即 RST） | 必须用**裸 IP** `47.108.85.223:7882` 直连 |
| `s.ayla.trise.top:26211`（樱花，流量有限） | 正常 | **仅作回退，不得用于常规拉流** |

#### 约束 C4：推流端配置

| 项 | 当前值 | 目标值 |
|---|---|---|
| 分辨率 | 1080p | **1080p（保持）** |
| 帧率 | 30fps | **30fps（保持）** |
| 码率 | 3000 kbps | **3000 kbps（保持）** |
| 编码器 | NVENC | **NVENC（保持）** |
| **GOP** | **8.33s** | **1s（★ 唯一必须改的项）** |

> **只有 GOP 需要改**：分辨率/帧率/码率/编码器全部保持现状。GOP 从 8.33s 改为 1s 是延时从 60s+ 降到 4~5s 的**必要前提**——SRS 只能在关键帧处切分片，GOP 8.33s 时分片永远 ≥8.33s。

## 5. 需求清单

### 5.1 播放稳定性需求（P0）

| ID | 需求 | 验收 |
|---|---|---|
| S1 | 全屏状态下播放器自愈重建后，全屏层必须同步刷新画面 | 全屏中人为断网 5s，恢复后画面自动回来 |
| S2 | 自愈失败后必须有界重试，不得永久放弃 | 连续失败后仍能在 60s 时间窗后重新尝试 |
| S3 | 播放器实例失效必须能被检测并强制重建 | 模拟实例死亡，系统自动恢复 |
| S4 | 窗口尺寸变化不得触发纹理重建 | 反复拖动窗口尺寸 20 次，无黑屏 |
| S5 | 切后台/最小化后返回必须自动续播 | 移动端切后台 30s 返回、桌面最小化 30s 恢复，均自动播放 |
| S6 | 任何时刻只能有一个画面槽位持有播放器 | 小窗开启期间，页面侧不得重新 attach |

### 5.2 延时需求（P0）

| ID | 需求 | 验收 |
|---|---|---|
| L1 | 起播必须贴近直播边缘（≤1 个分片） | 进房首帧延时 ≤2s，落后 ≤1 分片 |
| L2 | 播放过程中延时不得持续累积 | 连续观看 30 分钟，落后量 P95 ≤ 5s |
| L3 | SRS 分片与窗口必须显式配置 | 配置文件可见 `hls_fragment 1` / `hls_window 10`（GOP=1s 时） |
| L4 | 推流端 GOP 必须 ≤2s | OBS 配置截图 + SRS 日志分片时长验证 |

### 5.3 交互需求（P1）

| ID | 需求 | 验收 |
|---|---|---|
| I1 | 刷新键必须跳到直播边缘（不是 playlist 末尾） | 点击后 position 与边缘差 ≤2 分片 |
| I2 | 刷新必须有可见反馈 | 点击后有「已贴边 / 正在追上」状态提示 |
| I3 | 网络异常必须有可解释的状态 | 断网时显示「网络已断开，重连中」而非干等 |

### 5.4 双端一致性需求（P0）

| ID | 需求 |
|---|---|
| P1 | Web 与 Flutter 在 S1~S6、L1~L4 上行为一致 |
| P2 | 任何有意的端差异必须登记在开发文档 §7「端差异登记表」 |
| P3 | 视觉表现必须遵循 [design.md](../design.md) §12.7，不得新增视觉语言 |

## 6. 验收方式

### 6.1 自动化验收

| 项 | 方法 |
|---|---|
| 自愈状态机 | 单元测试：模拟 stall / fatal / 实例死亡，断言重建次数与时机 |
| 全屏刷新 | Widget 测试：全屏中触发播放器重建，断言全屏层拿到新 videoView |
| 刷新键贴边 | 单元测试：mock seekable 范围，断言 seek 目标为 `end - 1片` |
| 端差异 | 对照表审查 |

### 6.2 人工验收（必须）

| 项 | 步骤 |
|---|---|
| G1 窗口变化 | 全屏/窗口化/最大化/最小化/拖动尺寸 各 20 次，记录黑屏次数 |
| G2 断网恢复 | 断网 5s / 10s / 30s 后恢复，记录恢复时间 |
| G3 后台恢复 | 移动端切后台 30s、桌面最小化 30s |
| G4 刷新键 | 人为落后 10s 后点刷新，记录前后 position |
| G5 延时 | 同屏放秒表，录屏后逐帧对比，目标 4~5s |
| G6 单观众长时观看 | 1 个客户端连续观看 1080p30@3000kbps 30 分钟，记录卡顿/黑屏次数 |

## 7. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| **服务器是 WiFi 接入（校园网），上行低谷仅 2.0 Mbps** | 1080p@3000kbps 需要 3 Mbps，低谷时可能卡顿 | 优先插网线（千兆口当前 NO-CARRIER）；否则接受偶发卡顿 + 3s 内自愈 |
| **推流端 GOP 由用户控制** | 不改 GOP 则分片无法切到 2s，延时下限卡在 16s | 需求 L4 明确要求；开发文档给 OBS 配置步骤 |
| **volx 7882 实测拉流仅 3.6 KB/s**（待复测） | 若隧道本身慢，走 volx 的目标无法达成 | 开发文档 §6 列为「必须复测」项 |
| **SRS 配置变更需重启容器** | 会短暂中断推流 | 需用户批准后执行，选低峰期 |
| **双端同步改动** | 任一端遗漏会导致行为不一致 | 开发文档按端分列任务，验收必须双端 |
