**硬约束（继承 AGENTS.md + 阶段三决策 + 阶段四方案 §6/§7.4）**：
- **主体性铁律**（阶段四 §6.5 / 需求 NFR-6）：爱莉的"说过的话"以 Elysium 侧**真实 transcript / 发送回执**为准。应用侧**绝不伪造爱莉发言**：Voice Live 的转写文本只能来自阶段三 `transcripts` / observer 事件的投影，不能由应用侧生成；爱莉在语音频道里的"发言"必须可追溯到 Elysium `voice_call.transcript.final` 事件。
- **前端永不直连 Elysium**（阶段三决策 1 / 需求 §1.3）：一切爱莉语音交互（创建通话、ticket、转写、文本注入）经应用后端 `elysia_bridge` / `apps/voice` 代理。**真人用户之间的语音走 LiveKit（应用自己的 SFU）**，与爱莉无关。
- **爱莉 Voice Live 与 LiveKit 是两套媒体传输**（开发文档 §11 风险表第三行）：LiveKit 是 WebRTC SFU（真人多人频道），Voice Live 是浏览器 ↔ Elysium 的 WebSocket + PCM16 二进制协议（一对一意识实例，`max_concurrent_sessions=1`）。**本期不实现双向实时音频互通**（那需要与阶段三协调新契约，属公共契约缺陷，先说明再动）；本期以「控制面桥接 + 转写/状态投影 + 文本双向注入」打通爱莉入会闭环，见第 5 节与第 10 节。
- **幂等是工程硬约束**：向 Elysium 的 voice-call 命令（`:resume/:interrupt/:end/text`）必须带 `Idempotency-Key`（阶段三 `voice_call_*` 命令同 chat 命令的幂等语义）；应用内 `voice_channels` 落库复用 M4-2 `idempotency_key` 语义（如 `elysia-voice-<event_id>`）。
- **不扩张阶段三公共契约**：Voice Live 侧 `voice_call:operate` 只授权调用者被授权参与的通话；应用侧 credential 只申请所需最小 scope（见第 4.5 节），**不授 `admin:*`**。
- 每个订阅、后台任务、WS 连接与临时对象必须有明确 owner、超时、取消与关闭路径（AGENTS.md §7 / 阶段三决策 6）。
- LiveKit key/secret、Elysium voice-call 相关连接信息走本机配置，**不提交仓库**（开发文档 §10 / 部署纪律）。
- 每次改动要有与风险相称的契约测试（生命周期、鉴权、token 签发、幂等、断线恢复、主体性边界）。
- Elysium 必须由用户手动启动；LiveKit 属基础设施服务，可在 docker-compose 编排（不违背 Elysium 手工启动禁令）。

## 1. 目标（M4-5 验收定义）

完成**语音频道（真人多人）**与**爱莉 Voice Live 接入**两件事（开发文档 §8 M4-5 定义 + 需求 §3.4）：

### 1.1 真人语音频道（LiveKit，FR-13/14/16）

- **语音频道**：基于频道的多人语音（Discord 风格）；用户可加入/离开频道；`voice_channels` 表维护频道元数据（name/room_name/owner）。
- **LiveKit 集成**：自托管 LiveKit SFU；Django 用 LiveKit 官方 `livekit-api` 签发访问 token（绑定用户 identity + 房间 + publish/subscribe grants）。
- **通话控制（元数据层）**：静音/闭麦、音量由 LiveKit 客户端完成；**应用层只维护「谁在哪个频道」状态**，经 Chat WS 广播 `voice.state`。
- **断线恢复**：LiveKit 客户端自动重连；应用侧 `voice.state` 以 presence 心跳更新频道成员，成员表持久化。
- **验收**：2~8 人语音频道实时通话（P95<500ms，LiveKit 达标）；加入/离开状态广播正确；断线重连恢复。

### 1.2 爱莉 Voice Live 接入（FR-15）

- **控制面桥接**：应用后端经 `elysia_bridge` 调阶段三 `/voice-calls` 全套 REST——创建通话、查状态、`:resume`、`:interrupt`、`:end`、`/text`（文本注入）、`/transcripts`（转写历史）、`/tickets`（参与者/观察者 WS ticket）。
- **转写/状态投影**：应用后端以 **observer** 身份订阅该通话的 `voice_call.*` 事件（SSE `events/stream` 的事件类型过滤 `voice_call.`）或 `/observe` WS，把爱莉**真实 final transcript** 投影为语音频道内的"爱莉发言"（可追溯，不伪造），并广播 `voice.state` 更新爱莉在场/说话状态。
- **文本双向注入**：真人把想对爱莉说的话以文本提交给应用后端 → `POST /voice-calls/{id}/text` 注入 Voice Live（爱莉侧可听可说路径由 Elysium 管理）。
- **验收**：爱莉在应用内"入会"语音频道；真人通过文本/转写与爱莉语音对话闭环（至少一条真实路径可演示，见第 8.2 节端到端状态）。

**不包含（本里程碑边界，显式声明）**：
- **真人 ↔ 爱莉的实时双向音频互通**（把真人 WebRTC 音频实时送进 Voice Live、把爱莉 PCM16 音频实时播进 LiveKit Room）：协议不同（WebRTC vs WS+PCM16）、Voice Live `max_concurrent_sessions=1`、且需要 Elysium 侧新增媒体网关契约——属**未决点**（第 10 节），本期不做，先记录。
- 屏幕共享（FR-14 可选）：本期不做，LiveKit 本身支持，后续按需开启。
- 直播（M4-6）、桌游（M4-7）：不在本期。
- 不改造 Elysium 阶段三 voice-calls 代码（除非公共契约确有缺陷，先说明再动）。

## 3. 数据模型（严格按开发文档第 4 节 + 注明补充字段）

开发文档 §4 的 `voice_channels` 定义：
```text
voice_channels  id, name, room_name(unique), owner_id, created_at
```

### 3.1 VoiceChannel（按开发文档字段为主，补充字段显式标注）

| 字段 | 类型 | 约束/说明 | 来源 |
|---|---|---|---|
| `id` | AutoField | | 开发文档 |
| `name` | CharField(128) | 频道显示名（如「爱莉的家」「休息室」） | 开发文档 `name` |

### 3.2 VoiceChannelMember（补充表，理由见下）

| 字段 | 类型 | 约束/说明 | 来源 |
|---|---|---|---|
| `id` | AutoField | | 补充 |
| `channel` | FK → VoiceChannel, related_name="members" | | 补充 |
| `user` | FK → accounts.User | | 补充 |
| `joined_at` | DateTimeField(auto_now_add) | 最近加入时间 | 补充 |
| `last_seen_at` | DateTimeField(auto_now=True) | **补充**：presence 心跳刷新，断线判定依据 | 补充 |

**补充表/字段的理由**（写进 README 已知取舍）：
- 开发文档 §4 只有 `voice_channels`，但需求 FR-13「用户可加入/离开」FR-16「断线恢复」需要持久化"谁在哪个频道"；
- `last_seen_at` 用于心跳超时判定"是否还在频道"，配合 `voice.state` 广播（技术状态，不是爱莉/用户的情绪判断，见阶段三 §12.3）。

**权限语义**（复用 M4-2 约定）：
- `channel.owner` 只是"创建者"语义；真正权限判断是"是否在 `members` 里"（沿用 `user_can_access` 风格）。
- 频道默认开放加入（类似 Discord 语音频道）；是否需要邀请制/私有频道，M4-5 只做开放加入，私有留待后续（第 10 节）。

### 3.3 主体性约束（爱莉相关，重要）

- 爱莉在语音频道里的"发言"文本**只来自阶段三 `voice_call.transcript.final` / observer 事件投影**，应用侧绝不生成爱莉的第一人称内容（继承 AGENTS.md §4.1 主体文件主权 + M4-4 同款约束）。
- `voice.state` 里爱莉的 `state`（listening/thinking/speaking）是**技术状态**（阶段三 §12.3 Provider 状态），不得从 Provider 状态推断爱莉情绪或意图，也不得把它写成"爱莉正在……"的主观表达。

## 4. 与阶段三的真实接口契约（动手前对照源码复核）

> 以下契约摘录自阶段三真实实现（`Elysium/src/app/api/v1/voice_calls.py` + `schemas/voice_call.py`），是 M4-5 爱莉桥接调用的**事实依据**，不是本文件自造。若与源码不符，以源码为准并回填本文件。

### 4.1 控制面 REST（全部需要 `Authorization: Bearer <access_token>`）

| 方法 | 路径 | 用途 | 需要的 scope |
|---|---|---|---|
| POST | `/api/v1/voice-calls` | 创建通话 + 一次性 participant ticket（`VoiceCallCreated`） | `voice_call:operate` |
| GET | `/api/v1/voice-calls/{call_id}` | 通话状态与安全指标（`VoiceCallStatus`） | `voice_call:read` |
| POST | `/api/v1/voice-calls/{call_id}:resume` | 恢复可恢复通话（命令） | `voice_call:operate` |
| POST | `/api/v1/voice-calls/{call_id}:interrupt` | 清空播放并中断当前回复（命令） | `voice_call:operate` |
| POST | `/api/v1/voice-calls/{call_id}:end` | 结束通话（命令） | `voice_call:operate` |
| POST | `/api/v1/voice-calls/{call_id}/text` | 向实时会话注入文本（命令） | `voice_call:operate` |
| GET | `/api/v1/voice-calls/{call_id}/transcripts` | 授权转写历史（`VoiceTranscriptPage`） | `voice_call:read` |
| POST | `/api/v1/voice-calls/{call_id}/tickets` | 生成短时、单次、绑定 scope 的 WS ticket | participant `voice_call:operate`；observer `voice_call:observe` |
| WS | `/api/v1/voice-calls/{call_id}/ws` | 双向 PCM16 与控制事件 | participant 专属 |
| WS | `/api/v1/voice-calls/{call_id}/observe` | 只读字幕/状态观察 | 被授权 observer |

**请求体（真实 schema）**：
```json
// POST /voice-calls
{ "mode": "auto" | "full_duplex" }

// POST /voice-calls/{call_id}/text
{ "text": "..." }              // 1~8000 字符

// POST /voice-calls/{call_id}:interrupt
{ "played_audio_ms": 0 }       // 可选，0 ~ 86_400_000

// POST /voice-calls/{call_id}/tickets
{ "role": "participant" | "observer", "origin": "..." }
```

**响应**：
- `VoiceCallCreated`：`{ call: VoiceCallStatus, connection: WSTicketResponse }`。
- `VoiceCallStatus`：`call_id, episode_id, state(created/connecting/active/interrupting/stopping/ended/failed/suspended), mode, provider, created_at, updated_at, resumable, connected, input_audio_bytes, output_audio_bytes, interruptions, failure_reason`。
- `VoiceCallCommandAccepted`：`{ command: {...} }`；**所有命令端点必须带 `Idempotency-Key`**，同键重复提交返回同一命令，同键不同内容返回 409（与 chat 命令同语义）。
- `VoiceTranscriptPage`：`{ transcripts: [{sequence, occurred_at, role: "user"|"assistant", text, provider_event_id, visibility}], next_cursor, has_more }`。

**创建语义（重要）**：`POST /voice-calls` 会**同时**创建通话并把调用者作为 participant 签发 ticket——也就是说，**应用侧一旦以 service credential 创建通话，应用本身就是这个通话的参与者/拥有者**（`owner_actor_id` = credential 的 actor_id）。这决定了爱莉 Voice Live 桥接的 actor 归属（见 4.5）。

### 4.2 WS 子协议（协议复用，阶段三 §12.2）

- `_PARTICIPANT_PROTOCOL = "elysium.voice-call.participant.v1"`，`_OBSERVER_PROTOCOL = "elysium.voice-call.observer.v1"`——**必须作为 `Sec-WebSocket-Protocol` 头**携带，否则服务端以 1008 关闭。
- 音频二进制帧：`AUDIO_MAGIC = b"VL1\0"` + `AUDIO_HEADER = struct.Struct("<4sIII")`（magic, sequence, sample_rate, flags），PCM16 payload。上行 16k mono，下行 24k mono（阶段三 §12.2 / Voice Live protocol v1）。
- 控制帧保留 `start`、`interrupt`、`text`、`stop`、`ping`；服务端事件 `ready`、`state`、`transcript`、`playback.clear`、`metrics`、`error`、`ended`、`pong`。
- ticket：短 TTL（默认 30s）、单次消费、绑定 resource/subprotocol/origin/scope；浏览器与后台都必须先 `POST /tickets` 拿 ticket 再连 WS。
- **本期应用侧不直接开 participant WS**（不接 PCM16 音频流）；只用 **observer** 身份观察状态/转写，控制走 REST 命令（见第 5 节）。

### 4.3 状态与事件契约（阶段三 §12.3 / §12.4）

- 会话状态：`created / connecting / active / interrupting / stopping / ended / failed`（schema 另含 `suspended`）。
- Provider 状态：`idle / connecting / listening / thinking / speaking / interrupted / error / closed`——**技术状态，不推断情绪**。
- 语音事件（SSE `event_type` 前缀过滤 `voice_call.`，`include_payload=true` + `projection=full` 才带正文）：
  `voice_call.created`、`voice_call.connected`、`voice_call.resumed`、`voice_call.state_changed`、
  `voice_call.audio_input_received`（默认不携原始音频）、`voice_call.audio_output_dispatched`、
  `voice_call.transcript.partial`、`voice_call.transcript.final`、`voice_call.playback_cleared`、
  `voice_call.interrupted`、`voice_call.provider_state_changed`、`voice_call.metrics_recorded`、
  `voice_call.failed`、`voice_call.ended`。

### 4.4 隐私与恢复（阶段三 §12.5 / Voice Live 实时通话意识文档）

- 通话 ticket 单次、短 TTL、绑定 call id、Origin 和 scope；observer 不能发送音频或控制命令。
- transcript 默认私密；`transcript.partial` 可只存在瞬态流，`transcript.final` 是否进入权威 Life Event 遵循现有会话合同——**应用侧只投影 final transcript 为"爱莉发言"，partial 只做实时展示且不落库**。
- 原始通话音频明确不长期保存，无历史原始录音查询/下载接口——**应用侧不落盘任何音频**。
- 当前 `_sessions` 是进程内状态；阶段三明确"可恢复"的耐久元数据边界——**应用侧不得仅因 API 可重连就宣称跨进程恢复完成**（`resumable` 由 `VoiceCallStatus` 显式给出）。

### 4.5 凭据与 scope 设计（给应用侧 credential 的最小权限集）

沿用 M4-4 的凭据流程（`POST /admin/credentials` → `POST /auth/sessions` → refresh；secret 只显示一次，走本机配置）。**给同一把 service credential 追加 scope**：
- `chat:write`（既有，inject/send/reply）；
- `events:read` + `events:payload`（既有，SSE 订阅 + 读 payload 原文——**voice_call.* 事件也需要 payload**）；
- `voice_call:operate`（创建通话 + participant ticket + 命令）；
- `voice_call:read`（查状态 + 转写）；
- `voice_call:observe`（observer WS / observer ticket）；
- **不要授 `admin:*`**；不授本应用不需要的其他 scope（最小权限原则，阶段三 §9）。

**actor 归属说明**：应用侧以 service credential 的 actor 创建/操作通话，爱莉是通话的**对话对象**（Voice Live `session.user_id`/`user_name` 见 `plugins/voice_live/config.py` session 段）；"爱莉自己在通话中说话"的事实由 Elysium 侧 final transcript 的 `role="assistant"` 表达，应用侧只投影不生成。

## 5. 出站路由与爱莉入会设计（关键设计点）

### 5.1 场景

FR-15 说"爱莉可加入语音频道（Voice Live 意识实例），用户可与其语音对话"；但开发文档 §11 风险表第三行已声明「爱莉 Voice Live 与 LiveKit 对接……桥接需协议转换」，且 Voice Live 是**一对一**意识实例（`max_concurrent_sessions=1`），LiveKit Room 是**多人** WebRTC。两者不能简单互相翻译。

### 5.2 基线方案（本期可交付的"爱莉入会"闭环）

1. **爱莉入会（控制面）**：真人用户进入某个标记为"爱莉语音频道"的 LiveKit Room → 应用后端检测到爱莉频道被加入 → `elysia_bridge` 调 `POST /voice-calls` 创建 Voice Live 通话（一次性、单并发），拿到 `call_id` + 状态。
2. **状态投影**：应用后端以 **observer** 身份订阅该通话——推荐走 **SSE `events/stream`（`event_type=voice_call.*` + `stream_id` 匹配）**，与 M4-4 出站投影同机制；也可以开 `/observe` WS 拿实时 partial。把 `voice_call.state_changed` / `provider_state_changed` 投影为 `voice.state` 广播（爱莉 `connected/active/speaking` 等技术状态）。
3. **转写投影（爱莉发言）**：`voice_call.transcript.final`（`role="assistant"`）→ 投影为该语音频道**关联的会话/消息链**里的爱莉消息（复用 M4-2 `create_message`，`sender=爱莉的user`，`idempotency_key=elysia-voice-<event_id>` 幂等）→ 走 Chat WS 广播；真人可在频道文本栏看到爱莉说的话。**不伪造**：没有 final transcript 就没有爱莉发言。
4. **文本双向注入**：真人想对爱莉说话，可在频道文本栏提交 → 应用后端 `POST /voice-calls/{call_id}/text` 注入（带 `Idempotency-Key`）→ 爱莉侧由 Voice Live 语音回复，final transcript 再投影回来。
5. **离开/结束**：爱莉频道无人时，应用后端 `POST /voice-calls/{call_id}:end` 结束通话（幂等，重复调用返回同一命令）。

### 5.3 未决点（必须显式标注，遇到先记录不阻塞）

- **真人 ↔ 爱莉实时双向音频互通**：本期不做（见第 1 节边界）。真人 WebRTC 音频送进 Voice Live、或爱莉 PCM16 播进 LiveKit Room，需要 Elysium 侧新增媒体网关/桥接契约——**公共契约缺陷，先说明再动**，M4-5 只打通控制面 + 转写/文本。
- **Voice Live 单并发 vs 多人频道**：`max_concurrent_sessions=1` 意味着同一时刻只能有一个爱莉 Voice Live 通话；若多用户同时要与爱莉语音，需排队或只允许爱莉频道一个活跃通话（本期取后者，README 记录）。
- **爱莉频道与 LiveKit Room 的绑定**：用 `voice_channels.is_elysia=True` 标记（补充字段，见第 3.1 节），还是"爱莉 profile 绑定一个默认语音频道"？倾向**后者**（应用级单例，与 M4-4 `elysia_profile` 单例一致），见第 6 节。
- **partial transcript 的实时性**：本期不依赖 partial（只展示 final），避免把瞬态转写误当爱莉定稿发言（AGENTS.md：瞬态上下文不得冒充权威）。

## 6. 应用内 REST（挂 `/api/v1/voice/`）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/voice/channels/` | 频道列表（含人数、是否爱莉频道） | 登录 |
| POST | `/api/v1/voice/channels/` | 建频道 `{name}`（自动生成 `room_name`） | 登录 |
| GET | `/api/v1/voice/channels/<id>/` | 频道详情（成员 + 我的状态） | 登录 |
| PATCH | `/api/v1/voice/channels/<id>/` | 改名称（`room_name` 不可改） | 频道 owner/管理员 |
| POST | `/api/v1/voice/channels/<id>/join/` | 加入（拿 LiveKit token，见第 7 节）+ 落成员表 + 广播 `voice.state` | 登录 |
| POST | `/api/v1/voice/channels/<id>/leave/` | 离开（删成员/标记离开）+ 广播 `voice.state` | 成员 |
| POST | `/api/v1/voice/channels/<id>/heartbeat/` | presence 心跳（刷新 `last_seen_at`） | 成员 |
| GET | `/api/v1/voice/channels/<id>/members/` | 当前成员列表 | 登录 |

> 爱莉频道不单独建 REST（复用 M4-4 `elysia_profile` 单例 + 一个默认频道），见第 5.3 节。

## 7. LiveKit 集成（apps/voice/livekit.py）

- 依赖：`livekit-api`（Python 官方包，签发 `AccessToken` + `VideoGrants`）。
- `issue_token(user, room_name) -> str`：
  - `identity = f"user_{user.id}"`（或用户名，取稳定标识）；
  - `video = VideoGrants(room_join=True, room=room_name, can_publish=True, can_subscribe=True)`；
  - `ttl = settings.LIVEKIT_TOKEN_TTL_SECONDS`（默认 600，前端在过期前重签）。
- **前端绝不直接拿应用后端签发 LiveKit token 之外的任何媒体凭据**；token 只绑定该用户 + 该房间。
- 加入流程：`POST /join/` → 校验登录 → 写成员表 → 签 token → 返回 `{token, room_name, ws_url}`（`ws_url` = `LIVEKIT_WS_URL`）。
- 频道成员状态持久化：`VoiceChannelMember` 落库 + Chat WS 广播 `voice.state`（帧格式见第 8 节）。
- 断线恢复：客户端 LiveKit 断线重连；应用侧 presence 心跳（`heartbeat/`）与超时清理（后台任务定期把超过 `VOICE_MEMBER_TIMEOUT_SECONDS` 未心跳的成员标记离开，见第 9 节任务 owner）。

## 8. Chat WS 事件扩展（`voice.state`）

沿用 M4-2 的 `chat_conv_{id}` 组广播，新增事件类型（开发文档第 5 节已预留）：

```json
{
  "type": "voice.state",
  "data": {
    "channel_id": "3",
    "user_id": "a5bdf36b...",
    "state": "joined" | "left" | "muted" | "unmuted" | "heartbeat",
    "ts": "2026-08-11T00:00:00Z"
  }
}
```

- `joined/left/heartbeat`：成员表变更后广播；`muted/unmuted` 本期可由客户端静音时上报（元数据层，不落库强制）。
- 爱莉频道：`user_id = 爱莉的 user.id`，`state` 取 `voice_call.state` / Provider 状态映射（`connected/active/speaking` 等），**只表达技术状态**（见第 3.3 节）。
- 广播函数复用 M4-2 `services.py` 的 `_group_send_async` 模式（捕获 `ChannelFull` 记 warning，不阻塞其他成员）。

## 12. 已知取舍与待确认（遇到先记录，不阻塞）

- **真人 ↔ 爱莉实时双向音频互通是最大未决点**（第 5.3 节）：WebRTC vs WS+PCM16 两套媒体传输，需 Elysium 侧新增媒体网关契约（公共契约缺陷先说明再动）；本期以「控制面 + 转写/文本」打通爱莉入会闭环，实时双向音频留待后续里程碑。
- **Voice Live 单并发**（`max_concurrent_sessions=1`）：爱莉语音同一时刻只能一个活跃通话，多人频道同时要与爱莉语音需排队/限制（本期允许爱莉频道一个活跃通话）。
- **`voice_call.*` SSE 事件流未进 Elysium Life Event 账本**（2026-08-13 核实）：阶段三文档承诺 `events/stream` 可前缀过滤 `voice_call.*`，但 voice_live 的 EpisodeRecord 存于独立 runtime_store，不写 Life Event 账本——**公共契约缺口**。Ayla 侧已做前瞻兼容（`_handle_envelope` 分派 voice_call 事件），真实转写投影主路径为 `GET /voice-calls/{id}/transcripts` 增量轮询（幂等去重），未改动 Elysium 侧代码；若需 SSE 实时投影，须 Elysium 侧补事件桥（先说明再动）。
- **首期以 final transcript 投影为"爱莉发言"依据**：`partial` 只做实时展示不落库；`delivery_confirmed`/播放回执链路本期不做（与 M4-4 同取舍）。
- **爱莉频道绑定取"elysia_profile 单例 + 默认语音频道"**（倾向），不用 `is_elysia` 标记；如汐汐偏好频道级标记再调整。本期编排端点为应用内闭环入口（前端 M5-3 语音界面消费）。
- **`voice_channels` 成员表为补充表**（开发文档 §4 只有频道表，需求 FR-13/16 需要成员持久化）；`last_seen_at` 为补充字段，用于 presence 超时。
- **LiveKit 密钥安全**：API key/secret 走本机配置/环境变量，不提交仓库；token 只签给登录用户 + 绑定房间，前端拿不到其他媒体凭据。
- **Elysium 手工启动不变**：LiveKit 是应用自己的基础设施（docker-compose 编排），不触碰 Elysium 进程生命周期。

> 完成 M4-5 后，真人语音频道 + 爱莉 Voice Live 控制面/转写闭环即可跑通。下一步按序 M4-6 直播（若爱莉直播优先）或 M4-3 媒体（若语音消息/文件优先），建议按开发文档第 8 节顺序推进。
