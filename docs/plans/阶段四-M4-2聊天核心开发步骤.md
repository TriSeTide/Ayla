## 1. 目标（M4-2 验收定义）

完成**私聊 + 群聊**的聊天核心闭环：

- 会话（私聊/群聊）、会话成员（角色/禁言）、消息（文本/图片/语音/文件/表情/引用/@）、已读回执、撤回（限时）
- 私聊 REST + 群聊 REST + 群管理（建群/退群/成员/公告/群主管理员）
- 应用内 Chat WebSocket：`message.new/recall/read/reaction`、`typing`、断线补发（`last_message_seq`）、慢消费者不阻塞
- 消息幂等（`idempotency_key`）、离线消息上线补发
- 契约测试：两人私聊、十人群聊、幂等、越权 403、WS 连接/重连/补发

**不包含（本里程碑边界）**：
- 媒体上传/缩略图/表情包资产（M4-3）
- 爱莉桥接（M4-4）——但本里程碑的消息模型与 `idempotency_key` 契约是 M4-4 的地基，必须做扎实
- 语音/直播/桌游（M4-5~M4-7）

## 3. 数据模型（严格按开发文档第 4 节落库）

### 3.1 Conversation（会话）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | AutoField 主键 | 简单整数即可（消息帧里的 conversation_id 是字符串，序列化时转 str） |
| `type` | CharField | `PRIVATE`/`GROUP` 二选一，choices 约束 |
| `title` | CharField(128) | 私聊可为空（展示时用对方昵称）；群聊必填 |
| `owner` | FK → User | 群主；私聊会话 owner 可记发起方（仅作语义，权限判断以成员表为准） |
| `announcement` | TextField(blank) | 群公告（补字段，README 注明） |
| `created_at` | DateTimeField(auto_now_add) | |

约束：`type + 参与者` 决定唯一性——**私聊同两人只能有一个会话**（在 services 里做幂等查找，不在 DB 层硬约束，见 3.2 说明）。Meta `db_table="conversations"`。

### 3.2 ConversationMember（会话成员）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | AutoField | |
| `conversation` | FK → Conversation, related_name="members" | |
| `user` | FK → User | |
| `role` | CharField(16) | `member`/`admin`/`owner`，choices |
| `muted` | BooleanField(default=False) | 禁言（群内管理员可设） |
| `joined_at` | DateTimeField(auto_now_add) | |

约束：`unique_together (conversation, user)`。**私聊会话由 services 用 `get_or_create_conversation(user_a, user_b)` 幂等创建**：先查两人共有的 PRIVATE 会话，没有则建。注意私聊成员是双向两条记录（A-B 会话要建 (conv, A) 和 (conv, B) 两条），权限判断按"是否在 members 里"而不是按 owner。

### 3.3 Message（消息）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | AutoField（对外序列化为字符串） | |
| `conversation` | FK, related_name="messages" | 加 db_index（消息按会话分页查询是主路径） |
| `sender` | FK → User | |
| `type` | CharField(16) | `text`/`image`/`voice`/`file`/`emoji`/`system`，choices |
| `content` | TextField(blank=True) | 文本内容；图片/语音/文件消息存引用描述，媒体本体 M4-3 |
| `media_id` | CharField(64, null, blank) | 预留 M4-3 媒体引用，本里程碑可为空 |
| `reply_to` | FK → Message(null, on_delete=SET_NULL) | 引用回复；引用被删后置空而非级联 |
| `status` | CharField(16, default="sent") | `sent`/`delivered`/`read`/`recalled`，choices |
| `idempotency_key` | CharField(64) | **唯一索引**（`unique=True`）——幂等契约的核心 |
| `seq` | PositiveBigIntegerField | 会话内单调递增序号，用于补发与分页游标（见 3.4 说明） |
| `created_at` | DateTimeField(auto_now_add) | |
| `recalled_at` | DateTimeField(null, blank) | 撤回时间 |

Meta：`db_table="messages"`；索引 `(conversation, seq)` 唯一。

### 3.4 关于 `seq` 的说明（重要，别跳过）

- `seq` 是**会话内**的消息序号，从 1 开始单调递增，用于：① 断线补发（客户端带 `last_message_seq`，服务端补发 `seq > last_message_seq` 的消息）；② 历史分页游标。
- 生成方式：**不要用 `auto_now`/自增主键顶替**。在落库时用 `conversation.messages.aggregate(Max("seq")) + 1` 或更稳的方式：`seq = (conversation.messages.order_by("-seq").first().seq if 有消息 else 0) + 1`，在 `@transaction.atomic` 内完成，保证同一会话内不重复。
- 并发写同一会话时靠 `unique (conversation, seq)` 兜底：冲突就抛 IntegrityError，由 services 层重试一次或返回 409（记录在 README 的已知取舍里）。
- 简单实现可接受：本里程碑并发不高，`Max(seq)+1` 在事务内足够；**必须**保留 `unique` 约束防止脏数据。

### 3.5 MessageRead（已读回执）

| 字段 | 类型 | 约束/说明 |
|---|---|---|
| `id` | AutoField | |
| `message` | FK → Message, related_name="reads" | |
| `user` | FK → User | |
| `read_at` | DateTimeField(auto_now_add) | |

约束：`unique_together (message, user)`。语义：读到哪条 = 已读回执发到该条。私聊里给"对方发的消息"标已读，群聊里可选（本期实现私聊必做、群聊记录但不广播要求）。

## 4. 领域服务（apps/chat/services.py —— 复用核心）

> 为什么要有 services：REST 视图和 ChatConsumer 都要做"发消息"和"标已读"，且都要在落库后走 channel layer 广播。把这两件事收敛到 services，避免两处各写一份、广播逻辑漂移。

```python
# 关键函数签名（供你实现，可调整但不改语义）
def get_or_create_conversation(a_user, b_user) -> Conversation
    """私聊幂等：找两人共有的 PRIVATE 会话，没有则建（含两条成员记录）。"""

def user_can_access(user, conversation) -> bool
    """会话成员/群管理员权限判断；越权在视图层返回 403。"""

def user_role_in(user, conversation) -> str | None
    """返回 member/admin/owner 或 None（不在会话）。"""

def can_manage_group(user, conversation) -> bool
    """群管理员/群主才可：加踢人/禁言/改公告/改成员角色。"""

def create_message(user, conversation, *, content, msg_type="text",
                   reply_to=None, idempotency_key=None, media_id=None, seq=None) -> Message
    """幂等创建消息：同 idempotency_key 已存在则返回既有消息（不重复落库）；
    否则在事务内算 seq 并落库。调用方负责广播。"""

def find_by_idempotency_key(conversation, key) -> Message | None

def recall_message(user, message) -> Message
    """撤回：仅发送者本人、且 created_at 在限时窗口内（默认 2 分钟，settings 可配
    MESSAGE_RECALL_SECONDS=120）。成功置 recalled + recalled_at。"""

def mark_read(user, message) -> None
    """幂等写入 MessageRead；若该消息 sender != user 且用户已读，广播 message.read。"""

def conversation_seq(conversation) -> int
    """当前会话最大 seq。"""
```

广播约定（统一从这里发，事件帧严格按第 5 节）：
- `message.new`：发到 `chat_conv_{conversation_id}` 组，含 `message_id/sender_id/content/type/media/reply_to/seq/ts`
- `message.recall`、`message.read`、`message.reaction`（本期 reaction 只做事件占位，不建表，除非你顺手建 reaction 表）
- `typing`：`chat_conv_{id}` 组，`{user_id, conversation_id, is_typing}`

## 5. REST API（挂 `/api/v1/chat/`）

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| GET | `/api/v1/chat/conversations/` | 当前用户会话列表（含未读数、对方信息/群标题） | 登录 |
| POST | `/api/v1/chat/conversations/private/` | body `{user_id}` 开启/获取私聊会话 | 登录，目标存在 |
| POST | `/api/v1/chat/conversations/` | 建群 `{title, member_ids[]}`（owner=当前用户） | 登录 |
| GET | `/api/v1/chat/conversations/<id>/` | 会话详情（成员列表 + 我的角色） | 会话成员 |
| GET | `/api/v1/chat/conversations/<id>/messages/?before_seq=&limit=` | 历史分页（`before_seq` 游标，默认最新，按 seq 倒序） | 会话成员 |
| POST | `/api/v1/chat/conversations/<id>/messages/` | 发消息 `{type, content, reply_to?, idempotency_key, media_id?}` | 会话成员（禁言者 403） |
| POST | `/api/v1/chat/conversations/<id>/messages/<mid>/read/` | 标已读 | 会话成员 |
| POST | `/api/v1/chat/conversations/<id>/messages/<mid>/recall/` | 撤回（限时，仅发送者） | 发送者本人 |
| POST | `/api/v1/chat/conversations/<id>/typing/` | 声明正在输入（触发 `typing` 广播） | 会话成员 |
| POST | `/api/v1/chat/conversations/<id>/members/` | 加人（body `{user_ids[]}`） | 群管理员 |
| DELETE | `/api/v1/chat/conversations/<id>/members/<user_id>/` | 踢人 | 群管理员；群主不能踢自己 |
| POST | `/api/v1/chat/conversations/<id>/members/<user_id>/mute/` | 禁言/解除 `{muted: bool}` | 群管理员 |
| PATCH | `/api/v1/chat/conversations/<id>/` | 改群标题/公告 `{title?, announcement?}` | 群管理员 |

> 公告字段：开发文档 Conversation 表没有 announcement，你可以在 `Conversation` 上加 `announcement`（TextField blank）或建独立字段；**倾向直接在 Conversation 上补 `announcement` 字段**（一条迁移搞定，避免过度设计）。补字段要在文档/README 里注明。

**响应统一**：消息序列化含 `id(str), conversation_id(str), sender_id(str), type, content, media_id, reply_to(id 或 null), status, seq, created_at`。会话序列化含 `id(str), type, title, owner_id, members[], my_role, unread_count`。

**幂等返回语义**（严格按开发文档 9.1 验收）：
- 同 `idempotency_key` + 同 `conversation` + 同 `sender` 重复 POST：返回 200 + 原消息（不重复落库）。
- 同 key 但内容不同：返回 409 Conflict，detail 说明冲突。

## 6. Chat WebSocket（apps/chat/consumers.py）

### 6.1 连接协议

- 路径 `/ws/chat/?token=<jwt>`，**JWT 握手方式完全复用 M4-1 Presence 的 `_jwt_user_from_scope`**（把它抽到公共位置或复制一份，不要破坏 accounts 现有行为）。
- 连接成功后，客户端发 `subscribe` 帧（JSON）订阅会话组：
  ```json
  {"type": "subscribe", "conversation_ids": ["1", "2", "3"]}
  ```
  服务端逐个校验用户是否成员，是则 `group_add` 到 `chat_conv_{id}`，并把当前会话的 `conversation_seq` 回给客户端（用于后续 `last_message_seq` 补发基线）。

### 6.2 消息帧（严格按开发文档第 5 节）

```json
{
  "type": "message.new",
  "data": {
    "conversation_id": "1",
    "message_id": "42",
    "sender_id": "a5bdf36b...",
    "content": "你好",
    "type": "text",
    "media": null,
    "reply_to": null,
    "seq": 3,
    "ts": "2026-08-10T00:00:00Z"
  }
}
```

事件类型：`message.new` / `message.recall` / `message.read` / `message.reaction` / `presence.update` / `typing` / `live.danmaku` / `live.status` / `tabletop.event` / `tabletop.view` / `voice.state` / `elysia.reply`（本里程碑只实现前三个 + `typing`，其余类型保持协议命名但不实现）。

### 6.3 补发与重连

- 客户端重连后带 `last_message_seq` 帧：`{"type": "resume", "conversation_id": "1", "last_message_seq": 5}`。
- 服务端 `group_add` 后，把该会话 `seq > last_message_seq` 的消息逐条（或批量数组）发 `message.new` 补发，最后发一条 `{"type":"history.sync", "conversation_id":"1", "last_seq": <当前最大seq>}` 表示补发完成。
- 不重复：补发依据 `seq` 判断，客户端以 `seq` 去重（幂等恢复）。

### 6.4 慢消费者不阻塞广播

- `group_send` 是异步投递，channel layer 有容量上限（Redis layer 默认 `capacity`）。广播失败（`ChannelFull`）时**捕获并记 warning，不抛断当前连接**，保证单个慢消费者不影响其他成员（开发文档 9.2）。
- 在 `services` 的广播函数里统一 try/except `ChannelFull`。

### 6.5 广播处理器

Consumer 内实现与事件类型同名的方法（`async def message_new(self, event)`、`message_recall`、`message_read`、`typing_handler` 等），收到 `group_send` 的事件后 `send_json` 给客户端。事件里的 `user_id`/`sender_id` 用于前端过滤"自己发的 vs 别人发的"，服务端照发即可（不做回环过滤，客户端按 `sender_id` 判断）。
