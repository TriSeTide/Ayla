## 1. 目标（M5-1 验收定义）

完成**前端工程基座**，为后续所有界面模块提供统一底座：

- Vite + React 18 + TypeScript 工程（`web/` 目录）
- 路由（React Router）：登录/注册页 + 受保护的主布局（会话列表/聊天/设置等占位路由）
- 全局状态（Zustand）：auth（token/当前用户）、presence（在线用户）、UI（主题等）
- 认证闭环：注册 → 登录 → JWT 存取与自动刷新 → 登出；401 统一拦截跳登录
- API 客户端（fetch 封装）：自动带 Authorization、错误归一、401 处理
- Presence WebSocket：连接 `/ws/presence/`，维护在线状态
- 健康检查接线：`GET /api/v1/health/live/` 用于启动自检

**不包含（本里程碑边界）**：
- 聊天界面（M5-2）、语音（M5-3）、直播（M5-4）、桌游（M5-5）、爱莉集成（M5-6）
- 样式方案落地：本期只定架构与最小可用样式，不做完整视觉系统

## 3. 后端契约（M5-1 直接对接，按真实代码为准）

> 以下契约以 `Ayla/backend` 当前代码为准（不是拍脑袋）。

### 3.1 认证

| 方法 | 路径 | 入参 | 返回 |
|---|---|---|---|
| POST | `/api/v1/auth/register/` | `{username, email, password(≥8), nickname?}` | 201，`UserPublicSerializer` 字段 |
| POST | `/api/v1/auth/login/` | `{username, password}` | 200，`{access, refresh}` |
| POST | `/api/v1/auth/refresh/` | `{refresh}` | 200，`{access}`（**ROTATE_REFRESH_TOKENS=True → 也会返回新 refresh**，需前端更新） |
| GET | `/api/v1/me/` | 需 Authorization | 200，`UserPublicSerializer` 字段（含 `online`） |
| PATCH/PUT | `/api/v1/me/profile/` | `{nickname?, avatar?, signature?, status?}` | 200，profile 字段 |

> 登录接口是 SimpleJWT 的 `TokenObtainPairView`（返回 `access` + `refresh`）；刷新是 `TokenRefreshView`。
> `ROTATE_REFRESH_TOKENS=True`：**每次 refresh 都返回新 refresh**，前端必须用新值覆盖旧值，否则下次刷新会失败。

### 3.2 用户与好友（M5-1 只做数据契约留痕，界面 M5-2 起做）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/users/search/?q=` | 按用户名/昵称搜用户 |
| GET | `/api/v1/friends/` | 好友列表 |
| GET | `/api/v1/friends/requests/` | 好友申请列表 |
| POST | `/api/v1/friends/requests/` | 发起申请 `{to_user_id, message?}` |
| POST | `/api/v1/friends/requests/<id>/action/` | `{action: accept|reject}` |
| DELETE | `/api/v1/friends/<user_id>/` | 删除好友 |

### 3.3 Presence WebSocket

- 路径：`/ws/presence/?token=<jwt>`
- 握手：JWT query token（`AuthMiddlewareStack`，与 backend `accounts.consumers._jwt_user_from_scope` 一致）
- 消息协议（以 backend `accounts/consumers.py` 为准，实施前先读它）：
  - 服务端推 `presence.update` 帧（在线用户集合或增量）
  - 客户端可发 `ping`，服务端回 `pong`
- M5-1 目标：连上、拿到在线用户集合、能收到增量、断线重连（有界退避）

### 3.4 健康检查

- `GET /api/v1/health/live/`：无鉴权，返回 200（用于启动自检）
- `GET /api/v1/health/`：只读、快速、区分预期禁用与真实故障（AGENTS.md 第 8 节）

## 4. 关键实现要点

### 4.1 Token 生命周期（不要写进 localStorage）

- 内存存 access + refresh（Zustand `auth` store）。
- 请求拦截：`Authorization: Bearer <access>`。
- 401 且非 refresh 端点：静默调用 refresh（带重试互斥锁，避免并发请求都触发刷新），成功后重放原请求；刷新失败 → 清空 auth → 跳登录。
- 页面刷新恢复：启动时若有 refresh token（持久化 refresh 到 `sessionStorage` 可接受，或内存 + 每次刷新重新登录——**倾向 sessionStorage 存 refresh**，见已知取舍），调 refresh 拿新 access。
- 定时续期：access 30min，可在 access 过期前（如 25min）静默续期；或依赖 401 拦截即可（简单优先）。

### 4.2 API client（fetch 封装）

```ts
// 统一：baseURL 前缀、JSON、Authorization、非 2xx 归一为 ApiError{status, detail}、
// 401 触发 refresh 重放
```

- 错误归一：后端 DRF 错误结构 `{detail: string}` 或字段错误 `{field: [msg]}`，前端统一转成可读消息。
- 重放逻辑：被 401 拦截的请求要记住并重试一次；refresh 本身 401 视为登出。

### 4.3 Presence

- 单例连接（避免多页面/多组件各连一条）。
- 收到 `presence.update` 后更新 `presence` store。
- 断线：指数退避重连（1s→2s→4s→...上限 30s），重连成功重置退避；期间 UI 显示"连接中"（不阻塞主功能）。

### 4.4 路由与守卫

- `/login`、`/register` 公开；其余走 `ProtectedRoute`（无 access → 重定向 `/login`，带 `?next=` 回跳）。
- `HomeLayout` 为受保护主布局：左侧（会话列表占位）+ 主区域 `<Outlet/>`，为 M5-2 预留插槽。
- 登出：清 store + 断开 presence WS + 跳 `/login`。

### 4.5 与后端联调方式（dev）

- Vite dev server proxy：`/api` → `http://localhost:8100`，`/ws` → `ws://localhost:8100`（配 `ws: true`）。
- **注意**：8000 端口被 Elysium 主进程占用（阶段三 API），Ayla 后端实际在 **8100** 启动；`vite.config.ts` 默认 `VITE_DEV_PROXY_TARGET=http://127.0.0.1:8100`。
- 后端 `ALLOWED_HOSTS=["*"]` 已放行；本地 dev 无需 CORS 插件（走同源 proxy）。若直连后端域名则需配 CORS（backend 未装 `django-cors-headers`，需先确认）。

## 9. 已知取舍与待确认（遇到先记录，不阻塞）

- refresh token 持久化：**倾向 sessionStorage 存 refresh**（关闭标签页即失效，XSS 面小于 localStorage，刷新页面可恢复会话）。若要更强安全可内存 + 刷新即重登，体验差一些。二选一，README 注明。
- 样式方案：本期只用全局 CSS + 最小变量，视觉系统（设计 token / 组件库）留待 M5-2 或后续统一。
- CORS：本地 dev 走 Vite proxy 同源，无需 CORS；若未来前端直连后端域名，需先评估在 backend 加 `django-cors-headers`（涉及公共契约变更，先说明）。
- Presence 增量 vs 全量：以 backend `accounts/consumers.py` 实际协议为准；若后端推全量集合，前端直接替换；若增量，前端按 user_id 合并/移除。
- `ROTATE_REFRESH_TOKENS=True`：每次 refresh 都返回新 refresh，前端必须用返回值覆盖旧值，否则下次刷新 401。测试要覆盖"刷新后新 refresh 已持久化"。
