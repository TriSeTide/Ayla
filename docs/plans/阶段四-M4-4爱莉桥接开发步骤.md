**硬约束（继承 AGENTS.md + 阶段三决策 + 阶段四方案 §6）**：
- **主体性铁律**（阶段四 §6.5 / 需求 NFR-6）：应用只作为**带 actor/source 的观察**进入 Elysium；爱莉的"已表达"以 Elysium 侧真实发送/播放回执为准，**应用绝不伪造爱莉说过的话、不写主体文件、不替爱莉判断意义**。
- **前端永不直连 Elysium**（阶段三决策 1 / 需求 §1.3 铁律）：一切 Elysium 交互经 `apps/elysia_bridge/` 代理；前端/应用内用户只连应用自己的 REST/WS。
- **SSE 观察 + 命令端点发送**（阶段三决策 2 / §9.2）：`/api/v1/events/stream` 只用于**观察** Life Event；爱莉的回复经 `POST /api/v1/chat/messages:send` / `{id}:reply` 命令端点发出。**不要把 SSE 事件误当成"爱莉已发送"**——SSE 里出现的回复是"爱莉打算说什么"，真实回执以 `delivery_confirmed` 为准（本期可先以 SSE 投影为准并在 README 记录取舍，见第 10 节）。
- **幂等是工程硬约束**：应用侧向 Elysium 的命令请求必须带 `Idempotency-Key`；应用内落库复用 M4-2 的 `idempotency_key` 语义。
- 每个订阅、后台任务、DB 连接与临时对象必须有明确 owner、超时、取消与关闭路径（AGENTS.md §7 / 阶段三决策 6）。
- 桥接的 Elysium 连接信息（URL、service credential）走本机配置，**不提交仓库**（开发文档 §10）。
- 每次改动要有与风险相称的契约测试（生命周期、授权、幂等、SSE 断线恢复、主体性边界）。

## 1. 目标（M4-4 验收定义）

完成**爱莉 ↔ 应用**的聊天闭环（开发文档 §8 M4-4 定义 + 需求 §3.7）：

- **service credential 获取**：应用后端获取 Elysium service credential（`POST /admin/credentials` 一次性 secret → `POST /auth/sessions` 换 session token），后台自动 refresh；撤销/轮换有明确路径。
- **爱莉用户身份**（FR-26 / FR-23）：爱莉在应用内是**一个真实 User**，可被搜索、私聊、@、加群；`elysia_profile` 维护该 User ↔ Elysium stream_id 的唯一映射。
- **入站（用户 → 爱莉）**（FR-24）：应用内用户给爱莉发消息 → `elysia_bridge` 记录应用内消息（复用 M4-2 消息模型）→ `POST /chat/messages:inject` 注入 Elysium 主链，触发爱莉思考。
- **出站（爱莉 → 用户）**（FR-25）：应用后端**订阅 `GET /events/stream`（SSE）** → 按事件类型 + 本应用 stream 过滤出爱莉回复 → **投影为应用内消息**（`elysia.reply` 语义：落库 + 走 M4-2 Chat WS 广播 `elysia.reply` 事件推给对应 conversation 在线用户）→ 离线用户下次上线按 `last_message_seq` 补发。
- **断线恢复**：SSE 断线用 `Last-Event-ID`/cursor 补历史；应用内 WS 断线复用 M4-2 的 `last_message_seq` 补发。
- **契约测试**：inject 入站（mock Elysium）、SSE 出站投影（mock Elysium）、`elysia_profile` 生命周期、凭据管理、主体性边界（不伪造爱莉发言）。

**不包含（本里程碑边界）**：
- 语音/直播/桌游桥接（M4-5~M4-7）——`elysia_profile` 与桥接骨架要为这些复用，但本期只做**聊天闭环**；`elysia_profile` 的 `platform` 字段先按开发文档保留，M4-5~M4-7 再扩展。
- 媒体上传（M4-3 尚未交付，若已交付则爱莉消息带媒体走 M4-3 通道，本期不扩展）。
- 不改造 Elysium 阶段三代码（除非公共契约确有缺陷，先说明再动）。
- 不实现「应用 → Elysium」历史回灌或爱莉状态双向同步。

**补充字段的理由**（写进 README 已知取舍）：
- `display_name`/`created_at` 是应用侧管理展示，不涉及 Elysium 主体语义；

## 4. 与阶段三的真实接口契约（动手前对照源码复核）

> 以下契约摘录自阶段三真实实现（`Elysium/src/app/api/v1/`），是 M4-4 调用的**事实依据**，不是本文件自造。若与源码不符，以源码为准并回填本文件。

### 4.1 入站：`POST /api/v1/chat/messages:inject`

- 鉴权：`Authorization: Bearer <access_token>`，scope 需含 `chat:write`。
- 请求体（`InboundMessageInjectRequest`）：
  ```json
  {
    "stream_id": "<爱莉的stream_id>",
    "content": "<用户消息文本>",
    "sender_name": "<应用内昵称，可选>",
    "sender_id": "<应用内用户id，可选>",
    "sender_cardname": null,
    "chat_type": "private",
    "platform": "elysia-app"
  }
  ```
  字段约束（`schemas/inbound_message.py`）：`stream_id`/`content` 必填；`content` 1~100_000 字符；`sender_name`/`sender_id`/`sender_cardname` 可选、strip 后非空且 ≤240；`chat_type` ∈ `private|group`；`platform` 可选。
- **`platform`/`chat_type` 省略时**：从权威账本投影该 stream 的既有 provider 身份；账本不可投影则拒绝。本应用**显式传 `platform="elysia-app"` + `chat_type`**（快速路径，避免把独立应用消息误判为已停用平台的来源）。
- 返回 `202 Accepted`：`{"message_id": "...", "stream_id": "...", "accepted": true}`（**同步端点，无 Idempotency-Key**）。
- 语义：把用户消息交给 Elysium 主链（`ON_MESSAGE_RECEIVED` → Distributor → Chatter）触发爱莉思考；**本端点不产生对外发送**，回复由命令端点发出（inbound_messages.py 模块 docstring 明示）。
- 错误：stream 不存在 404（`stream_not_found`）；未授权 401/403。

### 4.2 出站：`GET /api/v1/events/stream`（SSE，观察通道）

- 鉴权：`Authorization: Bearer <access_token>`。
- 用途（阶段三决策 2）：应用后端**订阅** Elysium Life Event 流，观察爱莉回复。这是**只读观察**，不是发送通道。
- 请求参数：`Last-Event-ID`（标准 SSE 断点恢复）或 `cursor` query；两者同时提供且不一致时返回显式错误（§7.3）。
- **事件过滤（EventFilter）**：订阅时可按 `event_type`、`channel`、`stream_id`、`source_instance_id`、`occurred_after/before` 过滤；`include_payload` + `projection=full` 需要更高授权（`events:payload` 或 platform_service 角色）。
- **事件信封（EventEnvelope）**，关键字段：`event_id`、`sequence`、`event_type`、`stream_id`、`reply_target`（`{type, id}`）、`actor`（`{type, id, display_name}`）、`channel`、`payload`、`visibility`、`correlation_id`、`causation_id`。
- **event_type 过滤**：聊天消息事件类型见 `Elysium/src/app/api/v1/chat.py` 的 `_MESSAGE_FACTS`：`chat.message.received`、`chat.message.delivery_confirmed`、`text`（旧通道归一化）。**本应用订阅 `event_type` 前缀过滤**，只取 `chat.message.*` 且 `stream_id` 属于本应用 `elysia_profile.stream_id`。
- **payload 授权**：`include_payload` 默认 `false`（summary 投影，只给 `content_ref`/`metadata`，不给原文）。**应用要拿到回复内容，必须请求 `include_payload=true` + `projection=full`**，这要求 service credential 具备 `events:payload` scope 或 platform_service 角色（见 4.4 凭据 scope 设计）。
- **心跳与 gap**：服务端 `: heartbeat` 不推进业务 cursor；历史缺口返回结构化 SSE 错误帧 `{"error":{"code":"history_gap",...}}`，带 `recovery.cursor`，应用侧**必须**按 recovery cursor 重连，禁止把游标跳到尾部伪装连续（AGENTS.md §5.1）。
- **断线恢复**：客户端断线不推进服务端 durable cursor；重连时带 `Last-Event-ID`（上次收到的 `id:` 即 cursor）补历史。
- **本应用如何路由**（第 5 节详述）：所有用户 → 同一个爱莉 `stream_id` 注入，爱莉回复事件带 `stream_id` 与本应用 profile 匹配；**具体回给哪个用户**依赖事件里的 `reply_target` / `correlation_id` / payload 中回显的 `sender_id`。若 Elysium 事件无法可靠回显来源，这是**待协调的未决点**（第 10 节）。

### 4.3 出站发送：命令端点（真正的发送通道）

- **`POST /api/v1/chat/messages:send`**：向已授权 stream 发送文本或规范化 message parts。scope `chat:write`，**必须带 `Idempotency-Key`**，返回 `202` + `ChatCommandAccepted`（含 `command_id`、`status`）。请求体含 `stream_id`、`parts`（`[{type:"text", text}]`）等。
- **`POST /api/v1/chat/messages/{id}:reply`**：显式引用当前 actor 可见的原消息回复。同样 `chat:write` + `Idempotency-Key`，返回 `202`。
- 其它命令：`{id}:edit`、`{id}:recall`、`/reactions`、`{id}:mark-read`、`messages:forward`、`streams/{id}/poke` 等（本期只用到 send/reply，其余按需扩展）。
- **幂等语义**：同 `Idempotency-Key` 重复提交返回同一命令；同键不同内容返回 `409`（阶段三 §7.3 / chat_commands.py）。应用侧**必须**为每次发送生成 `Idempotency-Key`（建议 `elysia-send-<uuid>`），重试用同一 key。
- **命令结果**：`CommandStatus` 有 `SUCCEEDED`/`FAILED`/`DELIVERY_UNKNOWN`/`REJECTED` 等。`DELIVERY_UNKNOWN`（平台超时未确认）不得伪装成成功或失败，也不得盲目自动重发（阶段三硬约束）。
- **本期发送策略**：M4-4 首期以 SSE 投影为准（爱莉回复在 SSE 事件里已含内容），命令端点主要供**将来**需要主动推送/补发时使用；但**必须在文档与契约测试里把命令端点链路打通**（凭据、scope、幂等键、结果解析），避免 M4-4 留下"只能观察不能发"的半截能力。

### 4.4 凭据流程（service credential → session token）

阶段三 `admin.py` + `auth_store.py` + `runtime.py` 的真实流程：

1. **创建凭据**：`POST /api/v1/admin/credentials`，body `{actor_id, scopes, resource_grants?}`，scope 需 `admin:credential`（管理员/受信平台服务）。返回 `201` + `{credential: {...}, secret: "<一次性明文>"}`——**secret 只在创建时返回一次**，应用侧必须立刻安全落盘（本机配置，不提交仓库）。
2. **换 session**：`POST /api/v1/auth/sessions`，body `{grant_type, service_credential, audience}`（`grant_type=service_credential`）。返回 `{session, access_token, refresh_token}`。
3. **后续调用**：所有阶段三接口带 `Authorization: Bearer <access_token>`。
4. **refresh**：`POST /api/v1/auth/sessions/current:refresh`，body `{refresh_token}`，返回新 access/refresh 对。access TTL 默认约 30 分钟，refresh 约 7 天（阶段三运行时配置）。**应用侧在 access 过期前自动 refresh，失败则重走凭据流程或告警**。
5. **撤销/轮换**：`DELETE /api/v1/admin/credentials/{credential_id}` 撤销（旧 session 立即失效）；`POST /api/v1/admin/credentials/{credential_id}:rotate` 轮换（返回新 secret，同样只显示一次）。应用侧捕获 `401/credential_revoked` 后应走恢复流程。
6. **scope 设计（给应用侧 credential 的最小权限集）**：
   - `chat:write`（inject + send/reply）；
   - `events:read` + `events:payload`（SSE 订阅 + 读 payload 原文）——若平台服务角色默认含 payload，可省 `events:payload`；
   - 不要授 `admin:*`（应用不是管理员，只用平台服务凭据）。
   - **最小权限原则**（阶段三 §9）：不授予本应用不需要的 scope。

### 4.5 后台订阅任务（SSE 长连接）

- `management/commands/run_bridge.py`：独立管理命令，启动 SSE 订阅循环，**明确 owner**（Django 后台任务管理，见 AGENTS.md §7）。
- 生命周期：启动时用最新 cursor 或 `Last-Event-ID` 建立连接 → 持续读 SSE → 解析 EventEnvelope → 过滤 → 投影落库 → 广播 → 断线/心跳超时/错误帧时**按最后安全 cursor 重连**（有界退避），进程收到 SIGTERM/SIGINT 优雅关闭（关连接、关任务）。
- 慢消费者/阻塞：SSE 读取是单连接拉取，**不阻塞 Elysium 主链**（Elysium 侧已是 queue + limit 设计）；应用侧处理慢时要限速/降级，不能拖垮应用后端。
- 多实例部署提示：若应用后端多实例，SSE 订阅只能一个 owner（否则重复投影），用 Redis 锁/分布式任务占位（本期单实例即可，README 记录）。

## 5. 出站路由设计（关键设计点）

### 5.1 场景

FR-23 说"维护爱莉的 `stream_id` 作为应用内唯一会话"；FR-26 说爱莉是真实用户可被私聊。两者合起来：**应用内所有用户与爱莉的私聊，都通过同一个爱莉 `stream_id` 注入 Elysium**。那么爱莉回复后，SSE 事件如何知道回给**哪个应用内用户**？

### 5.2 基线方案

- **inject 时回显来源**：应用侧在 inject 请求里带上 `sender_id`（= 应用内用户 id 的稳定标识）作为来源。
- **出站匹配**：收到 `chat.message.*` 事件且 `stream_id == elysia_profile.stream_id` 时，从事件的 `reply_target`/`correlation_id`/payload 中**寻找回显的应用内 `sender_id`**：
  - 若事件带 `reply_target`（指向 Elysium 侧该用户消息的 id），应用侧维护「Elysium 消息 id ↔ 应用内消息」映射（`inject` 返回的 `message_id` + 应用内消息的 `idempotency_key`），据此定位会话；
  - 若事件 payload/metadata 回显 `sender_id`，直接用应用内用户 id 定位会话；
  - **匹配不到时**：降级为「推给爱莉 profile 对应的默认会话/广播给订阅了该 stream 的应用内会话」，并在日志留 warning（不静默丢弃，见 AGENTS.md 失败路径留日志）。
- **投影落库**：定位到应用内 conversation 后，用 M4-2 `create_message`（`sender=爱莉的user`、`conversation=该用户与爱莉的私聊/相关群`、`idempotency_key=从事件构造的稳定key`，如 `elysia-<event_id>`）落库，然后广播 `elysia.reply`（或 `message.new`）给该 conversation 组。
- **幂等**：以 `elysia-<event_id>` 作为 `idempotency_key`，重复收到同一事件（SSE 重放）不会重复落库。

### 5.3 未决点（必须显式标注，遇到先记录不阻塞）

- **Elysium 侧出站事件是否可靠回显"应用内 sender_id / reply_target"**：这取决于 Life Event 对 `chat.message.*` 事件的投影（`reply_target` 来自事件原始 `reply_target`，而 inject 注入的消息本身没有 reply_target）。**首期实现前必须先验证**：向一个真实/测试爱莉 stream inject 一条带 `sender_id` 的消息，看爱莉回复事件里能否定位来源。若不能，需要与阶段三协调——这属于**公共契约缺陷**，先说明再动（不能私自扩阶段三）。
- 多用户同时私聊爱莉时的并发回复路由正确性。
- 群聊场景（爱莉在群里）：本期可只支持「爱莉私聊」，群聊爱莉纳入 M4-4 边界或留待后续，需与汐汐确认。
