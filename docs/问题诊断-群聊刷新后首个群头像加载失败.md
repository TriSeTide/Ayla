# 问题诊断：群聊界面刷新后首个加载的群聊加载不出图片

## 📋 问题描述

**现象**：
- 在群聊界面（`/group/:id`）刷新页面后
- 首个加载的群聊无法显示头像图片
- 其他群聊的头像可以正常显示

**影响范围**：
- 宽屏：ServerRail 左侧群列表的首个群头像
- 窄屏：HomePage 主页的群卡片/列表项头像
- 可能也影响其他使用 Avatar + ResourceImage 的地方

---

## 🔍 根因分析

### 问题根源：竞态条件（Race Condition）

当用户刷新页面后直接进入 `/group/:id` 时，存在以下执行顺序：

#### **场景 1：正常情况（后续群聊）**
```
1. main.tsx 预加载启动 → loadCoreData()
2. Promise.all([listConversations(), ...]) 开始请求
3. 用户停留在页面，未触发新请求
4. 数据返回 → useChatStore.setConversations(convs) ✅
5. 组件渲染 → 使用已加载的数据 ✅
6. ResourceImage 请求头像 → 成功 ✅
```

#### **场景 2：竞态条件（首个群聊刷新）**
```
1. 用户直接访问 /group/:id（或刷新该页面）
2. main.tsx 预加载启动 → loadCoreData() Promise.all 开始
3. GroupPage useEffect 检测到 conversations.length === 0
4. GroupPage 立即发起 chatApi.listConversations() 请求（第二个请求）
5. 第二个请求先返回 → useChatStore.setConversations(list)
6. 组件渲染 → currentGroup = conversations.find(c => c.id === id)
7. ServerRail 渲染 Avatar → ResourceImage 开始请求头像
8. 第一个请求（预加载）返回 → useChatStore.setConversations(convs) ⚠️
9. conversations 状态被覆盖 → 触发重新渲染
10. ResourceImage 组件卸载/重新挂载 → blob URL 被 revoke ❌
11. 新的 ResourceImage 尝试加载 → 缓存中的 blob URL 已失效 ❌
```

### 技术细节

#### **1. ResourceImage 的缓存机制**
```typescript
// ResourceImage.tsx line 8
const blobCache = new Map<string, string>();

// line 58-64：检查缓存
const cached = blobCache.get(src);
if (cached) {
  setResolvedSrc(cached);
  return;
}
```

**问题**：
- 缓存使用 `src`（完整 URL）作为 key
- blob URL 永久存储，不会自动 revoke
- 但当组件因父组件状态变化而重新挂载时，旧的 blob URL 可能已经失效

#### **2. 预加载与页面加载的冲突**
```typescript
// main.tsx line 43-58
const loadCoreData = async () => {
  const [convs, voices, lives] = await Promise.all([
    listConversations(),  // 第一个请求
    // ...
  ]);
  useChatStore.getState().setConversations(convs); // ⚠️ 无条件覆盖
};

// GroupPage.tsx line 133-149
useEffect(() => {
  if (conversations.length > 0) return; // ⚠️ 只检查是否为空
  chatApi.listConversations()  // 第二个请求
    .then((list) => {
      useChatStore.getState().setConversations(list); // ⚠️ 先返回先写入
    });
}, [conversationRetry]);
```

**冲突点**：
- 两个并发请求都调用 `setConversations()`
- `setConversations` 无条件覆盖，不检查数据是否已存在
- 后返回的请求会覆盖先返回的数据
- 触发组件重新渲染 → ResourceImage 重新挂载

#### **3. Zustand 状态更新触发重渲染**
```typescript
// stores/chat.ts line 43-44
setConversations: (conversations) =>
  set({ conversations, loading: false, error: null, lastFetched: Date.now() }),
```

**问题**：
- 即使数据内容相同，调用 `set()` 也会触发重渲染
- 导致已经渲染的 Avatar → ResourceImage 组件重新挂载
- 之前加载的 blob URL 在新实例中可能失效

---

## 🎯 解决方案

### **方案 1：防止重复加载（推荐）** ⭐

**原理**：让 `setConversations` 在数据已存在时跳过更新，避免无意义的重渲染。

**修改文件**：`web/src/stores/chat.ts`

```typescript
setConversations: (conversations) => {
  const { conversations: current } = get();
  // 如果数据已存在且非空，跳过更新（避免预加载与页面加载冲突）
  if (current.length > 0) {
    console.log('[ChatStore] 数据已存在，跳过重复加载');
    return;
  }
  set({ conversations, loading: false, error: null, lastFetched: Date.now() });
},
```

**优点**：
- ✅ 简单直接，只需修改一处
- ✅ 防止重复加载导致的状态覆盖
- ✅ 避免无意义的重渲染

**缺点**：
- ⚠️ 如果数据确实需要刷新，需要先调用 `reset()` 清空

---

### **方案 2：使用加载中标志位**

**原理**：在 chat store 增加 `isLoadingConversations` 标志位，防止并发请求。

**修改文件**：`web/src/stores/chat.ts`

```typescript
interface ChatState {
  // ...
  isLoadingConversations: boolean; // 新增
}

export const useChatStore = create<ChatState>((set, get) => ({
  // ...
  isLoadingConversations: false,
  
  setConversations: (conversations) => {
    set({ 
      conversations, 
      loading: false, 
      error: null, 
      lastFetched: Date.now(),
      isLoadingConversations: false, // 标记完成
    });
  },
}));

// 新增辅助函数
export async function loadConversationsOnce() {
  const { conversations, isLoadingConversations } = useChatStore.getState();
  if (conversations.length > 0 || isLoadingConversations) {
    return; // 已有数据或正在加载，跳过
  }
  
  useChatStore.setState({ isLoadingConversations: true });
  try {
    const list = await listConversations();
    useChatStore.getState().setConversations(list);
  } catch (e) {
    useChatStore.setState({ isLoadingConversations: false });
    throw e;
  }
}
```

**修改调用方**：
- `main.tsx`：使用 `loadConversationsOnce()`
- `GroupPage.tsx`：使用 `loadConversationsOnce()`
- `HomePage.tsx`：使用 `loadConversationsOnce()`

**优点**：
- ✅ 防止并发请求
- ✅ 保持语义清晰

**缺点**：
- ⚠️ 需要修改多个调用方
- ⚠️ 代码量较大

---

### **方案 3：ResourceImage 缓存使用 media_id**

**原理**：缓存 key 使用 `media_id` 而非完整 URL，避免 URL 变化导致缓存失效。

**修改文件**：`web/src/components/ResourceImage.tsx`

```typescript
// 从 URL 提取 media_id 作为缓存 key
function getCacheKey(src: string): string {
  if (src.startsWith(MEDIA_PATH_PREFIX)) {
    // /api/v1/media/{media_id}/content → media_id
    const match = src.match(/\/media\/([^/]+)\//);
    return match ? match[1] : src;
  }
  return src;
}

// line 57：使用 media_id 作为 key
const cacheKey = getCacheKey(src);
const cached = blobCache.get(cacheKey);
if (cached) {
  setResolvedSrc(cached);
  return;
}

// line 72：写入缓存
blobCache.set(cacheKey, objectUrl);
```

**优点**：
- ✅ 提升缓存命中率
- ✅ 避免 URL 参数变化导致重复请求

**缺点**：
- ⚠️ 不能根本解决竞态问题（重渲染仍会发生）
- ⚠️ 需要解析 URL

### **组合方案：方案 1 + 方案 3**

同时实施两个方案，互补解决：

1. **方案 1（防止重复加载）**：

## 📝 总结

**根本原因**：预加载与页面加载的并发请求导致状态覆盖，触发组件重渲染，使得首个加载的头像 blob URL 失效。

**核心修复**：在 `setConversations` 中检查数据是否已存在，避免无意义的重复设置。

**增强方案**：优化 ResourceImage 缓存策略，使用 media_id 作为 key，提升缓存鲁棒性。

**验收目标**：刷新页面后首个群头像立即显示，无加载失败。
