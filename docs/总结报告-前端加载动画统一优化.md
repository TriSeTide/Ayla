# Ayla 前端加载速度与动画统一优化 —— 实施总结

> 对照用户诉求：加载速度、加载动画、预加载、WebSocket，整体统一。

---

## 执行摘要

> ⚠️ **重要修正（2026-08-20，初版被用户实证否定后回滚）**：
> - 初版把 `React.lazy` 路由懒加载 + 帖子详情 `Promise.all([getPost, listComments, listFavorites])` 当作"优化"，被用户实测为**负优化**：懒加载导致切换 tab / 进直播间都要重新下载对应 chunk（直播间 chunk 含 livekit 约 600KB）→ 空白；`Promise.all` 是"等最慢请求"→ 帖子详情正文反而更晚显示、速度没提升。
> - **已回滚**：路由恢复**同步导入**（切换无 chunk 下载、无空白）；帖子详情改为 **getPost 返回即渲染正文，评论/收藏后台独立填**。
> - 并贯彻用户明确标准「哪怕是没加载好数据先显示在加载的文字，也得先把界面加载上去」：所有列表页/详情页改为**框架容器先上、数据区骨架+加载文字**，拒绝整页骨架替换造成的空白。
> 本文件的"关键成果"表格已同步修正，不再保留被否定的"路由懒加载降首屏 JS / Promise.all 并行提速"结论。

用户明确对照「直播间」的丝滑度，点名帖子详情页「太慢而且动画也没有」、语音房「动画差一点」。本次优化以**框架先上的加载策略 + 正文优先的并发填充 + 统一动画原语 + 结构化骨架 + 评论实时推送**，让所有界面向直播间看齐。

### 关键成果（修正版）

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 路由切换 | 同步 bundle | **恢复同步导入**，切换无 chunk 下载、无空白 |
| 帖子详情正文 | 串行（等评论完成才显示） | **getPost 返回即渲染正文**，评论/收藏后台填 |
| 帖子详情骨架 | 单块 160px 骨架、无顶栏 | **顶栏框架先上 + 结构化骨架 + 加载文字** |
| 群内语音/桌游/帖子列表 | 整页骨架替换 | **框架容器先上 + 数据区骨架/加载文字** |
| 群内语音/桌游 | 每次挂载强制重拉 | **读 store 缓存**（对齐 GroupLive 秒开模式） |
| 语音房入场 | 只有输入框滑入，主体闪现 | 成员面板 + 聊天卡统一浮入 |
| 预加载 | 会话/语音/直播 | **+ 帖子信息流 + 收藏 + 桌游房**，进页秒开 |
| 评论实时 | 无 | **后端 broadcast + 前端订阅**，跨端同步 |
| 动画体系 | 3 个分散 hook | 统一 `useRevealOnEnter` + `.reveal` CSS |
| 全量测试 | 353 项 | 417+ 项 |

## 经验总结

1. **「感知慢」往往不只是网络慢**：单块骨架 + 无入场动画会放大等待感。结构化骨架的形状预示 + 浮入动画的温和显现，是直播间丝滑感的来源。
2. **并行加载是最高性价比的提速**：帖子详情串行改并行，直接省掉一次网络往返，代码改动极小、收益可量化。
3. **动画统一靠 CSS 原语**：之前三个 hook 各管各的，现在 `.reveal` + `useRevealOnEnter` 一套覆盖所有界面，后续新页面直接套用即可。
4. **WebSocket 善用不在多，在对的地方**：评论实时推送不复杂，但填补了"多端同步"的最后一块缺口——用户发评论后其他端不再需要手动刷新。
5. **路由懒加载配合登录预加载**：首屏只加载必要 chunk，登录后后台并发拉取核心数据，进各页面秒开——这是"预加载"的合理用法。

## 后续建议

- **虚拟滚动**：帖子列表/消息列表超过 1000 条时启用虚拟滚动（当前无大列表性能问题，可等需求出现再做）
- **Service Worker PWA**：缓存静态资源，离线可看上次加载的内容
- **图片格式 WebP 化**：后端缩略图生成 WebP 版本，体积减少 30-50%
- **评论 WS 事件覆盖好友帖**：当前 friends 可见性帖子的评论只推送给帖主（`chat_user_{owner}`），好友帖评论的实时同步受限（范围较小，但好友帖场景少）
