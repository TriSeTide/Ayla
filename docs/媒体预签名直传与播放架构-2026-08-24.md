# 媒体预签名直传与播放架构（2026-08-24）

> 大文件上传/播放的字节流**完全不再经过 Django 数据面**。应用服务器只做信令、鉴权决策与落库；字节流浏览器与 MinIO 点对点。

## 背景与动机

runserver 被 daphne 接管后走 ASGI，`ASGIHandler.read_body()` 会把整个请求体先读进内存才开始执行视图：

- PUT 3GB 视频 = Django 进程内存暴涨 3GB+ → Windows 动态建 C 盘临时页文件承接 → C 盘两段式掉空间又恢复。
- Channels 同步视图 thread_sensitive 串行执行：complete 占线程几十秒~分钟，期间**所有**请求（含首帧加载）排队。
- 旧 Range 实现 `bytes=0-` 开放区间被解析为读到文件尾并全量 read 进内存——3.5G 视频 preload=metadata 即触发。

根治 = QQ/微信同款架构：数据面旁路，字节流浏览器与对象存储点对点。

## 上传：预签名直传

```
浏览器 --PUT presigned_url--> MinIO
   |                              ↑ copy_object（服务端复制）
   +--POST :complete--> Django（head 校验+落库，不碰字节流）
```

- `POST /media/uploads` 建会话，响应含 `presigned_url`（`generate_presigned_url("put_object")`，TTL ≥ 600s）。
- 前端 XHR 直打该 URL（进度/取消语义不变）；完成后 `POST /media/uploads/{id}:complete`。
- complete 轻校验：`stat` 对齐 expected_size → Range 读头部 64B 魔数嗅探（保留安全校验）→ ETag(MD5) 作 content_hash → `copy_object` 服务端复制落正式 key → 删 tmp。
- 旧 `PUT /media/uploads/{id}` 端点保留兼容（流式写 MEDIA_TMP_DIR 再 put_stream），前端默认不走。
- 兼容通道的服务端中转临时文件走 `MEDIA_TMP_DIR`（默认 `backend/runtime/media_tmp`，数据盘），禁止回落系统 Temp。

### 坑

1. `generate_presigned_url` 的 Params 混入 ACL 等 extra args 会把对应头纳入签名，直传请求必须原样携带否则 S3 报 "headers not signed"（400）。presign 时只签 Bucket/Key/ContentType。
2. 直连请求绝不可附加 Authorization 头（同理 400）。前端 XHR 不带 Bearer。
3. content_hash 契约由 sha256 更新为 **ETag MD5 内容指纹**（用途=内容寻址去重；完整性强校验由客户端负责）。单次 PUT 的 ETag 即 MD5。

## 播放：预签名 GET 直连

- `POST /media/{id}:sign` 签发前完成 can_access_media 鉴权，返回对象存储 `presign_get` URL（TTL 600s）。
- `<img>/<video>` 直连拉流：preload=metadata、拖动 seek、moov 尾部探测的 Range 请求由 MinIO 原生处理——播放流量完全不占用 Django/Channels 同步视图串行队列。
- 前端 `getSignedMediaUrl` 缓存 URL 至到期前 60s，自动重签。
- Django content 端点保留双通道鉴权（Bearer 登录 or 签名票据 verify）作为兼容通道；Range 分支用 `open_range_stream` 流式转发，支持 start-end/start-/-suffix 三形态分块响应（修复开放区间全量 read 进内存缺陷）。

## 权限：can_access_media 覆盖 segments 引用

图文混排（第四轮 M7）消息的 media 引用存在 `segments` JSON 内而非 media_id 列——权限判定两种形态都要覆盖：

```python
msgs = Message.objects.filter(media_id=media.media_id)          # a) 单媒体消息列
seg_msgs = Message.objects.filter(segments__icontains=media_id) # b) segments JSON 粗筛
# b) SQLite JSONField 无 contains；icontains 对序列化文本 LIKE 粗筛，
#    Python 层精确校验 segments 结构（防文本误命中放权）
```

回归事故：跨账号查看对方所发混排视频 403 白泡（B 判 False），即漏了 b 形态。契约测试：`test_segments_reference_member_access`。

## 前端要点

- 预签名绝对 URL 统一经 `toSameOriginMinio()` 改写为 `/minio/...` 同源代理路径（Vite `/minio` proxy：rewrite 剥前缀 + changeOrigin 保持签名 host 校验），规避跨源与 Private Network Access 策略差异；生产经反代同理（host 可加 MINIO_PUBLIC_ENDPOINT 覆盖，待实现）。
- 气泡图片用 320px 缩略图（GIF 例外走原图保动图），点击进查看器才加载原图。
- ImageViewer 以 `createPortal(document.body)` 挂载——消息气泡的 backdrop-filter（毛玻璃）会创建 containing block，把 position:fixed 的查看器困在气泡内。
- 已读/未读回执标记不实现（产品决策）：消息状态仅内部流转，不在气泡展示。

## 视频 faststart 重排（moov 前置，2026-08-25）

起播延迟根治：手机/相机直出 mp4 普遍 moov 在文件尾，浏览器起播前需 2~3 次 Range 往返（读头→读尾拿元数据→回头缓冲）；重排后一次顺序读即可边下边播。

- 实现：`apps/media/faststart.py`——纯容器级重排（等价 ffmpeg `-c copy -movflags +faststart`，本机无 ffmpeg 故纯手写）：顶层 box 索引 → 新布局 ftyp→moov→其余原序 → moov 内 stco/co64 chunk 绝对偏移修正（偏移所属 box 的新旧位置差）→ 流式写出。总字节数与音视频编码不变。
- 安全边界：首 box 非 ftyp（WebM/EBML 等）显式拒绝；已 faststart / 无 moov 幂等跳过；截断/越界抛 FastStartError 由上层吞掉保留原对象——播放可用性永远不受影响。
- 替换流程：`services.ensure_video_faststart`——original 下载到 MEDIA_TMP_DIR 临时文件 → 重排 → put_stream 到 tmp key → stat size 校验 → 服务端 copy 覆盖 original → 删 tmp；content_hash 同步更新为替换后 ETag。
- 触发：`POST /media/{id}:poster` 成功后 daemon 线程异步执行（绝不占用 thread_sensitive 同步队列）；存量视频用管理命令 `manage.py ensure_video_faststart`（幂等可重复跑）。
- 前端配合：封面/气泡一律渲染 thumbnail 海报帧（不挂 video 元素拉流）；查看器 `<video poster>` 同帧衔接 + `preload="auto"`；**hover/tap 或详情页挂载时创建 detached `<video>` 预热缓冲**（`warmUpVideoElement` 池，上限 4 个 LRU），查看器挂载时 `takeWarmVideoElement` 直接接管已缓冲元素——起播缓冲与用户点击决策时间窗重叠（视频平台 hover 预载同款）。
- 测试：`apps/media/tests/test_faststart.py`（算法 11 项 + services 集成 6 项；核心断言已用 venv 直跑脚本先行验证通过，pytest 全量待 dev extras 可装窗口统一执行）。
