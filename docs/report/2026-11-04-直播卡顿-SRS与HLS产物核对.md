## 一、结论摘要

**HLS 产物本身是健康的：分片真实 1s、GOP 真实 1s、码率平稳 3.0–3.2 Mbps、无丢帧、无跳号、无 DISCONTINUITY 需求之外的异常。** Lead 此前怀疑的「多片大小完全一致（404012/403824 交替）」是**采样假象，不成立**——实测 21 片尺寸 384648–416984 字节，极差 8.1%，且 404012 只出现 1 次、403824 也只出现 1 次，不存在交替。

真正的 SRS 侧问题是两类，**都与网络无关**，且都会造成用户可感知的卡顿：

1. **【确定发生，独立于网络】重推流触发 HLS 全量销毁，产生 29.7 秒 m3u8 404 空洞。** 2026-11-04 13:12:15 推流中断，`hls_dispose 120s` 在 13:14:15.7 把 m3u8 删掉；13:14:16.090 起浏览器/libmpv 持续收到 **404**，直到 13:14:45.817 新推流重建文件才恢复。nginx 与 SRS 日志双向印证。这不是网络问题，是 SRS 的 `hls_dispose` + 推流端断线重连的组合效应。
2. **【确定发生，独立于网络】GOP=1s 与 1440p60 高码率组合，导致每秒一次的瞬时带宽尖峰。** 实测 I 帧 ≈107 KB，而 P/B 帧平均 ≈6 KB。I 帧在 16.7ms 内涌入，瞬时速率约 51.6 Mbps，是平均码率（3.13 Mbps）的 **16.5 倍**；且 22.7% 的字节集中在 1/60 的时间里。任何在 3.4 Mbps 附近徘徊的出口/链路（本机 send_30s 已测得 6.5–7.5 Mbps 但含多客户端）都会在 I 帧时刻排队，表现为「每秒卡一下」。

另外更正两处 Lead 记录中的事实偏差：**实际生效配置不是 `conf/srs.conf`**，挂载覆盖为 `ayla-deploy/srs.conf`；**音频实际是 48000 Hz**，不是 44100 Hz。

**注意项（非缺陷，但需知晓）**：`EXTINF` 声明 1.000s，而 ffprobe 实测容器时长 1.0137–1.0317s。这是 SRS 按「目标 1s + 等关键帧」裁切时的正常表现——每片含 60 个视频帧（恰好 60/60fps = 1.000s 视频），音频 47 个 AAC 帧（47×1024/48000 = 1.0027s），容器时长被末尾音频帧尾部垫高。**播放器按 EXTINF 推进时间轴，实测偏差 ≤31ms/片，累计 20s 窗口内 <0.6s，不构成卡顿源。** 但如果客户端用实测 PTS 而非 EXTINF 推进，会有轻微音画不同步累积，属可观察但不严重。

### 3.3 为什么 HTTP 取到 3 行 master，而 nginx 日志是 2113 字节 —— 已完全解释

**两个观察都对，只是取的 URL 不同。** SRS 的 `hls_ctx=on` 会对 m3u8 做两段式返回：

| 请求 | 返回 | 字节 |
|---|---|---|
| `GET /live/<key>.m3u8`（**无** `hls_ctx` 参数） | **master**：`#EXTM3U` + `#EXT-X-STREAM-INF:BANDWIDTH=1,AVERAGE-BANDWIDTH=1` + 指向自身的变体 | **134** |
| `GET /live/<key>.m3u8?hls_ctx=<token>`（**带**参数） | **真实 media playlist**，21 条 `EXTINF` + 分片，且**每个 ts 行也追加 `?hls_ctx=<token>`** | **2113** |

字节差可以精确算出来：

```
磁盘 1756 + 21 片 × 17 字节("/?hls_ctx=xxxxxxxx".len) = 2113   ✅ 完全吻合
```

实测验证：

```
$ curl -sk "https://127.0.0.1:8089/live/<key>.m3u8"                 → 134 B  （master）
$ curl -sk "https://127.0.0.1:8089/live/<key>.m3u8?hls_ctx=<任意>" → 2113 B （真实 playlist）
```

Lead 侧「只有 3 行 master」是因为**没有带 `hls_ctx` 参数**（或带的是从别处拿到的 token 但请求时丢了）。而 nginx 日志里 `libmpv` 与 Edge 浏览器都带 `hls_ctx=yl937024` / `433922z5`，所以拿到 2113 字节的完整列表。**这不是矛盾，也不是 bug，是 SRS 5 的 hls_ctx 会话机制。**

> `hls_ctx` 是 SRS 为每个 HLS 播放会话生成假连接用的 session id，用于统计与回调；代价是**所有 CDN/nginx 缓存必然 miss**（full.conf 原文：「Note that it will make NGINX edge cache always missed」）。当前没有任何 CDN 缓存层，所以暂无影响，但若将来上 CDN，必须关掉 `hls_ctx`/`hls_ts_ctx`。

### 3.4 分片在 m3u8 中的写入时序（无竞态）

对 23 次 m3u8 更新做了竞态检测：**「m3u8 引用的最后一片 > 磁盘上最后一片完整 ts」的情况出现 0 次**。SRS 先 rename `.ts.tmp` → `.ts`，再更新 m3u8，顺序正确，播放器不会拿到 404 的分片。

## 五、GOP 实测

**结论：GOP = 1 秒 = 60 帧，每个分片恰好 1 个 I 帧。**

```
$ ffprobe -select_streams v:0 -show_entries frame=key_frame,pts_time -of csv=p=0 /tmp/hw2/s-3620.ts

0,289.049000,...              B
0,289.066000,...              B
0,289.083000,...              P
... （共 60 帧，仅 1 个 I）

keyframe count: 1 / total video frames: 60   （3620、3621、3622 三片一致）

连续 2 片 I 帧 PTS：
  x-4751.ts  I-frame pts = 1420.033000   (60 帧)
  x-4752.ts  I-frame pts = 1421.033000   (60 帧)
→ 间隔 = 1.000 s  ✅
```

### 历史文档「GOP 8.33s」已被推翻

历史记录 GOP 8.33s 对应 60/7.2 或类似编码设置。**当前实测 GOP=1s**，配置注释也写「GOP=1s 前提下分片 1s」，说明 2026-11-01 的性能优化确实把 GOP 改短了。**当前事实：GOP=1s，fragment=1s，两者对齐，分片边界干净。**

### ⚠ 但 GOP=1s 在高码率 1440p60 下带来新的卡顿风险（独立于网络）

实测帧大小分布（`x-4751.ts`）：

```
I 帧（1 个/秒）：  107653 B ≈ 105 KB
P/B 帧（59 个/秒）：平均 ≈ 6122 B，最大 36681 B（场景切换）
```

| 量 | 数值 |
|---|---|
| I 帧占总码率比例 | 107653 / 367345+107653 ≈ **22.7%** 的字节集中在 1/60 的时间里 |
| I 帧瞬时速率 | 107 KB / 16.7ms ≈ **51 Mbps**（相对平均 3.1 Mbps = 16 倍） |
| 每秒出现的尖峰次数 | **1 次** |

**这就是「每秒卡一下」的 SRS 侧候选机制。** 播放器每次要在一个 `fetch` 里把含 I 帧的分片拉下来；分片若走 RTMP/HTTP-FLV 非分片通道，则 I 帧时刻的瞬时需求会顶到链路瓶颈，造成排队抖动。GOP 从 8.33s 缩到 1s 后，这种尖峰从「每 8.3 秒一次大卡」变成「每秒一次小抖」——**频率是原来的 8 倍**。对 3.4 Mbps 出口余量不足的链路，这是实质恶化。

### 6.4 重要更正：音频是 48000 Hz，不是 44100 Hz

Lead 记录「AAC 44100 stereo」，**SRS API 也报 44100**，但这是 SRS 的一个已知上报缺陷。三种独立证据表明真实值是 48000：

1. **ADTS 头直接解码**：`ffmpeg -c:a copy -f adts` 后读 `sampling_frequency_index=3` → **48000 Hz**
2. **ffprobe 读 TS/FLV**：`sample_rate=48000`
3. **音频时长自洽**：47 帧 × 1024 采样 ÷ 48000 = **1.0027s**，与 1s 分片吻合；若按 44100 算则是 1.0914s，与实测不符

**SRS 日志本身已经把矛盾写出来了**：

```
7B audio sh, codec(10, profile=LC, 2channels, 0kbps, 48000HZ), flv(16bits, 2channels, 44100HZ)
                                                          ^^^^^^^^^^                    ^^^^^^^^^^
                                                          真实 AAC 元数据              RTMP FLV 头里的值
```

**根因**：推流端（OBS 类）写进 FLV 序列头的 AudioTagHeader 是 **44100**，但实际 AAC 编码器输出 **48000**。SRS 的 API 读 FLV 头 → 报 44100；转 TS 时用真实 AAC 元数据 → 写 48000。**这是推流端的一个真实配置 bug**，会造成：
- 部分严格按 FLV 头解复用的播放器（尤其旧版 OBS 播放链、某些硬件解码器）按 44.1k 重采样 48k 音频 → **音调偏低 8.8%、音画不同步随时间累积**
- 这与网络完全无关，且是**持续性**的

**建议**：在推流端把音频采样率显式设成 48000，确保 FLV 头与 AAC 实际一致。

## 七、会导致卡顿的项清单

按「是否独立于网络」「是否已确证发生」两个维度排列：

### A. 已确证发生 且 完全独立于网络

#### A1. 【最严重】重推流触发 HLS 销毁，产生 29.7 秒 404 空洞

时间线（全部来自 SRS 与 nginx 日志，双向印证）：

```
13:12:15.733  推流中断（440x284i cleanup when unpublish）
13:12:15.733  WARN client disconnect peer. ret=1007
13:14:15.7    hls_dispose 120s 到期，SRS 删除 m3u8 与全部 ts
13:14:16.090  第一个 m3u8 404  （+0.4s，精确吻合）
13:14:17.186  404
... 共 28 次 404，间隔 ~1s ...
13:14:43.962  推流端重连成功（0628d822）
13:14:44.992  新会话首个分片写入
13:14:45.817  最后一次 404（重建前的请求）
13:14:46+     恢复正常
```

**n 侧证据（nginx）**：
```
"GET /live/<key>.m3u8?hls_ctx=yl937024" 404 9  ← libmpv/浏览器
"GET /live/<key>.m3u8?hls_ctx=yl937024" 404 9
... 28 条 ...
```

**SRS 侧证据（同一时刻）**：
```
http miss file=./objs/nginx/html/live/<key>.m3u8
```

**影响**：任何在 13:14:16–13:14:45 期间打开的播放器，会连续 30 秒拿不到播放列表 → hls.js 重试耗尽后报致命错误 → 用户看到「一直转圈」或「播放失败」。已连上的播放器则因连续 404 触发 `levelLoadError` 后自杀。

**为什么这属于 SRS 侧缺陷而非纯网络问题**：`hls_dispose 120` 意味着「推流一断，2 分钟后连文件带目录全删」。若推流端在 2 分钟内重连（本次断了 148 秒，>120s），播放器必然吃满 404。**把 `hls_dispose` 设成 0（禁用）或远大于重连窗口，就能完全消除这段空洞。** 这是纯配置问题。

#### A2. 【高频】GOP=1s × 1440p60 产生每秒一次的 I 帧带宽尖峰

见第五节实测。I 帧 105 KB vs P/B 均 6 KB，**22.7% 字节集中在 1/60 时间**。GOP 从 8.33s 缩到 1s 使尖峰频率提升 8 倍。对出口余量紧的链路（net-prober 同事正在测）会表现为规律性每秒卡顿。

**为什么独立于网络**：即使链路总带宽充足，TCP 单流也会因突发被 shaper/bufferbloat 排队。这是编码参数问题（GOP 与码率/分辨率不匹配）。

#### A3. 【持续】推流端音频采样率声明错误（FLV 头 44100 vs 实际 48000）

见 6.4。会导致部分播放器音调偏移 8.8% 与音画不同步累积。纯推流端配置问题。

#### A4. 【配置面】`hls_dispose=120` 与短分片窗口的组合放大故障

`hls_window 20`（20 秒内容）配合 `hls_dispose 120`（120 秒后才销毁）。看似合理，但结合 A1 说明：**销毁后重建需要推流端重连 + SRS 重新积累至少 1 个分片才能生成有效 m3u8**，恢复时间远长于窗口本身。

### B. 已确证发生，但影响较小 / 需客户端配合

#### B1. `http miss ... -N.ts` 497 次（旧 key `be86d2a1...`）+ 13 次（当前 key）

播放器请求了不在窗口内的分片。可能是：
- 客户端 m3u8 缓存陈旧（请求已被 cleanup 删除的旧分片）
- 播放器预取越过窗口尾部

单次 404 分片会让 hls.js 触发一次 fragment 重试，通常能自愈，但若连续发生会造成可见卡顿。**这属于客户端 m3u8 刷新策略问题，归 client-auditor 判定。**

#### B2. `publish timeout 5000ms` 6 次

推流端有 5 秒级静默。已包含在 A1 的断线事件中，非独立问题。

#### B3. `EXTINF 声明 1.000` vs 实测 1.0137–1.0317

偏差 ≤31ms/片，20s 窗口累计 <0.6s。**不构成卡顿源**，但若客户端用 PTS 而非 EXTINF 推进会有轻微不同步。
