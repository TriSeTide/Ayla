# 媒体链路 500（迁移未执行）根因与修复 —— 2026-09-10

> 状态：已修复（2026-09-10）
> 关联：`docs/architecture/media-storage-expiration.md`（媒体分级过期方案）、提交 `66042a0`（含迁移 0004）

## 现象（用户报告）

群聊默认组消息不再显示、再发消息不再存储、表情包无法上传——用户感知"整个存储都坏掉了"。

## 时间线与证据

1. **2026-09-10 下午**：提交 `66042a0`（聊天媒体分级过期）——`MediaObject` 新增 `original_expired_at`/`expired_at`（迁移 0004），`:sign` 视图开始访问这两个字段。
2. **用户重启 Ayla**（新代码生效）：`:sign` 访问 `media.original_expired_at` → 生产库无此列 → `OperationalError: Unknown column 'media_objects.original_expired_at' in 'field list'` → 500。
3. **连锁影响**：前端所有媒体加载（表情包/图片/视频/头像）走 `:sign` → 全部失败；媒体消息不渲染（"消息不显示"）；上传后渲染失败（"表情包无法上传"、"消息不存储"的感知来源）。
4. **诊断**：
   - dbhub（frp 隧道跨接的远程库）查到的 `ayla` 库最后写入 2026-08-22——**不是用户当前运行环境**（误导，弃用）；
   - 本机 MySQL（127.0.0.1:3306，`.env` 配置）确认：`media_objects` 无新列、`django_migrations` 无 0004 记录、messages 今天 14:05 仍在写入（服务在跑）；
   - 实测 `POST /api/v1/media/{id}:sign` → 500 `OperationalError`（Django 调试页确认 `Unknown column 'media_objects.original_expired_at'`）。

## 根因

**迁移 0004 未在生产库执行**，而新代码（`:sign`）已开始访问新字段。**Django runserver 只打印未应用迁移警告、不自动执行**（Django 5.2 源码 `BaseCommand.check_migrations` 仅 `stdout.write` 提示 "Run 'python manage.py migrate' to apply them."，不调用 migrate）——这是 Django 的设计行为，不是本机配置问题。警告在 runserver 启动输出中容易被忽略，导致"新代码 + 旧 schema"静默上线。

## 已执行操作（含可逆性）

1. **手动执行迁移**：`python -m django migrate media 0004`（workdir=`Ayla/backend`，`DJANGO_SETTINGS_MODULE=config.settings`）→ OK。可逆：`migrate media 0003` 回滚（DROP 两列）。
2. **launcher.py 启动前自动迁移**（提交 `66042a0` 之后的新提交）：`main()` 在端口检查后、启动 runserver 前执行 `manage.py migrate --no-input`；迁移失败拒绝启动（显式失败，不静默上线旧 schema）。下次用户重启 Ayla 即生效。
3. **验证**（实测 API）：
   - `:sign` original/thumb → 200（此前 500）；
   - 三步上传（建会话 201 → PUT 200 → complete 201）→ 全通；
   - 消息列表（默认组 subgroup_id=8）→ 200 返回消息；
   - 发文本消息到默认组 → 201（seq 620）。
4. **清理测试数据**：测试媒体（API DELETE，连带 MinIO 对象）、测试消息（SQL）、3 个上传会话（SQL）、临时文件——全部 0 残留。

## 验证结果

- 媒体上传/签名/消息列表/消息发送链路全部恢复（实测 200/201）；
- 用户刷新前端页面后媒体应恢复显示（`:sign` 不再 500）；
- `migrate --no-input` 幂等（"No migrations to apply"）。

## 仍然待决（归属人：用户）

- **runserver 自动迁移**：已确认 Django 设计如此（只警告不执行），launcher 已改为启动前显式迁移，无需再深究；
- 本机 MySQL 与 dbhub（frp 远程库）是不同环境，诊断时以本机 `.env` 配置为准；
- 顺带发现：`emoji`/`favorites` 两 app 有模型变更未生成迁移（历史遗留，migrate 会提示但不阻塞），建议后续补 `makemigrations`。
