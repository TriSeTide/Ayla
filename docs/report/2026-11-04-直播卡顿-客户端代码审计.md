### 1.2 「每 0.5s 一次 m3u8 请求」的最终归因（Lead 的核心异常线索）

**已排除「Ayla 有 setInterval 重复 loadSource / 双播放器 / StrictMode 双挂载」这一整类假设。** 实测归因是 **hls.js 自身的 live playlist 刷新节奏在「播放列表不前进」时退化为 targetduration/2**，叠加**上游 HLS 生产者卡死 151 秒**：

- 正常期：该浏览器上下文（`hls_ctx=yl937024`，Edge 桌面）**1 次/秒**，1711 秒里 1555 秒是 1 次/秒，156 秒是 2 次/秒。
- 异常期：**2026-11-04 21:12:18 → 21:14:15 连续 118 秒稳定 2 次/秒**，同时**分片下载数归零**（`ts=0`）。
- 机制（hls.js 源码）：`computeReloadInterval()` 在 playlist **未更新**时执行 `reloadInterval /= 2`（`hls.js:10957-10963`），把 1s 变 0.5s。而「未更新」的判据是 `this.endSN !== previous.endSN`（`hls.js:9206`）——即 **SRS 没有产出新分片**。
- 交叉印证：同期 SRS 侧分片序号 `SN` 从 3331 → 3332 用了 **151 秒**（正常 1 秒/片）。hls-inspector 的独立结论（`hls_dispose 120s` + 推流端断线重连 → 29.7s m3u8 404 空洞）与本文互补：**404 空洞是其中一段，151s 的分片停摆是更长的一段**。

> 所以：**2 次/秒不是 Ayla 的 bug，是「上游不产片」的可靠指示器**。但它暴露了 Ayla 的真实缺陷——**上游停摆 151 秒，Ayla 客户端全程 0 次重建、0 次用户可见错误提示**（见 §2.2）。

## 二、逐条缺陷

### D1【严重】低延时配置把缓冲压到 2.0s，低于抖动尾部 —— 「网络抖动」被放大成「可见卡顿」

- **file:line**：`Ayla/web/src/player/hls.ts:43-46`（`new Hls({ lowLatencyMode: true, liveSyncDurationCount: 2 })`）
- **机制**：
  - hls.js 的目标延迟 = `liveSyncDurationCount × targetduration` = 2 × 1.0s = **2.0s**（`hls.js:34661-34663`：用户显式设了 `liveSyncDurationCount` ⇒ 走 `targetLatency = liveSyncDurationCount * targetduration`，**不再走**低延时模式的 `partHoldBack/holdBack`）。
  - 这个 2.0s 是「播放位置到直播边缘的距离」，**不是可用的前向缓冲**。播放器必须先把当前 1s 分片下完才能播到分片末尾，因此真正能吸收抖动的余量 ≈ **1 个分片（1s）**。
  - Lead 实测：分片下载 p50=0.39s、**p95=1.48s、max=6.69s**，**10% 的分片下载速率低于流码率（3.26Mbps）**。即抖动尾部（1.48s / 6.69s）**超过**了 1s 的吸收余量。
  - 结果：每个「慢分片」都会把前向缓冲吃穿 → `video` 触发 `waiting` → `bufferStalledError`。这与 Lead 实测 `video.buffered` ahead **p10=0.06s、p50=1.34s** 完全吻合：p10 只有 60ms 意味着 **10% 的时间里播放器已经贴到缓冲末尾**。
  - Lead 的 A/B 是判决性证据：**同一台机器、同一时刻**，`liveSyncDurationCount:2` → `bufferStalledError` + 累计 17.5s 卡顿；`:4`（=4.0s 目标缓冲，约 3s 余量）→ 只卡 1s。**同一网络、同一服务端、只改这一个数字**，所以这不是网络问题，是配置把容差设到了网络抖动分布的下方。
- **用户可见现象**：画面每十几秒「定住一下再继续」，定住时长 1~3s；网络稍差时连续定住。
- **与网络无关的论证**：卡顿量与**配置数字**强相关（2 → 17.5s vs 4 → 1s），而网络条件在 A/B 两臂中相同。网络抖动是**输入**，Ayla 的配置决定了「抖动是否可见」。Ayla 当前选择让它可见。
- **补充（为什么低延时目标在这里拿不到收益）**：SRS 分片 1s、GOP 1s，即使 `liveSyncDurationCount:4` 端到端延时也只有约 4~5s，仍在需求文档 G5 的 4~6s 目标内。**当前 2.0s 的目标延迟换来的延时收益小于它造成的卡顿代价。**

### D2【严重】播放器重建后 watchdog 从未重新布防 —— 真正的卡死永远不会被自愈

- **file:line**（符号锚点优先，行号为审计截止快照）：
  - `liveSessionRuntime.ts` → `armWatchdog()` 内的 `onResume`：`this.clearStallTimer();`（**行 ~705-706**）
  - `liveSessionRuntime.ts` → `private clearStallTimer()`：方法体内执行 `this.watchdogCleanup?.(); this.watchdogCleanup = null;`（**行 ~735-742**）
  - `liveSessionRuntime.ts` → `private rebuildPlayer()` 内的 `this.armWatchdog(video);`（**行 ~573**）—— 全仓 **唯一** 调用点
- **机制**：
  1. `armWatchdog(video)` 只在 `rebuildPlayer()` 里调用一次，把 `waiting/stalled/error/playing/canplay` 五个监听器挂上，并保存 `watchdogCleanup`。
  2. 一旦出帧，`playing`/`canplay` 触发 `onResume` → `clearStallTimer()` → 该方法**不仅清定时器，还执行 `this.watchdogCleanup?.()` 把五个监听器全部移除**（`clearStallTimer` 末尾两行）。
  3. 此后**没有任何代码路径重新调用 `armWatchdog`**（全仓 grep 仅 `rebuildPlayer()` 内一处调用）。唯一重新布防的机会是下一次 `rebuildPlayer`——而重建正是靠 watchdog 触发的，形成死锁。
  4. 结论：**每个播放器实例在出过一次画面之后，就永久失去卡死检测能力。**
- **实测印证（决定性）**：2026-11-04 21:12:16 → 21:14:47，上游 HLS 停摆 **151 秒**，客户端全程：
  - 分片下载 **0 个**；
  - 桌面浏览器 hls.js **重建 0 次**（master playlist 134B 请求在 21:08:10 之后直到 21:29:07 才出现，中间无任何一次）；
  - Flutter mpv 侧 **重建 0 次**；
  - 播放器**没有上报任何 fatal 错误**（`onFatalError` 未触发 ⇒ UI 停在「正在播放」的假象，实际是黑屏/定格）。
- **用户可见现象**：直播定格或黑屏，**没有任何提示，点刷新键也没用**（刷新键走 `refreshPlayer` → 实例「健康」（`readyState` 有残帧）→ 走 `refreshToLiveEdge` → seek 到已经不存在的位置 → 仍是黑屏）。
- **与网络无关的论证**：这是纯控制流缺陷。哪怕上游 100% 健康、网络零抖动，只要发生一次「出帧后卡死」，watchdog 就不会救。**当前所有「自愈」实际上只在「从未成功出过画面」的路径上有效。**

### D3【高】重建冷却 4s + 连续失败计数，把 1s 抖动升级成 4s+ 黑屏

- **file:line**（符号锚点优先）：`liveSessionRuntime.ts` 顶部常量 `STALL_TIMEOUT_MS = 2_000`（行 ~30）、`REBUILD_COOLDOWN_MS = 4_000`（行 ~32）、`MAX_CONSECUTIVE_REBUILDS = 3`（行 ~43）、`REBUILD_COUNT_RESET_WINDOW_MS = 60_000`（行 ~38）；`armWatchdog()` 内 `rebuildIfStuck` 的 `if (!this.canAutoRebuild() ...) return;`；`scheduleHealRebuild()` 的封顶分支 → `setCurrentPlayerError()` + `scheduleHealRetry()`
- **机制**：
  - 一次真实抖动 → `waiting` → 2s 后判死 → 重建（HLS 重新握手 + 拉 master + 拉 playlist + 拉分片，**实测一轮 ≥1s**，Lead 记录 volx TLS 握手 0.4~4.9s）。
  - 重建后 `rebuildPlayer()` 里 `this.lastRebuildAt = Date.now();`，**之后 4s 内 `canAutoRebuild()` 恒 false** ⇒ 这 4s 里任何卡顿都不会被处理（`rebuildIfStuck` 首行直接 return）。也就是说**一次 1s 抖动换来的是一次「1s 卡顿 + ≥1s 重建黑屏 + 4s 自愈真空」**。
  - 若这 4s 内又卡住且没出帧，2s 后触发 `scheduleHealRebuild()`，但 `canAutoRebuild()` 仍为 false → 落到封顶分支 `setCurrentPlayerError(reason)` + `scheduleHealRetry()` → **UI 显示「播放失败 + 重试」，并静默等 60s**。
  - `MAX_CONSECUTIVE_REBUILDS=3` 在 60s 窗口内用完即封顶；封顶后只报错 + 排 60s 后重试 ⇒ **用户看到「播放失败」并必须等 1 分钟**（或手动点重试）。
- **用户可见现象**：轻微抖动 → 画面定住 → 短暂黑屏（重建）→ 可能直接跳到「播放失败」，需要手动点重试或等一分钟。
- **与网络无关的论证**：2s 判死 + 4s 冷却 + 60s 静默期全部是客户端硬编码常量。网络抖动只提供触发信号，**放大倍数（1s → 4s+/60s）完全由这些常量决定**。
- **注**：Flutter 侧已经把这些值放宽（`kStallTimeoutMs = 6000`、`kRebuildCooldownMs = 8000`，`Ayla/flutter/lib/player/hls_player.dart:34,37`），**Web 侧仍是激进的 2000/4000 —— 双端不一致，且 Web 侧是错的那一端。**

### D4【高】没有「上游已停止产片」的判定 —— 分片停摆 151s 仍显示「正在播放」

- **file:line**：Web `liveSessionRuntime.ts` 的 `armWatchdog()`（只监听 `waiting/stalled/error/playing/canplay`，**不监听「playlist 不前进」**）；Flutter `Ayla/flutter/lib/player/hls_player.dart:361-388`（`_onStall` 同样只由平台 buffering 信号驱动）
- **机制**：SRS 停止产片时，客户端拿到的是**合法的 200 响应、内容不变的 playlist**（实测 size 恒为 2113 字节，21:12:18→21:14:15 每秒两次全部 `200 2113`）。hls.js 认为「playlist 没变」是正常直播状态（`liveMaxUnchangedPlaylistRefresh: Infinity`，`hls.js:39297`），**不报错、不触发 fatal**。而 mpv 侧同样只是「没有新数据」，不抛错。
- **实测**：151s 停摆期间，客户端 **0 次重建、0 次 fatal、0 次 UI 状态变化**。用户看到的是定格画面，而 UI 仍认为在播。
- **用户可见现象**：画面永久定格（本次 151s），无提示、无自愈、刷新键无效。
- **与网络无关的论证**：这是「缺少一个判据」的缺陷。服务端停摆与网络中断在客户端表现不同（前者 HTTP 200 但内容不变，后者连接错误），Ayla 只处理了后者。

### D5【中】分片下载失败不降级、不报错，只在 fatal 时 startLoad()

- **file:line**：`Ayla/web/src/player/hls.ts:49-63`（只处理 `data.fatal`，`!data.fatal` 直接 return）、`:52-56`（`NETWORK_ERROR` 一律 `hls.startLoad()`）
- **机制**：
  - 分片 404/超时在 hls.js 里是**非 fatal** 的 `fragLoadError`（`fatal: false`），因此 `:51` `if (!data.fatal) return;` 把它全部丢弃 ⇒ Ayla 完全不知道分片在失败。
  - fatal 的 `NETWORK_ERROR` 一律 `startLoad()`（`:54`），而 `startLoad()` 不带位置参数时默认 `-1`（`hls.js:41539-41542`），且 `lastCurrentTime > 0` 时会被覆盖为 `lastCurrentTime`（`hls.js:19758-19761`）⇒ **重试会从旧位置继续，而不是跳到直播边缘**，在已经落后的情况下会越修越落后。
  - 实测：21:14:16-21:14:45 的 28 次连续 404（hls-inspector 记录）期间，客户端只看到「playlist 404」，没有任何用户可见提示，也没有主动重建。
- **用户可见现象**：分片级故障时画面卡住但无提示；恢复后可能长时间落后于直播边缘。
- **与网络无关的论证**：错误分级处理策略是代码选择。hls.js 已经把「非 fatal 的分片错误」明确交给应用层决策，Ayla 选择忽略。

### D6【低/已排除为主因】单档位 HLS，无 ABR 降档空间；但 hls.js 仍会「判定带宽不足」并降低 maxBufferLength

- **file:line**：`Ayla/web/src/player/hls.ts:43-46`（未设 `maxBufferLength`，取默认 30）；SRS master 只有一路 `EXT-X-STREAM-INF:BANDWIDTH=1`
- **机制**：
  - master playlist 只有 1 个 variant（`BANDWIDTH=1,AVERAGE-BANDWIDTH=1`，实测 master 响应 134 字节）⇒ `hls.levels.length === 1` ⇒ hls.js 的 ABR 切换逻辑被短路（`hls.js:6007, 6094`），**不存在「反复降档/切流」**。
  - **但**：hls.js 仍会按实测吞吐估算带宽（`abrEwmaDefaultEstimate` 初值 500kbps，`hls.js:39361`），并在「缓冲不足 + 估算低于档位码率」时调用 `reduceMaxBufferLength()` **下调全局 `maxMaxBufferLength`**（`hls.js:12170-12178`，日志 `Reduce max buffer length to Ns`）。这是**单向**的（只在 `resetLoadingState` 等少数路径恢复），一旦因抖动被下调，后续更容易再次触发。
  - 这条**不是卡顿主因**（因为 D1 已经把目标缓冲压到 2s，maxBufferLength=30 实际从未成为约束），但它解释了「为什么抖动之后即使网络恢复，播放器恢复得也慢」。
- **结论**：**已排除「ABR 反复降档切流」作为卡顿主因**（单档位不可能切档）；保留「带宽估算下调 maxMaxBufferLength」作为次要放大因素。

### D7【中，Flutter 独有】Windows 纹理尺寸从未固定 —— 文档结论需修正

- **file:line**：`Ayla/flutter/lib/player/platforms/media_kit_impl.dart:131`（`_sizeDecider = null;`）、`:230-238`（`_applyTextureSize` **定义了但全仓无调用点**）、`Ayla/flutter/lib/player/texture_size.dart:16`（注释声称「Ayla 从未调用过 setSize，全仓 grep 0 命中」）
- **复核结论（对需求文档 B4 的修正）**：
  - 需求文档 B4 说「窗口缩放触发纹理注销重建」在 Ayla 里可触发。**复核后：该路径当前不可达**，因为 `_sizeDecider` 被显式置 null（`:131`）且 `_applyTextureSize` 无调用点 ⇒ **纹理尺寸完全跟随视频分辨率，从不被 Ayla 改写**。
  - 也就是说：**Ayla 既不固定纹理尺寸（B4 未修），但也没有引入「因窗口变化而 setSize」的新重建源**。`VideoOutput::CheckAndResize()`（`third_party/media_kit_video/windows/video_output.cc:241-266`）在 `required != current` 时会 `Resize()`（`:268`）→ `UnregisterTexture` + `RegisterTexture`（`:272, :324`）。由于 `GetVideoWidth()`（`:366-413`）在 `width_` 为空时读 `video-out-params` 的 dw/dh（**视频自身分辨率**），只有**视频分辨率真的变化**才会触发重建。
  - **所以「窗口拖动 20 次黑屏 20 次」在代码上不成立**；真正的风险是「视频分辨率变化」（例如推流端改输出分辨率，或 mpv 在重连后重算 dw/dh）——这是**低频事件**，不足以解释「时不时卡顿」。
  - **遗留真实缺陷**：`texture_size.dart` 整套决策器（136 行）+ `media_kit_impl.dart` 的 `_applyTextureSize` 是**死代码**，注释与实现互相矛盾（`:127` 指向一个不存在的 `_maybeApplyTextureSize`）。这会让后续维护者误判 B4 已修。
- **与网络无关的论证**：渲染层问题，与网络无关。但它**不是本次卡顿的原因**（本次卡顿有明确的时间相关性：与分片下载停摆同步）。

### D8【中，Flutter】自愈阈值已放宽，但「封顶后静默 60s」与 Web 同构

- **file:line**：`Ayla/flutter/lib/player/hls_player.dart:34`（`kStallTimeoutMs = 6000`）、`:37`（`kRebuildCooldownMs = 8000`）、`:50`（`kMaxAutoRebuilds = 2`）、`:322-328`（封顶 → `onError` + `_scheduleRetryAfterCooldown`）、`:343-352`（60s 后重试）
- **机制**：与 Web 的 D3 同构，但阈值更宽松（6s/8s vs 2s/4s）。封顶后同样进入 60s 静默期。
- **实测**：2026-11-04 20:26:53 → 21:15:13 期间，Flutter（libmpv）侧**共创建 22 个播放器实例**，其中 20:26:53→20:31:57 的 5 分钟内密集创建 **16 次**（含多次「同一秒内 2 次」，即连续重建）。这是「卡顿 → 重建 → 卡顿」周期抖动在服务端的直接证据。
- **与网络无关的论证**：重建频率与「服务端分片生产」时间线对照：20:36:00 有一个 11s 生产缺口、20:38:36 有 31s 缺口、20:49:44 有 189s 缺口、20:54:40 有 55s 缺口——**Flutter 的重建时间点集中在这些缺口前后**。说明重建是被上游缺口触发的，而每次重建又要重新握手，把短暂缺口放大成长时间黑屏。

## 三、客户端侧对「是否完全由服务器 WiFi / 带宽导致」的回答

**结论：不是。服务器 WiFi（29% 重传、上行 2~9Mbps 波动）是「触发条件」，Ayla 客户端代码是「放大器」，两者叠加才产生用户实际看到的卡顿。三条独立证据链：**

1. **同一网络、同一时刻，只改一个客户端配置数字，卡顿从 17.5s 降到 1s**（Lead 实测 A/B：`liveSyncDurationCount` 2 → 4）。若完全由带宽导致，改客户端配置不会有效果。**⇒ 客户端配置是必要条件。**

2. **服务端 HLS 产物是健康的**（hls-inspector 独立核对：分片真实 1s、GOP 1s、码率平稳 3.0–3.2Mbps、无丢帧无跳号）。分片生产的少数缺口（151s、189s、55s、31s）确实存在，但**客户端在这些缺口期间 0 次重建、0 次提示**（D2/D4）——即便服务端完全健康，只要出现一次「出帧后卡死」，Ayla 也不会自愈。**⇒ 客户端缺陷独立成立。**

3. **Flutter 侧 5 分钟内重建 16 次**，时间点与上游缺口对齐，但每次重建都是「销毁 + 重新握手 + 重新拉 playlist」，把「服务端 11s 缺口」放大成「客户端数十秒黑屏」。**⇒ 客户端把服务端的小故障放大成大故障。**

**因此正确的分工是：**
- **服务器侧**（不在本报告范围）：WiFi 重传 29%、上行低谷 2Mbps、`hls_dispose 120s` 造成的 404 空洞、GOP/码率组合的 I 帧瞬时尖峰 —— 这些是**输入侧**问题，必须修，但修完后客户端仍会因 D1/D2/D3 产生卡顿。
- **客户端侧**（本报告）：D1 缓冲目标过低、D2 watchdog 不重新布防、D3 自愈参数过激、D4 缺少停摆判定 —— 这四条**独立于网络**，必须修。

> 一个可以直接落地的判据：把 `liveSyncDurationCount` 从 2 改到 4（或显式设 `liveSyncDuration: 4`），端到端延时仍约 4~5s（在需求 G5 的 4~6s 内），而卡顿按 Lead 实测从 17.5s 降到 1s。**这是单行改动、收益最大的一条。**

## 四、已排除项（附排除依据）

### E1 setInterval / 周期性 loadSource / 重复 attach（已排除）
- `Ayla/web/src` 全量 grep：`loadSource` 只出现 2 处（`player/hls.ts:65` 与其测试），`new Hls` 只出现 1 处（`hls.ts:43`）。**没有 setInterval 驱动播放器。**
- 播放器实例创建数 = master playlist（134B）请求数。实测 2026-11-04 20:17–21:38 桌面浏览器**仅 6 次**（20:17:19/20:17:21/20:57:30/21:05:18/21:05:49/21:08:10），**没有周期性重建**。
- 结论：2 次/秒的 m3u8 请求**不是**重复 loadSource，而是 hls.js 的 playlist 刷新（见 §1.2）。

### E2 React StrictMode 双挂载（已排除）
- `main.tsx:51` 确实启用 `<React.StrictMode>`，但 `liveSessionRuntime.enter()` 有同频道幂等分支，`attachPlayer()` 有 URL + 健康双条件幂等。
- 实测：21:12:05 那次重建是**单次** master 请求，不是成对。StrictMode 双挂载会产生**成对**的 master 请求（2 个 134B），实测 20:17:19/20:17:21 是这种模式（间隔 2s，属于页面初次进房的两个视图并存），但**不是持续 2 次/秒的来源**。
- 结论：StrictMode 会造成「进房瞬间多一次握手」，**不解释 118 秒持续的 2 次/秒**。

### E3 Flutter 重复 attach（已排除）
- `Ayla/flutter/lib/player/hls_player.dart:235-243`：`attach` 有 URL + `_platformHealthy` 双条件幂等；`:440-460` `rebuild` 有 `_rebuilding` 防重入闸门。
- 实测：同一 mpv context 内 playlist 轮询间隔稳定 **2s**（`433922z5`：292 次间隔为 2s，17 次为 1s），**无重复实例并发**。

### E4 双播放器 / 双流抢流（已排除，实测 0 次）
- 代码侧确有防范：Web `attachPlayer()` 有 `miniPlayerActive` 槽位守卫；Flutter 有 `AylaPictureSlot` 枚举（`live_support.dart:147, 243, 428, 814, 841, 1032, 1046, 1275`）+ `_attachPlayer` 唯一出口守卫（`:672-676`）。
- **实测**：2026-11-04 21:00–21:20 期间，**同一秒内存在 2 个并发 mpv context 的次数 = 0**；桌面浏览器并发 ctx = 0。20:27–20:39 的密集重建是**串行**的（旧 ctx 结束、新 ctx 开始），不是并发。
- 结论：**「双播放器抢流」在当前代码版本下已被修复，不再复现。**（需求文档 B6 已落地。）

### E5 ABR 反复降档/切流（已排除）
- master 只有 1 个 variant（`BANDWIDTH=1`），`hls.levels.length === 1` ⇒ ABR 切档逻辑短路（`hls.js:6007, 6094`）。**物理上不可能切档。**
- 详见 D6：仍有「maxMaxBufferLength 被下调」的次要影响，但不是主因。

### E6 `backBufferLength` 配置（已排除）
- Ayla 未设 `backBufferLength`，取 hls.js 默认 `Infinity`（`hls.js:39262`）。`liveBackBufferLength` 默认 `null`（`hls.js:39310`）。
- `trimBuffers`（`hls.js:22546-22585`）在 `backBufferLength` 为 `Infinity` 时 `isFiniteNumber()` 为 false ⇒ **不做任何 back buffer 裁剪**。这不是卡顿来源（不裁反而更安全）。
- 结论：`backBufferLength` **与本次卡顿无关**，Lead 任务清单里这一项可以关闭。

### E7 「低延时模式 + 无分片列表导致反复重载」（已排除）
- 实测 m3u8 响应：**第一次请求返回 master（134B，只有 `EXT-X-STREAM-INF`），第二次同 ctx 请求返回 media playlist（2113B，含 `EXT-X-MEDIA-SEQUENCE` + 21 个 `EXTINF:1.000`）**。
- 即 SRS 的 `hls_ctx` 机制是「首次建会话返回 master，之后返回 media playlist」。**分片列表是有的**（21 片），不是「只有 master」。
- 实测 `MEDIA-SEQUENCE` 在正常期每秒 +1（7613→7614→7615→7616），**没有反复重载**。
- 结论：假设不成立。

### E8 窗口尺寸变化触发纹理重建（代码路径已确认不可达）
- 见 D7：`_sizeDecider` 被置 null（`media_kit_impl.dart:131`），`_applyTextureSize` 无调用点，Ayla 从不调用 `setSize` ⇒ `width_` 恒为空 ⇒ `GetVideoWidth()` 恒读视频自身分辨率 ⇒ **窗口尺寸变化不会改变 `required_width/height`** ⇒ `CheckAndResize` 恒 early-return。
- 结论：**「拖窗口导致黑屏」在代码上不成立**（与需求文档 B4 的描述有出入，需修正文档）。
