# Ayla 全界面体验审查与完善规划

> 文档类型：产品体验审查、功能缺口盘点、分阶段实施规划
> 本轮复审时间：2026-08-16
> 审查对象：Ayla Web（`http://127.0.0.1:5173`）
> 审查方式：Playwright 实际浏览器巡检 + 375×760 / 1440×900 截图查看 + DOM/源码核对
> 本文目的：作为后续 AI 分批完善 Ayla 的任务入口；本轮只审查、记录和规划，不修改业务代码。
> 桌游玩法：暂不实现，仅记录房间框架、通用收藏和横向契约。

---

## 0. 复审结论先行

Ayla 的路由、壳层和主要场景已经成型：登录/注册、主页/群、语音大厅与房间、直播大厅与房间、帖子列表与详情、桌游房间框架、消息中心/私聊、搜索、个人和收藏均有入口；窄屏有 BottomTabs，宽屏有 TopNav、群服务器栏/频道栏和直播封面侧栏。

但此次重新完整查看后，结论比“已有骨架、补几个功能”更严格：当前仍是**低数据密度的演示骨架**，距离可持续使用的社交产品还有一组相互关联的体验缺口：

1. **跨页面活动态没有成为系统级能力**：语音连接、直播控制/观看状态与路由展示没有完全分离，用户离开页面后缺少任意位置的快速回返入口。
2. **内容资产普遍是占位或退化文本**：群头像、用户头像、直播封面、帖子图片、语音消息、表情包等虽有局部类型/组件，但真实创建、上传、预览、失败重试和全局复用没有闭环。
3. **聊天和消息是“能输入文字”的最小实现**：输入栏缺少 QQ 式工具区；发送慢、pending/失败重试、草稿、已读游标和红点状态机没有统一可见契约。
4. **直播播放器和弹幕仍非完整观看体验**：侧栏/列表已经有结构，但视频呈现、封面首帧、控制栏、弹幕在视频上方飘屏、主播控制台和结束总结仍需产品化。
5. **移动端只是响应式，不是完整移动交互**：横向滑动、方向锁、跟手吸附、返回手势、输入法顶起和横屏手机触控策略仍需补齐。
6. **空态与错误态的产品信息不足**：空数据页面可导航，但很多页面首屏留白很大；loading、失败、重试、连接中/重连中/已结束没有统一状态视觉。

因此不能继续按单点修补。建议先做状态/性能/资源地基，再做统一聊天与收藏，然后直播、语音、手势和动效，最后再做搜索、通知、多设备和扩展能力。

## 1. 本轮审查范围、证据与边界

### 1.1 实际走查页面和操作流

- 一级路由：`/home`、`/voice`、`/live`、`/posts`、`/games`、`/messages`、`/search`、`/profile`、`/favorites`
- 详情/房间：`/chat/:id`、`/posts/1`、`/live/1`，以及语音大厅进入房间、群内场景入口
- 操作：窄/宽导航切换、帖子进入详情、帖子收藏、直播卡片进入、弹幕输入、消息/好友 tab、个人编辑入口、创建按钮、更多菜单
- 视口：竖屏 `375×760`、横屏/桌面 `1440×900`；后续仍需 `480×800`、`768×1024`、`1024×768` 和真实触摸设备

### 1.2 本轮截图与可复核证据

- 复审截图：本会话生成并查看了当前主页竖屏、主页横屏，以及重点路由截图/快照；正式交付不得只依赖截图文件，应以路由、DOM、操作步骤和本报告判断共同复核。
- 控制台：当前页面未发现 Error；仅见 React Router v7 future flag 警告，属于升级提示，不是页面崩溃证据。
- 既有点击报告：`docs/report/前端全功能点击测试报告.md` 已记录 mock 后端下的完整点击验收和 LiveKit 双向通话修复；本报告是在其上重新审查，不将 mock 通过等同真实服务闭环。

### 1.3 证据边界

当前后端数据在不同页面存在空数据、重复直播卡片和测试内容。应区分：真实 UI 缺口、后端列表/媒体契约缺口、测试数据导致的视觉问题、WS/LiveKit/HLS 基础设施限制。后续 AI 必须在报告中标注“代码已证实 / 浏览器已证实 / 真实服务待证实”，禁止把 mock 空态当成真实产品结论。

## 2. 横屏/竖屏逐界面复审记录

### 2.1 登录/注册

**现状**：表单与登录/注册路由存在，属于基础壳层。

**需要补齐**：品牌引导和爱莉身份表达、密码强度与显示切换、提交 loading、防重复提交、字段级错误、账号已存在/网络失败、验证码或安全策略、键盘焦点顺序、窄屏键盘顶起和成功后的过渡。登录态/登出态必须用真实浏览器分别验收，不能只依赖注入 token。

### 2.2 主页/群

**观察**：竖屏空态信息很少，只有“还没有加入群聊”和创建/加入方向；横屏有 TopNav，但无群数据时主区域大面积留白。群卡片/列表结构存在，但当前数据下无法体现真实封面、群头像、状态角标和动态密度。

**问题/规划**：

- 群头像需要真实上传、裁剪、失败回退，并在 ServerRail、群头、群卡片、群内顶部和活动浮层统一。
- 空态应提供插图/线性图标、创建群、搜索发现、邀请加入三个明确下一步，而非只靠大块留白。
- 有数据时卡片应展示封面轮播、成员/在线状态、未读、最近动态和可进入的目标；封面缺失应明确“暂无封面”，不能看起来像未加载。
- 卡片/列表切换应保存偏好，桌面内容最大宽度和窄屏滚动区域需稳定。
- 群信息、公告、成员、权限、入群审批、转让/解散应分层，不能把管理能力全部留在一个占位区。

### 2.3 语音大厅、语音房、离开语音

**已具备**：大厅卡片、进入/加入语义、成员状态、麦克风/扬声器控制、LiveKit 基础链路和真实双向可听修复已在既有报告记录。

**仍缺**：

- 离开语音页面不等于退出语音连接；页面返回、浏览其他页面、刷新、断网、重连和退出登录需分别定义。
- 任意页面的语音悬浮按钮：房间名、人数、麦克风状态、当前说话者/连接状态，点击回房；收起不能销毁连接，退出需二次确认。
- 语音房文字聊天、表情/图片、消息收藏、@、引用回复、草稿和未读。
- 真实头像/光环、房主/主持人/静音/离线的图标+文字双通道；锁房、禁言、踢出、邀请、权限失败提示。
- 麦克风/扬声器选择、测试音量、降噪/回声消除状态、浏览器权限失败和设备切换。
- 语音房收藏、最近进入、分享/邀请链接。

### 2.4 直播大厅、开播准备、直播间、结束页

**现状**：大厅已有在播筛选、刷新、两列/多列卡片；卡片与直播侧栏存在封面占位；宽屏侧栏 240px、收起为浮动按钮；窄屏直播间默认沉浸式并可打开列表。

**关键缺口**：

- 开播设置应从大厅创建弹窗迁移到独立“开播准备/控制台”：标题、封面上传裁剪、可见范围、分类标签、麦克风/摄像头预览、弹幕/录制开关、设备和推流状态。
- 必须有入口：个人页“我的直播间/开播控制”、直播大厅“我要开播”、直播中全局浮层、主播面板“返回控制台”。
- 播放器不能停在原始占位：封面首帧、加载骨架、播放/暂停、静音、音量、清晰度、全屏、画中画、播放失败/等待推流/服务不可用/已结束四态。
- 直播主信息完整显示：头像、昵称、标题、标签、在线人数、关注和收藏；后端列表直接带主播昵称，避免长期“未知主播”。
- 弹幕除右侧列表外，必须有视频上方轨道层；轨道按宽度计算，节流、入队、避免重叠，列表和飘屏使用同一事件源；关闭飘屏不关闭列表。
- 直播结束页提供时长、峰值观众、弹幕摘要、回放/删除和封面标题管理。
- 直播收藏、历史观看、分享卡片和直播中退出/恢复策略。

### 2.5 帖子列表、帖子详情、群内帖子

**现状**：帖子卡、作者信息、评论数、详情、收藏切换、评论输入和发布入口存在；群内帖子路由已接入，前端传 `scope=group:<id>`。

**缺口**：

- 真实用户头像、图片九宫格上传/预览/压缩/失败重试；视频/链接卡片可作为后续媒体类型。
- 列表卡片的正文折叠、引用、话题/群来源、分享、删除/编辑确认、收藏成功反馈。
- 群内帖子卡必须稳定进入详情；详情需保留群上下文、返回群帖子、评论、收藏和分享，不能只显示全站 feed。
- 评论回复树、@成员、分页/加载更多、删除权限、失败重试和输入草稿。
- 帖子收藏最终进入统一多类型收藏，而不是单独一套接口语义。

### 2.6 桌游

只保留房间列表、房间进入、创建、收藏、邀请和通用 loading/error/empty 契约；玩法规则、棋盘和回合系统另立专项，不纳入本计划主批次。

### 2.7 消息中心、私聊、群聊输入

**观察**：宽屏消息中心是会话列表+内容两列，窄屏私聊隐藏底栏；空会话时两侧留白大。当前最明显的产品缺口是输入区和状态反馈，不是再加一个导航。

**统一 `InputBar` 规划**：

- 文本多行输入、发送状态、Enter/Shift+Enter规则；
- 输入框下方表情包（最近/收藏/分类/搜索）；
- 图片选择、粘贴/拖拽、缩略图预览、上传中/失败重试；
- 按住说话、松开取消、上滑锁定、计时、权限和不支持浏览器降级；
- 可扩展文件、引用、@、回复预览；
- 按会话保存草稿，媒体统一支持 `text/image/emoji/voice/file/reply`；
- 语音消息应有波形、时长、播放进度和未播放态。

消息系统还需要 pending→sent→failed/retry 状态、乐观 UI 可回滚、发送耗时指标、断线重连提示和防重复发送。不能让“按钮点了很久才出现消息”成为默认体验。

### 2.8 搜索

路由、历史 chips 和结果分组已存在；复审仍建议增加自动聚焦/联想、最近搜索管理、类型筛选、排序、分页/加载骨架、无结果推荐和结果目标可用性提示。搜索应成为用户、群、帖子、直播、桌游等资源的统一索引，而不是页面级拼接请求。

### 2.9 个人、收藏、更多菜单

个人页目前能编辑昵称/签名和状态，头像仍应接入统一资源管线；应补头像上传裁剪、修改失败回滚、账号安全/设备会话、通知设置、我的内容统计和“我的直播控制台”入口。

收藏必须从帖子扩展为统一模型：帖子、消息、直播间、语音房、桌游房、群/频道。每项保存 `targetType + targetId + snapshot + createdAt`；目标消失显示“内容已不可用”，不能静默消失。收藏页增加类型 tab/chips、搜索、排序、取消收藏确认/反馈、来源跳转。

### 2.10 横屏手机与响应式

不能只以宽度推断桌面能力：横屏手机仍是触控设备。需要验证顶部/底部安全区、手势、输入法、浮动按钮、抽屉侧栏和可点击尺寸；`1024px` 不能出现 TopNav 与 BottomTabs 双重导航；`375px` 输入区、FAB、弹层不能互相覆盖。

## 3. P0：状态、性能、资源地基

### P0-1 `SessionActivityStore`

统一管理 `voiceSession` 与 `liveSession`，区分 `idle/connecting/connected/reconnecting/leaving/ended/failed`；记录 `sessionId/sourceRoute/owner/lastError/updatedAt`。路由展示和媒体生命周期分离，刷新、断网、退出登录有显式恢复/清理规则。

验收：语音房→主页→帖子→私聊→个人→悬浮按钮回房，媒体持续；直播中→其他页→控制台，结束后浮层消失；重连不伪造在线。

### P0-2 统一 loading、发送、错误和已读

所有超过 300ms 的请求显示玻璃骨架；列表 stale-while-revalidate；requestId/取消/超时防旧响应覆盖；消息 pending/已发送/失败可重试；WS/REST 降级可见；红点由服务端已读游标驱动，确认失败不得清除。

### P0-3 统一媒体资源管线

媒体 descriptor 至少含原图、缩略图、宽高、类型、尺寸、alt、归属、加载/失败状态。头像、群头像、直播封面、帖子图和媒体消息统一懒加载、缓存、渐进加载、解码失败回退和重试；移动端控制尺寸与并发。

### P0-4 性能基线

记录首屏、路由切换、发消息、加入语音、进入直播间的 Performance/Profiler 数据；路由和媒体模块懒加载，列表分页/虚拟化，弹幕有限环形缓冲，Zustand selector 拆分，禁止音量高频更新导致整页重渲染。

## 4. P1：功能横向补齐

1. 统一 `InputBar`：表情、图片、语音输入、草稿、媒体预览和失败重试。
2. 多类型收藏：消息、直播、语音、群、桌游房框架。
3. 群内帖子进入详情并保留上下文。
4. 已读/红点状态机：会话、好友申请、群邀请、帖子、直播/语音邀请分开统计，多窗口同步。
5. 直播开播准备/控制/结束三页、封面管线、播放器和弹幕飘屏。
6. 语音全局入口、房内聊天、设备设置、房主管理、收藏/邀请。

## 5. P2：手势、动效、空态与视觉丰富度

- 一级 tab、群内场景左右滑动；直播间滑动切换，方向锁、阈值、跟手 transform、松手吸附、切换锁；按钮/键盘/无障碍等效入口。
- 返回手势和沉浸式房间手势；窄屏输入法顶起与安全区；横屏手机按触屏策略处理。
- 卡片、气泡、收藏、发送、面板开合 150–300ms；骨架、成功、失败、重试、取消均有状态动画。
- 遵守 `Ayla/docs/design.md`：Y2K Frost 冰蓝/樱粉玻璃、Fredoka/Nunito/Space Grotesk、每屏最多三处辉光；不用扫描线、glitch、emoji 功能图标和重阴影。
- 空态必须包含图形、解释、下一步 CTA；骨架不能白屏；`prefers-reduced-motion` 关闭呼吸、滑入和弹幕飘动，仅保留透明度反馈。

## 6. 建议实施批次与验收门槛

### 批次 A：状态与性能地基（最高优先）

`SessionActivityStore`、统一 loading/发送/错误、已读游标、资源 descriptor、头像/群头像/封面基础组件。验收：跨页面回返、失败可重试、红点可服务端确认、无白屏。

### 批次 B：聊天与收藏

`InputBar`、表情/图片/语音消息、草稿、消息收藏、多类型收藏、群内帖子详情。验收：私聊/群聊/语音房同一输入体验，媒体可回滚重试，收藏可跨类型跳转。

### 批次 C：直播

开播准备/控制/结束页、开播入口、封面上传、播放器、弹幕轨道、直播收藏和全局控制入口。验收：主播完整开播闭环、观看播放闭环、列表与飘屏事件一致。

### 批次 D：语音

全局浮层、房内聊天、设备设置、房主管理、邀请和收藏。验收：离开页面不退出，多用户真实通话与消息并行稳定。

### 批次 E：移动行为和动效

横滑、返回、吸附、横屏手机、空态/骨架/反馈动画、reduced-motion。验收：真实触摸端跟手，键盘与等效控件可用。

### 批次 F：扩展能力

统一搜索、分享卡片/深链/邀请、通知中心、活动历史、多设备同步、离线草稿、推送、埋点、性能面板和诊断页。桌游玩法另立专项。

## 7. 后续 AI 执行规则

每个批次开始前必须记录：

1. 改变哪条用户流程；
2. 哪些是页面状态、哪些是跨页 session；
3. API/WebSocket/LiveKit 契约、超时、错误和回滚；
4. 窄屏、宽屏、横屏手机的等效操作；
5. 是否影响语音/直播生命周期；
6. 是否需要数据库/API schema；
7. 定向单测、Playwright 实流和截图验收；
8. 是否同步 `design.md`、计划文档、审计报告和工作日志。

每批只改一个可验收主题，先真实流程再视觉细节；禁止用 mock 通过冒充真实后端，禁止把失败伪装为空态，禁止一次性顺手重构所有页面。

### 推荐立即执行的十项

1. 语音跨页面保持连麦与全局回房浮层；
2. 直播中全局返回开播控制台；

## 8. 第二轮有数据复审：实际走查结果

> 本节是对上一版“空态审查”的纠正。用户指出空数据不能代表完整界面，因此本轮使用 Playwright `page.route` 在浏览器运行时注入一组丰富、结构符合 API 契约的测试数据；没有修改业务代码、没有写入后端数据库。覆盖群、成员、未读、帖子、直播、语音房、桌游房、收藏、搜索结果和聊天消息。

### 8.1 本轮数据集

- 3 个群：星光小屋、深夜电台、旅行同好会；有成员数和不同未读数。
- 4 个语音房：公开、群内、好友可见、我已加入；成员数从 3 到 15。
- 5 个直播间：4 个直播中、1 个未开播；有主播昵称、来源、直播侧栏数据。
- 6 个帖子：3 位作者、标题/正文/评论数、收藏态交错。
- 4 个桌游房：等待中/对局中、不同人数和房主。
- 4 个收藏：帖子、直播、语音、桌游混合类型。
- 5 类搜索结果：用户、群聊、帖子、直播间、桌游室。
- 群聊天消息包含文字消息、发送者、已读/发送状态；另外用媒体消息结构验证了输入/消息类型契约。

### 8.2 竖屏有数据复审（375×760）

- **语音大厅**：4 张卡片能显示房名、来源、人数、加入/进入；“我在其中”状态可见。但卡片内容主要仍是文字行，缺房主头像、成员头像堆叠、正在说话者、麦克风状态和最近活动预览。
- **直播大厅**：5 张卡片能显示直播状态、标题、主播、来源；但封面仍是渐变/占位，不是实际直播视觉；缺观看人数、主播头像、互动指标、收藏、标题标签和视频首帧预览。状态标签和卡片层级偏轻，无法快速区分热门/关注/好友直播。
- **帖子流**：6 张卡片能连续滚动，作者首字头像、昵称、时间、标题、正文、评论数、收藏态都出现；但测试数据中重复标题和正文暴露出卡片信息结构单薄，真实内容若较长时缺媒体、话题、群来源、分享/更多操作，作者区域也缺头像图片和在线语义。
- **桌游大厅**：4 个房间显示等待中/对局中、人数、来源，结构清楚；不过封面/游戏类型图形、房主头像、座位预览、最近活动、收藏入口缺失。玩法不在本次范围。
- **搜索页**：五类结果可以同时出现，结果密度比空态合理；但页面容易变成长列表纵向堆叠，缺筛选 chips、分组折叠、结果高亮、加载分页和跨类型统一卡片；用户结果头像仍多为首字母。
- **消息中心**：即使注入群会话和聊天消息，`/messages` 首屏仍主要显示“爱莉入口 + 暂无会话”，群会话没有以私信会话列表展示。这不是测试数据不足，而是消息中心数据模型只展示私信/好友，群消息被留在群路由，用户无法在一个收件箱看到所有未读来源。宽屏右侧仍是“选择一个会话”，首屏利用率低。
- **收藏页**：混合注入帖子/直播/语音/桌游后，当前页面仍以帖子内容为主，其他类型退化成“帖子”或缺少类型化展示，说明后端类型虽有枚举，前端收藏中心还没有真正完成多类型渲染、筛选和来源跳转。

### 8.3 横屏有数据复审（1440×900）

- **群聊天**：横屏三列结构（群栏、场景栏、内容区）清楚，群切换和场景切换入口齐全；但聊天消息没有按注入历史显示在群聊天主区，仍落到“还没有消息”，说明测试响应格式与实际 chat store 的分页/详情契约还需真实核对，也暴露了前端对历史数据失败时的空态降级过于安静。输入区只有文本框和发送按钮，没有表情、图片、语音、附件、引用和录音状态。
- **直播间**：横屏有 240px 直播列表侧栏、返回、收起、直播状态、主播面板和弹幕侧栏；然而中间视频主区仍是较大的空/原始播放器区域，没有封面首帧、控制栏、播放失败分层、主播信息卡、观看数或弹幕飘屏轨道。右侧只有列表/输入，距离“直播间”而更像“频道控制骨架”。
- **帖子/搜索/桌游**：宽屏导航稳定，内容仍以单列/简单卡片为主，未充分利用 1440px 空间；需要最大宽度、双列/辅助信息栏、筛选工具条和详情预览，而不是把移动端长列表原样拉宽。
- **个人页**：有数据时“我的发帖”和“正在玩的桌游”可见，但我的直播间为空的原因和入口不清楚；缺头像上传预览、我的直播控制台、活动时间线、通知设置和多设备状态。

### 8.4 本轮发现的具体新问题

1. **数据注入必须按真实接口契约验证**：聊天历史需要核对真实响应形状；测试路由即使返回“看似正确”的 `results`，如果页面读取的是数组或另一字段，仍会静默落空。这说明生产代码需要 schema 校验和可观测错误，而不是把契约不匹配渲染为空态。
2. **头像缺失会触发崩溃**：当注入的会话成员缺少 `user` 或 `label` 时，`Avatar` 出现 `Cannot read properties of undefined (reading 'slice')`。真实 API 脏数据、部分字段或加载中对象不应让整个页面崩溃，Avatar 和列表需要安全回退、错误边界和资源加载态。
3. **WebSocket 403 在 mock 数据审查中持续刷屏**：页面虽然 REST 有数据，但 chat/presence WS 仍尝试连接并报 403；需要把连接失败明确显示为“实时连接不可用/正在重连”，并合并重复错误，避免控制台和用户状态失真。
4. **直播封面仍是占位，不是有数据就自动变丰富**：API 当前 `LiveChannelDescriptor` 没有封面 URL 字段；必须先补媒体资源契约和上传流程，不能只增加卡片文字。
5. **群内语音/直播/桌游没有沿用全局列表数据**：注入全局语音/直播/桌游数据后，群内场景仍显示“群内还没有”，这可能是正确的群归属过滤，也可能是测试数据没有设置 `group`；正式验收必须准备带 `group:'g1'` 的专属样本，并检查空态是否解释当前筛选范围。
6. **收藏类型扩展未完成视觉和跳转闭环**：枚举支持 `post/live/voice/game/group` 不等于收藏页支持五类；必须逐类显示来源、状态、目标不存在和跳转。
7. **“有数据”不等于“有媒体体验”**：文字数量增加后，页面仍缺图片、真实头像、直播封面、语音波形、动态成员和状态变化；下一轮数据夹具必须包含可访问的图片/音频/视频资源与加载失败样本。

## 9. 复审后的最终判断

Ayla 当前不是“还有几个按钮没接”的状态，而是**在有数据时，路由和基础卡片确实可以铺开，但真实内容资产、媒体层、消息聚合、跨页面 session、状态反馈和移动行为仍没有形成产品闭环**。上一次只看空态是不充分的，本轮已用有数据夹具重新查看并将新证据写入本文。后续应以本报告的批次和验收门槛为准，逐项交付、逐项截图、逐项记录真实服务证据；本轮开始进入实施阶段：已先落地 P0-1 的会话活动态索引、AppShell 跨页面回房入口、语音 heartbeat runtime owner，以及 Avatar 缺失/图片加载失败安全回退；LiveKit/直播 HLS 与 WS 资源 owner 迁移、完整跨页面持续连接和真实后端验证仍待后续批次；本轮另补充登出时释放已迁移语音 heartbeat 的清理契约，并为聊天输入补齐失败可见、单条重试与同一幂等键复用；已读红点改为服务端确认成功后清除，确认失败保留未读；ChatConversationRoute 已接入统一 loading/error 状态和可操作重试。

**后续实施记录（实时连接状态可见性）**：在 `0881dd2` 之后补齐 P0-2 的一项基础体验：`RealtimeStatusBanner` 不再只显示笼统的“重连中/不可用”，而是按聊天、在线状态、语音、直播列出当前处于 `connecting/failed` 的通道、中文状态和可诊断的最后错误；`online/offline` 恢复时 store 明确清除旧错误，避免状态视觉残留。已通过实时状态定向测试 2 项、类型检查和生产构建；构建仍有既有 chunk 体积与动态导入提示。该项仍未替代真实 WS 403/LiveKit/HLS 验收，后续需在真实服务中验证错误文案脱敏、重连收敛和跨页面状态稳定性。

**后续实施记录（聊天草稿）**：统一 `MessageInput` 已补齐按会话保存草稿：私聊与群聊共用 `ChatDraftsStore`，切换会话时恢复对应文本，发送成功只清除当前会话草稿，失败重试保留内容与原幂等键。已通过输入栏重试测试与草稿 store 测试共 3 项、类型检查；仍未扩展到媒体/语音输入，后续按批次 B 继续。

**后续实施记录（聊天历史分页失败可见）**：群聊与私聊的“加载更早消息”失败现在复用历史错误提示，不再在滚动触发分页失败时静默停住；用户可通过当前历史重试入口恢复。

**后续实施记录（媒体受控上传 API 地基）**：前端 `api/media.ts` 补齐与后端真实三步契约一致的 `uploadMediaFile`：创建上传会话、PUT 原始二进制、幂等完成并返回 descriptor；`api/client.ts` 支持 Blob 原始请求体，不会错误 JSON 序列化文件；超过服务端声明大小时在上传前失败。媒体上传定向测试 2 项、类型检查通过，已在聊天输入栏接入图片选择：选择后显示上传进行中，完成受控上传后发送带 `media_id` 的图片消息，上传/发送失败保留错误提示；媒体上传与输入栏合计 4 项定向测试通过，类型检查通过。
