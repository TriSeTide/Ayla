# Ayla 前端加载速度与动画统一优化 —— 调研报告

> 项目：Ayla Web 前端（`Ayla/web`，React 18 + Vite + TS + Zustand）
> 触发：用户反馈「进入直播间和进入桌游房的加载和进入速度很丝滑，进入语音房速度还不错但动画差一点，进入帖子详情页速度太慢了而且动画也没有。可以向直播间看齐一下。不止这些界面，整体上所有界面都要统一做好优化」
> 日期：本次实施
> 状态：根因分析 + 方案设计

---

## 一、执行摘要

用户的核心诉求是**三件事**，且强调「整体统一」：

1. **加载速度** —— 尽最大可能优化加载速度；
2. **加载动画** —— 优化、复用、统一动画；
3. **加载策略** —— 适当使用预加载优化加载，善用 WebSocket。
4. **验收参照系** —— 以「直播间 / 桌游房」进入速度与动画为标杆，向它们看齐。

调研确认：直播间/桌游房已经把「进房动画 + 结构化骨架」做得很规范，语音房速度不错但**进房体缺少统一入场动画**（只有输入框滑入），而**帖子详情页是当前最差的界面**，同时命中「串行加载 + 骨架弱 + 无入场动画 + 无评论实时推送」四个短板，因此把帖子详情页作为本次优化的核心靶点。

---

## 二、现状盘点（逐界面）

### 2.1 直播间 / 桌游房（标杆 ✅）

- **进房动画**：`hooks/useEnterRoomAnimation.ts` 驱动——底栏下滑走（shell store `setBottomTabsLeaving`）+ 输入框 `translateY(100%→0)` 滑入（250ms ease-out 延迟 100ms）。
- **加载骨架**：进入直播间即渲染播放器三态，列表页有 `posts-skeleton` 等结构化骨架。
- **结论**：动画方向纪律和骨架规范已经成型，作为本次对齐的基准。

### 2.2 语音房（速度不错，动画差一点 ⚠️）

- **加载**：进房走 `useVoiceChannel.join()`，REST join → LiveKit → 成员对账，列表由 `lastFetched` 缓存 + WS 对账，体验不错。
- **动画**：`VoiceRoomBody` 只有**输入框**（`.voice-room-composer`）用了 `useEnterRoomAnimation` 做 `translateY` 滑入；但**进房体本身**（成员面板 `.voice-room-voice-card`、聊天卡 `.voice-room-chat-card`）**没有任何入场动画**——用户点进语音房后成员面板是「闪现」出来的，没有直播间那种「浮入」感。→ 这就是「动画差一点」的根因。
- **骨架屏**：房内成员面板/聊天卡无骨架，加入过程（LiveKit 连接 + 成员对账）期间可能短暂空白。

### 2.3 帖子详情页（最差,核心靶点 ❌）

`pages/PostDetailPage.tsx` `load()`：

```ts
postsApi.getPost(id)
  .then((p) => { setPost(p); return postsApi.listComments(id); })  // ← 串行！
  .then((list) => setComments(list))
```

- **串行加载**：`getPost` 完成后才开始 `listComments`，两条 HTTP RTT 叠加。→ 从点进来到全部内容可见 ≈ 2 × 网络往返 + 后端各一次查询。
- **骨架弱**：`loading` 时只渲染**单个** `<div className="skeleton" style={{height:160}}/>`，既没结构也没质感，用户感知「慢」。
- **无入场动画**：`usePostDetailTransition` 只负责 shell 层底栏让位（原位交叉淡化），**详情正文卡片 / 评论列表没有任何浮入动画**。用户点进来看到的是「白屏 → 突现内容」。
- **无评论实时推送**：`ws/chat.ts` 只有 `post.created` / `post.deleted`，**没有 `comment.created` / `comment.deleted`**。自己发评论靠本地 `setComments` 追加，但**其他端（另一个浏览器/用户）看不到实时评论**，刷新才有。这属于「未善用 WebSocket」。

### 2.4 其余界面（统一优化面）

| 界面 | 现状 |
|---|---|
| 主页 /group | 已有进群动画 + 下拉回主页，较完整 |
| 群内五场景 | 已有 `group-scene-fade` 淡入 |
| 消息中心/搜索/个人页 | 有基础骨架，但入场动画与加载结构不一 |

## 三、根因分析

### 3.1 为什么「帖子详情慢」——加载链路

资源消耗分解（理想网络，无缓存）：

```
点进 /posts/:id
  └─ 串行：
     1) GET /posts/:id/            → RTT₁
     2) GET /posts/:id/comments/   → RTT₂   （等 1 完成才开始）
     3) GET /favorites/?type=post  → RTT₃   （并发于 1，但结果只用于收藏态）
  总可见时间 ≈ RTT₁ + RTT₂
```

优化后（并行）：

```
     1) GET /posts/:id/            ─┐
     2) GET /posts/:id/comments/   ─┤  Promise.all 并发
     3) GET /favorites/?type=post  ─┘
  总可见时间 ≈ max(RTT₁, RTT₂) ≈ RTT₁
```

→ **串行改并行即切掉一次完整的网络往返**，是「帖子详情慢」最直接、收益最大的修复。

### 3.2 为什么「感知慢」——骨架与动画

即使网络不慢，单块骨架 + 无入场动画会放大「等待感」。直播间/桌游房之所以「丝滑」，是**结构化骨架（内容形状预示）+ 浮入动画（内容温和显现）**双重作用下，用户感知不到"卡一下"。帖子详情两者皆缺。

### 3.3 为什么「语音房动画差一点」

进房体（成员面板、聊天卡）无入场动画，只有输入框动了 → 视觉上"只有底部在动，主体突然出现"，缺少直播间整体浮入的节奏。

### 3.4 为什么「整体不统一」——动画原语缺失

直播间/语音房/帖子详情/进群目前各用各的 hook 与内联 `style.transform`，没有共享的「内容入场动画原语」。规范（design.md §7）虽定义了时长/缓动，但**没有一个可复用的 CSS 类 + 组件封装**让每个界面一致落地。

## 四、方案设计（总纲）

统一一套「**加载三件套**」，让所有界面都向直播间看齐：

1. **并发预加载**：进入详情/房间前并行发关键请求（`Promise.all`），消除串行 RTT。
2. **结构化骨架**：一个统一 `Skeleton` 组件 + 预制布局，每个异步界面加载期画「内容形状」，取代单块空白骨架。
3. **统一入场动画原语**：新增 `useRevealOnEnter` hook + `.reveal` CSS 动画（150–200ms 浮入淡入，`prefers-reduced-motion` 降级），直播间/语音房/帖子详情/列表统一套用。

### 4.1 统一动画原语（新增）

- **CSS（base.css 或 app.css）**：新增 `@keyframes reveal-in`（`translateY(8px)+opacity 0→1`，180ms `--ease-out`）与 `.reveal` 类；`prefers-reduced-motion` 下只保留透明度渐变（对齐 design.md §7）。
- **Hook `useRevealOnEnter(active=true)`**：返回 `entered` 布尔，进入后一步 `rAF` 置真；与直播间 `<LivePlayer>` 的进入节奏一致。作为 `useEnterRoomAnimation` 等既有 hook 的**统一底层**，消除三处分散实现。

### 4.2 帖子详情页优化（核心）

1. **加载并行**：`load()` 改为 `Promise.all([getPost, listComments, listFavorites])`，一次性并行拉取。
2. **结构化骨架**：加载期渲染「详情卡形状 + 评论列表形状」的结构化骨架（`.post-detail-skeleton`），而非单块。
3. **入场动画**：详情正文卡 + 评论列表套 `.reveal`，评论逐条 stagger（每 40ms 递增，总 300ms 内），营造直播间浮入节奏。
4. **评论实时推送**（WebSocket 增强，后端+前端）：
   - 后端 `posts/services.py` 新增 `broadcast_comment_created/created_deleted`，评论创建/删除时向「帖子的可见范围（群/好友/作者）或全局 feed」推送 `comment.created` / `comment.deleted`。
   - 前端 `ws/chat.ts` dispatch 新增两个 case，`PostDetailPage` 订阅 `chatWS.onFrame`，收到 `comment.created` 实时插入、`comment.deleted` 实时移除 + 更新 `comment_count`。

### 4.3 语音房动画统一

- `VoiceRoomBody` 进房体（成员卡、聊天卡）套 `.reveal` 入场动画（与直播间同源）；加入时成员面板浮现，输入框仍按原时序滑入。

### 4.4 预加载增强

1. **login 预加载补 posts**：`main.tsx` 的 `loadCoreData` 增加 `listPosts({scope:"feed"})` + `listFavorites("post")` 写入 posts store（不阻塞启动，失败静默）。
2. **路由级懒加载**：`App.tsx` 用 `React.lazy` + `Suspense` 分包页面，首屏只加载当前路由 chunk，降低首屏 JS 体积。
3. **列表/详情数据预热**：帖子卡片 `PostCard` 点击跳详情前，若 store 已有该 post 直接带出（详情页首帧可用缓存渲染）。

### 4.5 全界面统一

把 `.reveal` 骨架与入场动画应用到消息中心、搜索、个人页等异步列表，统一节奏。

## 六、验收口径（详见《验收清单》）

- 帖子详情从「点进」到「正文+评论可见」的可见时间，较串行前**减少约一次网络往返**；
- 帖子详情有结构化骨架 + 浮入动画，不再单块白板、不再突现；
- 语音房进房体有统一入场动画；
- 评论在其他端可实时到达（`comment.created`）；
- 全部界面统一 `.reveal` 原语、统一骨架，`prefers-reduced-motion` 降级正常；
- TypeScript、Vite 生产构建、Vitest 定向测试通过。

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 路由懒加载引入 loading/布局问题 | `Suspense` fallback 用统一骨架，宽度/高度占位 |
| 评论实时推送泄漏到无权用户 | 广播范围严格对齐帖子的可见性（群组/好友/作者/公开 feed），与 `post.created` 同纪律 |
| 入场动画在 reduced-motion 下未降级 | hook/CSS 双保险，`prefers-reduced-motion` 只保留透明度渐变 |
| 并行加载竞态 | `id` 依赖 + `cancelled` 标志（沿用现有模式） |
