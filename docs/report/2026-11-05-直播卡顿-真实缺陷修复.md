## 0. 先说清楚：卡顿根因不在这些缺陷里

**当前「时不时卡一下」的根因是 WiFi 空口质量，不是代码。** 实测证据：

| 指标 | 实测值 | 说明 |
|---|---|---|
| **tx retries / tx packets** | **53975 / 63303 = 85.3%** | 每发 100 包重发 85 次 |
| 网关 RTT（纯 WiFi 一跳） | p50=44.8ms、**max=426ms** | 未出公网就抖成这样 |
| WiFi 协商速率 | **8.6 ↔ 154.8 Mbit/s（18 倍波动）** | MCS 在 0~5 之间乱跳 |
| 分片下载（客户端侧） | p50=**3.11s**、89% 慢于实时 | 而分片只代表 1 秒内容 |
| 慢分片 ↔ RTT 尖峰相关性 | **17/17 = 100%** | 每个慢分片都对应一次抖动 |
| 信号强度 | -48~-55 dBm（**很强**） | 不是信号问题 |
| 驱动 | mt7925e（MediaTek WiFi 7） | 该型号 Linux 高重传已知问题 |

**已排除**：带宽不足（1 推 2 拉需 6.4Mbps，空口上限 24.4Mbps，余量 3.8×）、帧率（30fps 同样卡）、
客户端类型（Web/Flutter 都卡）、服务器产片（回环取分片 p50=4ms、0% 超时）、推流掉帧（59.96fps 零丢帧）。

**结论**：本文的修复修的是**独立的真实缺陷**，不会让当前卡顿消失。
要让卡顿消失，必须解决 WiFi —— **插网线走 enP7s7**（现仍 DOWN）。

## 2. 本轮修复的 5 项真实缺陷

### 2.1 watchdog 出帧一次后永久失效（Web，最严重）

**文件**：`Ayla/web/src/runtime/liveSessionRuntime.ts`

**缺陷**：`clearStallTimer()` 同时承担两个职责（清定时器 + 拆 5 个 video 监听器），
而 `armWatchdog()` 的 `onResume`（playing/canplay 出帧）会调用它。
`armWatchdog` 全仓只在 `rebuildPlayer()` 里调用，重建又靠 watchdog 触发 ⇒ **死锁**：
播放器出过一次画面后永久失去卡死检测。

**证据**：服务端日志印证 —— 2026-11-04 21:12:16→21:14:47 上游停摆 **151 秒**期间，
浏览器 hls.js 重建 **0 次**、Flutter mpv 重建 **0 次**、**0 次 fatal**，
用户看到静默定格而 UI 仍显示「正在播放」。

**修复**：拆成两个方法 —— `clearStallTimer()` 只清定时器；新增 `detachWatchdog()`
负责拆监听器，只在 `destroyPlayer()` / `leave()` 调用。

**回归锁**：新增测试「出帧一次后 watchdog 仍然有效」，并做**变异验证**：
把旧行为塞回去，该测试立刻失败 ✅

### 2.2 判死阈值低于正常分片耗时（Web）

**文件**：`Ayla/web/src/runtime/liveSessionRuntime.ts`

**缺陷**：`STALL_TIMEOUT_MS = 2000`，而实测正常分片下载 p95=1.48s、max=6.69s。
阈值低于正常耗时上界 ⇒ **正常抖动被当成故障**，触发重建（重建要重新握手 + 拉
playlist + 拉分片 ≥1s），把「1 秒抖动」升级成「1 秒卡 + 重建黑屏 + 冷却真空」。

**修复**：2000 → **6000**，与 Flutter 端 `kStallTimeoutMs=6000` 对齐
（此前双端不一致，Web 是错的那端）。`REBUILD_COOLDOWN_MS` 4000 → **8000** 同理对齐。

**注意**：这项与 2.1 **必须一起改**。watchdog 修好后如果阈值仍是 2s，
在这条 p50=3.11s 的链路上会每 2 秒重建一次，反而更糟。

**附带**：四个常量改为 `export`，测试直接引用，避免以后改常量时测试静默失效。

### 2.3 hls_dispose 120s 造成 29.7 秒 404 黑洞（服务端）

**文件**：服务器 `/home/ayerelysia/Elysia/ayla-deploy/srs.conf`（bind mount 成容器内 `conf/docker.conf`）
+ 仓库副本 `Ayla/srs.conf`、`Ayla/deploy/examples/srs.conf.example`

**缺陷**：SRS 默认 `hls_dispose=120s`，推流中断 2 分钟后删除 m3u8 + 全部分片。
推流端重连常超过 2 分钟 ⇒ 播放器连吃 **28 次连续 404 / 29.7 秒**（nginx + SRS 日志双向印证）。

**修复**：新增 `hls_dispose 0`（不自动销毁；分片回收仍由 `hls_cleanup` 按窗口滚动）。

**验证**：重启后容器 healthy；文件数稳定 **62 个不再增长**、`MEDIA-SEQUENCE` 持续推进
⇒ `hls_cleanup` 正常滚动回收，磁盘不会无限增长（占用 26MB）。

**备份**：`srs.conf.bak-20261105-*`

### 2.4 分片错误被静默丢弃（Web）

**文件**：`Ayla/web/src/player/hls.ts`

**缺陷**：`if (!data.fatal) return` 把 hls.js 的非 fatal 分片级故障（404/超时/解析失败）
全部丢弃 ⇒ 分片持续失败时画面卡住但 UI 无任何信号。
另外 fatal `NETWORK_ERROR` 时无参 `startLoad()` 等价于 `startLoad(-1)`，
而 hls.js 在 `lastCurrentTime > 0` 时会用旧位置覆盖，语义不稳定。

**修复**：新增 `onFragmentError` 回调（仅观测，不改变 hls.js 恢复流程）；
重试改为 `startLoad(video.currentTime > 0 ? video.currentTime : -1)` 保证「原地重试」。

### 2.5 上游停摆无判定（Web，新增能力）

**文件**：`Ayla/web/src/player/hls.ts` + `liveSessionRuntime.ts`

**缺陷**：上游停止产片时 HTTP 仍返回 200、playlist 内容不变，hls.js 认为这是正常直播状态
（`liveMaxUnchangedPlaylistRefresh = Infinity`），**不报错、位置静默** ⇒ 用户看到无提示的定格。

**修复**：
- `hls.ts` 新增 `onPlaylistLevelUpdated`（`LEVEL_UPDATED` → 上报 `startSN`）
- runtime 新增 `UPSTREAM_STALL_WINDOW_MS = 12_000` 与
  `noteMediaSequence / reportUpstreamStall / clearUpstreamStallTimer / resetUpstreamStallWatch`
- 序号停滞超窗口 ⇒ `currentPlayerError = "直播流已中断（上游停止推送），恢复后自动继续"`
- 恢复前进 ⇒ 自动清除；**不触发重建**（停摆期间重建也拉不到数据）

**回归锁**：新增 2 条测试（停摆上报 / 停摆不重建），并做**变异验证**：
把上报语句删掉，测试立刻失败 ✅

## 3. Flutter 侧复核结论：无同构缺陷

**逐行复核 `Ayla/flutter/lib/player/hls_player.dart`：**

- `_clearStallTimer()`（:473-476）**只取消定时器**，不拆任何监听器
- 监听器是 `p.onStall / p.onResume / p.onFatal / p.onPosition`（:302-305），
  挂在**平台播放器对象**上，随 `dispose` 一起消失，不存在「拆了不重挂」的路径
- `_onResume()`（:441-443）只调 `_clearStallTimer()`

⇒ **Flutter 没有 2.1 那个 bug**。本轮 Flutter 侧**零改动**。
