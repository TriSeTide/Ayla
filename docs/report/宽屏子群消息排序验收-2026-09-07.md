# 宽屏子群消息排序验收（2026-09-07）

## 原因与变更

用户要求宽屏群侧栏「聊天」下子群随新消息前移，默认组固定第一。
调查 `ChannelSidebar.tsx`、subgroup store 和子群 API 发现，侧栏直接按列表顺序渲染，
接口没有提供已读后仍可用于排序的活动依据。

本次在子群响应增加只读 `last_message_seq`，从现有会话消息按子群聚合最大序号；
默认组合并历史 `subgroup_id=NULL` 消息。前端将 REST 与已接收消息取最大序号合并，
防止早到 WS、迟到 REST 或重连补发回退顺序。宽屏独立投影先固定默认组，再按序号倒序，
并列保持原序；先排序再取前三项，窄屏基础列表顺序不变。

没有新增数据库字段、迁移或权威数据修复。只读聚合与界面投影可通过回退本次代码撤销，
无需数据恢复或备份回放。未启动、停止或重启用户服务，未提交/暂存代码。

## 边界

同日用户指出“群聊尚有未读却清掉红点”后，补充真实 GroupChat/MessageList 验证复现了
进入子群即整组已读的问题。此前测试将 MessageList mock，并明确期待“切换即全读”，
验收覆盖有缺口；“收到新消息也能排序”不代表“未看到的消息仍正确保留未读”。
现已修正该行为和测试，详见 [群聊可视消息已读修复验收](群聊可视消息已读修复验收-2026-09-07.md)。

现有 UI 的 `sendPoke` 不传 `subgroup_id`，因此仍归默认组；本次仅消费已有归属，
没有变更戳一戳发送路由。实际部署的接口与浏览器真实收发链路尚未进行线上端到端验收，
由用户在日常运行环境确认；本次未为此发送任何真实消息。

稳定行为说明见 [子群功能文档](../subgroups.md) 与 [设计规范 §12.4](../design.md#124-频道侧栏-channelsidebar宽屏主页群场景)。
