# 开播控制台无限循环（请求风暴 + Failed to fetch）事故记录

日期：2026-09-06
影响：开播控制台（`/live/start/:channelId`）在 owner（主播本人）进入时无限循环请求，界面最终显示 "Failed to fetch" 错误页；跳转错乱；控制台反复闪烁。

## 现象（用户报告 + 浏览器复现）

- 任意入口进入开播界面，控制台报错刷屏：
  - `WebSocket connection to 'wss://.../ws/live/{id}/' failed: WebSocket is closed before the connection is established.`（同一 URL 反复出现 25+ 次）
  - `Failed to load resource: the server responded with a status of 404`（媒体 :sign 接口，见下节"非本事故根因"）
  - `Uncaught TypeError: Cannot read properties of undefined (reading 'startTime')`（浏览器扩展注入的 web-vitals，与 Ayla 代码无关）
- 页面表现为：进入开播控制台后显示错误（Failed to fetch / 只有返回键），或显示成普通直播间外观（无主播面板、无推流地址、无删除按钮）。
- 用户形容"开播界面显示错误，跳转错误"。

## 根因（确凿，Playwright 网络日志 + 代码链验证）

**前端无限循环：useLiveRoom effect 的 deps 包含 `isOwnerConsole`，而它随 store 的 `current.channel` 进房瞬间翻转，导致 enter/leave 死循环。**

循环链（owner 身份进入开播控制台时）：

1. 挂载 → `useLiveRoom` effect（deps 含 `isOwnerConsole`）→ `liveSessionRuntime.enter(channelId)`
2. `enter()` 内部无条件 `store.clearCurrent()` → `current.channel = null`
3. `LiveStudioPage` 的 `showOwnerPanel = Boolean(channel?.is_owner)` 变 `false` → `isOwnerConsole` 变化
4. effect deps 变化 → cleanup（`detachView → leave()`，再次 `clearCurrent()`）→ setup（`enter()` 再清）
5. 循环：每轮 3 个 API（`channels/{id}/`、`status/`、`danmaku/`）+ WS connect/close
6. 最终浏览器连接池耗尽（`ERR_INSUFFICIENT_RESOURCES`）→ `Failed to fetch` → 错误页；
   WS 反复"closed before the connection is established"（连接尚未建立就被 disconnect.close()）

为什么只有 owner 触发：非 owner 频道的 `is_owner=false` → `showOwnerPanel` 恒 false → deps 不变，不循环。用户 xixi（76 直播中）与 123（127 直播中）均以 owner 身份测试开播控制台 → 必现。

### 回归点

`c78c27f`（2026-09-01，feat(live): 直播适配手机端浮动小窗 任务 05）将 useLiveRoom effect deps
从 `[activityRoute, channelId, ownerConsoleRoute]` 扩展为
`[channelId, activityRoute, ownerConsoleRoute, isNarrow, isOwnerConsole, options.keepLiveActivity]`。

此前的验收（小窗 32 项）测的是普通直播间（isOwnerConsole 恒 false），未暴露；owner 进开播控制台才触发。

### 证据

- Playwright 网络日志：`channels/127/`、`126/` 互相交替、单频道请求数百次
- console：`ERR_INSUFFICIENT_RESOURCES`、`Failed to fetch`（VisibilitySelector 拉群列表也因连接池耗尽失败）
- 修复前页面 URL 在频道间跳动（76→127→126→127…），即用户感知的"跳转错误"

## 修复

### 第一层：useLiveRoom effect deps 死循环（初始进入 / 同频道）

`Ayla/web/src/hooks/useLiveRoom.ts`：

- 将 `isNarrow` / `isOwnerConsole` / `options.keepLiveActivity` 用 ref 持有最新值
  （`isNarrowRef` / `isOwnerConsoleRef` / `keepLiveActivityRef`）
- effect deps 收窄为 `[channelId, activityRoute, ownerConsoleRoute]`（真正的进房/切房键）
- cleanup 的 `detachView` 从 ref 取值（退房时仍按最新 UI 态决定「进小窗 or 完整销毁」）

### 第二层：侧栏切频道整页重挂载竞态（修复第一层后由用户复测暴露）

`Ayla/web/src/components/motion/PageTransition.tsx`：

- `resolvePageKey` 新增 `/live/start/:channelId` → `/live/start` 归一（此前不归一，
  测试特意断言"开播控制台详情不归一"）。原因：pageKey 含 channelId 时侧栏切频道
  （/live/start/:a → /live/start/:b）触发整页重挂载，AnimatePresence(mode="sync")
  新旧两页并存，旧页卸载 cleanup 的 `liveSessionRuntime.leave()` 清掉新页刚建立的
  会话（alive/channelId/clearCurrent/断 WS），新页 `enterAsync` 的 `alive` 检查
  提前 return，`channel` 永不设置 → 界面退化为普通直播间（默认"直播间"标题）、
  `showOwnerPanel=false`（无主播面板/删除按钮）、WS 未连（"弹幕已断开"）、
  `srsStatus` 未设置（"正在查询直播状态…"）。刷新即恢复（无旧页竞争）。
- 同步更新 `src/vitest/page-transition.test.tsx` 断言。切频道不再重挂载页面，effect 因
  channelId 变化在同一组件实例内 cleanup→setup，单例无竞争。

### 第三层：跨页面进入开播控制台竞态（群内进入 / 浮层返回复现）

`Ayla/web/src/runtime/liveSessionRuntime.ts` + `Ayla/web/src/hooks/useLiveRoom.ts`：

- **机制**：`liveSessionRuntime` 是全局单例，而多个页面（LiveStudioPage / LiveRoomPage / GroupLive
  的 LiveRoomBody）的 useLiveRoom 都在 effect cleanup 里无条件 detachView→leave。**页面间切换**
  （群内开播 → 控制台、浮层"返回直播间" → 控制台、普通直播间 → 控制台）时，AnimatePresence
  (mode="sync") 新旧页并存：旧页卸载的 cleanup 的 leave() 会把新页刚建立的会话清掉
  （alive=false / channelId=null / clearCurrent / 断 WS）→ 新页 enterAsync 的 alive 检查
  提前 return → channel 永不设置 → 控制台退化（"直播间"默认标题）+ 无主播面板 + 弹幕断开。
  侧栏切换（同组件 effect 重跑，cleanup 先于 setup）不受影响，所以前两层的修复覆盖不到跨页路径。
- **修复**：liveSessionRuntime 增加**会话代际 epoch**——每次完整 enter 递增并返回；
  detachView/leave 接受调用方持有的 epoch，与当前 epoch 不一致（会话已被更新的 enter 接管）时
  **拒绝销毁**。useLiveRoom effect 持有 enter 返回值并在 cleanup 回传。旧页卸载的 leave(旧 epoch)
  被拒绝，新页会话完整保留。刻意销毁路径（enter 内切频道、关闭小窗、退出登录）不传 epoch，行为不变。
