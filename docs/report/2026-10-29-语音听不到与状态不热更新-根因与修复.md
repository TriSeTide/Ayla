# 语音「听不到 / 状态不更新」根因与修复（2026-10-29）

> 一次性事故与验收记录。稳定行为已落到代码注释与
> [livekit-单udp端口方案.md](./livekit-单udp端口方案.md)；
> 本文件保存**排查过程、每条证据的来源、以及已被证伪的中间结论**，
> 避免同一问题被重复调查。

## 1. 用户实报的现象（全部稳定复现）

| # | 现象 |
|---|---|
| P1 | 电脑端：音频条在跳，但耳机完全没声音 |
| P2 | 手机端：音量是「通话」形态（音量键调通话音量） |
| P3 | 电脑/手机开麦，对方什么都听不到（web 开麦则正常） |
| P4 | Flutter 端头像在线光环、关麦静音状态不跟随 WS 热更新 |

对照：**web 端参与时一切正常**（能发能收、状态实时），只有原生端出问题。
这条对照是后续定位的关键线索 —— 它把嫌疑范围从「服务端/网络」收窄到
「原生端独有的代码路径」。

## 2. 逐条根因

### P1：耳机没声音 —— connect 前那次切设备被 ADM 初始化覆盖

诊断手段：CoreAudio 端点峰值表（`peak_all.ps1`，直接读每个物理端点的
IAudioMeterInformation::GetPeakValue），在远端持续发 440Hz 时采样。

证据（同一台机器、同一次通话）：

| 场景 | 通信端点(Realtek) | 多媒体端点(耳机) |
|---|---|---|
| 生产路径（connect 前切到耳机） | **0.4401** | 0.0001 |
| connect **之后**强制切到耳机 | 0 | **用户当场听到声音** |
| connect **之后**强制切到虚拟声卡 | 0 | VB-Audio 0.3557 |
| 对照：OS 默认播放 440Hz wav | 0 | 0.3663 |

结论：**切换动作本身有效**，但 connect 之前设的那次不生效。
原因（libwebrtc 源码确认）：ADM 的 Windows playout 通道要等首次
startPlayout 才打开，并按**当时的**系统默认（= 默认通信设备）初始化，
把之前那次 `SetPlayoutDevice` 覆盖掉。

所以"已经切过"推不出"正在往那个设备播" —— 原实现里那条
「同名设备就跳过」的幂等守卫正是让后续重切失效的直接原因。

修法：connect 后与首次订阅到远端音频后各**强制重切一次**；
普通开麦/关麦不重复切（避免反复 Stop/Init/Start playout 造成静音抖动）。

### P3：开麦对方听不到 —— 误选到永远静音的虚拟录音设备

根因：flutter_webrtc 的 `GetUserMedia` 在调用方没指定麦克风时，
无条件 `SetRecordingDevice(0)`。ADM 的录制设备枚举顺序就是 Windows
端点枚举顺序，下标 0 完全可能是虚拟回环设备。

本机实测枚举（`cap_list.ps1`）：
```
0 = 内部 AUX 输入 (Steam Streaming Speakers)   ← 永远静音
1 = 麦克风 (MIXLINE Stream)
2 = 耳机 (vivo TWS 3i)
...
=== 系统默认录音端点（多媒体角色）===
麦克风阵列 (Realtek(R) Audio)
```

于是开麦后发出去的全是静音。音频条偶有抖动是因为 VAD/噪声统计还有残余。
**web 端走浏览器自己的选麦逻辑，所以只有它一直正常** —— 与用户观察完全吻合。

修法：
- vendor flutter_webrtc 到 `flutter/third_party/` + dependency_overrides；
- 补丁：不指定采集设备时**不再**硬选下标 0，交给 ADM 用系统默认录音设备；
- Dart 侧发布麦克风前显式选系统默认采集端点（日志可断言）。

验证：日志出现 `采集设备已切到系统默认麦克风: 麦克风阵列 (Realtek(R) Audio)`，
且 `LOCAL tx energy` 由恒为 1.2e-5 变为持续增长。

### P2：手机通话音量 —— 播放轨属性在 ADM 初始化时固定

`AudioManager.setAudioSessionOptions(mediaPlayback)` 只改**会话**
（mode/焦点/外放），改不了**已经建好的播放轨**：WebRTC 的 AudioTrack
属性在 ADM 初始化时固定，flutter_webrtc 只有拿到
`androidAudioConfiguration` 才把 usage/content 传给 JavaAudioDeviceModule，
否则用默认 `USAGE_VOICE_COMMUNICATION`。

修法：在构造第一个 Room **之前**调
`LiveKitClient.initialize(initialAudioSessionOptions: mediaPlayback())`。
保留 MainActivity 的原生兜底（mode/焦点/外放），两者互补。

验证（模拟器 `dumpsys audio` + 音量键）：

| | STREAM_MUSIC | STREAM_VOICE_CALL |
|---|---|---|
| 修前（按 4 次音量-） | 10→10（不变） | 15→1 |
| 修后（按 4 次音量-） | 10→7（生效） | 1→1（不动） |

### P4：光环 / 静音态不热更新 —— 四条独立真因

1. **presence 多连接不感知**：`PresenceConsumer.disconnect()` 无条件
   clear + 广播 offline，不检查同账号是否还有其它活连接。同账号双端并存、
   或重连时旧 socket close 晚到，都会把**仍然活着的新连接**广播成 offline；
   而 `presence.self` 只在建连时发一次，新连接不会自愈 ⇒ 光环一直灰。
   → 改为 Redis 连接集合（引用计数）+ 单连接 TTL 标记；Redis 不可用时
   **绝不广播离线**（无法证明是最后一条就不猜）。
2. **心跳间隔与 web 不一致**（25000 被误写成 15000）→ 改回 25000 + 双向契约测试。
3. **幽灵成员永不清理**：`mark_stale_members_left` 全仓零调用，
   生产频道里仍有 67.9 小时前的成员。→ 新增 `manage.py voice_reap_stale_members`
   （幂等 / --dry-run / 与正常 leave 共用同一广播路径）+ cron 每分钟。
4. **muted/unmuted 服务端根本不存在**：只由各端本地合成、从不广播 ⇒ 跨端必然不同步。
   → 新增 WS `voice.mute` 上报帧，服务端校验后复用既有 `voice.state` 形态广播。

## 3. 已被证伪的中间结论（重要，别再走一遍）

- ❌ **「心跳 15000 是光环失效的原因」** —— A/B 实测：25s 与 15s 各静置 70s
  （> presence TTL 60s），两组都 `still_open=true` 且 ping/pong 正常。
  服务端收到 ping 就 setex 续期，两个值都远小于 60s，**都不会被判死**。
  改回 25000 仍然正确（与 web 同源），但它不是光环失效的根因。
  `ws_manager.dart` 里原先那段因果注释已就地改写。
- ❌ **「切换输出设备 API 不生效」** —— 实测把设备切到虚拟声卡后峰值确实迁移过去
  （VB-Audio 0.3557）。API 有效，问题是**时序**与**幂等守卫**。
- ❌ **「手机端是 AudioSession 配置问题」** —— mediaPlayback 已生效
  （mode=MODE_NORMAL + 焦点 USAGE_MEDIA），但播放轨仍走通话 usage；
  真正的一步是 ADM 初始化参数。

服务器 `~/Elysia/ayla-deploy/backend/Dockerfile` 原本用清华 pypi 源，
自 2026-10-27 起在构建容器内不可用（`Could not find a version that satisfies
the requirement setuptools>=68`）。已改为阿里云源。

### 部署陷阱
`web/dist` 是 bind mount，**替换内容后必须 recreate nginx 容器**
（`docker compose up -d --no-deps --force-recreate nginx`），
否则 403 Forbidden（容器内仍指向旧 inode）。
