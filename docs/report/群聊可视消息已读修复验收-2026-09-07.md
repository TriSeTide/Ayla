# 群聊可视消息已读修复验收（2026-09-07）

## 问题与证据

用户反馈群聊尚有未读时红点被清除，要求与私信一致，看到多少就读多少。
之前的侧栏排序验证没有覆盖真实 `GroupChat` 与 `MessageList` 滚动已读链路；
旧测试反而将“切换子群即整组已读”作为预期。该验证缺口已在上一份排序报告直接更正。

2026-09-07 的浏览器复现使用真实 `GroupChat`、`MessageList`、`ChannelSidebar` 与状态管理，
全部 API 由独立 fixture 模拟，未发送真实消息或写入业务库：

1. 默认组有 10 条未读，序号 21–30；另一子群有 101、102 两条未读。
2. 1440px 视口只有消息 28、29、30 的可见比例达到 60%。
3. 修改前记录到一条无请求体的 `POST /subgroups/s1/read/`，以及三条单消息 exact 请求；
   默认组 21–30 全部成为已读，红点由 10 变 0，实际尚未看到 7 条。另一组仍为 2。

## 根因与修复

- `GroupChat` 进入/切换子群时无条件调用整组已读；普通未读标签回调还丢弃了范围参数，
  再次调用整组接口。现已移除这两条自动批量路径：进入只拉历史，标签只定位，
  消息交给既有 60% 可见观察器逐条 exact 确认。私信既有语义不改。
- 群聊 WS 用“当前在底部”直接推定看过，甚至列表未渲染/历史加载时也可能触发。
  现在群聊与未知会话先入未读，只有明确私信继续既有快捷路径。
- `subgroup.read` 旧回执只有数量，客户端整组清零，重复或迟到回执可能清掉新消息。
  后端响应与广播增加 `marked_seqs`，表示本次固定范围内全部已确认的序号；重试即使
  `marked=0` 仍返回确认范围。前端使用集合减法，同步子群、会话与缓存消息属性。
- 群聊单条 exact 响应额外返回 `subgroup_id`，旧 null 消息解析为真实默认组 ID；
  默认组列表尚未加载也能登记确认。迟到列表/编辑响应保留快照之后的新消息，并过滤
  本账号已经确认的序号；迟到历史将同一确认投影为 `read_by_me=true`。
- 账号退出/身份变更清理子群确认状态，已读异步响应检查发起用户，防止跨账号应用。
  @我/回复标签取当前子群未读交集，未看到的特殊消息与其他子群保持各自未读。

只修改工程逻辑、只读 API 字段和可重建前端状态；没有数据库字段迁移、历史重写、
生产数据修复或备份恢复操作。回退本轮代码会恢复原行为，但不能撤销已经生成的真实已读
回执，因此本轮未尝试给用户历史消息重新制造未读。没有启动、停止或重启用户服务。
