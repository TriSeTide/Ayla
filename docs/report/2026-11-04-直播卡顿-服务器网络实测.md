## 0. 一句话回答

**带宽是主因，但不是唯一原因。** 服务器出口上行「够 1 路、勉强够 2 路、不够 4 路」：
WiFi 空口实测上行天花板 **24.4 Mbps**（设备层，已含全部协议开销），而 4 个 HLS 观众按每客户端各拉一份 3.4 Mbps 需要 **13.9 Mbps 净荷 ≈ 23.6 Mbps 空口**，余量仅 **≈1.03 倍**（即已经打满）。
叠加 WiFi 重传率 **42–61%** 与樱花隧道 p95 **0.76–2.74 s** 的分片取用时延 + Send-Q 峰值 **417 KB** 的队头阻塞，卡顿 = 带宽打满 × 高重传 × 隧道抖动三者相乘，带宽是第一约束。

## 1. 核心结论摘要

| 判定项 | 结论 | 关键数字 |
|---|---|---|
| 出口上行是否够用 | **不够 4 路，够 1–2 路** | 空口天花板 24.4 Mbps；4 路需 23.6 Mbps；余量 ≈1.03× |
| WiFi 是否瓶颈 | **是**，且是「重传吃空口」型瓶颈 | 重传率 42–61%，airtime 仅 13–25% 就已达 24 Mbps 上限 |
| 带宽是否是唯一主因 | **否** | 带宽充足时段（2 观众，6.9 Mbps 出口）仍有 4% 分片 >1 s |
| 樱花隧道是否额外劣化 | **是** | ts p50 0.51 s / p95 0.76 s / max 0.99 s；对照本机 8443 p50 0.009 s |
| 是否 tcpMux 单连接 | **否（多连接池）**，但仍是共享瓶颈 | 到 frps 116.153.47.201:8088 常态 27 条 TCP，单条 Send-Q 峰值 417 KB |
| 丢包 | 良好 | 网关 0/60、0/100 丢包；8.8.8.8 5%/60 → 0%/100 |

### 1.1 判据（任务第 8 项）

- **「带宽不足」成立**：4 观众时实测 HLS 出口仅 3.19 Mbps（应 ≈13.6），12% 分片耗时 >1 s；6 观众时完全拉不动（0 分片成功）。
- **「带宽不是唯一」成立**：2 观众、出口 7.92 Mbps（仅占 24.4 Mbps 上限的 32%）时，仍出现 5/124 = 4% 分片 >1 s，平均分片 0.66 s —— 此时带宽充足，卡顿来自隧道时延与 WiFi 抖动。
- 因此：**卡顿 = 带宽打满（主因）× WiFi 重传（放大器）× 隧道时延抖动（触发器）**。

**重传 42–61% 对有效吞吐的折算**：

```
有效吞吐 = 标称 PHY 速率 × (1 − 重传率) × (1 − 竞争退避损失)
         = 172 Mbit/s × (1 − 0.52) × ~0.9
         ≈ 74 Mbit/s  ← 理论单流有效上限
```

但实测空口只跑到 **24.4 Mbps** 就封顶（airtime 仅 25%），说明**真实约束不是 PHY 速率，而是 CSMA/CA 竞争 + 重传占用的空口时间**：同频 5 个 + 邻道 9 个 AP 在 20 MHz 信道上竞争，每次重传都要重新抢信道。

> 换算：**若重传率从 52% 降到 5%，同样 airtime 可承载的有效吞吐约提升 1.9×**（≈46 Mbps），4 路直播的余量会从 1.06× 回到 ~2×。

## 3. 专项回答：樱花隧道是不是 tcpMux 单连接承载全部流量？

### 3.1 隧道拓扑（实测）

```
frpc.toml (volx, pid 3292376, tcpMux=true)
  ├─ ssh            22   → remote 6020
  ├─ ayla-srs-rtmp  1935 → remote 1935      ← 推流上行（实测走 volx 2101，RX 3.1 Mbps）
  ├─ ayla-live-pull 8443 → remote 7882      ← HLS 备用入口
  └─ mind-sandbox   8200 → remote 8200

樱花 natfrp (pid 2242468, 支持 Sakura Mux)
  └─ 26211 → 本机 127.0.0.1:443 (nginx)
       └─ 443 server block 承载：
            /live/*   HLS（547 次 / 3 min）
            /api/*    API（25 次 / 3 min）
            /ws       WebSocket（7 次 / 3 min）
            /minio/*  MinIO（1 次 / 3 min）
```

**回答**：**是的——26211 这一条隧道入口承载了 HLS + API + WS + MinIO 全部 Web 流量**（nginx 443 一个 server block 全包）。
**但它不是单条 TCP 连接**：frp/natfrp 用连接池，实测到 `116.153.47.201:8088` 常态 **27 条 TCP**（frpc pid 2242468 占 37 条，含其它 proxy）。所以严格说是「**共享同一隧道 + 同一 WiFi 出口的 27 条连接池**」，而非单连接 mux。

### 3.2 队头阻塞证据（`ss -tin` 0.5 s × 30 采样）

| 时刻 | max Send-Q | delivery_rate 波动 | retrans 累计 | rcv_ooopack |
|---|---|---|---|---|
| 22:54:18 | 0 | 18.87 → 5.29 Mbps | 454 | 6 |
| 22:54:20 | **416,394 B** | 14.91 Mbps | 454 | 6 |
| 22:54:22 | **417,312 B** | 22.04 Mbps | 454 | 6 |
| 22:54:23 | **415,996 B** | 11.00 Mbps | 454 | 6 |
| 22:54:24 | 235,636 B | 19.78 Mbps | 454 | 6 |
| 22:54:25 | 326,958 B | 14.58 Mbps | 454 | 6 |
| 22:54:27 | 143,162 B | 12.23 Mbps | 454 | 6 |
| 22:54:28 | 90,388 B | 13.84 Mbps | 454 | 6 |
| 22:54:29–33 | 0 | 5.67 → **49.99** Mbps | 454 | 6 |

**判读**：

1. **Send-Q 在 0 ↔ 417 KB 之间剧烈振荡** —— 这是应用层持续写入、内核发送队列积压再排空的典型形态。417 KB 在 ~13 Mbps 下 ≈ **0.26 s 的排队延迟**，而这只是单条连接；27 条连接共享同一 WiFi 出口时，队头阻塞被放大。
2. **delivery_rate 在 5.29 – 49.99 Mbps 之间摆动（≈9.4 倍）** —— 说明该 socket 的实测送达速率极不稳定，与 §2.5「到网关 41% 包 >20 ms」完全吻合：瓶颈在 WiFi 空口排队，不在 frps。
3. **rcv_ooopack = 6、retrans 累计 454**（104.6 MB 发送量）—— 应用层乱序/重传量级很小，**说明隧道本身不是主要丢包源**；真正的问题是从服务器到 AP 的这一跳。
4. `cwnd` 在 76 ↔ 436 之间大幅摆动，`rtt` 31–68 ms（min 6 ms）—— 典型的「拥塞窗口被空口抖动反复打回」。

> **修正一个常见误判**：frpc.toml 注释里写「tcpMux=true 导致语音与 ssh/推流/拉流共用一条 TCP，任一流突发即队头阻塞（rcv_ooopack 34688）」—— 本次实测 volx 那条路径的 `rcv_ooopack` 已不是问题（累计仅 6），**历史结论在当前拓扑下不再成立**；当前队头阻塞来自 WiFi 空口排队，而非 tcpMux 单连接。

## 4. 风险与缓解（按优先级）

### P0 — 立即执行（不需要改代码）

**R1. 把服务器从 WiFi 切到有线（enP7s7）**
- 现状：`enP7s7` 全 0 计数，**没有插网线**；唯一出口是 20 MHz 的 WiFi，空口天花板 24.4 Mbps。
- 收益：绕过 42–61% 重传、绕过 5 个同频 + 9 个邻道 AP 竞争、绕过 41% 包 >20 ms 的空口排队。有线千兆下 4 路直播（13.6 Mbps）余量 ≈ **70×**。
- 这是**单点收益最大**的改动，且零代码风险。

**R2. 把直播码率从 2560×1440@30 3.0 Mbps 降到 720p/1.5 Mbps（或加 ABR 多档）**
- 现状：1 秒分片 390 KB，单客户端 3.2 Mbps；4 客户端 = 13.6 Mbps，正好卡在 24.4 Mbps 空口上限。
- 收益：1.5 Mbps 时 4 客户端仅 6 Mbps 需求，空口余量 **4×**，且分片变小后对隧道 p95 0.76 s 更耐受。
- 必须与 ABR 一起做：HLS 多码率档位让弱网客户端自动降到低档，而不是所有客户端都吃满 3.2 Mbps。

### P1 — 高优先（配置层，需评审后执行）

**R3. 缩短樱花隧道的分片传输时延**
- 现状：ts 经 26211 p50 0.511 s、p95 0.761 s、劣化时 2.741 s；本机直取仅 0.009 s。
- 措施：① 给 26211 单独一条 frp proxy（不与 /api、/ws、/minio 共享 443 server block），避免小请求被大分片排队；② 关闭 frp `transport.tls.enable`（隧道内再套 TLS 纯属浪费，公网段已有 HTTPS）；③ 客户端启用 HTTP/2 或长连接复用，避免每条连接付 0.29 s TLS 握手。

**R4. 提高 WiFi 发送功率 / 换 40 MHz 或 80 MHz**
- 现状：`txpower 3.00 dBm`（极低），20 MHz 带宽，同频 5 个 AP。
- 措施：`iw dev wlP9s9 set txpower fixed 2000`（20 dBm，需 sudo）可提升 SNR、降低重传；信道宽度若 AP 支持 40/80 MHz，可显著提高空口容量（但需评估与邻道 AP 的干扰权衡）。
- 注意：本机 `sudo` 需要密码，本次**未能验证**调整后的效果。

**R5. 减少 HLS 客户端的分片请求频率**
- 现状：1 秒分片 = 每客户端每秒 1 个 ts + 每 0.5–1 s 1 次 m3u8 轮询。4 客户端 ≈ 8–12 req/s，全部经同一隧道。
- 措施：`hls_fragment` 从 1 s 调到 2 s（减少 50% 请求数，代价是延迟 +1 s），或客户端把 playlist 轮询降到 1×TARGETDURATION。
- 这与「低延迟」目标冲突，需产品决策。

### P2 — 中优先（需进一步验证）

**R6. 处理 volx 路径的严重抖动**
- 现状：volx 7882 取 ts p50 2.048 s、max 7.423 s；volx frps RTT max 589 ms。
- 建议：若 volx 仅作为推流入口（当前实测推流走 volx 2101，RX 3.1 Mbps），可保持；但**不要**把 volx 7882 作为 HLS 备用拉流入口，它比樱花差 4×。

**R7. 关注 cloudflared 隧道与 QQ/ToDesk 的偶发占用**
- 现状：本次 3 分钟窗口内 cloudflared 仅 0.2 KB、QQ/cursor-server 均 <1 KB，**未构成干扰**。
- 建议：保留监控，若后续出现卡顿需复测时，优先看这些进程是否有突发。
