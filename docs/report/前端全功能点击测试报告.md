### #6 语音服务未配置：LiveKit 基础设施 + token 签发 + 协议兼容（2026-08-16 追加）

- **现象**：真实环境进语音房报「语音服务未配置，暂不可用」——join 返回 503；配置与 token 修复后，进房再报「could not establish pc connection」——WebRTC 媒体路径失败。
- **根因（四层）**：
  1. LiveKit 容器未运行（docker-compose 定义了 `livekit` 服务但从未启动）；
  2. `backend/.env` 缺 `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET`，`livekit.issue_token` 抛 `LiveKitNotConfigured` → join 503；
  3. 配置后 token 签发仍崩溃：`livekit-api 1.2.0` 的 `with_ttl()` 需 `datetime.timedelta`，代码传 `int` 秒 → `to_jwt()` TypeError；
  4. **媒体路径失败**（「could not establish pc connection」）：docker-compose 只映射 TCP 7880/7881，**未映射 UDP 媒体端口**（LiveKit 默认 `rtc.portICERange [7882, 7886]/udp`）；且 `--dev` 模式广播的 host 候选是 **Docker 内网 IP `172.18.0.5`**，浏览器（宿主机）无法直达 → ICE 无可用 candidate pair。
- **改动**：
  - `docker-compose.yml`：livekit 镜像 `v1.7` → `v1.13`（v1.7 与 livekit-client 2.21 协议不匹配：客户端 `/rtc/v1` 404 → 降级 `/rtc` 后立即断开；v1.13 走 protocol 17 完全兼容）；
  - `docker-compose.yml`：livekit 端口映射补 **UDP**（`7882-7886:7882-7886/udp`），并挂载 `livekit.yaml` 配置（`command: --config /livekit.yaml`）；
  - **新增 `livekit.yaml`**：`rtc.tcp_port: 7881`、`rtc.port_range_start/end: 7882-7886`、**`rtc.node_ip: 192.168.1.12`**（宿主机局域网 IP，浏览器可直达；换网络需改此值）；
  - `backend/.env`（Git 忽略）：补 `LIVEKIT_API_KEY=devkey`、`LIVEKIT_API_SECRET=devsecret`、`LIVEKIT_WS_URL=ws://127.0.0.1:7880`、`LIVEKIT_TOKEN_TTL_SECONDS=600`；
  - `backend/apps/voice/livekit.py`：`with_ttl(timedelta(seconds=ttl))`；
  - `backend/apps/voice/tests/test_livekit.py`：TTL 断言 `600`/`300` → `timedelta(seconds=...)`。
- **验证**：
  - 后端：`apps/voice/tests` **31 通过**；
  - 真实 API：注册测试用户 → 建频道 → join 返回 200 + token（len 387）+ `ws_url=ws://127.0.0.1:7880`（不再 503）；
  - 真实浏览器（Playwright + 5173 前端 + 8100 后端 + LiveKit v1.13）：livekit-client 2.21 连接成功，服务器日志确认 `protocol: 17` participant 加入房间、PublisherOffer 发出；**UI 显示「媒体已连接」**（房间页成员「在频道中」+ 静音/离开按钮）——媒体链路打通。
  - **结论更正**：早前「headless 浏览器 ICE 必然失败」是**错误归因**——真正根因是 UDP 未映射 + node_ip 广播内网 IP；两者修复后，即使 headless 浏览器媒体连接也成功。

### #7 两个账号同房间都开麦但听不到对方（LiveKit 远端轨道未 attach）

- **现象**：用户两个真实浏览器（两个账号）进同一语音房间、都开了麦，**互相听不到声音**；各自 UI「媒体已连接」、成员「在频道中」、麦已开，但无声音。
- **根因**：`livekit-client` 的 `TrackSubscribed` 事件**只对连接后新订阅的轨道触发**；加入时房间里已存在成员的轨道会被直接放进 `audioTrackPublications`，**不触发 TrackSubscribed**。`web/src/livekit/client.ts` 只在 `TrackSubscribed` 里 `attach()` → **先进房者已开麦的轨道永远不会被 attach → 后进房者听不到他**（依赖实际事件顺序，两个窗口可能互相都听不到）。诊断证据：独立 Room 连接后 `remoteParticipants` 能看到已发布 audio track（`kind: audio, muted: false`），但 `TrackSubscribed` 事件一个都没触发，`#ayla-voice-audio` 容器始终不存在。
- **改动**：`web/src/livekit/client.ts` `createLiveKitRoom` 新增 `attachExistingRemoteAudio()` —— `connect()` 成功后遍历 `room.remoteParticipants` 的 `audioTrackPublications`，对 audio 轨道 `attach()` 补齐（`TrackSubscribed` 只覆盖新订阅）；保留原 TrackSubscribed/TrackUnsubscribed 处理。
- **验证**：
  - 新增契约测试 `web/src/vitest/create-livekit-room.test.ts`（5 例，mock livekit-client）：连接后 attach 已存在轨道 / TrackSubscribed 新轨道 attach / 视频不 attach / 退订 detach / 连接失败抛错；
  - `tsc --noEmit` 无错；livekit 相关 vitest **30 通过**；
  - 双会话实测（Playwright 两个 tab，voice_user_b + voice_test_user 同房间）：后进房者 `#ayla-voice-audio` 容器 **2 个音频元素正在播放**（`src:true, vol:1, muted:false, paused:false`，含先进房者开麦轨道）；先进房者 **1 个正在播放**（含后进房者轨道）——**双向可听**。修复前该容器不存在（audioCount 0）。
