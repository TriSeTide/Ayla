# 直播在 App 端无法播放（web 正常）—— 根因与修复

> 2026-10-18 用户实报：把流推到直播后「手机 / 电脑 App 不能正常播放，
> 但 web `https://s.ayla.trise.top:26211/live/2` 正常」。
> 截图证据：播放器区域纯黑 + 屏幕中央一个白色 `U` 形转圈，无任何文案、永不结束。

---

## 1. 复现与定位（实测，非推断）

### 1.1 先证明流本身没问题

```bash
# 后端容器内直接序列化频道 2（线上真实数据）
{"id": 2, "title": "test", "status": "live",
 "hls_url": "https://live.trise.top:7882/live/be86d4a1….m3u8",
 "flv_url": "https://live.trise.top:7882/live/be86d4a1….flv"}

# SRS 侧流是活的（H264 High 1920×1080 + AAC 44.1k）
curl -s http://127.0.0.1:1985/api/v1/streams/   # publish.active=true, frames 持续增长
```

服务器本机经 nginx 8443 → SRS 8089 取 m3u8 / 变体 / ts 分片全部 200 且分片有效。

### 1.2 App 侧失败点：TLS 握手被重置

用 **App 真正使用的播放内核**（media_kit → mpv → ffmpeg/mbedTLS）直接打该 URL：

```
ffmpeg: tcp: Successfully connected to 47.108.85.223 port 7882
ffmpeg: tcp: ffurl_read returned 0xffffd8ba
ffmpeg: tls: mbedtls_ssl_handshake returned -0x4e
stream: Failed to open https://live.trise.top:7882/live/<key>.m3u8
```

- TCP 能连上 ⇒ 不是 DNS / 安全组 / frp 隧道没通；
- **TLS 阶段被对端重置**（`-0x4e` = `MBEDTLS_ERR_SSL_CONN_EOF`）；
- 同一台机器 `openssl s_client` 有时能过、有时被重置；连续 24 次采样全部失败，
  且 TLS1.2 / TLS1.3 / 带 ALPN 都试过 —— 属于**链路上中间设备对非标准端口的
  TLS 强干扰**，不是证书问题（证书链完整、SAN 覆盖 `*.trise.top`）。
- 浏览器走 BoringSSL/系统栈能过 ⇒ 所以 **web 一直正常，只有 App 挂**。

### 1.3 决定性验证：同源地址能播

给 nginx 的 443 / 8080 两个 server 块加 `/live/` 反代到 SRS 后，
再用同一个 mpv 打**应用同源**地址：

```
ffmpeg/demuxer: hls: Opening 'https://s.ayla.trise.top:26211/live/<key>.m3u8?hls_ctx=…'
ffmpeg/demuxer: hls: Opening 'https://s.ayla.trise.top:26211/live/<key>-150.ts?hls_ctx=…'
[final] state=true buffering=false pos=0:00:23.79 dur=0:00:50.09
```

⇒ 位置持续推进到 23.8s、分片连续加载，**同一个播放器、同一个流，只要换成同源就正常**。

## 2. 第二个缺陷：为什么会「永远转圈」而不是报错

修好地址之前，用户看到的是一个**不会结束的加载动画**。这是播放器状态机的三个 bug：

| # | Bug | 后果 |
| --- | --- | --- |
| 1 | `playing=true` 被当作「已恢复」并取消卡顿计时器 | mpv 在「连上但无数据」时 `playing` **也是 true** ⇒ 计时器被立刻取消，永不重建、永不报错 |
| 2 | 卡顿计时器在 4s 重建冷却期内命中时**只 `return`，不重排** | 计时器被置空后不再启动 ⇒ 之后永远不再检查 ⇒ 永久卡在转圈 |
| 3 | 自动重建**没有次数上限** | 即使真的重建，也是每 2s 重建一次的死循环，UI 永远停在 loading |

另外 `media_kit` 的 `Video` 组件**默认挂内置控制条**，其中含缓冲时的大号白色
`CircularProgressIndicator` —— 截图里那个白色 `U` 形圈就是它（不是 Ayla 画的）。
它与 Ayla 自己的悬浮控件（左下刷新 / 右下全屏）重复，且让「加载中」看起来像卡死。
web 侧 `<video>` 不带 `controls`，Flutter 侧本应同样只交出画面。

## 3. 修复清单

### 3.1 播放地址归一到 API 同源

`flutter/lib/core/net/live_play_url.dart`（新增）
- 规则：只重写 `/live/<name>.m3u8|flv|ts`，保留 query（SRS 的 `hls_ctx` 是播放会话上下文）；
- 只在**显式注入** `--dart-define=AYLA_API_BASE=…` 时生效：本地开发没有 `/live/` 反代，
  重写会把能播的地址改坏；
- 已经同源 ⇒ 原样返回；非直播路径（VOD / 媒体接口 / 相对路径）⇒ 一律不动。

接线点（**两处都做**，防注入快照绕过）：
- `widgets/live/live_channel_snapshot.dart` 的 `fromJson` → `hlsUrl` / `flvUrl`；
- `pages/live_support.dart` 的 `_attachPlayer()` / `retryPlayer()`（attach 前再兜一次）。

服务端（`deploy/examples/nginx.conf.example` + 线上 `/etc/nginx/conf.d/default.conf`）：
在 **443 与 8080 两个 server 块**加

```nginx
location ~ ^/live/.+\.(m3u8|flv|ts)$ {
    proxy_pass https://127.0.0.1:8089;
    proxy_ssl_verify off;
    proxy_set_header Host $host;
    http_version 1.1;                # 实为 proxy_http_version 1.1
    proxy_buffering off;
    proxy_read_timeout 86400s;
}
```

> 后端 `SRS_PLAY_URL` **不需要改**：它仍是独立拉流入口的绝对地址，
> 归一发生在客户端（这样 web 侧行为与既有部署完全不变，回滚只需回滚 App）。

### 3.2 状态机（`flutter/lib/player/hls_player.dart`）

- 新增 `HlsPlatformPlayer.onPosition`：**位置真的前进**才算起播（`_markStarted()`）；
  `playing` 不再触发 `onResume`（只有「已起播 + playing」才恢复）；
- 冷却期命中 ⇒ **重排**一个冷却窗口后再试，不再静默放弃；
- 连续自动重建封顶 `kMaxAutoRebuilds = 2`，超限 ⇒ `onError` ⇒ UI 显示
  「播放失败 + 重试」；用户点重试走 `retry()`，**重置计数**（人手重试不设上限）；
- 自愈参数（`stallTimeout` / `rebuildCooldown` / `maxAutoRebuilds`）可注入，测试用毫秒级。

两平台实现都上报位置：

| 平台 | 位置来源 |
| --- | --- |
| Windows（media_kit/mpv） | `player.stream.position` |
| Android/iOS（video_player） | `controller.value.position` 变化时 |

### 3.3 去掉 media_kit 内置控制条

`flutter/lib/player/platforms/media_kit_impl.dart`：

```dart
return Video(controller: vc, controls: NoVideoControls);
```

`NoVideoControls` 是 media_kit 官方的「无控件」常量（= `null`），必须**显式传**，
否则默认是 `AdaptiveVideoControls`。
