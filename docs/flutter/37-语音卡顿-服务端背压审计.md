### 2.5 channels_redis 的丢帧是**逐 key 静默丢弃**

版本（容器内实测）：

```bash
$ docker exec ayla-backend sh -c 'pip list 2>/dev/null | grep -iE "channels|daphne|redis"'
channels                      4.3.2
channels_redis                4.3.0
daphne                        4.2.3

redis                         5.3.1
```

`group_send` 的 Lua（`/usr/local/lib/python3.11/site-packages/channels_redis/core.py:544–584`）：

```lua
local over_capacity = 0
local current_time = ARGV[#ARGV - 1]
local expiry = ARGV[#ARGV]
for i=1,#KEYS do
    if redis.call('ZCOUNT', KEYS[i], '-inf', '+inf') < tonumber(ARGV[i + #KEYS]) then
        redis.call('ZADD', KEYS[i], current_time, ARGV[i])
        redis.call('EXPIRE', KEYS[i], expiry)
    else
        over_capacity = over_capacity + 1
    end
end
return over_capacity
```

```python
if channels_over_capacity > 0:
    logger.info(
        "%s of %s channels over capacity in group %s",
        channels_over_capacity,
        len(channel_names),
        group,
    )
```

**三个必须读准的细节**（这是本节最重要的一段）：

1. **判定粒度是 redis key，不是 channel**；
2. 日志**分母是 channel 数**（`len(channel_names)`），**分子是 key 数** —— **两者量纲不同**；
3. `else` 分支**只计数、不抛异常、不通知任何人** ⇒ 丢帧完全静默。

**而 key 是把「同一进程的所有 channel」合并的**：

```text
$ docker exec ayla-backend python -c "..."
group voice_audio_3    -> redis key asgi:group:voice_audio_3
channel 示例：specific.<client_prefix>!<uuid4>
  non_local_name('specific.abc!def') = 'specific.abc!'
  channel redis key = 'asgispecific.abc!'
```

⇒ **一个 daphne 进程在同一 group 里只占 1 个 redis key**（`client_prefix` 每进程随机生成一次）。
⇒ 日志里的「5 channels」若**只来自 2 个进程生命周期**，就只有 **2 个 key** ⇒ 最多只能报「**2 of 5**」。

**这与现场完全吻合**（下节）。

### 2.7 复现实验：完整复刻出生产日志的「2 of 5」

用**隔离前缀** `auditprobe__`（**不碰生产 `asgi*` 键**）在容器内做参数扫描：

```text
复现目标：生产日志里的 '2 of 5 channels over capacity in group voice_audio_3'

1 个活进程(1连接) + 1 个死进程遗留        channels=2  keys=2  ->  1 of 2 channels over capacity in group voice_audio_3
1 个活进程(2连接) + 1 个死进程遗留        channels=3  keys=2  ->  1 of 3 channels over capacity in group voice_audio_3
1 个活进程(2连接) + 2 个死进程遗留 <=生产  channels=4  keys=3  ->  2 of 4 channels over capacity in group voice_audio_3
1 个活进程(2连接) + 3 个死进程遗留        channels=5  keys=4  ->  3 of 5 channels over capacity in group voice_audio_3
```

结合 §2.6 的现场构成（**2 个在线 channel ∈ 当前进程 1 个 key；3 个死 channel ∈ 2 个死 key**
⇒ channels=5、keys=3、其中 **2 个 key 打满**）：

> **`2 of 5 channels over capacity in group voice_audio_3` 被完整解释：
> 5 个 channel 分布在 3 个 key 上，其中 2 个是「永不排空的死进程 key」，同时处于打满状态。**

单 key 打满的过程（死 key 永不 BRPOP）：

```text
模拟：一个永不排空的 key（等价于进程已死的 group 成员），按 50fps 灌入音频帧
capacity=100  expiry=60
  帧 0    ZCARD=1     TTL=60    丢帧=False
  帧 50   ZCARD=51    TTL=60    丢帧=False
  帧 99   ZCARD=100   TTL=60    丢帧=False
  >>> 第 100 帧开始丢（= 2.0 s 音频），当时 ZCARD=100
  帧 100  ZCARD=100   TTL=60    丢帧=True
  帧 399  ZCARD=100   TTL=53    丢帧=True
```

⇒ **只要 2 秒的连续说话，一个死 key 就打满 100 帧，此后每帧都丢、每帧都打一条 INFO 日志。**
这解释了为什么日志是 **20ms 一条**、以及为什么是 **510 条**这个量级。

## 三、根因链（一句话 + 逐环证据）

> **一句话根因**：**redis 与 backend 生命周期解耦，导致 group 里沉淀了多代已死 daphne 进程的
> channel 成员；`group_expiry=24h` 使它们长期不朽，而 `group_send` 对每个成员 key 都要写一份、
> 死 key 2 秒即打满 `capacity=100` 并在其后每帧静默丢弃 —— 于是产生大量 `over capacity` 日志，
> 并使每帧的 Redis 扇出成本随历史重启次数线性膨胀。**

| # | 环节 | 证据 |
|---|---|---|
| 1 | redis 容器 8 天、backend 7 小时，重启不清 group | §2.1 `docker ps` / `inspect` |
| 2 | 单 daphne 进程，进程内 `_ROOMS` 可信 | §2.2 `/proc` 命令行、Threads=4、Listen 仅 1 次 |
| 3 | group 里 3 个成员，prefix 全 ≠ 当前进程 | §2.6 `distinct client_prefix` 与被删成员对照 |
| 4 | 死成员 24h 不回收 | §2.6 `group_expiry= 86400` + `core.py:517` |
| 5 | 每帧写一份到每个 key，死 key 无消费者 | §2.5 Lua、`_map_channel_keys_to_connection` 按 `non_local_name` 合键 |
| 6 | 打满后**静默**丢弃（只 `logger.info`） | §2.5 Lua 的 `else over_capacity+=1` |
| 7 | 2 秒即打满 ⇒ 20ms/条日志、510 条量级 | §2.7 单 key 灌入实验 |
| 8 | `2 of 5` 的分子/分母量纲 | §2.5 + §2.7 参数扫描 |

### 3.1 ⚠️ 必须更正的一条推论（不能把日志当成用户丢帧）

任务背景里写的是「**任一客户端 socket 变慢 → 该连接 Redis 队列积压 → 音频帧被丢 → 断续**」。
**这条链在本案的证据下不成立，必须更正**：

- Lua 是 **逐 key** 判定。**当前进程的 key 有自己的 BRPOP 消费者在跑**（每个 WebSocket
  consumer 都在 `await_many_dispatch([receive, channel_receive])` 里循环 `receive()`），
  ⇒ 只要消费侧不长时间停顿，**在线 key 的 ZCARD 会保持在低位，不会被丢**；
- 因此 `over capacity` 的 **475 条「2 of 5」中被丢的是死 key**，不是发给在线客户端的帧；
- **「慢客户端」确实会制造背压，但背压的落点是 `BoundedQueue`（进程内 receive_buffer）**，
  不是这里的 group key：

```python
class BoundedQueue(asyncio.Queue):
    def put_nowait(self, item):
        if self.full():
            # ... it's better to drop messages that exceed the channel layer capacity
            #     than to continue to malloc() forever
            self.get_nowait()          # 丢最旧
        return super(BoundedQueue, self).put_nowait(item)
```
（`core.py:62–72`，容量同为 `self.capacity`=100）

⇒ **在线侧的真实丢帧路径是 `receive_buffer` 打满**，它和 group 的 `over capacity` 是
**两条不同的丢弃点**，不能混为一谈。

**所以本文的立场是**：这些日志是**链路异常与结构性缺陷的强指标**（必须修），
但**不能直接当作「用户听到的断续」的证据**。用户听感的归因见 §五 §5.7。

## 四、影响面

### 4.1 确认受影响（有证据）

| 面 | 影响 | 量级 |
|---|---|---|
| **Redis 扇出成本** | 每帧对 **每个 key** 做 zremrangebyscore + ZCOUNT + ZADD + EXPIRE | 实测 5 成员/3 key：**median 1.15ms / p95 2.16ms / max 3.29ms** 每帧 ⇒ @50fps ≈ **58ms CPU/秒/每说话人**（单核 5.8%） |
| **成本随重启线性膨胀** | key 数 = 历史进程代数（24h 窗口内），不随在线人数 | 当前 2 代死 prefix 已在；若 24h 内重启 5 次 ⇒ 5 个死 key/帧 |
| **日志污染** | 每丢一帧一条 INFO | **510 条/19 分钟**，且淹没真正有用的语音日志 |
| **监控失真** | `over capacity` 看着像「实时过载」，实际是「历史残留」 | 会把排查引向「加容量/买带宽」的错误方向 |
| **group 成员表语义污染** | `voice_chan_3` 同样沉积（`voice_catalog` 已 6 个全死成员） | 状态广播也走同一条路 |

### 4.2 真实存在、但**本案例未证实**（不能写成已发生）

| 面 | 机制 | 为什么未证实 |
|---|---|---|
| **在线 key 被打满** | 消费循环停顿 > 2s 即打满 | 需要事件循环被长任务占住。**风险真实**：见 §4.3 |
| **客户端抖动缓冲不足** | 见 §5.7 | 已由另两位同事处理，本文不重复 |
| **frp 抖动/丢包** | 见 §5.6 | 无用户侧 RTT/丢包采样 |

### 4.3 一条被实测出来的隐患：每帧都踩全进程共用的 DB 线程

`channels` 的 consumer 每分派一条消息就 `await aclose_old_connections()`：

```python
# channels/db.py:22
async def aclose_old_connections():
    return await sync_to_async(close_old_connections)()
```

`sync_to_async` 默认 `thread_sensitive=True` ⇒ 落到 asgiref **全进程唯一的单线程执行器**
（`asgiref/sync.py:409` 的 `single_thread_executor = ThreadPoolExecutor(max_workers=1)`）。
**语音每 20ms 一帧 ⇒ 每个说话人每秒 50 次 `await` 这个钩子**，与**全进程所有 DB 工作抢同一个线程**。

实测（容器内）：

```text
BASELINE aclose_old_connections: median=0.046ms p95=0.062ms
WHILE 250ms DB query holds the thread: median=0.3ms max=260.0ms
```

⇒ **一旦有 250ms 的慢查询/写库，所有帧的分派都会被顶到最多 260ms**；
若这类停顿密集出现，在线 key 就可能在 2 秒内被打满 —— **那时才真的丢在线音频**。
这是一条**结构性风险**，不是本次日志的成因，但必须登记。

### 5.1 【P0】一次性清理死 group 成员（运维）

现状：`voice_audio_3` / `voice_chan_3` / `voice_catalog` 都有死成员。

建议做法（**择一，均需用户批准后执行**）：
1. **最稳**：`redis-cli` 对 `asgi:group:<group>` 做 `ZREMRANGEBYSCORE`，只删**当前进程
   `client_prefix` 之外**的成员；
2. 次稳：`DEL` 掉这几个 group 键，等在线连接自然 `group_add` 回来
   （**代价：正在连的 WS 会有一段时间收不到广播**，需在无人语音时做）；
3. 激进：`FLUSHDB` —— **禁止**，会波及 presence/限流等全部缓存。

- **风险**：误删在线成员 ⇒ 该连接静默收不到音频（**表现为「听不见」，且客户端无感**）。
- **回滚**：无状态可回滚；在线连接重新 `group_add` 即恢复；必要时让客户端重连。
- **注意**：`redis` 有密码，命令需在容器内用 `REDIS_URL` 的凭据（**本文不记录凭据**，已 <REDACTED>）。

### 5.2 【P0】让「进程死亡」不再留渣（代码建议，未实施）

- **根因不是 capacity 太小，而是成员不会被及时摘除**。三个候选：
  1. `audio_consumer.disconnect()` 已在做 `group_discard`（`audio_consumer.py:128`），
     但**进程被 kill / 容器重启时根本不会执行** ⇒ 靠它兜不住；
  2. **缩短 `group_expiry`**（见 5.3）是「容忍侧」修法；
  3. **根治侧**：把音频 group 的成员维护挪到「带心跳的 Redis Hash」（`audio_relay.py:19–24`
     注释里已写明这是横向扩展时该做的事），`group_send` 前先过滤掉心跳超期的成员。
     **代价**：要改 `audio_relay` + `audio_consumer`，并补契约测试。

### 5.3 【P1】显式 `capacity` / `expiry` / `group_expiry`

现状（`config/settings.py:98–105`）**只有 `hosts`**，其余全是库默认：

```python
CHANNEL_LAYERS = {
    "default": {
        "BACKEND": "channels_redis.core.RedisChannelLayer",
        "CONFIG": {"hosts": [REDIS_URL]},
    }
}
```

建议（**未实施**）显式化，例如：

```python
"CONFIG": {
    "hosts": [REDIS_URL],
    "capacity": 100,          # 每 key 上限（帧数）
    "expiry": 60,             # 消息存活秒数（当前默认）
    "group_expiry": 3600,     # ← 从 86400 降到 1h，显著缩短死成员残留窗口
}
```

**逐项权衡**：

| 参数 | 调大 | 调小 |
|---|---|---|
| `capacity` | 能容忍更长停顿，但**积压延迟更久**（100 帧=2s 已是语音不可接受值）⇒ **不建议调大** | 更快丢弃、延迟更短，但**更容易丢** ⇒ 对「死 key」无意义（反正没人收），对「在线 key」更快丢 ⇒ **不建议调小** |
| `expiry` | 消息滞留更久，重连后可能听到**2 秒前的旧音频** | 更快过期；**会缩短死 key 从打满到自然过期的恢复时间** ⇒ 可考虑 30s |
| `group_expiry` | 死成员存更久 ⇒ **成本更高** | 死成员更快回收；**但长时间静音的在线的用户也会被摘掉**，**风险：静音用户可能被踢出组而收不到广播** |

- **⚠️ 关键判断**：**调 `capacity` 治不了本案** —— 因为被丢的是**死 key**，
  它们永远排不空，调多大都会被打满，只是打满时间从 2s 变成 Ns。
  **真正有效的是 `group_expiry` 与 §5.2。**
- **风险**：`group_expiry` 调小会让「长时间不说话但在线」的连接被摘除；
  `channels_redis` 只在 `group_add` 时刷新分数，**没有心跳续期机制** ⇒
  **必须同时确认客户端有周期性重新 `group_add` 的路径，否则会漏广播**。
  （当前客户端只有应用层 `ping` 25s，**不会触发 `group_add`** ⇒ **这一条有真实回归风险，必须先验证**。）
- **回滚**：改回 settings 默认值并重启 daphne；无数据迁移，无不可逆操作。

### 5.4 【P2】音频帧绕开 `group_send` 的可行性与代价

**现状链路**（`audio_consumer.py:154–168`）：

```python
async def _handle_audio(self, payload: bytes):
    slot = await audio_relay.may_relay(self.channel_id, self.channel_name)
    if slot is None:
        return
    await self.channel_layer.group_send(
        self.room_group,
        {"type": "relay.audio", "sender": self.channel_name, "slot": slot, "payload": payload},
    )
```

每帧路径：**发送方 consumer → Redis（写 N 个 key）→ 接收方 consumer 的 BRPOP → 再 `send()` 到 socket**。

**问题**：① 多一次进程内外的往返（实测 ~1.15ms/帧/3key）；② 帧在 Redis 里排队，
天然引入「队列深度 = 延迟」的耦合；③ group 语义（广播给所有人）与音频语义（发给除自己外的 N-1 人）**不匹配**，
只能靠 `relay_audio()` 里 `sender == self.channel_name` 再过滤一次。

**候选方案 B1：服务端直接持 socket 引用，绕开 channel layer**
- 做法：`audio_relay.Room` 里存 **`channel_name` → 本进程 consumer 的 send 回调**，
  转发时直接遍历成员 `await consumer.send(bytes_data=...)`。
- **可行性**：**技术上可行**，因为 §2.2 已证实**单 daphne 进程**、`_ROOMS` 本就只在进程内有效
  （`audio_relay.py:19–24` 明确写了这个前提）。
- **代价 / 风险**：
  - **牺牲横向扩展**（现在是「本来就不能扩」，所以是**显式化既有约束**）；
  - consumer 实例的生命周期与 `disconnect` 必须严格配对，否则会持有僵尸引用（**比死 key 更难排**）；
  - `send()` 是**同步写 Twisted 缓冲区**，慢客户端会**直接顶爆内存**（见下）；
  - 需新增契约测试覆盖：并发 `send`、断连瞬间、背压。
- **结论**：**可以做，但不是本轮该做的**。收益（省 ~1.15ms/帧）远小于风险。

**候选方案 B2：保留 channel layer，但只发给「活」连接（`send()` 到 specific channel）**
- 用 `channel_layer.send(channel_name, ...)` 逐成员单发，替掉 `group_send`。
- **代价**：**每帧 N 次 Redis 往返**（比现在 N 个 key 更差）⇒ **明确不推荐**。

**⭐ 必须登记的硬约束：daphne/Twisted 的 WS 写路径没有背压**

```python
# twisted/internet/abstract.py:366
def write(self, data: bytes) -> None:
    ...
    self._tempDataBuffer.append(data)
    self._tempDataLen += len(data)
    self._maybePauseProducer()      # 只有注册过 streaming producer 才会 pause
    self.startWriting()

# _maybePauseProducer:354
if self.producer is not None and self.streamingProducer:   # ← daphne 不注册 producer
    if self._isSendBufferFull():
        self.producerPaused = True
        self.producer.pauseProducing()
```

⇒ `_tempDataBuffer` **无上限增长**。**任何「服务端直写 socket」的方案（B1）都必须自己实现
「该客户端积压超过 X 就丢帧/断开」**，否则慢客户端会把 daphne 内存吃光。
（也说明：**当前走 Redis 反而是有背压的** —— 这正是 `over capacity` 存在的原因；
「绕开 group_send」并不是单纯的减法。）

### 5.5 【P3】nginx `/ws/` 的 `proxy_buffering`：**实测不是主因**

容器内 `/etc/nginx/conf.d/default.conf` 的 `/ws/` 块（`443` 与 `8080` 两个 server 都有）：

```nginx
location /ws/ {
    proxy_pass http://ayla_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    ...
    proxy_read_timeout 86400s;
    proxy_send_timeout 86400s;
}
```

对照：同文件的 `/minio/` 与 `/live/` **显式写了 `proxy_buffering off`**，`/ws/` **没有**。

**判断**：
- 一旦握手返回 **101 + `Connection: upgrade`**，nginx 就切到**隧道模式**，
  `proxy_buffering` 只作用于 **HTTP 响应体**，**对升级后的 WS 帧不生效**
  ⇒ **不应把它列为本轮卡顿的成因**；
- 现场 nginx 访问日志也确实看到 `101`（见 §5.7 的 `101 56201` 等行），说明升级成功；
- **但**：为了**消除歧义与配置不一致**，建议在 `/ws/` 块补 `proxy_buffering off;`。
  **收益预期接近 0**，属于「顺手对齐」，**不要把它当作修复**。
- **风险**：极低；**回滚**：删掉该行 `nginx -s reload`。

### 5.7 【必读】客户端缺抖动缓冲 × 服务端**在线**丢帧 = **叠加**，不是替代

> 下面的「服务端丢帧」指的是**命中在线 key** 的那种丢帧（§4.3 的停顿场景），
> **不是**本轮日志里那些打在死 key 上的丢弃（§3.1）。两者不能混用。

现场 nginx 访问日志（**UTC**，+8 才是 CST；token 已 <REDACTED>）显示 WS 连接是**短命**的：

```text
UTC 26/Oct/2026:18:43:23 = CST 02:43:23   bytes=1915
UTC 26/Oct/2026:18:45:50 = CST 02:45:50   bytes=85      (相隔 0:02:27)
UTC 26/Oct/2026:18:56:10 = CST 02:56:10   bytes=3850    (相隔 0:10:20)
UTC 26/Oct/2026:19:01:27 = CST 03:01:27   bytes=124     (相隔 0:05:17)
UTC 26/Oct/2026:19:16:52 = CST 03:16:52   bytes=7703    (相隔 0:15:25)
UTC 26/Oct/2026:19:18:36 = CST 03:18:36   bytes=56201   (相隔 0:01:44)
UTC 26/Oct/2026:19:21:20 = CST 03:21:20   bytes=44752   (相隔 0:02:44)
UTC 26/Oct/2026:19:21:56 = CST 03:21:56   bytes=344     (相隔 0:00:36)
```

（`$body_bytes_sent` 对 WS 是整个连接生命周期写出的字节数。）

**两条结论**：
1. **03:01:27 / 03:16:52 / 03:18:36 / 03:21:20 / 03:21:56 与 backend 的 join/leave 一一对齐**
   ⇒ 用户在这 20 分钟里**反复进出房间 / 连接反复重建**。频繁重建本身就意味着**每次都要重新
   填抖动缓冲**，听感上就是「一开口就断」。
2. **服务端（在线 key）丢帧与客户端无抖动缓冲是叠加关系，不是二选一**：
   - **服务端丢帧**（帧被 Lua 判超容量丢弃，或 `BoundedQueue` 打满）⇒ 音频流**出现空洞**，是「**内容缺失**」；
   - **客户端无抖动缓冲** ⇒ 空洞前后到达的帧**被紧挨着播放**，听成「**咔哒/断续**」，是「**时序错乱**」；
   - 空洞会被抖动缓冲**放大成可听见的爆音**（没有缓冲时，丢一帧 = 直接跳变）；
   - 反之，抖动缓冲再大也**补不回丢失的帧**（Opus 无 PLC 深恢复）。
   ⇒ **两者都要治，但优先级不同**：客户端抖动缓冲/编解码**已由另两位同事处理**（本任务不重复），
   服务端这块按 §5.1/§5.2 清理 + §5.3 显式配置。
   ⚠️ **但请注意强度差异**：本轮审计**只证实了死 key 丢帧**（§3.1），
   **尚未证实在线 key 丢帧真实发生过** —— 它属于 §4.3 登记的**风险**，
   而非已发生的事实。所以「服务端是用户卡顿的主因」这句话**目前没有证据支持**。

### 6.1 审计过程中对「任务前提」的更正（已在本文件内直接改写，不保留旧说法）

- 任务背景：「任一客户端 socket 变慢 → 该连接 Redis 队列积压 → 音频帧被丢 → 断续」。
  **更正为**：本案日志里的丢帧是**发给已死进程 key** 的，**不是发给在线客户端**的；
  在线客户端的真实丢帧点是 `BoundedQueue`（§3.1）。两者成因与修法都不同。
- 任务背景暗示「调 capacity 可解」。**更正为**：**调 `capacity` 治不了本案**（§5.3），
  因为死 key 永远排不空，调多大都会被打满，只是打满耗时变化。
