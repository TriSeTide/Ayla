# Windows 自绘标题栏与默认最大化 —— 实现与验收

> 日期：2026-11-04　范围：`Ayla/flutter` 的 **Windows 桌面端**（未改 Web / 移动端）
> 需求（用户原话）：「把 windows 窗口原生顶部标题栏去掉，改成 Ayla 专属的美观的融入的标题栏。
> Ayla 启动默认最大化，标题栏要有最小化、窗口化、关闭」

## 2. 为什么原生侧必须动 C++（客户区 = 整个窗口）

`Win32Window::MessageHandler` 是**消息终点**：`FlutterViewController::HandleTopLevelWindowProc`
在 `FlutterWindow::MessageHandler` 里被调用，它把消息分发给 `WindowProcDelegateManager`
（`host_window.cc` 的 `HandleMessage` → `engine_->window_proc_delegate_manager()->OnTopLevelWindowProc`）。
所以改 `Win32Window::MessageHandler` 拦不到 `WM_NCCALCSIZE` —— 必须在 `FlutterWindow::MessageHandler`
**转发给引擎之前**处理，否则 window_manager 的 delegate 会抢先接管（它在直播全屏时用
`adjustNCCALCSIZE` 把客户区**再**撑大一个边框厚度，Flutter 视图会比窗口还大）。

### 2.1 WM_NCCALCSIZE → 返回 0

客户区 = 整个窗口 ⇒ 没有 caption、没有边框。两个必须处理的细节：

- **最大化时 Windows 会把窗口尺寸做成「工作区 + 不可见边框厚度」**。原样 return 0 会让 UI 的
  右边/下边被推出屏幕、左边/上边留一条等宽空隙 ⇒ 在 `IsZoomed` 时把 `rgrc[0]` 直接对齐 `rcWork`。
  这个补偿必须发生在**同一条** NCCALCSIZE 里，因为引擎收到 `WM_SIZE` 时会按客户区重排视图。
- **`wparam == FALSE` 的变体也要应答**（带 `RECT` 而非 `NCCALCSIZE_PARAMS`），否则从最大化
  还原的那一瞬间会闪一次系统 caption。

### 2.2 WM_NCHITTEST → 手工给缩放边

没有非客户区 ⇒ Windows 不再提供任何缩放边。`HitTestFrame` 按
`SM_CXSIZEFRAME + SM_CXPADDEDBORDER`（`GetSystemMetricsForDpi`，逐显示器正确）算出带宽，
按八向返回 `HTTOP/HTBOTTOM/HTLEFT/HTRIGHT/HTxxxCORNER`；最大化与全屏时一律 `HTCLIENT`。

> ⚠️ **这条原生边界在实际使用中基本不会触发**，原因写在下一节；它是兜底而不是主路径。

### 2.3 为什么缩放最终由 Dart 承担（本次调查的关键结论）

引擎的 Flutter 视图是一个 **`WS_CHILD` 子窗口**，铺满客户区
（`host_window.cc` 的 `SetChildContent`：`SetParent(content, window)` + 按客户区 `MoveWindow`）。
Windows 命中测试**先问子窗口**，子窗口过程对自身表面上的点一律返回 `HTCLIENT`，
而 `HTCLIENT` **终止**命中搜索 ⇒ 顶层窗口的 `WM_NCHITTEST` 对手持指针落点根本不被调用。

⇒ 缩放只能在指针事件真正到达的那一层做。落地为 `AylaResizeEdges`
（`windowManager.startResizing` → `WM_SYSCOMMAND / SC_SIZE`，与系统边框同源）。
这条结论**推翻**了「在 runner 里补 WM_NCHITTEST 就能拖边」的直觉方案，
若后续有人想把缩放搬回 C++，必须先解决子窗口的命中透传（子类化视图 HWND 或在视图上叠一个
`HTTRANSPARENT` 的窗口），否则一定点不动。

### 2.4 顺带修掉的一个既有缺陷

`FlutterWindow::SyncFullscreenWindowState` 原来用「客户区 < 窗口 ⇒ 不是全屏」作为
全屏判据之一（`client_fills_window`）。去边框后 **client == window 恒成立**，
于是「任务栏自动隐藏的显示器上的最大化窗口」会被误判成全屏：
Win11 圆角被关掉、`is_fullscreen_` 置位后 `WM_DPICHANGED` 不再重定位，跨屏拖动回不去。
现在判据只保留 `WS_THICKFRAME` 位（只有 `window_manager` 的 `SetFullScreen` 会剥掉它）。

## 3. 启动默认最大化

`main.cpp`：`window.SetStartMaximized(true)`，`Win32Window::Show()` 用 `SW_SHOWMAXIMIZED`
而不是 `ShowWindow(SW_SHOWNORMAL)` 之后再 `Maximize()`。差别是可见的：
后者会让窗口先以还原尺寸（1440×900）出现一帧再跳成最大化。

Dart 侧**不**再调 `maximize()`：窗口已经在最大化状态，重复调用会让 `maximize` 与
`unmaximize` 的窗口动画在启动瞬间各播一次。

## 4. 标题栏的设计取舍（为什么是「透明条」）

应用顶部已经有 `.top-nav` 浮动玻璃卡（`shell.css:162–178` + `auroraqua.css:262–270`：
高 64、外边距 12、圆角 16、模糊 18）。在它上面再加一条通栏玻璃会变成**两根并列横条** ——
那正是用户要否掉的「系统标题栏感」。因此 `AylaTitleBar` **不铺任何底色/模糊**：
透明条压在 `AylaAuroraBackground` 的极光上，只有左侧品牌字与右侧三键可见
（等价 Windows 11 / Discord 的 extend-content-into-title-bar）。附带收益：**零 `BackdropFilter`**，
不占 `test/perf_audit_test.dart` 的玻璃预算。

全部数值的推导来源（无自创）：

| 元素 | 取值 | 来源 |
|---|---|---|
| 条高 | 32 | `AylaTitleBarMetrics.height`；键的 40×40 命中区可溢出条高（Windows 11 标题栏同为 32） |
| 窗口键命中 | 40×40 | design.md §10「≥40px 触达目标」 |
| 悬停胶囊 | 32×32 + `--radius-pill` | `.top-nav-icon-btn` 同为 pill 族 |
| 悬停底色 | `--ice-500` `.18` | `shell.css:207–210`（全站唯一 hover 底色） |
| 关闭键悬停 | `--destructive` + `--surface` 图标 | 语义 token，**只有它**用危险色 |
| 图标 | 14px，线宽 1.3 | 比顶栏 20 / 模块 16 再小一档（低频附属控件） |
| 品牌字 | 13 / Fredoka 600 / ls .2 | 九级阶梯里 display 族最小档；派生自 `microTag`（自带 CJK 回退链） |
| 品牌渐变 | `linear-gradient(120deg, --indigo-700, --grape-700)` | `shell.css:239–260` 的 `.top-nav-logo` |
| 品牌圆点 | `--pink-500` 4×4 | `AylaSpacing.sp1`；不带辉光（`--glow-shadow` 全屏 ≤3 处） |
| 品牌左缩进 | 12 | 与下面玻璃卡的 `margin-left` 同一条竖线 |

窗口键字形是**自绘 painter**（`_WindowGlyphPainter`）而不是 `kAylaIcons`：它们属于 OS chrome，
不在 web `components/icons.tsx` 的业务图标集里，而 `kAylaIcons` 由 icons.tsx 生成、禁止手加。

## 5. 窗口状态的唯一 owner

最大化 / 还原可能由**系统**发起（双击、Win+↑、贴边吸附、任务栏菜单），所以三键只「请求动作」、
不「记账」：状态一律以 `window_manager` 的 `WindowListener` 事件为准，首帧再 `isMaximized()` 同步一次
（事件只覆盖「变化」，不覆盖「启动时就已经最大化」）。

`_AppRootState`（`lib/main.dart`）也订阅同一组事件，因为边缘缩放带铺在**页面之上**、与标题栏是
两棵不相关子树，唯一共同祖先是根 —— 把状态抬到根才让「窗口状态」只有一个 owner。

直播全屏（窗口级）时：标题条高度归零（`onWindowEnterFullScreen`），缩放带整组移除。

## 8. 调查中纠正的三条先前结论

1. **「在 runner 里补 WM_NCHITTEST 即可拖边」不成立** —— 原因见 §2.3（子窗口 HTCLIENT
   终止命中搜索）。本文件初稿曾按这个假设实现了一版真正的 `HandleResizeRelay`
   （从子窗口转发来的 `WM_NCLBUTTONDOWN` / `WM_MOUSEMOVE` 起 `SC_SIZE`），
   **该实现已删除**：这两个消息同样不会到达父窗口，留着就是死代码 + 误导后人。
2. **`restoreTitleBar()` 的 `TitleBarStyle.normal` 已改为 `hidden`** ——
   去边框后 `normal` 不再是「正确状态」，它会污染 window_manager 的

   `SetFullScreen` 的恢复分支会按「有标题栏」算客户区。

## 9. 第二轮：用户实报三问题的根因与修复（2026-11-04 同日）

用户截图反馈三条，逐条查证后的**真实根因**（初版实现各有失误，此处如实记录）：

### 9.1 三个窗口键难看、窗口化图标缺线

**根因**：初版 `_WindowGlyphPainter` 直接在 **16px 画布**上按比例乘系数绘制
（`w * 0.16` 之类），并且 `strokeWidth = 1.3`。等比缩放到 14px 后描边只有
14/24 × 1.3 ≈ 0.76 设备像素 —— 落在半像素上被抗锯齿抹淡，方框的上下两条边几乎消失，
这就是用户看到的「缺线」。同时几何与库里其它图标毫无关系，所以「难看」。

**修复**：改成与 `kAylaIcons` / `AylaSvgGlyph` 完全同构的画法 ——
**24 viewBox 坐标系里写死几何 + 整体等比缩放 + 描边 2**（`icons.tsx` 的 `base()` 同值）：

| 键 | 几何 | 事实源 |
|---|---|---|
| 最小化 | `M5 12h19`（Lucide `minus`） | 与库内 `iconPlus` 的 `M12 5v14M5 12h14` 同源 ⇒ 加减一对 |
| 最大化 | `rect 4.5,4.5,15,15` r≈1.6（Lucide `square` 收一档） | 与 `iconClose` 同厚度的方框 |
| 还原 | `rect 8.5,8.5,11,11` + `M4.5 15.5V4.5H15.5`（错位双框、后框缺右上角） | 系统「还原」键画法 |
| 关闭 | `M18 6 6 18M6 6l12 12` | **逐字**照 `iconClose` |

图标边长同时由 14 → **16**（= `.top-nav-module-icon` 同值），
让 2 单位描边渲染成约 1.33 设备像素，与全站图标同厚度。

### 9.2 窗口化时要有圆角 / 边框 / 阴影

**根因**：`WM_NCCALCSIZE` 恒返回 0 ⇒ 窗口没有非客户区，而
**这三样本来全由非客户区提供**：Windows 不再画阴影，也没有边框可圆。
Flutter 侧**无论怎么画都够不到窗口外**：Flutter 视图是铺满客户区的矩形子窗口。

#### ⚠️ 第一版做错了，变成 Win7 边框（同日实报，已修）

第一版为了「找回 DWM 阴影」设了 `DWMWA_NCRENDERING_POLICY = DWMNCRP_ENABLED`。
用户从最大化拖回窗口化的瞬间，右上角冒出**三个 Win7 风格的系统标题栏按钮**，
整个窗口套了一圈经典立体边框（截图实报）。

**根因（重要，别再踩）**：那个属性的语义是「让 DWM 渲染**非客户区**」。本窗口的非客户区
已被 `WM_NCCALCSIZE` 取消，于是 DWM 按窗口样式把**整套系统框补画回来**：经典立体边框 +
右上角三个系统 caption 按钮，正好盖在 Ayla 自绘的三个键上面。
截图里那三个按钮**不是我们画的**，是 DWM 画的。

> 结论：**`DWMWA_NCRENDERING_POLICY` 碰不得** —— 它的两个取值都会让 Windows 把经典
> Win7 边框 + 系统 caption 按钮画回来。唯一正常的状态是不设置。
> （本文件初稿据此写「阴影与系统标题栏只能二选一」，**该结论已被 §9.2b 的实测推翻**：
> 阴影来自 `CORNER_PREFERENCE=ROUND`，与 NC 渲染无关。）

#### 现在的做法

| 需要 | 做法 | 说明 |
|---|---|---|
| 圆角 | `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND` | 只裁剪不绘制，安全 |
| 系统框 | **不碰 `DWMWA_NCRENDERING_POLICY`** | 两个取值都会画出经典 Win7 框；保持默认（不设置）才是正常状态，详见 §9.2b |
| 窗口边线 | `DWMWA_BORDER_COLOR = --ice-300`（窗口化时） | 实测有效，只改颜色、不恢复系统 chrome；详见 §9.2b。~~Dart 侧 `AylaWindowOutline`~~ 已删除 |
| 窗口外阴影 | **DWM 自动提供** | 圆角窗口的默认行为，无需设置（用户确认已有） |

**单一 owner**：`flutter_window.cpp` 的 `ApplyFullscreenState` 里原来那份
`DWMWCP_DEFAULT` 已删除 —— `DEFAULT` 在 Win11 上等于**圆角**，会让「最大化窗口退出全屏」
拿到圆角 + 贴屏边、四角露桌面色。全仓 `DWMWA_WINDOW_CORNER_PREFERENCE` 只由
`SyncWindowFrameDecoration` 写。

Windows 10 上 `DWMWA_WINDOW_CORNER_PREFERENCE` 不存在，写入失败后代码保持旧观感
（方角、无自定义边），是正确降级。
### 9.2b 第二次修正：边线归 DWM、应用内描边删除（同日第三报）

第三轮用户反馈两条，指向同一个错误：

> 「现在修一下四个边角的圆角，仔细看会发现边线圆角并没有和窗口圆角重合。
|  去掉这个边线，我说的边线不是绘制在app内的，是窗口边线。不知道窗口边线能不能改，
|  目前窗口阴影已经有了，窗口边线是黑色。」

**根因**：我在 Dart 里画的 `AylaWindowOutline` 是**应用内**的一圈描边，它的圆角半径
（`AylaRadii.rCard` = 16）与**真正窗口**的圆角半径（DWM 给 Win11 的圆角）不是同一个数，
所以必然对不齐、看起来「没重合」。而且用户要的根本不是这条线，是**窗口自己的边线**。

**实测方法**（这次先量再改，不再推理）：写了一次性 Win32 探针，五个窗口并排，
全部先做「frameless 三件套」（`WM_NCCALCSIZE`→0 + `DwmExtendFrameIntoClientArea(0,0,0,0)`
+`SWP_FRAMECHANGED`，与 window_manager `setTitleBarStyle(hidden)` 等价），然后分别：

| 窗口 | 属性 | 实测结果 |
|---|---|---|
| 1 | 无 | 无边框、无系统标题栏（第一轮基线） |
| 2 | 仅 `CORNER_PREFERENCE=ROUND` | 圆角生效，无边框 |
| 3 | ROUND + `BORDER_COLOR=黑` | **黑边**，且**贴合圆角** |
| 4 | ROUND + `BORDER_COLOR=--ice-300` | **冰蓝边**，贴合圆角 |
| 5 | ROUND + `BORDER_COLOR=DWMWA_COLOR_NONE` | 无边框 |

三个颜色调用全部返回 `S_OK`；放大 3× 的截图确认边线沿圆角走、且圆角外无残留直角。

**修复**：

- **删除** Dart 侧的 `AylaWindowOutline`（连同 `main.dart` 的包裹）—— 应用内画不出窗口边线；
- 窗口边线改由 DWM：`DWMWA_BORDER_COLOR = --ice-300`（窗口化时），
  最大化 / 全屏写 `DWMWA_COLOR_NONE` 交回系统默认（避免屏幕边缘多一圈冰蓝线）；
- **窗口阴影本来就有**（DWM 对圆角窗口自动投影，用户确认已有）⇒ 无需任何额外设置。

#### ⚠️ 本轮同时纠正 §9.2 的一个错误结论

§9.2 曾写「阴影与系统标题栏是同一个开关的两面，只能二选一」。**这是错的**：
阴影是 DWM 对**圆角窗口**的默认行为，与 `DWMWA_NCRENDERING_POLICY` 无关。
真正的因果关系是：

- `DWMWA_WINDOW_CORNER_PREFERENCE = ROUND` → 有圆角 ⇒ DWM 自动给阴影；
- `DWMWA_NCRENDERING_POLICY` → **碰不得**（ENABLED / DISABLED 两个取值都会让 Windows
  把经典 Win7 边框 + 系统 caption 按钮画回来，这是两次实报的根因）；
- `DWMWA_BORDER_COLOR` → 只改边线颜色，安全（已实测）。

另外记录一个**枚举顺序**的坑：`DWMNCRENDERINGPOLICY` 的真实顺序是
`USEWINDOWSTYLE=0, ENABLED=1, DISABLED=2`（不是凭直觉的 ENABLED=1/DISABLED=2 → 反过来）。
我前两版把 1 和 2 标反了，导致两次「不同取值、同样 Win7 边框」的诡异现象。

### 9.4 条高的第三次调整：删掉那段留空带（同日第四报）

> 「现在把我图中标红框的留空部分删掉，Ayla的导航栏上移，使得窗口标题栏上下协调」

条高这条数字改了三轮，每轮都是被实报推着走的，记下来免得再绕：

| 轮次 | 条高 | 顶栏 `margin-top` | 结果 |
|---|---|---|---|
| 1 | 32 | 12（web 原值） | 条下面那 12px 属于内容区 ⇒ **看得到却拖不动** |
| 2 | 44 | 0 | 拖动范围对了，但品牌行贴条顶、**条底空出 12px** ⇒ 用户圈红要求删 |
| 3（当前） | **32** | **0** | 条高 = 品牌行高，窗口顶边缘到玻璃卡之间**无多余留白**；可拖拽区仍严丝合缝等于那片可见空间 |

关键点：**「删留空」与「拖得动」不矛盾** —— 矛盾的只有「条高 < 可见空带」这种组合。
第 2 轮之所以出现留空，是因为我保留了 44 的条高却只把品牌行画在上半部；
现在条高降到 32、顶栏外边距仍为 0（`wideMarginUnderTitleBar`），两者同时满足：

- 可见的上方空带 = 32px（只有标题条自己）；
- 可拖拽区 = 那 32px 的全部（`Positioned.fill`）；
- 品牌字在条内垂直居中（`Center`），与右侧三个窗口键同一中轴。

### 9.3 顶部拖拽命中范围不符合直觉（有时点得到有时点不到）

**两个独立根因**，都在初版实现里：

1. **命中区比用户认知的范围少 12px**（用户截图红框比标题条高）——
   标题条只有 32px，而它下方还有 `.top-nav` 的 `margin-top: 12px`
   （`auroraqua.css:263`），那 12px 属于内容区 ⇒ 点在那里没有任何反应。
   **修复**：首轮条高 32 → 44（把那段外边距收进条内，见 §9.4 的完整三轮表）；
   同时给 `AylaTopNav` 加 `underTitleBar`，桌面下用
   `wideMarginUnderTitleBar`（上边 0）——那 12px 从此归标题条，玻璃卡位置不变。
2. **`onPanStart` 的 18px slop + 双击识别器抢手势竞技场** ——
   `PanGestureRecognizer` 要指针移动 `kTouchSlop`(18) 才胜利，在几十像素高的条里
   显得像「粘住/没反应」；而 `onDoubleTap` 会在按下瞬间进场暂缓判决，
   命中率取决于双击计时器与移动速度的赛跑 ⇒ **时灵时不灵**。
   **修复**：新件 `AylaCaptionDragArea`，用裸 `Listener` 自判 ——
   3px 阈值即起拖、自己按「时间 ≤300ms + 位移 ≤8px」判双击、拖过就不再算点击、
   `startDragging()` **不 await**（原生 `SC_MOVE` 会阻塞到用户松手，await 会让
   「防连点」标志被整段拖拽占住）。

**命中优先级**（Stack 后者在上，代码里就是顺序，别调换）：
整条拖拽区 → 上边 4px 缩放带 → 左上/右上 12×12 缩放角 → **三个窗口键（最上）**。
右上角关闭键永远压在缩放带之上。

### 9.5 最大化→窗口化 的还原尺寸：按最大化尺寸等比缩放（同日第五报）

> 「最大化到窗口化时，默认窗口比例不对，要和最大化时等比，窗口小一些」

**根因**：`Create()` 里写死还原尺寸 `1440×900`（1.60:1），而最大化窗口等于所在显示器
的 `rcWork`（本机实测 **1938×1048 = 1.85:1**）⇒ 一还原就换成另一个长宽比，
看着就是「比例不对」。写死任何数字都躲不开这个问题：显示器、DPI、任务栏高度都会变。

**修复**（`Win32Window::ApplyProportionalRestore`，在最大化后的第一个 `WM_SIZE` 里跑一次）：

1. `GetWindowRect` 量出**已经最大化**的窗口矩形（这就是「最大化时的大小」）；
2. 取 `0.8` 倍 ⇒ 等比且更小；
3. 居中放进 `rcWork`；
4. `GetWindowPlacement` → 改写 `rcNormalPosition` → `SetWindowPlacement`
   （`showCmd` 保持 `SW_SHOWMAXIMIZED`，只记几何不立刻还原）。

**实测验证**（一次性 Win32 探针，跑完即删；不依赖 Flutter，也不需要跑 App）：

```
maximized: 1938x1048 ratio=1.8492
GetWindowPlacement ok=1 showCmd=3 rcNormal=10,10,1290,810
SetWindowPlacement ok=1 target=1550x838
restored: 1550x838 ratio=1.8496 at(185,96)
RESULT ratio_delta=0.00041 smaller=1
```

⇒ 长宽比差 0.0004（四位小数内相同）、确实更小、并且居中。

#### ⚠️ 踩掉的坑：`SendMessage(WM_GETMINMAXINFO)` 取 `ptMaxSize` 返回 0x0

第一版实现是「给窗口发 `WM_GETMINMAXINFO`，读 `ptMaxSize`」。探针实测打印出
`ptMaxSize: 0x0` ⇒ 还原窗口变成 **170×47**。原因：那个结构体只在**系统自己发送**
这条消息时才被填好，程序显式 `SendMessage` 过去会拿到全零（引擎的处理器还会先
按 `box_constraints_` 覆盖它）。所以改成直接量最大化窗口的矩形 —— 它本来就是答案。
