# 38 · 语音房「条子不跳 + 声音断续」根因与修复（Flutter）

> **任务**：用户实报 —— Ayla Flutter 语音聊天**太卡、断断续续**；**语音房左右跳动的音频条始终不跳动**（能听见声音、看不见对方音频条跳动）。web 端音频条正常（但声音也很卡），可参考。
>
> **性质**：**缺陷修复**（已改 `flutter/lib/`）。两条独立缺陷，**不是一个 bug 的两种表现**：
> ① 音频条不动 = UI 订阅链断开（纯 Dart，与音频链路无关）；② 断续 = 媒体层零缓冲 + 每帧分配（纯媒体层，与 UI 无关）。
> 二者叠加的症状恰好都是「有声音、体验差」，所以前几轮一直被当成同一个问题修，反复返工。
>
> **基线**：`cb9798e`（`docs(release): 1.0.24 发布说明`）+ 当时工作树（2026-10-27）。

## 零、结论摘要

| 项 | 内容 |
|---|---|
| **现象 A** | 语音房成员行右侧的跳动音量条**完全不跳**（所有人，包括自己在内）。声音正常能听见 |
| **现象 B** | 语音「断断续续」，一顿一顿；web 端也能听出卡但明显轻一些 |
| **根因 A** | `aylaVoiceMedia()` 是**全局单例**，回调容器 `_events` 在**构造体里**就接好了；但页面调 `aylaVoiceMedia()` **不传 events**，紧接着 `AylaVoiceSession` 又用 `bindMediaEvents(mediaEvents ?? AylaVoiceMediaEvents())` **另建一个孤儿对象**去绑。⇒ `setRemoteAudioLevels` / `setLocalAudioLevel` / `setMedia` **永不触发**，成员行 `audioLevel` 恒 0 |
| **为什么声音照旧** | 坏的只是**回调出口**。`RelayCallbacks` / `AudioEngineCallbacks` → 单例 `_events` 这条链完全正常，引擎照常编解码播放，所以听得见声音 |
| **为什么上一轮修完还不动** | `6185995` 修的是真问题（build 链上 `ref.read` 不建立订阅），但只解决了「store 变了页面不重建」。**store 本身从未被写入过**，所以那次修复没有任何可观察变化 |
| **根因 B（1.0.25+27 修过一半，反而更糟）** | Flutter 侧原本**完全没有抖动缓冲**（1.0.25 前的真缺陷）。1.0.25 补上了缓冲，但**判据用错了**：把 web 的 20ms「排播前瞻量」当成 FIFO 欠载阈值，而设备一次 `data_callback` 要吃掉 `bufferFrames=1024` 帧 = **21.3ms** ⇒ 阈值比单次消耗还小 ⇒ 稳态必然被判欠载 ⇒ `playing` 恒 false ⇒ **只预缓冲不写设备** ⇒ **成段静音**。详见 §六 |
| **为什么 web 好一些** | 同样的网络抖动，web 有调度器垫着（前瞻 20ms + 排播），丢掉的那一帧只是延后；Flutter 是立刻就静音 |
| **附带修复** | `AylaVoiceMedia.setTokenRefresher` **全仓 0 调用**（中继连续失败 3 次后的续期钩子恒返回 null）⇒ 在 `main.dart` 注入 |
| **状态** | 现象 A ✅ 已修并实机确认（条子开始跳）。现象 B **1.0.25+27 首发失败**（作者引入回归，见 §六），**1.0.26+28 已重修**：欠载判据改为「一次设备回调消耗量的 2 倍」，起播水位 100ms；闭环仿真下实测双峰流补零从 1069ms/28 次降到 **37ms/4 次**。**仍未实机验证**（音频须完整重启） |

## 一、现象 A：音频条完全不跳

### 1.1 数据链应有的形状（对照 web）

```text
web（useVoiceStore 是模块级 zustand store，selector 直读）

    → events.onRemoteAudioLevels({identity: level})
    → stores/voice.ts  setRemoteAudioLevels
    → VoiceChannelPanel.tsx:63  members[user_id].audioLevel
    → VoiceMemberRow.tsx:210  level={member.audioLevel}
    → .voice-meter-fill  width

Flutter（应等价）
  audio_engine.dart _startLevelTick()  Timer.periodic(100ms)
    → _events.onRemoteAudioLevels(snapshot)          ← engineCallbacks
    → voice_media.dart:77  _events.onRemoteAudioLevels
```

### 1.2 断点在哪（逐环证据）


```dart

// flutter/lib/pages/voice_support.dart（修复前 :255，构造函数里）
```

**两份不是同一个对象** ⇒ 引擎每 100ms 往 A 里打回调，而 `setRemoteAudioLevels` 绑在 B 上。
全仓 `grep -rn 'aylaVoiceMedia(' lib` 只有 1 个调用点、`mediaEvents` 只有 2 处 ⇒ **没有任何代码路径**能给单例补绑。

### 1.3 为什么它上线这么久才被发现

- 症状是「**条子不动**」，而音频链路是好的 ⇒ 第一反应永远是「电平没算对 / 没衰减 / UI 没订阅」，
  前两轮确实分别修了「衰减」（`faa25a5`）与「订阅」（`6185995`），都是真问题，但都治不到这一层；
- `dart analyze` 对「回调对象不是同一个实例」完全无感；
- 唯一的可观察面是**真机听 + 看**，而音频必须完整重启才验证得了。

### 1.4 修复

```dart
// voice_media.dart:93 —— 把单例自己的事件容器暴露出来
AylaVoiceMediaEvents get events => _events;

// voice_support.dart:265 —— 默认绑**媒体实例自己的**那一份
bindMediaEvents(mediaEvents ?? _media.events);
```
`mediaEvents` 仍保留为可选注入（测试替身用），生产路径不再有第二个容器。

### 1.5 顺带：把 10Hz 重建从整页收敛到成员面板

修通订阅之后会立刻暴露**新**问题：`AylaVoiceState.setRemoteAudioLevels` 每 100ms `notifyListeners()`，
而页面是 `ref.watch(voiceStateProvider)`（整个 store）⇒ **每秒 10 次重建整页 + `AylaVoiceRoomBody`（1419 行）**，
与音频采集/解码抢同一个 isolate（这正是 web 没有的性能问题：zustand selector 只重渲染成员行）。

改法（`voice_support.dart:1200–1340`）：

| 关注点 | 改动 |
|---|---|
| 页面字段 | `ref.watch(整个 store)` → 5 个字段级 `select`（频道描述 / selfId / selfInStore / rejoin / 成员数） |
| 电平 | **页面完全不订阅**；唯一重绘面 = `ListenableBuilder(listenable: voice)` **只包成员面板子树** |
| `elysiaUserId` | 从 builder 内 `ref.watch` 提到 build 期（否则走 10Hz 路径、晚注册依赖） |

⚠️ **不要**用「折叠成版本号再 `ref.watch`」的写法（本轮中途试过）：stamp 每 100ms 变一次，
等于把「watch 整个 store」换成「watch 每秒变 10 次的 stamp」，整页照样重建 —— 白做且多一次 O(成员数) 哈希。
静态锁见 §3.2 的 C 条。

## 二、现象 B：声音断断续续

### 2.1 与 web 的能力差距（逐条）

| 能力 | web（`wsRelayRoom.ts`） | Flutter（修复前） | 后果 |
|---|---|---|---|
| 抖动缓冲 | `:311–315` 每 slot 维护 `playHead`，WebAudio 按绝对时间排播：落后 <20ms 顺延、积压 >400ms 重置追赶 | **无**。`audio_engine.dart` 解码后直接 `p.write()` | 一次抖动 = 立刻补零静音 |
| 播放缓冲 | 浏览器音频线程自带 | `bufferFrames: 512` ≈ **10.7ms**，FIFO 默认 8192 帧 ≈171ms | 回调 94 次/秒，GC 一停顿就连丢多个回调 |
| 编码 | `AudioEncoder.configure({bitrate: 32000})`，编码在 **AudioWorklet**（独立线程） | `SimpleOpusEncoder.encode` 每 20ms **malloc 输入 + malloc 输出 + 两次 fromList**，在**主 isolate** | 每秒 50 次分配，GC 停顿正好落在播放回填窗口 |
| 解码 | `AudioDecoder`（WebCodecs，独立线程） | `SimpleOpusDecoder.decode` 同样每帧 malloc，且**每个 slot 一帧** | N 人说话时分配量 ×N |
| 采集缓冲 | AudioWorklet 内部固定 960 样本环形 | `List<int>` + `addAll` + `sublist`/`removeRange`（每 20ms 两次 O(n) 搬运 + 两次 List 分配） | 同上 |
| 下行解包 | `bytes.subarray(1)`（视图，零拷贝） | `Uint8List.fromList(bytes.sublist(1))`（**两次**整包拷贝） | 每帧多一次分配 |

`lib/poc/relay_protocol.dart:58–60` 的 `kJitterAheadTargetSec=0.02` / `kJitterResetAtSec=0.4` **是死常量**
（全仓只定义、无引用）—— 也就是说「抖动缓冲」在 Flutter 侧从来只是注释里的一句话。

### 2.2 为什么表现为「断断续续」而不是「延迟大」

FIFO 被抽干时，`third_party/flutter_miniaudio/src/miniaudio_bridge.c:162–164` 的行为是**补零**：

```c
if (samples_to_read < samples_needed) {
    memset(output + samples_to_read, 0, (samples_needed - samples_to_read) * sizeof(int16_t));
}
```

⇒ 每个被抽干的回调周期 = 一段**静音空洞**，下一个回调恢复出音 ⇒ 听感是「一顿一顿」，不是「整体慢半拍」。
缓冲越浅空洞越频繁；这正是「web 也卡但轻一些」的原因（它有 20ms 前瞻 + 独立音频线程）。

### 2.3 修复（媒体层，`lib/audio/*` + `lib/poc/relay_protocol.dart`）

#### A. 自适应抖动缓冲（把 web 的语义映射到 FIFO 模型）

web 那套是**带前瞻的调度器**，Flutter 没有调度器，只能靠 FIFO 自己垫 ⇒ 不能照搬「1 帧 lead」，
必须显式垫到起播水位。**决策抽成顶层纯函数** `decideJitterFrame()`（`relay_protocol.dart:191`）便于逐档单测：

| 常量 | 值 | 依据 |
|---|---|---|
| `kJitterAheadTargetSec` | **0.02** | web `:313` 权威值；Flutter 语义 = FIFO 深度低于一帧 ⇒ 下一回调必补零 |
| `kJitterResetAtSec` | **0.4** | web `:313` 权威值（积压丢弃） |
| `kJitterStartSec` | **0.06** | 新增。60ms = 3 帧，覆盖「连丢 2 帧」/「20–40ms 抖动 + GC 停顿」；再大就明显拖对话节奏 |
| `kJitterTargetSec` | **0.03** | 新增。比欠载阈值留 10ms，避免「抖—停—抖」循环 |

四态：`prebuffer`（攒水位，不写设备）/ `flush`（灌入）/ `play`（稳态直写）/ `drop`（积压追赶）。

⚠️ **与 web 的有意差异（登记）**：miniaudio fork 的 FIFO **没有 flush 导出**，
所以 400ms 高水位只能「丢掉后续入场帧、等设备把积压放完」（等效一次 ~400ms 空档），
而不是 web 的瞬间 `playHead` 前跳。要真正做到前跳必须给 fork 加清空接口（见 §四）。

#### B. 播放缓冲与水位数

| 常量 | 值 | 取舍 |
|---|---|---|
| `kPlaybackBufferFrames` | **1024**（21.3ms） | 512（10.7ms）回调 94 次/秒，一次 GC 连丢多个；2048（42.7ms）设备延迟翻倍而抖动缓冲已垫 60ms，不划算 |
| `kPlaybackFifoCapacityFrames` | **36000**（750ms） | 默认 8192 帧 = 171ms，**比 400ms 高水位还浅** ⇒ 防积压判断会永远是死代码 |

净延迟 ≈ 抖动缓冲 60ms + 设备周期 21ms ≈ **81ms**（web 同类方案 20–80ms 量级）。

#### C. 编解码改预分配 + 采集改环形缓冲

| 位置 | 改法 |
|---|---|
| 编码 `audio_engine.dart:226` | `SimpleOpusEncoder` → `BufferedOpusEncoder`（`inputBuffer` 一次分配，样本直接写进去）|
| 解码 `audio_engine.dart:237` | `SimpleOpusDecoder` → `BufferedOpusDecoder` |
| 采集 `audio_engine.dart:389` | `List.addAll`+`sublist`/`removeRange` → 固定环形缓冲 `kCaptureRingBytes`，全程只拷一次 |
| 播放 `audio_engine.dart:581` | 去掉每帧 `malloc`/`free`，复用一个 960 样本原生块（惰性分配、`dispose` 幂等置空）|
| 下行 `relay_client.dart:295` | `fromList(bytes.sublist(1))`（两次拷贝）→ `fromList(sublistView(bytes,1))`（一次）|

⚠️ **两处易错的 API 语义**（改这块必须知道）：
1. `BufferedOpus*` 的 `inputBufferIndex` 单位是 **字节**，不是样本数；写错会**静默**编出半帧/错帧（不抛异常）；
2. `BufferedOpusDecoder.decode()` 返回的 `Int16List` **是 `Int16List.fromList(...)` 的新拷贝**（`opus_dart_decoder.dart:358`），
   但它**下一帧就被覆盖**的语义仍要按「缓冲复用」理解，预缓冲阶段必须把样本搬出来。

#### D. `setTokenRefresher` 接线

全仓 0 调用 ⇒ 中继连续失败达 `kRelayReconnectRefreshAfter`(3) 次后的续期钩子恒返回 null，
token 过期导致的断连永远续不上（web `:688–693` 是 `refreshAccessToken()` + 取最新 store 值）。
在 `main.dart:245`（**`DioClient.instance.init()` 之后**）注入，并同时写进**模块级**变量 ——
因为登出会 `aylaVoiceMediaTeardown()` 把单例置空，而 `main` 每进程只跑一次。

## 六、事故：1.0.25+27 首发失败 —— 我自己引入的回归

> **用户复验原话**：「声音还是会断断续续的，不像是一直在连着声听的」。
>
> **本条是本文件的自我更正**：§二 描述的「加抖动缓冲」在 1.0.25+27 里确实发了，
> 但它**判据写错**，导致断续比修复前更严重。§二/§三 的结论不作为最终结论，
> 以本节为准。

### 6.1 错误是什么

`relay_protocol.dart` 把 web 的 `at < now + 0.02` 直接搬成 FIFO 欠载阈值：

```dart
// 1.0.25+27（错误）
if (fifoDepthSec < kJitterAheadTargetSec) {   // 0.02s
  return JitterDecision(action: JitterAction.prebuffer, playing: false, ...);
}
```

**物理上不成立**：

| 量 | 值 |
|---|---|
| 设备一次 `data_callback` 取走 | `kPlaybackBufferFrames = 1024` 帧 = **21.33ms** |
| 欠载阈值 | **20.00ms** |
| 结论 | **阈值 < 单次消耗量** ⇒ FIFO 只要逼近阈值，回调一次就跌穿 ⇒ 判定欠载 |

⇒ `playing` 被打回 false ⇒ 之后**每帧都只进 Dart 侧预缓冲、不写设备** ⇒
设备持续补零 ⇒ 起播条件 `fifoDepth + pending >= 60ms` 里 `fifoDepth` 恒 0，
而 `pending` 攒的是「还没送进设备的数据」⇒ **成段静音**，直到攒够再灌一次。

这正是用户描述的「**不像是一直在连着声听的**」——不是咔哒，是**成段的断**。

### 6.2 为什么上一轮的测试没发现

1.0.25+27 的 `voice_audio_jitter_test.dart` 有 38 条用例、全绿，但**它们锁的正是错误行为**：

```dart
// 1.0.25+27 的断言（错误语义）
test('★ 起播后不会因为「只有一帧」就立刻停（欠载阈值 20ms）', () {
  expect(d(_frameSec, 0, playing: true).action, JitterAction.play);
});
```

单点断言无法发现这个错误 —— 因为它描述的正是错的语义。**这是本轮最重要的方法论教训**：
音频这类「时序 + 闭环」问题不能用单点纯函数断言验收，必须用**闭环仿真**（虚拟设备按真实
样本精度消耗 + 虚拟网络按实测间隔投帧，跑 30 秒，量「累计补零时长」这个用户可感量）。

### 6.3 修正

```dart
// relay_protocol.dart（1.0.26+28）
const double kJitterCallbackSec = kPlaybackBufferFrames / kSampleRate;  // 21.33ms
/// 欠载下限 = 一次回调消耗量 × 2（吃一拍、留一拍容错）
const double kUnderrunFloorSec = kJitterCallbackSec * 2;                // 42.67ms
/// 稳态目标必须高于欠载下限（留半拍），否则「抖—停—抖」
const double kJitterTargetSec = kUnderrunFloorSec * 1.5;                // 64ms
/// 起播必须再高一档：要吞掉实测的 40–50ms 空档 + 一拍回调
const double kJitterStartSec = 0.10;                                    // 100ms
```

`decideJitterFrame` 的稳态分支改用 `kUnderrunFloorSec`；`kJitterAheadTargetSec` 保留为
「与 web 同源的语义锚点」，注释里显式标注**它不是欠载判据**。

### 6.4 验收证据（闭环仿真，`test/voice_jitter_loopback_test.dart`）

虚拟设备按 `kPlaybackBufferFrames` 消耗、虚拟网络按**服务端实测间隔**投帧，跑 30 秒：

| 到达模式 | 旧阈值（20ms / 起播 60ms） | 新阈值（42.7ms / 起播 100ms） |
|---|---|---|
| 理想 20ms 均匀 | 43ms 补零 / 1 次切断 | 85ms（仅起播预热）/ 1 次 |
| **服务端实测双峰**（75% 帧挤 <10ms，15% 落 40–50ms） | **1069ms / 28 次** | **37ms / 4 次** |
| ±10ms 抖动 | 43ms / 1 次 | 85ms（预热）/ 1 次 |

⇒ 在**真实测到的到达模式**下，旧阈值是 1.07 秒静音 / 28 次切断，新阈值降到 37ms / 4 次。

变异验证：把 `kUnderrunFloorSec` 改回 `0.02`、`kJitterStartSec` 改回 `0.06` ⇒ 仿真用例
与三条接线锁**全部变红**（`Expected: a value greater than <0.03> Actual: <0.02>`），恢复后全绿。

### 6.5 本次一并订正的错误文档结论

- 本文件 §二 原写「起播水位 60ms 足够」⇒ **已订正为 100ms**，依据是服务端的实测帧到达分布；
- `relay_protocol.dart` 原注释「`kJitterAheadTargetSec` 就是欠载判定阈值」⇒ **已改写**，
  明确它只是 web 的排播前瞻量；
- `voice_audio_jitter_test.dart` 原有用例「欠载阈值 = 20ms」「起播 60ms」「20ms 提前量就该继续播」
  ⇒ **已按新语义订正**，并在用例内写明旧断言为何是错的（避免下一个人以为是他改坏了）。

## 七、服务端实测：帧到达是「双峰」的（下一步的线索）

在用户实测期间直接从服务端日志取时间戳（`over capacity` 每条对应一次 `group_send` = 一帧），
统计帧间隔分布（64311 帧 / 1747 秒）：

```text
gap 直方图（10ms 桶，<300ms）:
    0- 10ms  48514  75.5%  ############################################################
   10- 20ms    234   0.4%  #
   20- 30ms    472   0.7%  #
   30- 40ms   2690   4.2%  ###
   40- 50ms   9887  15.4%  ############
   50- 60ms   1509   2.3%  #
   60-150ms    620   1.0%  #
```

**健康音频流应该是 20ms 一帧的窄峰**，实际是「75.5% 挤在 10ms 内 + 15.4% 落在 40–50ms」。
这意味着帧是**成簇到达 + 周期性空档**。本轮客户端缓冲已按此调参（起播 100ms）；
**但根因在链路（frp 隧道 / 采集批次）而非客户端**，后续应当：

1. 对比同一条隧道上 web 端的帧间隔分布（web 走 `live.trise.top:7881` 专线，
   Flutter 走 `s.ayla.trise.top:26211` 樱花隧道）—— **两者不是同一条链路**，
   这可能正是「web 也卡但轻一些」的原因；
2. 若确认是采集侧 MediaFoundation 批次投递（`record_windows` 默认缓冲约 100ms），
   考虑降低采集批次延迟；
3. 本轮同时确认：**下行 Redis 队列深度全程为 0**（60 秒 @20Hz 采样，max=0），
   服务端消费侧没有积压 ⇒ 服务端的「over capacity」确实与在线音频无关（与 37 号审计一致）。

## 八、遗留与后续

| # | 事项 | 归属 | 说明 |
|---|---|---|---|
| 1 | **miniaudio fork 没有 FIFO flush 接口** | Flutter | 400ms 高水位只能「丢入场帧等放完」（~400ms 空档），不是 web 的前跳。要真正对齐需在 `third_party/flutter_miniaudio` 的 bridge 加一个清空导出 |
| 2 | **`kOpusBitrate` 现在技术上可启用** | Flutter | `BufferedOpusEncoder.encoderCtl` 提供码率入口。本轮约束是「只修卡顿不动音质」，故仍为文档常量（`relay_protocol.dart` 里已就地订正「无法设置」这条过期结论）|
| 3 | **服务端侧音频质量指标为零** | 后端 | 目前只有 INFO 日志，没有丢帧/延迟/队列深度指标。本次排查最缺的就是这个（见 `docs/flutter/37-语音卡顿-服务端背压审计.md` §6 待决 7）|
| 4 | **`onPlaybackDelay` 口径** | Flutter | 现在打的是设备 FIFO 深度，**不含** Dart 侧预缓冲 ⇒ 起播阶段会短暂偏低。仅供诊断，不参与控制流 |

**与服务端审计的关系**（`37-语音卡顿-服务端背压审计.md`）：

- 该审计证明 `channels_redis` 的 `over capacity` 日志丢的是**死进程残留 key**，
  **不是**在线客户端的音频帧 ⇒ **不能**用这批日志解释用户听到的断续；
- 在线侧真正的服务端丢帧点是进程内 `BoundedQueue`，本次未观察到打满；
- 结论：本轮断续的**可证成因在客户端**（零抖动缓冲 + 每帧分配）。服务端那三条建议（清死成员 / 降 `group_expiry` / 摘热路径 `aclose_old_connections`）仍然该做，但**它们是稳定性与成本问题，不是本次断续的成因**。
