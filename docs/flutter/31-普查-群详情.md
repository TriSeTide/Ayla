#### 「入群申请」不热更新的**完整根因链**（HEAD `19a5d30`，已逐环取证）

1. **后端发了帧**：管理员收到 `group.request.new`——`views.py:1027-1044`（`create_join_request` 成功后，
   遍历 owner/admin 逐个 `services.broadcast_group_request_new`），载荷见 `services.py:971-983`（**扁平**结构）。
   另一个管理员处理掉时发 `join_request.resolved`——`views.py:1084-1103`（含「普查 W5 修复」注释）。
   ⇒ **帧确实发了，且发给了正确的人**。
2. **客户端收到了、也消费了**：`chat_ws.dart:533-540`（`group.request.new` ⇒ push notice + `_badges.fetch()`）、
   `:597-598` → `:927-937`（`join_request.resolved` ⇒ push notice + `_badges.fetch()`）。
   ⇒ **帧被消费了，但只消费到「通知 + 红点」，没有消费到「列表」**。
3. **红点会变、列表不变**：`badges_provider` 是全局 store，被 `app_shell.dart:221` `ref.watch` ⇒ 红点实时 ✅；
   而群详情页**没有订阅这个帧**，`_joinRequests` 也不在任何全局 store 里 ⇒ 界面不变 ❌。
   ⇒ 这是「**消费了但列表是私有快照**」与「**页面没挂 onFrame**」的**叠加**，正是用户点名的两种根因形态同时命中。
4. **唯一能救的操作都不在页内**：只有 `_bootstrap()`（进页时，`:202`）和本端审批（`:864-885`）会动
   `_joinRequests`；页面上**没有任何手动刷新入口**（web 也没有）。⇒ 用户必须**退出群详情再进**才能看到新申请。
5. **web 侧同病但成因不同**：web 的 `joinRequests` 在共享 record 里（能被 `setJoinRequests` 与
   `loadSocial` 刷新），但**没有任何 WS 帧触发 `joinPage.refresh()`**（`MessagesPage.tsx:97-110` 那份
   `loadFriendsTab` 只写在消息中心，`GroupInfo.tsx` 全文 0 命中 `onFrame`）⇒ **web 也是「重进页面才更新」**。
   所以 Flutter 这次补帧订阅，实际上是**超出 web 的实现**（更正确，但意味着不能再以 web 当验收基准）。

## 四、用户实报第 ① 条：**所有页面头像在线状态**不热更新

> 这条与群详情无直接关系，但它同样命中「群详情页的头像」，且是本轮普查里**唯一仍然对用户可见的 P1**，
> 因此在本报告内完整给出根因与清单。

### 4.1 根因（形态①，机制层面）

web 的等价物是 `usePresenceOnline(user)`：每个头像**自己订阅** `usePresenceStore`，
`presenceOnline(onlineUsers, withLiveStatus(onlineStatuses, user))` 实时求值
（`web/src/utils/displayStatus.ts:75-81`；调用点 `GroupInfo.tsx:764`、`MessageBubble.tsx:132`、`CommentList.tsx:119`、`DanmakuList.tsx:48`、`ConversationList.tsx:87` 等 40 处）。

Flutter 的 `AylaAvatarHalo` **HEAD 时 `online` 是不可变构造参数**（`avatar_halo.dart:56` `this.online = false`），
组件内**没有`ref.watch`** ⇒ presence 帧到达后光环永远不变。

### 4.2 工作树当前状态（**并行 worker 只修了一半**）

`_effectiveOnline` 在 `user != null` 时 `ref.watch(presenceStateProvider)`（`:121-130`）。
