### 8.2 性能事故与修法（**必须记住，别退回**）

- **事故**：首版把四层各自套 `ImageFiltered`。Flutter 的滤镜是 **layer 属性 —— 每帧合成重跑**，
  而 web 的 `filter: blur()` 是浏览器合成器缓存成纹理后只做变换。实测后果：渐变层一张
  3600×3600（51.8 MB）+ 湍流层 3600×2025（29.2 MB），五层峰值 200 MB+ 且逐帧重算 ⇒
  用户实测「太卡了完全没法正常看，debug 模式也是直接闪退」+ 爆显存黑屏。
- **修法**：`AylaAuroraBakedLayer` —— `saveLayer(imageFilter:)` 录制 → `Picture.toImage()`
  **一次性烘焙**，之后每帧只 `drawImage` + 变换（= 手写浏览器合成器那一步）。
- **预算**：低频层按最长边 cap 降采样（静态/渐变 1440 · 湍流 1024 · 光斑 512），
  五层总像素 `AylaFluidAurora.bakePixelBudget = 6M`（≈24 MB）；1080p 实测 ≈4.35M 像素。
- **回归锁**（`test/aurora_background_test.dart`，19 用例）：背景子树里**不得出现
  `ImageFiltered`/`BackdropFilter`**；`aylaAuroraBakePixels()` 在 1080p/4K 下都必须 ≤ 预算。
- **帧率口径**：`kAuroraFrameInterval` **默认 `Duration.zero`（满帧）**；
  它只是「低端设备 / 省电模式」的预留旋钮（设 33ms 之类即降档），正常路径不要动。

### 8.3 湍流纹理：按 **Skia 变体**精确复刻（不是规范参考实现）

- 规范 C 参考实现与浏览器**不一致**：规范里梯度向量长度 >1 会丢弃重抽（约 21.5% 概率触发），
  Chrome/Skia、Firefox/Gecko、Batik 都**不丢弃** ⇒ 随机数消耗序列不同、lattice 洗牌结果不同。
  本实现按 Skia：4 通道 × 256 项（每项恰好 2 个随机数）→ 洗牌 255→1 → 置换 + 归一化 + 16bit 量化；
- 采样点 **`(x + 1.0) × baseFrequency`**（Chrome 的 +0.5 +0.5；Firefox 是 `x × freq`，
  差 1 设备像素相位，想对齐改 `AylaTurbulenceSpec.sampleOffset` 即可）；
- `color-interpolation-filters` 初始 **linearRGB** ⇒ 表格作用在线性光，最后转 sRGB；
  `type='table'` 在浏览器里是 **256 项 8bit LUT**（非预乘取值 + 折线 + 截断）；
- **实测对账**：本实现输出 `mean alpha = 17.0711 / max = 73`，与 headless Chromium 实渲染同一条
  data URI 的统计（17.07 / 73）**一致**（逐字节层面 RGBA 98.92% 相同，其余差 1–2 LSB）；
- 生成在 **isolate** 里跑（debug JIT 下数百 ms），不阻塞 UI 线程。

### 8.7 第二轮：绘制顺序修正 + 画布重绘隔离（2026-09-25）

**① 背景发白（用户截图实报：「你是不是给光斑层加了一层全白遮罩」）** —— 根因是**绘制顺序**：
CSS 的 `background` 列表**第一项在最上层**，而 canvas 是「后画的盖住先画的」。原实现按列表顺序
正着画 ⇒ 第 9 层（中心暖白光晕）与 5–8 层（四边隔离白光斑）压在四角四色**之上** ⇒ 整片发白。
修法：新增 `AylaFluidAurora.paintOrder`（= `staticLayers.reversed`），绘制一律倒序；
回归锁 = `test/aurora_background_test.dart` 的「九层绘制顺序」用例。

**② 画布滚动重绘隔离** —— 画布是 `SingleChildScrollView` + 单个 Column，滚动时整列都会被
paint 遍历；现在 `_Section` 根包 `RepaintBoundary`（每个分区一个独立重绘边界），
让 `paintChild` 只更新 layer offset、不重绘子树。

**③ 一条被证伪的指标（诚实留档）** —— 我本想用「滚动一屏后仍需重绘的 RenderObject 数」做回归锁，
实测**加边界前后都是 4652**：`debugNeedsPaint` 在 `SingleChildScrollView` 里反映的是
「**未进入视口、因而没被绘制过**的节点数」（整列都会 layout、只有视口内的才 paint），
与 `RepaintBoundary` 无关 ⇒ 该指标**测不准，已删除**，只在 `perf_audit_test.dart` 留说明。
教训：**加锁前先验证这个指标真的会对被测量敏感**（否则它只是一条永远绿/永远红的噪声）。

### 8.9 第四轮：模糊扩散预留（修「裁切边旋转露出来」）+ 剩余动画隔离

**用户实报**：「背景总是出现裁切边旋转露出来」。两个叠加原因：

1. **模糊被裁成硬边**（主因）：CSS 的 `filter: blur()` 有 **filter region**（默认向外扩 10%），
   模糊结果可以**超出元素盒**；而 `Canvas.saveLayer` 会把内容裁在 bounds 内 ⇒ 边缘的扩散被
   切掉，露出**硬直边**。
   **修法**：新增 `AylaAuroraBakedLayer.blurOverscan`（= 3σ）—— 烘焙图四周多出空环、内容按原尺寸
   居中绘制，模糊自然渐隐到透明；层尺寸 +2×overscan、位置 -overscan，**中心不变**（旋转/缩放的
   基准点不受影响）。渐变层 overscan = 120（3×40），湍流层 = 180（3×60）；光斑层**不需要**
   （radial 70% 截止 ⇒ 内容边缘本就透明，避免白花像素预算）。
2. **几何覆盖**：150vmax 层在 `scale(0.78) + 漂移 4%` 的最坏相位下，内切圆 51vmax < 16:9 视口的
   角落距离 57.3vmax ⇒ **角落覆盖不足**。这是 **web 的既有行为**（同一份 150vmax 与关键帧；
   web 注释只算到「视口边缘 50vmax」没算角落），露出的部分由 `html` 静态兜底（同一套九层）填充
   ⇒ 修好第 1 条后是与 web 一致的**柔和过渡**。若用户仍要看不出边缘，可选把层加大到 ~170vmax
   （**偏离 web，需拍板**）。

**回归锁**（`test/aurora_background_test.dart`，现 21 用例）：
`overscan = 3σ 且 > 0` · 几何断言按「内容 + 2×overscan」对账 · `aylaAuroraBakePixels` 同步把
overscan 计入外框（1080p 实测仍 ≈4.4M 像素，预算 6M 内）。

**剩余 3 处动画隔离**（弹幕飘动条 / RefreshFab 旋转 / 录音波形）：⏳ 子代理并行进行中，完成后单独提交。
