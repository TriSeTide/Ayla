### 8.2 性能事故与修法（**必须记住，别退回**）

- **事故**：首版把四层各自套 `ImageFiltered`。Flutter 的滤镜是 **layer 属性 —— 每帧合成重跑**，
  而 web 的 `filter: blur()` 是浏览器合成器缓存成纹理后只做变换。实测后果：渐变层一张
  3600×3600（51.8 MB）+ 湍流层 3600×2025（29.2 MB），五层峰值 200 MB+ 且逐帧重算 ⇒
  用户实测「太卡了完全没法正常看，debug 模式也是直接闪退」+ 爆显存黑屏。
- **修法**：`AylaAuroraBakedLayer` —— `saveLayer(imageFilter:)` 录制 → `Picture.toImage()`
  **一次性烘焙**，之后每帧只 `drawImage` + 变换（= 手写浏览器合成器那一步）。
- **预算**：低频层按最长边 cap 降采样（静态/渐变 1440 · 湍流 1024 · 光斑 512），
  五层总像素 `AylaFluidAurora.bakePixelBudget = 6M`（≈24 MB）；1080p 实测 ≈4.35M 像素。
- **回归锁**（`test/aurora_background_test.dart`，19 用例）：背景子树里**不得出现
  `ImageFiltered`/`BackdropFilter`**；`aylaAuroraBakePixels()` 在 1080p/4K 下都必须 ≤ 预算。
- **帧率口径**：`kAuroraFrameInterval` **默认 `Duration.zero`（满帧）**；
  它只是「低端设备 / 省电模式」的预留旋钮（设 33ms 之类即降档），正常路径不要动。

### 8.3 湍流纹理：按 **Skia 变体**精确复刻（不是规范参考实现）

- 规范 C 参考实现与浏览器**不一致**：规范里梯度向量长度 >1 会丢弃重抽（约 21.5% 概率触发），
  Chrome/Skia、Firefox/Gecko、Batik 都**不丢弃** ⇒ 随机数消耗序列不同、lattice 洗牌结果不同。
  本实现按 Skia：4 通道 × 256 项（每项恰好 2 个随机数）→ 洗牌 255→1 → 置换 + 归一化 + 16bit 量化；
- 采样点 **`(x + 1.0) × baseFrequency`**（Chrome 的 +0.5 +0.5；Firefox 是 `x × freq`，
  差 1 设备像素相位，想对齐改 `AylaTurbulenceSpec.sampleOffset` 即可）；
- `color-interpolation-filters` 初始 **linearRGB** ⇒ 表格作用在线性光，最后转 sRGB；
  `type='table'` 在浏览器里是 **256 项 8bit LUT**（非预乘取值 + 折线 + 截断）；
- **实测对账**：本实现输出 `mean alpha = 17.0711 / max = 73`，与 headless Chromium 实渲染同一条
  data URI 的统计（17.07 / 73）**一致**；
  ⚠️ **「逐字节 RGBA 98.92% 相同」这句旧结论已作废**（2026-09-27 §8.18 更正）：当时的对比走了
  `toByteData(png)` 中转，而该接口按**预乘**解释输入 —— 它把当时那份**非预乘**数据整片钳成
  255，恰好掩盖了真实缺陷，于是对比显示出「几乎一致」。重做后（直接比原始字节）真实一致率是
  **97.98%**，且余下差异全部来自 8bit 预乘往返的量化；同一次重做还抓出**落盘格式必须预乘**
  这一硬约束（见 §8.18 第 3 条）。
- 生成在 **isolate** 里跑（debug JIT 下数百 ms），不阻塞 UI 线程。

### 8.7 第二轮：绘制顺序修正 + 画布重绘隔离（2026-09-25）

### 8.9 第四轮：模糊扩散预留（修「裁切边旋转露出来」）+ 剩余动画隔离

**用户实报**：「背景总是出现裁切边旋转露出来」。两个叠加原因：

1. **模糊被裁成硬边**（主因）：CSS 的 `filter: blur()` 有 **filter region**（默认向外扩 10%），
   模糊结果可以**超出元素盒**；而 `Canvas.saveLayer` 会把内容裁在 bounds 内 ⇒ 边缘的扩散被
   切掉，露出**硬直边**。
   **修法**：新增 `AylaAuroraBakedLayer.blurOverscan`（= 3σ）—— 烘焙图四周多出空环、内容按原尺寸
   居中绘制，模糊自然渐隐到透明；层尺寸 +2×overscan、位置 -overscan，**中心不变**（旋转/缩放的
   基准点不受影响）。渐变层 overscan = 120（3×40），湍流层 = 180（3×60）；光斑层**不需要**
   （radial 70% 截止 ⇒ 内容边缘本就透明，避免白花像素预算）。
2. **几何覆盖**：150vmax 层在 `scale(0.78) + 漂移 4%` 的最坏相位下，内切圆 51vmax < 16:9 视口的
   角落距离 57.3vmax ⇒ **角落覆盖不足**。这是 **web 的既有行为**（同一份 150vmax 与关键帧；
   web 注释只算到「视口边缘 50vmax」没算角落），露出的部分由 `html` 静态兜底（同一套九层）填充
   ⇒ 修好第 1 条后是与 web 一致的**柔和过渡**。若用户仍要看不出边缘，可选把层加大到 ~170vmax
   （**偏离 web，需拍板**）。

**回归锁**（`test/aurora_background_test.dart`，现 21 用例）：
`overscan = 3σ 且 > 0` · 几何断言按「内容 + 2×overscan」对账 · `aylaAuroraBakePixels` 同步把
overscan 计入外框（1080p 实测仍 ≈4.4M 像素，预算 6M 内）。

**剩余 3 处动画隔离**（弹幕飘动条 / RefreshFab 旋转 / 录音红点）：✅ **已完成**（子代理批次，见 §8.11；danmaku 落点是**整层边界**且有命中测试机理说明）。

> 只是它与用户当时看到的「白」不是同一个原因。

用户报「组件库第一张样张基本没问题，问题是 app 背景就是白很多」，并猜测「是不是没给背景自适应
缩放进 app 窗口」——**自适应本身是对的**（`AylaAuroraBackground` 用 `LayoutBuilder` 的约束，
= 窗口尺寸；`LoginPage` 全文也无任何全屏底色，已逐行确认），但排查中找到一个**真实的机制**：

**机制**：`AylaAuroraBakedLayer` 的烘焙是**异步**的（`Picture.toImage()`）。
就绪之前 `build` 返回 **`RawImage(image: null)`** —— 它**什么都不画**，直接透出兜底底色（白）。
更糟的是 `_bake()` **没有 try/catch**：一旦 `toImage` 抛异常（显存不足 / 设备丢失 / 尺寸异常），
`_baking` 永远停在 `true` ⇒ `_maybeBake` 以后直接 return ⇒ **该层永久空白**。

**为什么 app 比样张更容易踩**：层尺寸随视口走 —— 样张 1440×810 的流层是 2160，app 大窗口
（如 1920×1080）是 **2880**，烘焙图同样顶到 cap 2048 但**源尺寸更大、五层同时烘**，
首帧窗口更长、失败概率更高。而「白很多」正是「静态层空白 + 只剩兜底白」的样子。

**修法（两处）**：
1. `build`：`image == null` ⇒ **降级为直接绘制**（`CustomPaint` 调同一个 draw 函数）——
   宁可每帧重画一次，也不能给用户一块白板；降级路径**不施加 blur**（那会变成每帧跑滤镜，
   正是本组件要避免的），并在注释里写明这个取舍；
2. `_bake()`：加 `try/catch/finally` —— 失败时复位 `_bakedSize/_bakedRevision` 允许重试，
   `_baking` 一律在 finally 复位（此前异常会让它永久卡住）。

**回归锁**：`test/aurora_background_test.dart` 新增「烘焙未就绪/失败时降级为直接绘制 ——
背景永远不是白板」：断言背景子树里**不存在 image 为 null 的 `RawImage`**。
（另记一条测试纪律：**不要在测试里断言"首帧一定未就绪"** —— 实测测试环境下 `toImage`
常常在首帧就完成，那时序断言只会变成噪声。）

⏳ ~~仍需用户实机确认：这是从代码得出的最可能机制~~ —— **已由 §8.18 的逐像素对账取代**：
「app 白」的真实机制是湍流层未预乘（全屏均匀抬亮），已修并对账收敛。

### 8.15 第十轮：**光斑层补模糊扩散预留**（用户「少了一层的感觉」的正解，2026-09-27）

用户：「感觉还是少了东西，有种少了 web 一层的感觉，但我说不清是哪一层。我记得有湍流层、渐变层、光斑层」。

**先按要求「从代码数层」**（不是看图）：
- 全仓 CSS 里背景伪元素**只在 `base.css`**（其它文件零命中）；
- 被真正 `var()` 使用的 `--fluid-*` 只有 5 个：`gradient-speed` / `turbulence-speed` /
  `turbulence-opacity` / `blob-ice-rgb` / `blob-sakura-rgb` —— **实现全都有**；
  其余 8 个（`--fluid-blob-ice-svg` / `-sakura-svg` / `--fluid-blob-blur` / `-opacity` /
  `-speed` / `-ice` / `-sakura` / `--fluid-blob-glow-opacity` / `--fluid-gradient-angle`）
  **是遗留未用变量**（tokens.css 里注释也写了「光斑层已移除，保留变量备用」）⇒ 不需要实现。
⇒ **层数一致**（静态九层 + 渐变流层 + 湍流层 + 冰蓝光斑 + 樱粉光斑 = 5）。

**但用户的"少了一种感觉"是对的，而且找到了被削弱的那一层：光斑。**
上一轮我给渐变层/湍流层加了模糊扩散预留（overscan），**唯独跳过了光斑**，理由是
「radial 70% 截止 ⇒ 圆外已透明 ⇒ 不需要」——**这个判断是错的**：`blur(40px)` 会把**圆内的颜色
向外扩散**，而 `saveLayer` 把扩散裁在元素盒内 ⇒ 圆边界被**硬切**，观感从 web 的
「弥漫开的大片光」变成「一个圆斑」（用户截图里那个明显的淡蓝圆斑就是它）。
**已补上** `blobOverscan = 3×40 = 120`，与渐变/湍流层同构（中心不变、Transform 位移基准仍是
diameter）；测试里的「光斑不需要预留」注释同步**改成更正说明**，并加断言
`blobOverscan == blobBlur × 3`。

**本轮同时交付**（§8.14 的机制修复，一并提交）：`烘焙未就绪/失败时降级为直接绘制` +
`_bake 的 try/catch/finally 复位`（此前失败会让 `_baking` 永久为 true ⇒ 该层永久空白）。

#### ② 静态半透明 → 颜色 / 渐变 alpha（零视觉代价，−256 个 `Opacity` 层）

不透明色块 / 单条文本（抗锯齿 = coverage×color over 背景）/ 单层渐变 / 互不重叠的描边 ——
这几类都可以零视觉代价地换掉；**有重叠的**（色条压在半透明底上、玻璃模糊层 + 内容层）保留。

| `widgets/chat/share_bubble.dart` chevron | `Opacity(.7)` 包两条描边 | 描边色 ×.7 | `box-shadow` 无关：`BoxBorder` 在角部按**斜接**分割、两条边不叠加 |
| `widgets/chat/media_content.dart` 下载键 | `Opacity(enabled ? 1 : .55)` 包单图标 | 图标色 ×.55 | `:disabled` 语义；单图标无重叠 |

#### ② 对账方法（本轮的方法论突破，**别退回看图猜**）

1. **相位对齐**：web 侧用 `document.getAnimations().forEach(a => { a.pause(); a.currentTime = t })`

### 4.6 页面转场修复（2026-09-28 用户实报：切换生硬 + 登录注册页左侧会动 + 重影）

**用户反馈**：截图显示页面切换「太生硬、白屏淡入淡出太多」，且登录/注册页的左侧品牌区不应被动。

**定位到两个独立根因**（都实测红过）：

1. **平台默认转场与自研转场叠加**：`MaterialPage` 自带平台转场（Windows/Linux 默认
   `FadeUpwardsPageTransitionsBuilder`：300ms 上滑 + 整页淡入），与库内 `AylaPageTransition`
   （y +20 / scale .95 / 500ms 淡入）叠加 ⇒ 位移与白屏时间翻倍。web 侧 React Router
   **本身不做转场**（唯一 owner 是 `PageTransition.tsx`）。
2. **新旧页并存的所有权错位 + 重影**：`AylaPageSwap` 在 widget 层用 Stack 保留旧页，但
   · go_router 的 `ShellRoute` 的 `child` **就是** shell navigator，其 key 是
     `GlobalObjectKey(navigatorKey.hashCode)`（`go_router/lib/src/builder.dart:287`），**故意**靠
     同一 GlobalKey 复用 Element ⇒ widget 层再保留一份 ⇒ `Multiple widgets used the same GlobalKey`；
   · 用 `builder` 传内容时闭包读到**当前** child ⇒ 旧槽里放的是**新页副本** ⇒ 就是截图里的**重影**
     （两层一模一样的内容）。

**修复**：
· 新增 `theme/page_transitions.dart` 的 **`AylaPageTransitionsBuilder`**（Navigator 层，全局唯一 owner）：
  `animation` = 本页进场（y +20 / scale .95 / 500ms `auroraquaEaseOut`）、
  `secondaryAnimation` = 被新页覆盖（300ms 淡出）= web `AnimatePresence mode="sync"` 同语义；
  分档：群页只 opacity · `panelOwned` 整页不动 · **`/login` `/register` 完全无转场**
  （web 顶层 Route 在 AppShell 之外）· reduced-motion 直通；
· `theme/app_theme.dart` 的 `pageTransitionsTheme` 全平台指向该 builder（取代平台默认）；
· `layout/app_shell.dart` 内容区改为直接放 `widget.child`（**不再**用 `AylaPageSwap`）；
· `aylaPanelOwned` 从 `app_shell.dart` 移入 `router/shell_config.dart`（纯函数层，供 theme 复用、
  避免 theme→layout 反向依赖）；
· `AylaPageSwap` / `AylaPageTransition` **保留**（画布样张 + 自持叠放的局部场景），文件头写明
  「不要在 AppShell 里用它们做全局路由转场」及两条血泪原因。

**测试**：新增 `test/router_test.dart` **8 条**（转场 owner 非平台默认 · shell 纯函数 · 守卫 + `?next=`
回跳 · 成环防护 · catch-all · 转场分档 · **换页转场中途 `takeException()==null`**）——最后一条正是
抓出 GlobalKey 冲突的用例。
