## 1. 三个 hub 页的全部选项卡（逐档）

### 1.0 判据先说清（决定「帧来了这一档会不会变」的四道门）

```
WS 帧 ──①落域 store──► 域 store(channels/rooms) ──②订阅通路 diff──► updateCachedItems
                                                              │
                                          ③ 该档 record 是否 **已存在**（只有一个 tab 被 load 过才有 record）
                                                              │
                                          ④ items 变更判据：
                                             · updated：record.items 里**已有**该 id ⇒ 用新描述符替换（人数/状态/标题即时生效）
                                             · added  ：只认 _createdIds 提示 或 查询维度 false→true（**不含分类 tab 维度**）
                                             · removed：过 _matchesQuery 后被过滤掉
                                             · complete = fetchedAt!=null && !hasMore ⇒ added 才真正并入 items
                                             否则 invalidated=true ⇒ 页脚自动 refresh（AylaDirectoryLoadMore._maybeAutoRefresh）
                                                              │
                                          ⑤ 页面重建：controller.addListener(_onPagerChanged) → postFrame setState
```

证据：
- ①②：`room_frames.dart:241–323`（帧→store）、`directory_tracking.dart:122–162`（store→diff）、`directory_store.dart:476–586`（diff 本体）
- ③：`directory_store.dart:495`（`if (_records.isNotEmpty)`）+ `498–503`（只 patch 同 kind 的 record）；record 由 `load()` 的 `_patch` 建立（`directory_store.dart:708–715`）
- ④：`directory_store.dart:515–547`（updated/removed/added/complete/invalidated）；web 对照 `stores/directory.ts:148–196`
- ⑤：`voice_hub_page.dart:217/179–193`、`live_hub_page.dart:204/170–184`、`games_hub_page.dart:221/188–201`

> ⚠️ **关键判据（任务书要求）**：`updateCachedItems` 只对**已加载的 record** 做 diff。
> 某档从未加载 ⇒ store 里**没有 record** ⇒ 帧来也不凭空建 —— 该档首次进入时**由 REST 首屏决定**
> （60s 内命中缓存则直接用旧 record，见 `directory_store.dart:684–688` / web `:274`）。

### 1.1 语音大厅 VoiceHubPage（5 档）

web 事实源：`pages/VoiceHubPage.tsx:34–41`（FILTERS）、`:58–64`（options）、`:76–87`（前端二次过滤）
Flutter：`pages/voice_hub_page.dart:80–87`（filters）、`:195–237`（`_start()` 构造 options）、`:299–318`（前端二次过滤）、`state/hub_directory_options.dart:70–97`（options 单一事实源）

| 档 | label | options（含 filter） | directoryKey 关键段 | 帧能 patch 到？ | 新增能并入？ | 页面会重建？ |
|---|---|---|---|---|---|---|
| `all` | 全部 | `{filter:'all', 其余全 false/null}` | `filter=all` | ✅（record 存在时 updated/removed 生效） | ✅ created 帧（createdIds） | ✅ |
| `public` | 公开 | `{filter:'public', visibility:'public'}` | `filter=public, visibility=public` | ✅ | ✅ created 帧；⚠️ 前端再过滤 `visibility==public` 会兜底 | ✅ |
| `friends` | 好友 | `{filter:'friends', friends:true}` | `filter=friends, friends=true` | ✅（items 层） | ⚠️ 后端已过滤 + 前端用 `friendIds` 集合再过滤；`friendIds` 来自 social store 第一页（`hub_support.dart:472–482`），**好友关系变化不实时** | ✅ |
| `occupied` | **有人** | `{filter:'occupied', occupied:true}` | `filter=occupied, occupied=true` | ✅ 已有条目的人数会实时改 | ❌ **0→N 不会并入**（R-2，见 §2） | ✅ |
| `mine` | 我的 | `{filter:'mine', owner:currentUserId}` | `filter=mine, owner=uid` | ✅ | ✅ created 帧 + `matchesFilter mine` 判 `ownerId==me` | ✅ |

Flutter `directoryKey` 的 11 段顺序为 `userId|kind|groupId|onlyLive|filter|visibility|friends|occupied|status|owner|mine`（`directory_store.dart:174–184`），web 是等序 JSON 数组（`stores/directory.ts:88–92`）。

**该档是否会被帧更新到的结论**：
- 只要该 tab **被点开过**（有 record），`voice.channel.member_count_changed` / `.updated` / `.deleted` 都会 patch 到它的 **items 里已有的条目**；
- 「有人」档额外依赖「该房**本来就在**这一档的 items 里」——这就是用户实报的现场（见 §2）；
- 切 tab 会 `_start()` 重建 controller（`voice_hub_page.dart:283–297`），`load()` 命中 60s 缓存则不重拉（`directory_store.dart:684–688`）⇒ **切过去看到的是缓存里那份，可能仍是旧的**（这正是 §2.4 的第二个表现面）。

### 2.2 断点：⑦ 的 **added 判据**（R-2，未修）

```dart
// directory_store.dart:526-537（web stores/directory.ts:166-171 逐字同源）
final List<Object> added = _mergingPage ? const <Object>[] : <Object>[
  for (final Object item in next)
    if (!record.items.any((c) => _itemKey(c) == _itemKey(item)) &&   // 本档 items 里没有
        _matchesQueryOf(record, item) &&                              // 只判 groupId / onlyLive
        (_createdIds[kind]!.containsKey(_itemKey(item)) ||            // ← 只认「创建提示」
         (before[_itemKey(item)] != null &&
          !_matchesQueryOf(record, before[_itemKey(item)]!))))        // ← 查询维度 false→true
      after[_itemKey(item)]!,
];
```

`member_count_changed` 帧**不登记** `_createdIds`（只有 `.created` 帧登记：`room_frames.dart:267/156–166`；
web `stores/directory.ts:228–234`）。因此：

| 场景 | before（上次数域快照） | 本档 record.items | added | 结果 |
|---|---|---|---|---|
| 新房**创建**（created 帧） | 无该 id | 无 | ✅ `_createdIds` 命中 | 并入（若 complete）或 invalidated→自动 refresh |
| **已存在**的房从 0 人 → N 人 | **有**该 id（「全部」档取过 ⇒ 域 store 有） | **无** | ❌ 两个条件都不成立 | **不并入** ⇒ 「有人」档看不到 |
| 有人在房里但该档**从未加载** | —（无 record） | —（无 record） | — | 无 patch；切过去时 REST 首屏（`occupied=1`）会带上 ⇒ **切 tab 能看到** |
| 该房**本来就在**「有人」档 items 里（人数变化） | 有 | 有 | （走 updated 分支） | ✅ 人数即时刷新 |

**⇒ 用户实报的精确形态**：用户**已经在**「有人」档停留（record 已加载，items 里只有旧的有人的房），
另一个账号进入**一个已存在、此前无人**的语音房 ⇒ `member_count_changed` 到达 ⇒（修复后）REST 对账 →
`upsertChannel` 进域 store ⇒ diff：该房**不在** record.items、`_createdIds` 无、`before` 里存在且查询维度没变
⇒ **不并入** ⇒ 「有人」档纹丝不动。

### 2.3 与 web 的关系

web 是**同一份实现**（`stores/directory.ts:166–171`），即 web 也有这个缺口；但 web 的目录 record
**不会**像 Flutter 这样被 17 档全量预取（`appInit.ts:34–42` 只预取「全部」档）⇒ web 上「有人」档通常
在**首次点开**时才建 record，首次 REST 就已经把「有人的房」一并带回 ⇒ 观感上更少踩中这一档。
Flutter 预取让它**更容易**踩中（record 一直在、items 一直旧）。

### 2.4 建议修复方向（不改，仅给规格）

1. **（必须，R-2）给 `updateCachedItems` 的 added 判据补「分类维度 false→true」**：
   把 `_matchesFilterOf(record, item, currentUserId)` 的**前后值**纳入判据 —— 当
   `before` 里同 id 条目对**本 record 的 filter** 判 false、`after` 判 true 时，也算新增。
   这与 web 注释 `stores/directory.ts:115–120` 的「items 保持宽松、只算 total」**冲突** ⇒
   **属有意偏离 web，需用户裁决**（web 现状也确实漏这一档）。
2. **（建议）`member_count_changed` 分支补「0→N 视同需要重取该 kind 的 occupied 档」**：
   即帧到达后对 `filter=='occupied'` 的 record 置 `invalidated`（页脚自动 refresh 会拿回正确首屏）。
   代价：每次有人进房都触发一次 REST（可按 250ms 合并，参考 `group_presence.dart` 的合并窗口）。
3. **（替代方案，最小面）房内页进房成功后主动 `noteCreated(voice, id)`**：`AylaVoiceRoomHost._bootstrap`
   （`voice_support.dart:959–977`）在 `join` 成功后补一次 `aylaDirectoryStore.noteCreated(voice, channelId)`。
   这能让「自己进房」这一个高频场景立刻生效（但看不到「别人进房」，覆盖面小）。

## 3. 状态类选项卡的**通用**残余缺口（R-3）

同一机制在 5 个档重复，逐个给两侧证据：
