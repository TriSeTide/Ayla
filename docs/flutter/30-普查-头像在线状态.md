## 二、根因：`AylaAvatarHalo.online` 是不可变构造参数，且组件不订阅

### 2.1 组件本身（HEAD `ed7472e`）

```dart
// flutter/lib/widgets/base/avatar_halo.dart
46: class AylaAvatarHalo extends StatefulWidget {      // ← 普通 StatefulWidget，不是 Consumer(Stateful)Widget
47:   const AylaAvatarHalo({
51:     this.online = false,                            // ← 在线态是构造参数
...
59:   /// 在线状态（false = --ice-100 灰环）。
66:   final bool online;                                // ← final，构建后不可变
...
111:     final bool shouldBreathe = widget.online &&      // 呼吸
125:     if (widget.online != oldWidget.online ||        // 只在**父级重传新值**时才重启动画
151:     final Gradient ringGradient = widget.online      // 光环渐变（在线=彩环/离线=ice100）
259:     final bool breathe = widget.online &&
303:     boxShadow: widget.online &&
317:     final String stateLabel = widget.online ? '在线' : '离线';
```

**这是根因形态①「数据源错位」的教科书样本**：
组件只认「调用方此刻传进来的布尔」，**自己不看 presence store**。
所以即使 presence 帧 100% 正确地写进了 `presenceStateProvider`，
只要调用方（或调用方的调用方）用的是 REST 快照，光环就永远是快照那一刻的值。

### 2.2 web 的对照物不是「传 prop」而是「消费端订阅」

```tsx
// web/src/components/Avatar.tsx:15–36 —— web 的 Avatar 同样接 online prop（这点与 Flutter 一致）
18:   online = false,
28:   online?: boolean,
66:   className={`avatar-halo ... ${online ? "" : "is-offline"}`}
```
**web 的 Avatar 也是纯展示**（`Avatar.tsx:1–11` 文件头只讲视觉）。区别在于：
**web 的每个调用点自己就是订阅者**（`usePresenceStore` / `usePresenceOnline`），
React 的 store 订阅让**调用点的组件重渲染** ⇒ 新布尔值随 render 传进 Avatar。
Flutter 侧缺的正是这一层：**调用点是 Stateless/普通 Stateful，没有订阅**。

### 2.3 全库订阅点盘点（grep 可复现）

```
grep -rn "presenceStateProvider" Ayla/flutter/lib --include=*.dart | grep -v state/presence_providers.dart
→ pages/group_info_page.dart:545, :547
→ pages/user_profile_page.dart:469, :471
```
**只有 2 个文件、4 行**。对比 web：24 个消费点（§1.2）。

### P1-2 让叶子组件能自己订阅（气泡/评论/帖子/弹幕这类「深」调用点）

这些叶子拿不到页面 `ref`，两条可行形状：

- **形状 ①（组件自订阅）** 给 `AylaAvatarHalo` 新增 `AylaUserPublic? user` / `String? userId`，
  内部**真正订阅** presence。**三种实现里只有前两种有效**：
  - ①a `ConsumerStatefulWidget` + `ref.watch(presenceStateProvider)`
    （`consumer.dart:559–573`：`watch` → `_container.listen(target, (_,__) => markNeedsBuild())`）；
  - ①b 普通 `StatefulWidget` + `ListenableBuilder(listenable: presenceState, …)`
    （`AylaPresenceState extends ChangeNotifier`，`presence_state.dart:33`）；
  - ❌ **不要** `ProviderScope.containerOf(context, listen: true).read(presenceStateProvider)` ——
    **当前工作树正是这个写法，它不生效**（完整证明见 §8.2：`container.read` 不建监听
    + 该 InheritedWidget 的 `updateShouldNotify` 恒 false）。
  **⚠️ 兼容性坑**：`AylaAvatarHalo` 被大量既有 widget 测试用 `previewTheme`（**不含 ProviderScope**）渲染；
  `ProviderScope.containerOf` 在无 scope 时**抛 `StateError: No ProviderScope found`**（`framework.dart:109–111`）
  ⇒ 要么把这些测试宿主换成 `previewScope`（`theme/preview_theme.dart:80–84`），
  要么实现里 try/catch 降级（工作树的降级思路正确，只是**求值方式**错了）。
- **形状 ②（最小改动，不动叶子）** 沿用本仓既有的 `bool Function(AylaUserPublic?)` 注入范式
  （`conversation_list.dart:147`、`mention_picker.dart:104`、`request_rows.dart:329`、`comments.dart:674`、
  `post_card.dart:166`），把**所有调用点**都接上：`(u) => presenceOnline(onlineUsers, withLiveStatus(statuses, u))`，
  其中 `onlineUsers/statuses` 来自页面级 `ref.watch`（P1-1）。**叶子零改动，测试零风险。**

> **建议**：P1-1（页面订阅）+ 形状②（叶子注入）先做，覆盖 #3 #5 #7 #9 #10 #11 #22 #23 #24 #25 #28 #29 #30；
> 只有 **#8 气泡 / #18 弹幕**（每行一个发送者、页面不便逐条算）用形状①最自然。

### 8.2 工作树那版接线的机制**是错的**（本轮最重要结论）

当前工作树（`avatar_halo.dart` md5 `052c6583…`）的求值函数：

```dart
// 工作树当前写法（avatar_halo.dart:152–161）—— 无效：不建立 provider 监听
AylaPresenceState? _presenceOrNull() {
  try {
    return ProviderScope.containerOf(context, listen: true)
        .read(presenceStateProvider);          // ← 关键：container.read()
  } on StateError {
    return null;
  } catch (_) {
    return null;
  }
}
```

**为什么它不热更新（三条独立证据，逐条可查）**：

1. **`ProviderContainer.read()` 不创建任何监听器**
   （riverpod `container.dart:238–242`：`Result read<Result>(p) { return p.read(this); }` ——
   只是求值，不 `listen`、不注册回调）。
   ⇒ presence 帧写入 store 时，**没有任何人通知这个头像**。

2. **`containerOf(context, listen: true)` 注册的是 InheritedWidget 依赖，而不是 provider 依赖**
   （flutter_riverpod `framework.dart:100–102`：`dependOnInheritedWidgetOfExactType<UncontrolledProviderScope>()`）。
   而该 InheritedWidget 的 `updateShouldNotify` 是
   `container != oldWidget.container`（`framework.dart:287–289`）。
   `ProviderContainer` 是**登录周期内的长生命周期单例**（`presence_providers.dart` 的 provider 只建一次），
   **永不变化 ⇒ `updateShouldNotify` 恒 false ⇒ 依赖者永不重建**。

3. **对比正确写法**：`ConsumerState.ref.watch` 走的是
   `_container.listen<Res>(target, (_, __) => markNeedsBuild())`
   （flutter_riverpod `consumer.dart:559–573`）—— 它建立的是**真 provider 订阅**，
   store `notifyListeners` 时会命中回调并 `markNeedsBuild`。

**结论**：这版接线「代码看着通了、参数也传下去了、review 很容易放过」，
但 **`AylaAvatarHalo` 依然不会因 presence 帧重建 ⇒ 用户可见效果与修复前完全相同**。
这是本轮最危险的陷阱：**「传参」≠「订阅」**。

**两种正确写法**（择一即可）：

- **A（推荐）** 改 `ConsumerStatefulWidget` + `ref.watch(presenceStateProvider)`
  ⇒ 等价 web `usePresenceOnline`。
  **代价**：组件将要求 `ProviderScope` 祖先；当前大量既有 widget 测试用
  `previewTheme`（**不含 scope**）渲染，`ProviderScope.containerOf` 在无 scope 时
  **抛 `StateError: No ProviderScope found`**（`framework.dart:109–111`）
  ⇒ 需同步把相关测试宿主换成 `previewScope`（`theme/preview_theme.dart:80–84`），
  或在无 scope 时降级（工作树现有的 try/catch 思路是对的，只是求值方式错了）。
- **B（零风险）** 保留 `StatefulWidget`，但用
  `ListenableBuilder(listenable: presenceState, builder: …)` 包住光环渲染
  （`AylaPresenceState extends ChangeNotifier`，`presence_state.dart:33`）；
  `ListenableBuilder` 内部是真 `addListener` ⇒ 会重建。无 scope 时同样可 try/catch 降级。
- **C（最贴 web）** 不在组件里订阅，改为**页面级 `ref.watch` + 显式传值**
  （见 §5 P1-1），叶子组件保持纯展示 —— 这与 web「调用点自己订阅」的分层完全一致。

### 8.3 教训

**「加了参数」≠「订阅」≠「接上了实时」** —— 三者是三个不同的门槛：

| 门槛 | 反例（本轮真实发生） | 怎么证明真的过了 |
|---|---|---|
| 参数存在 | 组件加了 `user`/`userId` | 编译通过 |
| 参数传下去 | 14 个调用点传了 `userId: x.id` | 读调用点 |
| **真的会重建** | —— 工作树那版**卡在这一步**（`container.read` 无监听） | **帧驱动 UI 落地测试**（§6 末尾） |

验收判据必须是「**presence 帧到达后某处 UI 真的变了**」，而不是「参数传下去了」。
建议把这条写成 PR 检查项：凡涉及 presence/WS 实时性的改动，**必须附带一条
「注入帧 → 断言 UI 变化」的测试**，否则视为未完成。
