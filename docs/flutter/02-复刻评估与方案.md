> 调研日期：2026-09-16

> 约束回顾：目标是**一比一复刻** Ayla Web 现有界面与交互到 Flutter，打包 Windows/Android/iOS

## 1. 工程量总体直觉

先说结论：**这是一个完整的中大型社交应用，不是"聊天 Demo"**。有 web 源码 + design.md 规格书做对照，等于"有完整图纸照着画"，vibe coding 可行性高；但量在那里，预期是**多轮、分阶段的长期工程**。

体感拆分：

| 部分 | 占比体感 | 说明 |
|---|---|---|
| 纯 UI 重写（组件/布局/动效/双形态） | ~55% | 85 组件 + 15 layout + 19 样式文件的手写体系，逐组件对照翻译 |
| 数据与状态层（22 stores + 19 api + 4 ws + 37 hooks 逻辑） | ~25% | 代码量不小，但模式统一，翻译成本线性 |
| 实时媒体链路（音频中继 / HLS 直播 / 签名媒体） | ~15% | 代码量最小但**难度最集中**，平台无现成等价物 |
| 平台适配与打磨（三端差异/性能/手势手感） | ~5%+ | 收尾期的隐藏时间黑洞，建议预留 |

容易出成果的顺序（先甜后苦更符合 vibe coding）：**认证 → 群列表与聊天（窄屏） → 消息中心/私聊/搜索/收藏/个人 → 内容域（帖子/桌游） → 语音 → 直播 → 宽屏三列 → 手势与平台打磨**。语音/直播虽排后，但两条媒体链路建议**提前各做一次 PoC**（见 §5 热点 1、2），因为它们决定架构选型，不能等做到那一步再发现方案不可行。

## 2. 技术选型建议（web → Flutter 对照）

### 2.1 核心依赖对照表

| Web 端 | Flutter 侧建议 | 理由 |
|---|---|---|
| Zustand（22 store） | **Riverpod**（flutter_riverpod） | 声明式、无 Provider 树、provider 生命周期与 store 一一对应；KeepAliveProvider 对应全局 store，FutureProvider 对应预加载 |
| react-router 6 | **go_router** | 声明式路由、嵌套、重定向（`/` → `/group`）、守卫（ProtectedRoute → redirect）直接对应；24 条路由可直映 |
| fetch + 拦截器（api/client.ts） | **dio** | 拦截器做 401 静默刷新 + 重放一次；与 web 端 refreshPromise 互斥锁同构；上传进度/取消（XHR 语义 dio 原生支持） |
| 原生 WebSocket×4 通道 | **web_socket_channel** | 四通道（chat/live/voice/presence）均为文本帧（JSON）+ 音频通道需二进制帧（dart:io WS 原生支持 binary） |
| framer-motion | Flutter 动画体系（AnimationController / ImplicitlyAnimated / AnimatedSwitcher / Hero） | "跟手"→GestureDetector+Controller；"进出协同"→AnimatedSwitcher/FadeTransition；"编排"→多 Controller 编排。framer-motion 三职责在 Flutter 有天然对应 |
| hls.js | Android: **video_player**(ExoPlayer) / iOS: **video_player**(AVPlayer) / Windows: **media_kit** 或 video_player 桌面实现 | 见 §5 热点 2，三平台播放器选型是独立决策 |
|（无，手写） | 图标：**lucide_icons**（pub 包） | web 端 icons.tsx 是 Lucide 风格 2px 线性 SVG，lucide_icons 同源 |
| 字体（Fredoka/Nunito/Space Grotesk） | 打包字体 assets + 手动 fontFamily 回退链 | 三个字体均为 Google Fonts 开源字体可打包离线；CJK 走系统字体回退（fontFamilyFallback） |
|（无组件库，全手写） | 全手写 widget（不引入 shadcn 类库） | 1:1 复刻要求保留玻璃/辉光/圆角体系，现成组件库反而碍事；但可自建 tokens 化 widget 基类（GlassCard/GlassButton/GlassInput） |
| 媒体加载（ResourceImage） | dio 拉 bytes + Image.memory + 内存/磁盘缓存 | 签名鉴权图片无现成组件；GIF 动图需注意（Flutter 原生不支持 GIF 动画帧，web 端 GIF 走原图例外，需 gif 库或后端转格式） |
| zustand persist（会话恢复） | flutter_secure_storage / shared_preferences | refresh token 建议 secure storage；access token 内存态 |
| 原生 input[type=file]×4 入口（聊天多选/发文件/头像/群封面） | **file_picker** | 图片/视频多选进待发队列、文件消息、头像上传、建群封面，统一封装 |

### 2.2 架构目录映射

```text
Ayla/web/src/          →  lib/
├── api/               →  lib/data/  (dio 客户端 + 各域 repository)
├── stores/            →  lib/state/ (Riverpod providers，按 22 store 对应)
├── ws/                →  lib/ws/    (四通道连接管理器 + 事件分发)
├── livekit/           →  lib/audio/ (WS 音频中继封装，见热点 1)
├── player/            →  lib/player/(HLS 播放器封装 + 自愈逻辑)
├── runtime/           →  lib/runtime/(live/voice session 单例运行时)
├── components/        →  lib/widgets/（按 chat/live/voice/group/home/posts/… 子目录）
├── layout/            →  lib/layout/（AppShell/BottomTabs/TopNav/ServerRail/ChannelSidebar/FAB 族）
├── pages/             →  lib/pages/（go_router routes）
├── styles/tokens.css  →  lib/theme/  (Tokens 类 + ThemeExtension；禁裸 hex 纪律同步)
├── hooks/（手势/入场） →  lib/controllers/
└── utils/             →  lib/utils/
```

**复刻纪律（从 web 端继承）**：
- token 只用主题变量，组件内禁裸色值（对应"禁裸 hex"）
- 辉光限 3 处/屏；爱莉气泡与光环样式不可复用到普通用户
- `prefers-reduced-motion` → MediaQuery.disableAnimations 映射，全站动效开关
- 所有手势必须有等效按钮/键盘路径（web 端已全部具备，翻译时保留）

## 4. 状态管理对照（22 stores 翻译要点）

- **store → provider 一对一直译**：auth/chat/message/group/live/voice/posts/directory… 每个 store 的 state+actions 翻译为一个 provider 类，行为语义不变（乐观消息、游标分页、草稿隔离、未读增量）
- **红点体系**（badges/message）：`GET /me/badges/` 权威 + WS 事件驱动刷新，**无轮询**——Flutter 同样实现（AppShell 等价物订阅）
- **目录失效语义**（live.channel.* / voice.channel.* 前缀判定）：属于工程契约（列表游标作废/活动排序），Flutter 侧事件分发保留 `startsWith("live.channel.")` 判定逻辑，不能简化成"全量刷新"
- **JWT 生命周期**：401 拦截刷新互斥锁 + 重放一次；WS 重连前令牌预刷新（防 WSREJECT 循环）——dio 拦截器 + WS 连接管理器复刻同构逻辑
- **乐观消息**：聊天发送的乐观气泡 + 上传进度聚合（多文件按真实字节）+ 取消/重试/删除——纯前端状态逻辑，Flutter 用不可变 state + notifier 复刻；objectURL 生命周期对应 `Uint8List` 内存管理（注意 revoke 时机竞态，web 端已有教训）

## 5. 难度热点 TOP 8（按难→易，含为什么难）

### 热点 1：WS 音频中继（语音通话）—— 最难，需提前 PoC

- 现状：48kHz 单声道 Opus 二进制帧 over WS；web 端用 AudioWorklet 采集（PCM→AudioEncoder(opus)）+ WebCodecs AudioDecoder→AudioContext
- Flutter 无现成等价的"采集→Opus 编码→WS 帧→解码→低延迟播放"整链
- 方案方向：`record`（或原生通道）采集 PCM → libopus FFI 编码（dart 侧 ffi 绑定 libopus，pub 有现成绑定如 `opus_dart`/`flutter_libopus`）→ WS binary 帧上行；接收侧 opus 解码 → 连续 PCM 缓冲 → 播放（需低延迟播放器：`flutter_soloud` 流式喂 PCM 或原生 AudioTrack 通道）
- 风险点：端到端延迟（抖动缓冲策略）、Windows 端录制权限与设备枚举、三端采集格式统一
- **动作**：开工第一个 PoC 就是这个（echo 房间打通即可），它决定 lib/audio 层架构

### 热点 2：HLS 低延迟直播 —— 次难，选型依赖平台

- 现状：hls.js `lowLatencyMode` + `liveSyncDurationCount=2` + `startLoad(-1)` 贴边；Safari 原生 HLS；黑屏自愈（事件驱动卡顿检测/重建/跳边）；全屏锁横屏/iOS 原生全屏/PiP/迷你小窗
- Flutter 侧：**三平台播放器没有统一方案**
  - Android：ExoPlayer（video_player）支持 HLS 与 LL-HLS，可 seek 到 live edge
  - iOS：AVPlayer 原生 HLS，全屏用 AVPlayerViewController（对应 webkitEnterFullscreen 语义）
  - Windows：media_kit（mpv 内核，LL-HLS 支持取决于 mpv 构建）或 Microsoft Media Foundation（video_player_win）——**桌面 HLS 是最弱环**
- 必须自带实现：黑屏自愈状态机（事件驱动检测→重建→跳边）、refreshToLiveEdge 三级兜底、直播"未开播"与"播放错误"区分（以 /status/ SRS 判定）
- **动作**：第二个 PoC：三平台各放一段 SRS 流验证播放器 + 延迟体感 + 跳边

### 热点 3：毛玻璃视觉体系（全站材料）

- 现状：`.55` 半透明白 + blur(18~24px) saturate(1.4) + 亮边 + 宽软阴影；全站卡片/侧栏/弹层/输入框统一
- Flutter：`BackdropFilter` + `ImageFilter.blur` 可实现，但**移动端大量并发毛玻璃是性能重灾区**（每处一次离屏模糊）
- 策略：token 化 `GlassCard` 基类统一实现；按 design.md 已定义的降级链（不支持 backdrop-filter → `rgba(255,250,251,0.92)`）在 Flutter 用"低端设备/窗口缩小 → 高不透明实底降级"开关；弹层用 0.78 强玻璃（web 同款分层）
- 陷阱：BackdropFilter 的 stacking/裁剪行为与 web 的 containing block 问题同源（web 端踩过 createPortal 逃离祖毛玻璃的坑）——Flutter 用 Overlay 根级挂弹层规避同坑

### 热点 4：流体极光背景

- 现状：四层互质周期（22s/17s/10s）+ 负延迟 + SVG feTurbulence + 150vmax 旋转层 + 双光斑置换；全站生效
- Flutter：CustomPaint 画 2~3 层 radial 渐变 + 旋转/漂移（AnimationController 长周期）+ 光斑 blur（MaskFilter/ImageFilter），性能可控（一屏一个 layer）；feTurbulence 无直接等价——用多层渐变+扰动噪声近似或省略湍流层（视觉影响可接受）
- 纪律：reduced-motion 降级静态渐变；窄屏光斑上下半区 + 尺寸差异（80vw/70vw 概念按屏幕比例）

### 热点 5：签名媒体管线

- 现状：媒体 URL 需 Bearer；ResourceImage 拉 blob；缩略图 320px；GIF 例外；上传三步（建会话→流式 PUT 进度→确认+取消清理）；视频 poster 秒开
- Flutter：dio 带 header 拉 bytes + 图片缓存层（内存 LRU + 磁盘）；上传用 dio 流式 + onSendProgress 聚合；取消调 DELETE 清理（幂等）；视频封面用 poster 帧 + ▶ 角标（与 web 同逻辑）
- 注意：**图片消息的 GIF 动画**在 Flutter 需额外方案；大文件 1GB+ 流式上传在三端都要验证内存（web 端已修过 OOM，Flutter 用流式 + 分块）

### 热点 6：手势矩阵（窄屏）

- 现状：8 类手势共享统一松手契约（净位移 ≥1/3 或 ≥300px/s 且 ≥40px；交叉轴让位）；下拉刷新阻尼公式 `96×(1−e^(−dy/90))`；边缘返回 24px 起手
- Flutter：GestureDetector + 自定义 resolve 逻辑可完整复刻（手势竞技场天然处理交叉轴让位）；PageView 自带动量但**不满足自定义阈值契约**→ 需自写 pager（跟手 + 回弹 + 提交阈值 + dragElastic 0.8）；RefreshIndicator 可自定义 indicator 视觉（玻璃圆点三态）
- 每类手势 web 端都有等效按钮路径——翻译时按钮必须保留

### 热点 7：双形态布局与状态连续性

- 现状：断点 480/768/1024/1440 实时切换；宽屏三列壳（ServerRail 常驻 + 频道栏换群编排）；liveSessionRuntime 单例唯一持有 video，切换原子移动不重建（web 端踩过"代际交接"坑）
- Flutter：MediaQuery/布局 builder 切换两套 widget 树；**关键**——session 运行时（语音/直播）作为全局单例持有媒体连接，UI 树切换只搬运视图不重建媒体（对应 web 的 attachPlayer 幂等 + video 原子移动）；状态切换时的"旧请求不能落到新选择"竞态（revision 门）同样需要复刻

### 热点 8：实时事件总线与状态同步

- 现状：37 类事件 + 前缀族判定；心跳 ping/resume 恢复对账；WS 重连补拉；目录失效语义
- Flutter：web_socket_channel 四通道管理器 + 统一事件分发（事件→provider 对应表）；心跳/重连/恢复状态机直译；**注意**：web 端"WS 重连成功后补拉一次对账（红点）"等细节都要保留，否则状态漂移

## 6. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 音频中继整链不可行/延迟不可接受 | 高 | 开工先 PoC（热点 1）；备选：降级为服务端转码 WebRTC 直连（frp 限制下不可行——web 端已退役 LiveKit 的教训要尊重） |
| 桌面 Windows HLS 播放弱 | 中高 | media_kit 先行验证；备选：Windows 端降级为"打开外部播放器/浏览器"（需用户决策） |
| 移动端毛玻璃性能 | 中 | 降级开关 + 弹层少用毛玻璃；真机实测帧率 |
| 手势手感与 web 不一致 | 中 | 统一契约直译 + 三端真机调参（速度阈值在触屏差异存在） |
| 签名媒体缓存膨胀/内存 | 中 | LRU + 磁盘缓存（对齐 web 端 320px 缩略图策略，不全量拉原图） |
| 双形态切换状态丢失 | 中 | runtime 单例 + UI/媒体分离（web 端既有架构照搬） |
| 字体与图标一致性 | 低 | 打包字体 + lucide_icons 同源 |
| 测试覆盖 | 低 | widget test 覆盖关键状态机（聊天乐观发送/手势契约/WS 解析） |

## 7. 结论

1. **复刻可行且图纸齐全**：design.md 是完整视觉规格书，web 源码结构清晰、契约文档完备（architecture/ 目录），vibe coding 可以"照着翻译"而非"从零设计"
2. **量级判断**：完整三端交付是长期多阶段工程；窄屏单端（Android）MVP 路径最快见效
3. **两条媒体链路必须先 PoC**：音频中继与 HLS 直播决定架构，不能留到最后
4. **先窄屏后宽屏**：窄屏（≤768）覆盖全部功能域，宽屏三列是增量
5. 具体里程碑拆解与三平台适配细节见 `03-平台适配与实施路线.md`
