## 1. 三平台适配差异矩阵

> 差异点全部从 web 端**真实源码行为**推导（01 文档 §5/§10/§11 + design.md 对应章节），不是泛泛的平台清单。

### 1.1 Windows（桌面）

| # | 差异点 | web 端行为来源 | Flutter 侧方案 |

| W1 | 窗口尺寸自由变化，断点实时切换 | §9 断点 480/768/1024/1440，验证视口 375/768/1024/1440（窗口 resize 语义） | LayoutBuilder/MediaQuery 监听窗口宽度，断点实时切换双形态；窗口宽度即"视口" |

## 2. 断点策略的 Flutter 映射

### 2.1 断点定义（与 web §9 一致）

```text
<480   xs（窄屏）      —— 登录/注册卡片收窄（§5）
480–767 sm（窄屏）     —— 底部五 tab 形态
768–1023 md（宽屏）   —— TopNav + 侧栏形态（窄屏到宽屏的分界）
1024–1439 lg（宽屏）  —— 帖子双列瀑布（>1024，§12.18）
≥1440   xl（宽屏）    —— 最宽布局
```

- 形态判定只有两态：**≤768 窄屏（BottomTabs 系）/ >768 宽屏（TopNav + 三列系）**；子断点（480/1024/1440）影响页面内部细节
- 实现：`MediaQuery.sizeOf(context).width` + 自定义 `Breakpoint` 类；Windows 端窗口 resize 即触发（与 web resize 语义一致）

### 2.2 断点切换的状态连续性（web 教训直译）

web 端踩过的坑必须继承为设计约束：

- **媒体层与 UI 层分离**：语音/直播 session（runtime 单例）持有连接与播放器；宽窄屏切换只搬视图、不重建媒体（对应 §12.7.4"video 原子移动不重建"、`attachPlayer` 幂等）
- **全屏期间冻结断点判定**：web 端"手机点全屏锁横屏 → isNarrow 翻转 → 布局切换 → 播放器重建 → 黑屏"的坑（§12.7.3）→ Flutter 全屏期间锁定进入全屏前的窗口宽度/断点值
- **切群/切房的代际交接**：`liveSessionRuntime` epoch 机制（旧视图 cleanup 不能 leave 掉新会话）→ Flutter 用 session owner 令牌同构实现
- **旧请求不落新选择**：revision 门（快速切 tab 时旧请求不能覆盖新状态）→ provider 内 revision 计数同构

## 3. Flutter 工程落地建议

### 3.1 工程结构（feature-first）

```text
lib/
├── main.dart / app.dart
├── core/          # dio 客户端、WS 连接管理器、主题（tokens/字体/组件基类）、错误/降级
├── data/          # 各域 repository（对齐 web api/ 19 模块）
├── state/         # Riverpod providers（对齐 22 stores）
├── ws/            # chat/live/voice/presence 四通道 + 事件分发（对齐 ws/）
├── audio/         # WS 音频中继封装（Opus 编解码 + 播放缓冲）
├── player/        # HLS 播放器封装（三平台实现 + 自愈状态机）
├── runtime/       # live/voice session 单例
├── layout/        # AppShell/BottomTabs/TopNav/ServerRail/ChannelSidebar/FAB 族
├── widgets/       # 按域组件（对齐 components/ 85 个）
├── pages/         # go_router routes（对齐 pages/ 27 个）
├── controllers/   # 手势/入场控制（对齐 hooks/ 37 个）
├── utils/         # 对齐 utils/ 11 个
└── theme/         # Tokens 类 + ThemeExtension（禁裸色值纪律）
```

### 3.2 平台通道清单（需原生能力清单）

| 能力 | 方案 | 平台 |
|---|---|---|
| 鉴权图片加载（Bearer）+ 缓存 | dio bytes + Image.memory + LRU/磁盘缓存 | 三端 |
| 文件/图片多选 | file_picker | 三端 |
| 音频采集（48k 单声道 PCM） | record（Android/iOS）→ libopus FFI 编码 | 三端（Windows 需验证 record 桌面支持/原生通道） |
| Opus 编解码 | libopus FFI（`opus_dart`/自绑定） | 三端 |
| 低延迟播放（PCM 流） | flutter_soloud 流式 / 原生 AudioTrack | 三端（需 PoC） |
| HLS 直播 | video_player（Android ExoPlayer / iOS AVPlayer）/ Windows media_kit | 三端（Windows 弱） |
| 安全存储（refresh token） | flutter_secure_storage | 三端 |
| 音频会话/焦点 | audio_session | Android/iOS |
| 锁横屏 | SystemChrome.setPreferredOrientations | Android/iOS |
| 原生全屏/PiP | 平台通道/插件 | iOS/Windows(桌面) |
| 通知/推送 | 决策点：FCM/厂商通道 或 前台服务 | Android/iOS |

### 3.3 构建与分发

| 平台 | 构建 | 注意 |
|---|---|---|
| Android | APK/AAB | minSdk 按音频库要求；麦克风/相机权限声明；libopus 三 ABI（arm64-v8a/armeabi-v7a/x86_64） |
| iOS | IPA | Info.plist 权限描述（麦克风/相机/相册）；AVPlayer 视频后台策略 |

### 3.4 测试策略

- widget test：关键状态机（聊天乐观发送、手势提交契约、WS 事件解析、红点增量）——对应 web 154 个 vitest 中有价值的子集
- 集成测试（integration_test）：登录→进群→收发消息→进语音房→进直播间 核心链路
- 三端真机验收为主（视觉/手感/性能无法自动化）

## 5. 平台与节奏建议

1. **先 Android，后 iOS，最后 Windows**：Flutter 层三端共享（~90% 代码），平台差异集中在音频/视频/安全区/推送；Android 真机迭代最快
2. iOS 建议紧跟 Android（同一 Flutter 代码库，补 AVPlayer/安全区/审核项），窗口期小
3. Windows 放最后：桌面 HLS 弱环 + 鼠标 hover 打磨 + 分发形态（MSIX）都是收尾活；且"一比一复刻"的桌面体感与移动端差异最大，值得单独一轮
4. **范围决策点（需用户拍板）**：
   - 移动端后台消息送达：**前台服务保活 vs 推送通道（FCM/APNs）**——web 端无此概念，"一比一"严格讲不含后台推送，但移动端体验绕不开
   - 语音房锁屏后是否继续（iOS 后台音频）
   - Windows 端 HLS 弱环的接受度（是否接受 mediakit 分发体积/降级为外部播放器）

## 6. 整体结论

- **值得复刻**：图纸齐全（design.md 714 行规格 + web 源码 + architecture 契约文档），Flutter 侧无技术死路——最难的两条链路（音频中继/HLS）都有明确 PoC 路径
- **认知校准**：这是**长期多阶段工程**（9 个里程碑），按 vibe coding 节奏先窄屏 Android 全功能跑通（M0–M6），再回头补宽屏与 Windows
- **两条红线纪律继承**：毛玻璃降级链、辉光限 3 处、爱莉专属样式不复用、reduced-motion 开关——这些是 design.md 的灵魂，翻译时逐条对照
