## 一、直播弹幕「大图/动图后刷新不出来」（判为**两个独立病因叠加**）

### 1.1 病因 A（渲染层，`widgets/live/danmaku.dart`）

列表里的弹幕图槽位是 **96×64**（`app.css:3741–3747`），但 `_DanmakuImageButton` 构造
`AylaResourceImage` 时**既没传 `width`/`height`，也没传 `variant`**：

- 无尺寸 ⇒ 命中 `widgets/base/resource_image.dart:552–567` 的
  `if (width == null && height == null) { decodeW = null; decodeH = null; }`
  ⇒ `Image.network` 的 `cacheWidth/cacheHeight` 为空 ⇒ **按原图分辨率完整解码**。
  4000×3000 ≈ 12M 像素 ≈ 48MB RGBA；**动图还要逐帧解码 + 逐帧上传纹理**
  ⇒ 光栅/UI 线程被排满 ⇒ 后续弹幕的 build/layout/paint 排不上（用户看到的「刷不出来」）。
- 无 `variant` ⇒ `media_signer.dart:97` 走 original 分支 ⇒ 后端 `media/views.py:280–291`
  presign 的是 `storage_path`（**原图**）⇒ 为了 96×64 的槽位签名 + 下载 + 解码整张原图。

**为什么 web 没这问题**：`web/src/components/live/DanmakuList.tsx:72–78` 的 `ResourceImage`
最终就是一个 `<img loading=lazy>`。浏览器是**原生渐进解码 + HTTP 缓存**，位图按布局尺寸进渲染缓存；
Flutter 的 `Image.network` 在无 `cacheWidth/cacheHeight` 时是**一次性完整解码**。

> **互证**：web 的**飘弹幕层** `DanmakuOverlay.tsx:196` **自己就传了 `variant="thumb"`** ——
> 说明「列表侧不传 variant」在 web 上只是从没出过事，**不是一条应当照抄的语义**。
>
> ⇒ 判为**对 web 的有意偏离**，已在 `danmaku.dart` 文件头立节登记。

**修法**：列表槽位补 `width: 96 / height: 64 / variant: MediaVariant.thumb`；
4 个槽位尺寸常量（96/64 列表、72/36 飘层）让「布局尺寸 = 解码尺寸」同源。
**明确不复用** `chat/media_content.dart:538–539` 的「GIF 走原图」策略 —— 那是**聊天气泡**语义
（气泡随图放大），弹幕槽位是缩略预览 + 点击看大图。

**GIF 降档裁决（Lead 定）**：列表里动图**走缩略图**。硬理由：Dart 侧解码上限按**每帧像素**生效、
**不能限帧数** ⇒ 「列表里的原图动图」没有有界方案。要看动效 = 点开查看器（走 original）。
**不得**引入「原图 < 512KB 才走 original」这类经验阈值（本项目明令禁止凭经验拍阈值）。

### 1.2 病因 B（接线层，`pages/live_support.dart` + 三个直播页）

会话级探针实测：**WS 帧 → store → 历史窗口三段都是通的**（图片帧与文字帧都进得去）。
断的是 web 由 `useCursorHistory` 自带、而 Flutter 侧**没人消费**的三件：

| # | web | Flutter 修复前 | 后果 |
|---|---|---|---|
| ① **贴底跟随** | `useCursorHistory.ts:66–79` 的 `useLayoutEffect` 写 `list.scrollTop = list.scrollHeight` | `AylaCursorHistory.pendingScrollToBottom` **只置位、全仓零消费方** | 新弹幕进了窗口但列表**原地不动** |
| ② **有新弹幕 ↓** | `useDanmaku.ts:63–69` `scrollToBottom` | `AylaDanmakuList.onScrollToBottom` **未接线**；`hasNewer` 是**锁存位**（`cursor_history.dart:296`） | 提示亮着但点了没反应，永远回不到最新 |
| ③ **群内实时帧** | `GroupLive.tsx` 复用同一份 `useDanmaku` hook | `group_live_page` **从不调** `syncRealtimeToHistory()` | 群内直播的实时弹幕**永不出现** |

**为什么「重进就好」**：列表回原位后，图片行（96×64 + 昵称）比一行纯文字高得多，
连续几条就把可见区顶满 ⇒ 视觉上「卡住」；退出重进会重建列表并贴底 ⇒ 看起来像「重进才刷新」。

**修法**（`live_support.dart`）：新增会话级 `danmakuScroll` 控制器 +
`pumpScroll()`（消费置位并贴底）/ `handleDanmakuScroll()`（距底 <40 才继续跟随，
`kAylaFollowBottomSlack = 40` 对齐 web）/ `scrollDanmakuToBottom()`（有更新走 `returnLatest()`，
否则贴底 + 重新跟随）。三个直播页（`live_room_page` / `live_studio_page` / `group_live_page`）
统一注入 `danmakuController` / `onDanmakuScroll` / `onScrollToBottom`，并在 build 里
`addPostFrameCallback` 调 `pumpScroll()`（必须等本帧布局完成，`maxScrollExtent` 才是新值）。

**控制器生命周期纪律**：在 `dispose()` 里销毁而**不是** `stop()` —— `stop()` 可重入
（小窗让位后会再 `start()`），只有 `dispose()` 是终态。

**回归锁**：`test/live_danmaku_follow_test.dart`（8 例：贴底/幂等/跟随判定/回最新/
三页静态接线/群内同步/端到端帧入窗口）。
**反向验证**：摘掉 `pumpScroll` 与 `syncRealtimeToHistory` ⇒ **2 红**（精确打出
`live_room_page.dart 缺少接线：session.pumpScroll()`、`group_live_page.dart 缺少接线：session.syncRealtimeToHistory()`）；
恢复 ⇒ **8/8 绿**。

> ⚠️ **测试写法坑（本轮踩到，记下来）**：在 `testWidgets` 里 `await session.start()` 会**挂死** ——
> `start()` 内部有 `await Future.delayed(Duration.zero)`（让出事件循环以避开「build 期间改 provider」），
> fake clock 下该 timer 永不触发。必须 `await tester.runAsync(() => session.start())`。

## 二、语音房：图片点不开 + 手机端聊天弹窗「穿透」

### 2.1 「穿透」的真实机制（`widgets/voice/voice_room_body.dart` 的 `_NarrowChatOverlay`）

修复前用 `SizedBox(height: 0)` + `OverflowBox(alignment: bottomCenter, minHeight/maxHeight: 300)`
把 300 高的浮层**溢出到零高盒子外面**绘制。

**Flutter 的命中测试只走布局矩形**（本处高度为 0），`OverflowBox` 溢出的部分**不参与命中测试**
⇒ 视觉看得到、点不到 ⇒ 点击落到浮层**后面**的页面元素 = 用户说的「穿透」。

**web 为什么没这问题**：`voice.css:72–105` 是 `.voice-room-chat-list { position: absolute; bottom: 100% }`，
父级 `.voice-room-chat-card` 是 `position: relative` 的**流内元素** ⇒ absolute 子元素仍在卡片盒范围，
**正常参与命中测试**。

### 2.2 图片点不开

`_buildMessage` 的图片分支是**纯展示**：`ClipRRect + SizedBox(120×80) + AylaResourceImage`，
没有 `GestureDetector`、没有查看器（`voice_room_body.dart:744–755`）。

**注**：web 侧语音房聊天图**同样没有 onClick**（`VoiceRoomBody.tsx:192–200` 只有 `ResourceImage`；
对照同仓库聊天域 `MediaContent.tsx:140`、弹幕 `DanmakuList.tsx:131` 都挂了 `<ImageViewer>`
⇒ **语音房是 web 唯一漏掉图片查看器的媒体面**）。
⇒ Flutter 侧实现「点击打开大图」是**按用户实报的有意偏离**，已在组件文件头登记。

### 2.3 修法（含一处比初判更深的发现）

**浮层命中根因有两层**（第二层是实测才发现的）：
1. `RenderBox.hitTest` 首行是 `if (_size!.contains(position))`（`flutter/lib/src/rendering/box.dart:2952`）
   ⇒ 零高盒的溢出部分**永久不可命中**；
2. **更关键**：命中要求**从根到浮层每一个祖先 RenderBox 都包含该点**。聊天卡是 `mainAxisSize.min`
   的 Column（盒高 = 卡片自身高），上方 300px 不在其 size 里 ⇒ **即使把浮层改成自定义 RenderBox
   让它自己吃指针，命中也会在 Column 那层返回 false**。

> 这一点值得记牢：先写的「自定义 RenderBox 接管 hitTest」方案实测 `overlayTaps=0` 才定位到第二层，
> 该方案已删除、未留在代码里。「只改浮层自身」在这个结构下**不可能**修好。

**最终修法**：把浮层从聊天卡内部移到**语音卡槽的 `Stack`**：
```dart
Stack(clipBehavior: Clip.none, children: [
  Positioned.fill(child: voiceCard),
  Positioned(left: 0, right: 0, bottom: 0, height: 300, child: 浮层),
])
```
该槽底边 = 聊天卡顶边（Column 内相邻、gap 0）⇒ `Positioned(bottom: 0, height: 300)` 与 CSS
`bottom: 100%` 的**绘制几何完全重合**，且**祖先盒覆盖那 300px** ⇒ 命中链每一层都包含该点。
`_NarrowChatOverlay` 只保留视觉子树（`IgnorePointer`/`ExcludeSemantics`/`AnimatedOpacity` 240ms/
`TweenAnimationBuilder` translateY(12px)/`AylaGlassSurface` strong+blur18+上两角 rCard+
`0 -4px 16px rgba(70,91,146,.12)`）—— **视觉逐值未变**。

**图片可点**：新增 `_VoiceChatImageButton`（`Semantics(button)` + `MouseRegion(zoomIn)` +
`GestureDetector(behavior: opaque)`；`opaque` 是必须的 —— 加载/失败态是空装饰盒，不加会穿透）
+ `_VoiceChatViewerHost`（`aylaOverlayEntry` + `Overlay.of(context)`，与
`widgets/live/danmaku.dart` 的 `_DanmakuViewerHost` 同写法；用**最近** Overlay 而非 `rootOverlay`，
否则画布/测试宿主无 Navigator 会抛）。
配套：`AylaVoiceChatMessage` 新增 `media` 描述符（查看器要 mediaId/kind/mime 才能走原图签名 + 保存；
只有 thumbnailUrl 不够），`core/api/voice_api.dart` 的 `fromJson` 补 `media:`（**后端早已下发**
`apps/voice/views.py:349–356` 的 `MediaObjectSerializer`，此前 Flutter 侧把它丢了）。

**回归锁**：`test/voice_chat_overlay_test.dart`（4 例）：
① 窄屏展开态点浮层内图片**中心**（`tester.getRect` 取真实矩形，不用魔数）→ 打开 `AylaImageViewer`，
   且浮层下方观测器计数必须为 0；含三条几何断言（图片盒 120×80、图片按钮盒与本体盒中心重合、
   图片中心 y 落在浮层区间内）—— `applyPaintTransform`/`paint`/`hitTest` 任一处平移写错都会红；
② 窄屏收起态同坐标 → 不打开查看器且下方计数 = 1（真的零命中、不拦截）；
③ 宽屏点图片 → 打开查看器（两档共用 `_buildMessage`）；④ 图源逐值（src/fit/尺寸）。

**反向验证**（两轮，各自独立变红）：
· 反验 A（退回 `SizedBox(0)+OverflowBox`）⇒ ①变红，②③④绿；
· 反验 B（退回静态图片、无按钮）⇒ ①③一起变红，②④绿。

### 2.4 附带实测结论（需产品裁决，非本次引入）

**浮层展开时会盖住语音卡底部 300px 的成员操作按钮**（实测 `panelTaps` 由 1 → 0）。
这与 web **完全同构**：web 浮层也是 `z-index: 2` + `height: 300px` + `bottom: 100%`，盖住同一区域；
收起态 web 是 `pointer-events: none`，Flutter 是 `IgnorePointer(ignoring: !expanded)`，等价。
⇒ **未额外加裁剪或 pointer 边界**（加了就偏离 web）。若判断移动端需要更好体验，需单独立项。

## 三、私信界面头像不显示（**三条独立根因**）

### 3.1 根因①（数据层，最致命）：私聊 peer 推导**漏了「排除自己」**

`state/chat_state.dart:352-355`（修复前）：
```dart
if (conv.peer != null || !conv.isPrivate || conv.members.isEmpty) return conv;
return conv.copyWith(peer: conv.members.first.user);   // ← 直接取首条
```
web 事实源 `stores/chat.ts:129–133`：
```ts
const me = useAuthStore.getState().currentUser?.id;
const peerMember = normalized.members.find((m) => m.user.id !== me) ?? normalized.members[0];
```

**为什么必然会触发（不是理论风险）**：
· 后端 `ConversationMetadataSerializer` 对**私聊也不返回 `peer` 字段**
  （`apps/chat/serializers.py:514–535`；只有 `ConversationListSerializer` 给），
  而 `GET /chat/conversations/<id>/?metadata=1` 走的正是前者（`views.py:410–415`）
  ⇒ 私聊详情响应必然无 peer ⇒ **必然**落到本函数推导；
· 成员表是 `obj.members.select_related("user")[:2]`（`serializers.py:532`，**无 `order_by`**）；
· 对真库跑 30 个「私聊会话 × 成员视角」组合：**15 个的 `members[0]` 就是自己**
  （conv 1 / 2 / 3 / 7 …）⇒ peer 被写成自己 ⇒ 顶栏头像/昵称变自己，自己没设头像就是空串 ⇒ 文字首字。
· **错值还会粘住**：`upsertConversation` 合并时写 `peer: prev.peer`（`copyWith` 的 null 语义是
  「保留旧值」）⇒ 一旦先用 `metadata=1` 的错误推导写进 store，之后正确的目录摘要也**覆盖不回来**。

**修法**：新增模块级注入点 `aylaChatStateCurrentUserId`
（`main.dart` 启动期接线 `() => container.read(authNotifierProvider).user?.id`），
`_normalize` 改为 `firstWhere(m.user.id != me, orElse: members.first)` ——
`orElse` 保住 web 的 `?? members[0]` 语义（全脏数据时仍取首条，不造 null）。

> **为什么用注入而不是给 `upsertConversation` 加参数**：`AylaChatState` 是纯 ChangeNotifier，
> 文件头已登记「state 层不依赖 Riverpod」；web 的 `useAuthStore.getState()` 是模块级单例天然可读，
> 注入是同构写法。显式传参要改 14 处调用点、且 `chat_ws.dart` / `social_store.dart` 等 WS 路径
> 各要传一次，**漏一处就是同一个 bug**。

### 3.2 根因②（渲染层，影响全库 31 个光环使用点）：**空串 ≠ null**

`widgets/base/avatar_halo.dart:281 / :299`（修复前）用 `resourceUrl == null` 判「有没有图」。
但后端 `avatar` 是 `CharField(blank=True, default="")`（`apps/accounts/models.py:33`），
序列化原样透出 ⇒ **没有头像的用户拿到的是空串，不是 null**。

空串命中「有图」分支 ⇒ `AylaResourceImage(src: '')` ⇒ `resource_image.dart:307` 的
`if (src.trim().isEmpty)` 直接判 failed ⇒ 装饰图（`alt: ''`）只渲染 fallback
⇒ **视觉上就是文字首字**。也就是说：「没头像」这种**正常情况**走的是「图片加载失败」的路径
（还白跑一遍 loading → failed 状态机）。

web 事实源 `components/Avatar.tsx:46`：`imageUrl ? <ResourceImage …/> : safeLabel.slice(0,1)`
—— JS 的**假值判断**把 `''` 与 `null` 一视同仁，走**文字分支**。

**修法**：新增 `_avatarSrc` getter（`null` / 空串 / 纯空白串 ⇒ 均视为「无图」），
两处判断与 `src` 全部改用。**修在组件内而不是调用点** —— 全库 31 个光环使用点都可能拿到空串
（气泡/会话列表/成员表/弹幕/评论/顶栏…），逐点补 `_nonEmpty` 必漏。

### 3.3 根因③（放大器）：私信两条渲染路径的空串归一**不对称**

`conversation_list.dart:400` 群分支有 `_nonEmpty(conv.avatar)`，而私聊分支
`private_chat_pane.dart:321` 的 `resourceUrl: conv?.peer?.avatar` **没有归一**。
根因② 在组件内归一后这一处已无对外影响，故未改（避免跨文件提升私有函数）。

### 3.4 回归锁与反向验证

`test/chat_avatar_parity_test.dart`（13 例，三条根因各一组**独立**断言）：
组① 数据层 peer 推导 6 例（含 `members[0] 是自己` 的核心锁）；
组② 渲染层空串归一 4 例（含「空白串也按 null」与「有真 URL 不误伤」）；
组③ 私信接线 3 例（顶栏 / 气泡 / 对端无头像对照）。

**反向验证 A（回退根因①）**：3 条变红，其中核心锁
`Expected: 'u2' Actual: 'me'` 精确命中；其余 10 例仍绿 ⇒ 锁独立。
**反向验证 B（回退根因②）**：3 条变红（`Found 1 widget with type "AylaResourceImage"`）；
其余 10 例仍绿 ⇒ 锁独立。两组恢复后均 13/13 绿。

> **未改后端**：`ConversationMetadataSerializer` 对私聊不返回 peer 是**与 web 共用的既有契约**
> （web 也依赖它、靠前端推导）⇒ 不算后端缺陷，单方面改会与 web 分叉。前端推导修好后两端一致。

## 四、个人页分享键点击无效

`pages/profile_page.dart:376-380` 与 `pages/user_profile_page.dart:492-496` 把
`AylaShareButton` 的 `onPressed` 写成**空实现 `() {}`**（注释自认「分享面板接线属分享域批次」）。

**为什么点了完全没反应（而不是变禁用）**：`widgets/base/share.dart:981-982` 取
`this.onPressed ?? (_canSelfServe ? () => _openSelfServed(context) : null)` —— 非 null 的
`() {}` **优先进注入档** ⇒ 按钮可点、指针正常，但回调空转。

**web 为什么没这问题**：`components/share/ShareButton.tsx:21–33` 自己 `useState(open)` +
`createPortal` 弹 `ShareSheet`，页面只负责喂 `payload` ⇒ **「页面漏接线」这个失败模式在 web 架构上不存在**。

**修法**：删 `onPressed`，改传 `payloadBuilder: () => AylaSharePayload.user(...)`
（走组件库已有的**自给自足档**，与 web 同构；用 `payloadBuilder` 而非 `payload` 是既有约定 ——

## 五之二、第二轮复报（2026-10-26 晚）：弹幕刷新仍不正常的**真正根因**

用户复报（**这四条现象一起出现，把根因锁死了**）：
1. 发送出去还是没正常刷出来，还是要退出重进才刷；
2. 消息不刷出来**但会出现「有新弹幕」标签和「返回最新消息」**；
3. 此时点击「有新弹幕」**也无法跳转出未刷出的弹幕**；
4. **头像的在线光环也不是正常显示在线的**。

### 根因：`AylaCursorHistory` 是 ChangeNotifier，但**没有任何页面监听它**

第一轮补的是「谁去滚列表」（`pumpScroll` / `handleDanmakuScroll` /
`scrollDanmakuToBottom`），但**没人让页面重绘**：

```
live_room_page / live_studio_page / group_live_page
  addListener 的对象：_session · _directory · _viewerSheet
  ✗ 唯独没有 _session.history（AylaCursorHistory extends ChangeNotifier）
```

于是出现**看似矛盾**的两个现象，其实同源：
· `append()` 改 `items`、置 `hasNewer` —— 数据真的变了，但 `notifyListeners()`
  发给 **0 个监听者** ⇒ 页面不重建 ⇒ 列表不动；
· 点「返回最新」时 `returnLatest()` **其实成功了**（窗口已换成最新、`hasNewer` 已清），
  可页面照样不重建 ⇒ 用户看到「点了没反应」，且提示条因为不重绘而**仍挂在那里**。

> 这条最值得记：第一轮**所有测试都是绿的**，因为我写的锁都在验证
> 「数据有没有进窗口」和「控制器会不会滚」，唯独没验证**页面会不会重绘**。
> 教训：WS 热更新类缺陷，验收必须包含「界面真的变了」这一环，不能只测数据层。

### 修法

1. **转发**（`live_support.dart`）：会话 `_relayHistory()` 把 history 的
   `notifyListeners` 转发到会话本体，会话再 `notifyListeners()` ⇒ 页面既有的
   `_session.addListener(_onChanged)` 一处转发同时喂饱三个页面。
   `stop()` 里 `removeListener` + 复位守卫（`start()` 可重入）。
2. **点「返回最新」补贴底**：`scrollDanmakuToBottom()` 在 `returnLatest()` 成功后
   **主动** `pumpScroll()` —— 页面此刻还没重建、`pumpScroll` 要等下一帧，
   不主动消费就会「点完仍停在旧位置」。失败（`ok == false`）时**保留原窗口**，
   不假装已回到最新。
3. **头像在线光环**：`danmakuEntries()` 的签名从 `bool senderOnline = false`
   改为 `bool Function(String userId)? senderOnlineOf`。原签名三个页面都不传 ⇒
   **恒为 false** ⇒ 所有弹幕头像永远灰环。现由页面 watch `presenceStateProvider` 后
   注入求值器（web `DanmakuList.tsx:40–46` 的
   `presenceOnline(users, withLiveStatus(statuses, senderUser))` 同构）。

### 回归锁：`test/live_danmaku_refresh_test.dart`（7 例）

| # | 锁什么 |
|---|---|
| ① | **转发**：append 后会话的监听者收到通知（= 页面能重建） |
| ② | **重绘**：与页面同构地监听+setState ⇒ 新弹幕**真的渲染出来**（`find.text` 命中） |
| ③ | **点提示真能跳**：未脱挂时贴底并恢复跟随；脱挂时先 `returnLatest`，失败保留原窗口 |
| ④ | **头像在线实时**：三页都传 `senderOnlineOf`（静态审计）+ 逐条求值生效 |
| ⑤ | **发图照样刷**：图片帧到达后条目增加且描述符完整 |

**反向验证**：摘掉 `_relayHistory()` ⇒ ① 与 ② **一起变红**
（② 报「新弹幕必须真的渲染出来」找不到文本）—— 精确命中本轮根因；
恢复后 7/7 绿，且与第一轮的 8 + 4 例一起 19/19 全绿。

## 六、遗留与裁决记录

### 已裁决（本轮 Lead 定，已落地）

1. **列表动图降档**：走缩略图，看动效需点开查看器。硬理由：Dart 侧解码上限按**每帧像素**生效、
   **不能限帧数** ⇒ 「列表里的原图动图」没有有界方案。**禁止**引入「原图 < 512KB 才走 original」
   这类经验阈值（本项目明令禁止凭经验拍阈值）。
2. **`_listImageSrc` 保留 `?? mediaContentUrl(media_id)` fallback**：缩略图未就绪时原图是唯一可显示资源，
   且现在只按 96×64 解码 ⇒ 风险已有界。改成「没缩略图只显示骨架」反而制造新缺陷。
3. **peer 推导的 `me` 用模块级注入**而非给 `upsertConversation` 加参数（理由见 §3.1）。
4. **私信 `avatar: ''` 的归一放在 `AylaAvatarHalo` 组件内**（31 个使用点一起受益）。
5. **语音房图片可点开**：有意偏离 web（web 无此通路），按用户实报实现。
