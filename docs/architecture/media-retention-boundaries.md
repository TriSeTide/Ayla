# 媒体保留类别与过期边界（唯一事实源）

> 版本：2026-10-21 第 3 版（Q1/Q2 已裁决；Q2 经二次修正：过期媒体不可作资产，须重传原图）
> 状态：**边界定义已定稿；代码实现尚未对齐**（差距见 §7 差距表）
> 上位文档：`docs/architecture/media-storage-expiration.md`（机制细节）
> 关联报告：`docs/report/MinIO存储与过期机制调查报告-2026-10-21.md`
> 本文档取代上文 §2/§3 的类别与保护集合定义。两者冲突时**以本文档为准**。

## 1. 范围约束（用户已拍板）

| 媒体类别 | 过期策略 |
|---|---|
| **图片**（仅限聊天类） | 两级：**7 天删原图、保留缩略图** → **30 天完全过期** |
| **语音 / 文件 / 视频**（仅限聊天类） | 单级：**7 天直接删除** |
| **资产类** | **永久保留，永不进入过期流程** |

核心原则不变：**云端回收 ≠ 数据销毁**；DB 记录永不删行（只打 `original_expired_at` / `expired_at` 标记）。

## 2. 判定的唯一规则

一句话：**谁引用它，决定它是不是资产。**

```
媒体是「资产类」 ⟺ 它被至少一个「资产类引用」引用
媒体是「可过期」 ⟺ 它没有任何「资产类引用」
```

注意是 **"被谁引用"**，不是 "它是什么 kind"。同一个 `kind=image` 的对象：

- 发在聊天里 → 可过期（7 天删原图 / 30 天完全过期）
- 发在帖子里 → 永久（`PostImage` 引用）
- 先发聊天、后发帖子 → **永久**（一旦获得资产引用，永久豁免；反向不成立）

```
可过期候选 = MediaObject.objects.filter(
    created_at < now - 该 kind 有效 TTL,
    status = READY,
    expired_at is null,
)
可过期集合 = 可过期候选 − 资产引用集合
```

**两个方向都要管**（缺一不可）：

| 方向 | 规则 | 违反后果 |
|---|---|---|
| **出**（清理判定） | 有资产引用 ⟹ 永不过期 | 资产被误删 |
| **入**（引用建立） | 原图必须完好（未进入过期阶段）⟹ 才可成为资产 | 劣化/失效内容固化为永久资产 |

> "入"的规则见 §6.2：**已过期媒体不可用作头像/封面/帖图，必须重新上传原图**。

## 5. 归属矩阵（kind × 引用方）

`✓` = 该组合可成立；空白 = 业务上不会出现（创建时已校验）。

| kind \ 引用方 | A1 帖子图 | A2 表情 | A3/A4 评论 | A5 用户头像 | A6 群头像 | A7 封面 | E1 消息 | E2 段 | E3 弹幕 | E4 语音房 |
|---|---|---|---|---|---|---|---|---|---|---|
| **image** | ✓ 永久 | | ✓ 永久 | ✓ 永久 | ✓ 永久 | ✓ 永久 | ✓ 过期 | ✓ 过期 | ✓ 过期 | ✓ 过期 |
| **emoji** | | ✓ 永久 | | | | | ✓ 过期? | | | |
| **video** | ✓ 永久 | | | | | | ✓ 过期 | ✓ 过期 | | |
| **voice** | | | | | | | ✓ 过期 | | | |
| **file** | | | | | | | ✓ 过期 | | | |

**读法**：

- 任一行只要有 `永久` 列被引用 → 该对象永久，忽略其它 `过期` 列
- 全空白行 + 无任何引用 → 孤儿，按 kind 策略过期

**关键推论**：同一个 `kind=image` 的对象既可能在聊天里过期，也可能是帖图永久。**按 kind 一刀切是错的**，必须按引用判定——这是现行实现正确的地方，也是保护集合必须穷举的原因。

## 6. 已裁决问题（2026-10-21 用户拍板）

### 6.1 Q1 —— 表情包永不过期 ✅ 已裁决

**裁决：表情包当然不过期。**

架构上本来就成立，本次把隐式行为**显式化**：

- 消息发送要求 `media.kind == msg_type`（`chat/serializers.py:801-805`），故 `kind=emoji` 只能作 `type=emoji` 消息；
- 该类媒体的访问权**只能**经 `EmojiItem` 路径取得（`media/services.py:697-711`），即必须先收藏为表情；
- ⇒ 每个 `kind=emoji` 媒体必然挂在某个 `EmojiItem` 上 → 天然命中资产 A2 → 永久保留。

**实现要求**：`cleanup_media` 必须**显式跳过** `kind=emoji`，不能依赖"不在 TTL 表所以被跳过"的巧合。否则下次重构 TTL 表时，emoji 会被误当单级媒体 7 天删除。

### 6.2 Q2 —— 资产引用优先于过期判定 ✅ 已裁决

**裁决原话：「如果一张图出现在聊天记录里本应过期，但被人用作头像就不再过期」**

规则（2026-10-21 二次修正后）：

```
资产引用建立 ⟹ 媒体即刻转为「永久保留」，此后不再受 created_at 的 TTL 约束
前提         ⟹ 引用建立时原图必须完好（未进入任何过期阶段）
```

两条同时成立，缺一不可：

- **"不再过期"只管未来**：引用建立成功后，即使 created_at 早于 30 天前也不会被清理；
- **"必须原图完好"管入口**：引用建立的那一刻，媒体必须尚未开始过期（`original_expired_at` 与 `expired_at` 均为空）。

判定不是"上传后 N 天检查一次"，而是**每次清理时按当前引用实时判定**。所以"聊天里 3 天前发的图被设为头像" → 下次清理时已在保护集合内 → 永不删除；而"聊天里 40 天前的图（原图早删了）被设为头像" → **入口即被拒绝**，须重新上传原图。

**时序分支**（2026-10-21 二次修正后定稿）：

| 分支 | 设引用时媒体的状态 | 是否接受该 media_id | 正确做法 |
|---|---|---|---|
| **T1** | 完好（原图+缩略图都在，未过期） | ✅ 接受 | 永久保留 |
| **T2** | 阶段 1（原图已删、缩略图在） | ❌ **拒绝** | **重新上传原图**，得到新 media_id |
| **T3** | 完全过期（`expired_at` 非空，对象全删） | ❌ **拒绝** | **重新上传原图**，得到新 media_id |

> **2026-10-21 修正（用户原话）**：「这种时候上传同一张图片作为头像应该重新上传原图，而不是使用缩略图和过期」
>
> 即：**缩略图不是可用的资产内容**。阶段 1 之后的媒体只剩 720px 压缩图，质量已降级且原图不可恢复；把它固化成头像/封面/帖图，等于用一张劣化副本永久冒充原图，且用户永远无法再拿到原图。
>
> **正确语义**：资产引用只接受**完整原图**。媒体一旦进入任何过期阶段（阶段 1 或阶段 2），就**不再具备成为资产的资格**；用户想用它当头像，必须**重新上传原图**——这会生成一个全新的 `MediaObject`（新 media_id、新 created_at），从而获得完整的 7/30 天生命周期。原媒体继续按聊天媒体的原节奏过期，两者互不影响。

**因此规则简化为两条**：

```
资产引用建立时，media 必须同时满足：
    1. kind 匹配（见 §5 归属矩阵）
    2. status == READY
    3. original_expired_at is None      ← 新增：未进入阶段 1
    4. expired_at is None               ← 新增：未完全过期
```

条件 3 与 4 合起来即：**"原图完好、尚未开始过期"**。

**为什么不做 T2 的"缩略图降级"**：那是把技术降级包装成产品功能。用户要的是"这张图当我的头像"，不是"这张图的低清残影当我的头像"。聊天场景接受缩略图是因为对话上下文仍在、原图属于历史记录；资产场景是长期身份标识，必须原图。

**配套修复**：

| # | 修复 | 说明 |
|---|---|---|
| 1 | 资产类 6 处校验增加 `original_expired_at is None and expired_at is None` | 返回 `media_expired`（410 语义），提示前端重新上传 |
| 2 | `/content` 的 `store.head()` 捕获异常返回 404 | 否则阶段 1 后资产渲染 500（调查报告 §4.6）；虽然新逻辑下资产不会是阶段 1 媒体，但历史数据与竞态仍需兜底 |
| 3 | 聊天类 E1–E4 **不加**此校验 | 聊天本就允许发送即将过期的媒体（发送时未过期即可），符合"聊天媒体按 TTL 回收"的设计 |

**现行前端已满足此要求**（不需要改动）：所有资产入口都走 `uploadMediaFile()` 重新上传，从不复用聊天媒体——

### 6.3 Q3 —— 资产撤销后回落为可过期（沿用现行）✅

删帖 / 换头像 / 删表情包条目后，媒体不再有资产引用 → 下次清理按 `created_at` 判定：已超 TTL 则立即过期。符合预期，保持不变。

### 6.4 Q4 —— DB 记录永不删行（沿用现行）✅

`media_objects` 表随消息量无限增长。当前设计如此（前端需区分"已过期"与"不存在"）。百万级后需归档策略，本期不做。

## 8. 判定实现要求（供后续开发）

**必须收敛为单一函数**，避免 "可访问" 与 "受保护" 两套判定再次漂移：

```python
def protected_media_ids() -> set[str]:
    """返回被任一资产类引用（A1–A7）引用的 media_id 全集。

    新增任何"永久保留"语义的功能，必须在此处登记，否则该媒体会在
    到期后被删——见 docs/architecture/media-retention-boundaries.md §3。
    """
```

约束：

1. **全量扫描**，不得分页截断（漏判 = 资产被删）；
2. 引用形态三套解析器复用同一份正则（content URL：`/api/v1/media/{id}/content`）；
3. 新增资产引用类型时，**同一次提交**必须同时更新本文档 §3 与保护函数，并补契约测试；
4. 反向约束：`can_access_media()` 中承认的引用类型，若属于"永久"语义却不在 §3，视为缺陷（本次 A5/A7 即此类）。
