# Ayla 图片加载性能优化报告

**日期**：2025-01-21  
**问题**：用户反馈头像、群头像、直播封面、图片发送等加载特别慢  
**影响范围**：所有涉及媒体资源的界面（聊天、帖子、直播、个人资料等）

---

## 1. 问题根因分析

### 1.1 后端问题

#### ❌ 问题 1：Cache-Control: private, no-store 禁止浏览器缓存

**位置**：`apps/media/views.py:164`

```python
"Cache-Control": "private, no-store",
```

**影响**：
- 浏览器完全不缓存任何媒体资源
- 每次渲染图片（即使是同一张）都重新发起 HTTP 请求
- 用户在列表页来回滚动，同一个头像被重复请求几十次

**根因**：
- 设计时为了保护私密媒体，使用了最严格的 `no-store` 策略
- 但 `private` 本身已经确保不进入共享缓存（CDN/代理），`no-store` 过度限制了浏览器本地缓存

#### ❌ 问题 2：缺少 HTTP 304 Not Modified 支持

**位置**：`apps/media/views.py:149-200`

**影响**：
- 即使资源未变化，服务端每次都返回完整数据
- 对于头像等小图片（几 KB），响应头开销占比高
- 网络传输和服务端 I/O 压力大

**根因**：
- 响应中已经设置了 `ETag`（基于 `content_hash`）
- 但代码未检查请求头的 `If-None-Match`，未实现条件请求

#### ✅ 问题 3：缩略图是立即生成还是延迟生成？

**位置**：`apps/media/services.py:228`

```python
# 派生（尽力而为，失败不阻塞/不置 failed）
_generate_derivatives(media, data)
```

**结论**：✅ **缩略图在上传完成时立即生成**，不是延迟生成，这一点没有问题。

---

### 1.2 前端问题

#### ❌ 问题 4：每个 ResourceImage 组件都创建独立 blob URL

**位置**：`web/src/components/ResourceImage.tsx:39-66`

**影响**：
- 同一张图片（相同 `media_id`）在不同位置渲染时，每个都发起独立的 fetch 请求
- 例如：群聊列表中 20 个会话，如果 10 个会话的群头像是同一张图，会发起 10 次重复请求
- 每次创建的 blob URL 在组件卸载时立即被 `URL.revokeObjectURL()` 销毁，下次渲染又要重新请求

**根因**：
- 组件设计时没有考虑全局缓存层
- `useEffect` 清理函数中调用 `URL.revokeObjectURL(objectUrl)` 导致 blob URL 无法复用

#### ❌ 问题 5：派生资源（缩略图/波形图）同样 no-store

**位置**：`apps/media/views.py:213`

```python
resp["Cache-Control"] = "private, no-store"
```

**影响**：
- 缩略图比原图更频繁使用（列表预览、卡片展示）
- 同样无法被浏览器缓存，重复请求严重

---

### 1.3 架构层面

#### ℹ️ 观察：同步阻塞读取 S3

**位置**：`apps/media/storage.py:93-95`

```python
def get(self, key):
    resp = self._client.get_object(Bucket=self._bucket, Key=key)
    return resp["Body"].read()
```

**影响**：
- Django 视图在同步上下文中调用 `store.get(key)`
- 每次请求都阻塞读取完整对象再返回
- 对于大文件（语音、视频），延迟明显

**备注**：
- 本期未优化，属于中期改进范围（流式下载已支持 Range 请求）
- MinIO 在本地环境延迟较低，生产环境如果 MinIO 与应用服务器距离远，影响会放大

## 2. 已实施的优化方案

### 2.1 前端：增加 blob URL 全局缓存

**文件**：`web/src/components/ResourceImage.tsx`

**改动**：

```typescript
// 文件顶部增加全局缓存
const blobCache = new Map<string, string>();

// useEffect 中检查缓存
const cached = blobCache.get(src);
if (cached) {
  setResolvedSrc(cached);
  return () => { cancelled = true; };
}

// 请求成功后写入缓存
const objectUrl = URL.createObjectURL(blob);
blobCache.set(src, objectUrl);
setResolvedSrc(objectUrl);

// 清理时不再 revoke（缓存管理生命周期）
return () => { cancelled = true; };
```

**效果**：
- ✅ 同一 `media_id` 只请求一次，后续渲染直接复用 blob URL
- ✅ 用户在列表页来回滚动，头像不会重复加载
- ✅ 显著减少前端并发请求数量

**风险**：
- blob URL 不会自动释放，长时间运行可能占用浏览器内存
- 可考虑后续增加 LRU 淘汰策略（当前单会话内影响有限）

---

### 2.2 后端：允许浏览器缓存原图

**文件**：`apps/media/views.py:164`

**改动**：

```python
"Cache-Control": "private, max-age=3600",  # 缓存 1 小时
```

**效果**：
- ✅ 浏览器可以缓存媒体资源 1 小时
- ✅ `private` 确保不进入共享缓存（CDN/代理），仍保护私密性
- ✅ 用户刷新页面或重新进入聊天，头像/图片直接从浏览器缓存读取

**安全性**：
- ✅ 仍然是私密媒体（`private`）
- ✅ 访问控制逻辑未改变（权限检查仍在服务端）
- ✅ 缓存时效 1 小时后自动过期，不会永久缓存过时内容

---

### 2.3 后端：允许浏览器缓存派生资源（缩略图/波形图）

**文件**：`apps/media/views.py:213-214`

**改动**：

```python
resp["Cache-Control"] = "private, max-age=7200"  # 缩略图缓存 2 小时
resp["ETag"] = f'"{media.content_hash}-{key.split("/")[-1]}"'
```

**效果**：
- ✅ 缩略图缓存时间更长（2 小时），因为派生资源更稳定
- ✅ 列表页大量缩略图不再重复请求
- ✅ 增加 ETag 用于条件请求

---

### 2.4 后端：实现 HTTP 304 Not Modified

**文件**：`apps/media/views.py:149-169`

**改动**：

```python
# 304 Not Modified 支持：客户端提供 If-None-Match 且匹配 ETag
if_none_match = request.headers.get("If-None-Match")
if if_none_match and if_none_match == etag:
    resp = HttpResponse(status=status.HTTP_304_NOT_MODIFIED)
    resp["ETag"] = etag
    resp["Cache-Control"] = "private, max-age=3600"
    return resp
```

**效果**：
- ✅ 浏览器缓存过期后重新请求时，如果资源未变化，返回 304 空响应
- ✅ 节省网络带宽和服务端 I/O
- ✅ 对于头像等长期不变的资源，几乎不再传输数据

**原理**：
- 首次请求返回完整数据 + `ETag: "abc123"`
- 浏览器缓存 1 小时后，下次请求带上 `If-None-Match: "abc123"`
- 服务端比对 ETag，相同则返回 304，浏览器继续使用缓存

## 4. 实际验收方法

### 4.1 浏览器开发者工具验证

1. 打开 Chrome DevTools → Network 面板
2. 访问聊天列表页（包含多个头像）
3. **首次加载**：
   - 观察所有 `/media/{id}/content` 请求，状态应为 `200 OK`
   - 检查响应头：`Cache-Control: private, max-age=3600`
   - 检查响应头：`ETag: "..."`
4. **刷新页面**：
   - 观察所有媒体请求，状态应为 `200 (disk cache)` 或 `304 Not Modified`
   - Size 列显示 `(disk cache)` 表示浏览器缓存命中
5. **滚动列表**：
   - 新出现的头像首次加载为 `200 OK`
   - 滚动回之前区域，头像应为 `(memory cache)` 或不再发起请求

---

| 指标 | 优化前（预期） | 优化后（目标） | 验收标准 |

## 5. 后续优化建议（未实施）

### 5.1 中期优化（1 周内）

#### 优化 1：缩略图尺寸分级

**问题**：当前缩略图固定 320px，但头像显示通常只有 32-64px

**方案**：
- 增加 `thumbnail_small`（96px）用于列表头像
- `thumbnail`（320px）用于预览/详情页
- API 新增 `/media/{id}/thumbnail?size=small`

**收益**：
- 头像流量减少 70%（96px vs 320px）
- 首次加载速度提升 3-5 倍

---

#### 优化 2：批量预加载

**问题**：进入列表页时，头像按需懒加载，滚动时才请求

**方案**：
- 列表页渲染时收集所有 `media_id`
- 一次性批量预加载所有头像到前端缓存
- 用户滚动时直接从缓存读取

**收益**：
- 消除滚动时的加载延迟
- 减少并发请求，改善服务端压力

---

#### 优化 3：Redis 缓存热门图片

**问题**：MinIO 读取仍需网络 I/O，对于热门头像（群头像、系统表情）重复读取

**方案**：
- 增加 Redis 缓存层
- 热门图片（访问量 Top 100）缓存到 Redis
- TTL 1 小时，LRU 淘汰

**收益**：
- 热门资源响应时间从 50ms 降到 5ms
- 减少 MinIO 压力

---

### 5.2 长期优化（2 周以上）

#### 优化 1：接入 CDN 或 Nginx 反向代理

**问题**：Django 应用服务器不适合作为静态资源服务器

**方案**：
- MinIO 前置 Nginx 反向代理
- 或接入 CDN（需解决私密媒体鉴权）

**收益**：
- 响应时间降低 10-50 倍
- Django 应用服务器释放资源处理业务逻辑

---

#### 优化 2：图片格式优化（WebP）

**问题**：当前缩略图使用 JPEG，体积较大

**方案**：
- 缩略图生成时优先使用 WebP 格式
- 降级支持 JPEG（老浏览器）

**收益**：
- WebP 比 JPEG 小 30-50%
- 进一步减少流量和加载时间

---

#### 优化 3：响应式图片

**问题**：高 DPR 设备（2x/3x 屏幕）和低 DPR 设备使用相同图片

**方案**：
- 根据设备 DPR 返回不同尺寸
- API 支持 `/media/{id}/thumbnail?dpr=2`

**收益**：
- 低端设备节省流量
- 高端设备显示更清晰

---

## 6. 风险与限制

### 6.1 前端 blob URL 内存占用

**风险**：
- blob URL 不再自动释放，长时间运行可能占用浏览器内存
- 单个 blob URL 实际指向浏览器内存中的 Blob 对象

**缓解**：
- 当前单会话内缓存数量有限（<100 张图片）
- 浏览器关闭或刷新会清空缓存
- 后续可增加 LRU 淘汰策略（缓存 100 个后淘汰最少使用）

---

### 6.2 缓存一致性

**风险**：
- 用户修改头像后，浏览器缓存仍是旧头像（最多 1 小时）

**缓解**：
- `ETag` 基于 `content_hash`，内容变化后 ETag 自动变化
- 修改头像后，`media_id` 通常也会变化（重新上传）
- 1 小时 TTL 是合理的缓存过期时间

---

### 6.3 私密媒体安全性

**验证**：
- ✅ `Cache-Control: private` 确保不进入共享缓存
- ✅ 访问控制逻辑未改变（权限检查仍在服务端）
- ✅ 浏览器缓存仅存储在本地，不会泄露给其他用户
- ✅ Token 过期后，下次请求仍需重新鉴权
